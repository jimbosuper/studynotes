# 审查清单

> **放行**：已放行 · JimBo · 2026-11-22
> **最后更新**：2026-11-22

**这份清单不许照抄模板。** 工作流模板里有「审代码五维」「审产物四条」这一套，但它们是给「有后端、有数据库、有多人协作」的项目写的。本项目的审查对象只有两类：

| 审什么 | 依据 | 结论影响 |
|---|---|---|
| **内容同步与脚本** | TD1、PRD1 规则清单 | 影响构建与内容正确性 |
| **站点配置与样式** | PRD1 验收标准、页面规格 | 影响导航、链接、布局 |

**不审**笔记正文的技术正确性——那是内容源仓库的职责。

## 一、审什么

### 1.1 审同步脚本（`blog/scripts/*.mjs`）

| # | 维度 | 通过标准 | 判据来源 |
|---|---|---|---|
| 1 | 幂等 | 连跑两次产物字节一致 | TD1 §2.1 |
| 2 | 三种修补都在 | `C++` 改名、`${{ }}` 包裹、H1 去编号各有用例 | TD1 §3.1 |
| 3 | 修补边界正确 | 围栏代码块内不处理；行内代码才包 `<span v-pre>` | TD1 §3.3 |
| 4 | frontmatter 不覆盖已有的键 | 已有 `title` 时保留原值 | TD1 §3.1 |
| 5 | 校验能报错 | 故意造断链，退出码为 1 | TD1 §2.1 |
| 6 | 路径改名在复制时完成 | 不在事后 `mv`（会漏深层目录） | TD1 §3.2 |

**三条不审**：

| 不审 | 谁管 |
|---|---|
| 命名、缩进、引号 | 无 Lint，人工保持一致 |
| 注释是否够 | 代码里的注释解释「为什么」即可 |
| 脚本性能 | 5 秒内跑完，不值得审 |

### 1.2 审站点配置与样式

| # | 维度 | 通过标准 | 判据来源 |
|---|---|---|---|
| 1 | 导航与侧栏一致 | `navbar.ts` 的项都有对应目录；侧栏首项是 `00-内容导读` | 页面规格 §三 |
| 2 | 链接可达 | 构建后全量 href 扫描 missing 0 | PRD1 AC-05 |
| 3 | 首页卡片完整 | 12 张，链接与内容区对应 | PRD1 AC-09 |
| 4 | 目录页结构 | 总览表 + 每方向明细表；三层方向正确嵌套 | PRD1 AC-06 |
| 5 | 深浅色正确 | 默认浅色；切深色后渐变变亮色版本 | 页面规格 §七 |
| 6 | 响应式断点 | ≤720px 隐侧栏与右目录 | 页面规格 §二 |

**两条不审**：

| 不审 | 归谁 |
|---|---|
| 配色是否好看 | 人（门 2） |
| 文案措辞 | 人（门 1 / 门 2） |

## 二、按什么审

**审的是「能不能用」，不是「写得好不好」。** 判断顺序：

1. **先看证据** —— 每份产物都要有可跑的命令或可点的页面。没有证据的结论不作数。
2. **再看边界** —— 差分、例外、没覆盖的部分，写清楚了才算通过。
3. **最后看一致性** —— 文档之间对不上（如 PRD 说 12 张卡片、页面规格说 10 张），是阻塞项。

## 三、必检项

### 3.1 审同步脚本：六条

| # | 必检 | 怎么验 |
|---|---|---|
| 1 | 只读源库 | `git -C ../fullstack-notes status` 应为 clean |
| 2 | 目标目录先清空 | 同步后不应残留上次的文件（造一个假文件试） |
| 3 | 跳过集合完整 | `.git`、`.openchamber`、`node_modules`、`.DS_Store` 不出现 |
| 4 | 三种修补都生效 | 各造一个样本，同步后检查 |
| 5 | 校验退出码正确 | 造断链后 `echo $?` 应为 1 |
| 6 | 输出可读 | 结尾那行统计与校验结果存在 |

### 3.2 审站点配置：四条

| # | 必检 | 怎么验 |
|---|---|---|
| 1 | 构建退出码 0 | `npm run build; echo $?` |
| 2 | 页数与预期一致 | `find dist -name '*.html' \| wc -l` = 365（或本次改动的预期值） |
| 3 | 死链为 0 | 构建后跑链接扫描 |
| 4 | 三处域名一致 | `grep -n 'studynotes-90w' theme.ts` 应命中 3 行 |

## 四、分级

**分级只按影响判，不按修改难度判。** 「改起来很麻烦」不是降级的理由。

| 级别 | 定义 | 例子 |
|---|---|---|
| P0 | 广泛灾难性影响 | 整页内容残缺、全站构建失败、内容大面积缺失 |
| P1 | 高概率可见缺陷 | 主栏目 404、导航项缺失、侧栏顺序错 |
| P2 | 有明确触发条件的中等问题 | 某篇深层链接断、某宽度下卡片挤压 |
| P3 | 低风险但可行动 | 措辞、间距细节、图标大小 |

**与测试报告用同一套定义**（见 `05-测试/01-测试策略.md` 第七节）。

## 五、结论四档

| 结论 | 条件 | 下游 |
|---|---|---|
| 通过 | 无 P0 / P1 | 进验收 |
| 有条件通过 | 无 P0 / P1，但有 P2 未修，且有人认领、有时点 | 进验收，**剩余 P2 由人确认后才能上线** |
| 退回修改 | 有 P0 / P1 | **回写这份产物的人** |
| 退回重写 | P0/P1 超过 15 条，或**自检可发现占比 > 50%** | 回写这份产物的人；这已经不是改几条的事，是重做 |

**「有条件通过」不是「放行」。** 写清哪几条 P2、谁在什么时候修；没写清就是「通过」。

## 六、不审什么

| 不审 | 归谁 | 为什么 |
|---|---|---|
| 笔记内容的技术正确性 | 内容源仓库 | 审查不该替作者判断领域知识 |
| 配色审美 | 人（门 2） | 机器判不了 |
| 文案措辞 | 人（门 1 / 门 2） | 同上 |
| 构建性能 | 无 SLA 要求 | 40 秒可接受 |
| 代码风格 | 无 Lint | 本项目无此维度 |
| 文档之间是否同步 | 各角色自己的「完成判据」 | 审查只看本次对象内的一致性 |

## 七、拿不准时

**默认动作是「记为 P2 并写清为什么拿不准」**，不是放过也不是升 P1。

| 情况 | 处置 |
|---|---|
| 不确定是不是缺陷 | 记 P2，写「未确认：<原因>」 |
| 不确定影响面 | 记 P1，附复现步骤，让人判 |
| 不确定归哪个角色 | 归「写这份产物的人」 |
| 与模板冲突但项目实际更合理 | 记 P3 + 写「与模板偏差，理由：<项目实际>」 |

**本项目有意裁剪的模板位置，审查时不该判为缺陷：**

| 偏差 | 理由 |
|---|---|
| 没有 `test/` 目录 | 无单元 / e2e 可测的对象 |
| 没有 `deploy/` 与 `deploy/env/` | 部署完全托管，仓库内只有 `wrangler.jsonc` |
| 没有数据库设计 / ER 图 / 状态机 | 无数据库、无状态实体 |
| 没有 BRD / MRD | 个人站，无商业投入与市场 |
| 有 3 份 ADR，不按「每个决策一份」铺满 | 只给影响后续所有决定的选型立文件；其余取舍写在各产物正文里 |
| 只有一条分支 | 单人项目，无测试环境 |
| 没有 Lint / Formatter | 代码量极小，构建把关 |
| 架构图示用 Archify、部署拓扑手写 SVG | 前者 9 节点适合模板化；后者 7 节点 3 链路，直接画更可控 |

**这些写在 `docs/README.md` 第五节**，审查时对照那节判断。

## 八、自检可发现占比

**每条发现都要标一栏：作者自检时能不能发现。**

| 标注 | 含义 | 怎么判 |
|---|---|---|
| `可发现` | 作者照本清单的必检项过一遍就能发现 | 清单里有对应项，且证据在产物里直接可见 |
| `不可发现` | 只有跑起来、跨文件对照、或换视角才看得出 | 需要复现、需要跨模块推演、需要下游视角 |

**判据：`可发现` 占比 > 50% → 裁决必须写「自检不足」，退回。**

**本项目的判法**：验证与审查分两段执行，判据不同。`可发现` 指「作者自己按本清单必检项过一遍就能看到」，`不可发现` 指需要跑起来、跨文件对照、或换视角。**分诊时按这个判，不按执行者是不是同一个人判。**
