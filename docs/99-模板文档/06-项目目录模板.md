# 项目目录模板

新建项目时按本文建目录。**`docs/` 照抄，另外三个目录按项目裁剪。**

---

## 一、根目录

```text
<项目根>/
├─ README.md       # 项目是什么、怎么跑；新人第一个打开的文件
│
├─ AGENTS.md       # 给 AI 的项目说明；命令、技术栈、已知陷阱
│
├─ .gitignore      # 必须含 deploy/env/ 与 docs/99-tmp/
│
├─ .gitlab-ci.yml  # GitLab 只认根目录，放别处不会执行
│
├─ src/            # 源码；分层确定，结构按技术栈
│
├─ test/           # 按工具分层；用不到的工具层不建
│
├─ deploy/         # 按平台分层；用不到的层不建
│
└─ docs/           # 全部项目文档；结构固定
```

**根目录不放其他东西。** 临时文件进 `docs/99-tmp/`。

---

## 二、src/ —— 分层固定，结构按技术栈

### 2.1 一个仓库 = 一个项目，多端是多仓库

**这份模板描述的是「一个部署单元」。** 如果一个产品有多个端，**每端一个仓库、各用本模板各建一次**，不在一个仓库里塞多端。

```text
智能耳机整套产品
├─ repo-backend/        ← 后端仓库（本模板完整一份：src/ test/ deploy/ docs/）
├─ repo-app/            ← 移动端仓库（本模板完整一份，src/ 只放 app/）
└─ repo-web/            ← Web 仓库（本模板完整一份，src/ 只放 web/）
```

**每个仓库都有自己的 `docs/`、自己的 8 道门、自己的版本号。** 后端和 App 的 PRD 版本可以不同——它们是两条独立的交付链，靠需求编号（`PRD1`）跨仓库对齐。

**为什么不塞进一个仓库**：

| 塞进一个仓库的代价 | 多仓库的好处 |
|---|---|
| 三套构建工具链混在一起，CI 要按目录分流 | 每仓库一条流水线，互不干扰 |
| 一个端发版要把其他端一起带上 | 各端独立发版、独立回滚 |
| `src/frontend` 这个词对小程序/App 不准确 | 每仓库的 `src/` 只描述自己那种形态 |
| 一个仓库的 `docs/99-归档/` 会膨胀三倍 | 归档各管各的 |

**跨仓库的对齐点只有三处**：需求编号（`PRD<N>`）、接口契约（后端 TD 第二节）、环境地址（各自 `04-项目环境规范.md` 指同一套环境）。**这三处对不上，就是三个工程各跑各的。**

### 2.2 单仓库内的分层

**固定的三条**：按功能模块分；前端与后端模块同名对齐；共享代码只放一处。

```text
src/
├─ frontend/
│  ├─ app/            # 页面与路由；框架有强制路径就按框架来
│  ├─ components/     # 通用组件；跨模块复用才放这里
│  ├─ modules/        # 功能模块，一个功能一个目录
│  │  └─ notes/       # 模块名与 backend/modules 下同名
│  │     ├─ index.ts  # 模块入口
│  │     ├─ api.ts    # 调后端接口
│  │     └─ types.ts  # 仅前端用的类型
│  └─ common/         # 前端共用：类型、常量、工具函数
├─ backend/
│  ├─ api/            # 路由与控制器；只做参数校验与转发
│  ├─ modules/        # 与 frontend/modules 同名对齐
│  ├─ db/             # schema 与迁移；迁移必须可回滚
│  └─ common/         # 后端共用：中间件、工具
└─ common/            # 前后端共用类型；不写业务逻辑
```

**上面这套只适用于前后端分离的 Web 应用。** 纯 CLI、纯库、移动端不能照抄。

抄之前先确认三件事：

| 检查 | 不确认的后果 |
|---|---|
| 前端框架有没有强制路由目录（如 Next.js 的 `app/`） | 目录放错，路由不生效 |
| 后端框架有没有强制模块结构（如 NestJS 的 controller/service 同目录） | 与框架打架，两套结构并存 |
| 是否真有跨端共享代码 | 三层 `common/` 变三份复制代码 |

**只留用得上的层。** 纯后端删 `frontend/`，纯前端删 `backend/`，单端删顶层 `common/`。模块内部怎么分写进 `docs/04-开发/01-代码规范.md`。

## 三、test/ —— 核心三层固定，工具层按需

**分层依据是「跑起来需要什么」，不是「测什么功能」。** 要浏览器进 `playwright/`，不要的进 `vitest/`。

```text
test/
├─ vitest/            # 单元与组件；不需要浏览器
│  ├─ unit/           # 纯函数、hook、route handler
│  └─ components/     # jsdom 下的组件渲染与交互
├─ playwright/        # 需要真实浏览器
│  ├─ e2e/            # 完整用户路径
│  ├─ visual/         # 截图比对
│  └─ a11y/           # 可访问性扫描
├─ maestro/           # 移动端流程（YAML）；有 App 才建
│  └─ flows/
├─ k6/                # 压力测试（JS 脚本）；要压测才建
│  └─ scenarios/
├─ fixtures/          # 各层共用的测试数据与账号
└─ helpers/           # API 客户端、等待、清理
```

| 层 | 建的条件 |
|---|---|
| `vitest/`、`playwright/`、`fixtures/`、`helpers/` | **固定，都建** |
| `maestro/` | 有移动端 App |
| `k6/` | 需要压测 |
| `visual/`、`a11y/` | 有视觉回归 / 可访问性要求 |

**每条命令对应一个目录。** 用不上就整层删掉，不留空目录——空目录会让 AI 以为这里该有测试。

**后端不是 Node 时**，`vitest/` 换成对应语言的工具目录（如 `pytest/`），不要两套并存。

**开发自写的单元测试不在这里**，跟着源码放 `src/`（`*.test.ts`）。`test/` 归测试角色独立验证。

## 四、deploy/ —— 四层固定，层内按需

**分层依据是「跑在什么平台上」，不是文件类型。** 一个平台一个目录，装齐这个平台要的一切。

```text
deploy/
├─ docker/
│  ├─ Dockerfile                 # 统一构建入口：多阶段，--target frontend|backend
│  ├─ .dockerignore              # 没有它，node_modules 与 .git 会进镜像
│  ├─ docker-compose.dev.yml     # 开发覆盖：源码挂载、暴露 db 端口
│  ├─ docker-compose.test.yml    # 测试覆盖
│  └─ docker-compose.prod.yml    # 生产覆盖：重启策略、资源限制、对外端口
├─ k8s/                          # 真上集群才建
│  ├─ config/                    # 先建；configmap 不到位，workload 起不来
│  │  ├─ namespace.yaml
│  │  ├─ configmap.yaml
│  │  └─ secret.yaml.example     # base64 不是加密，只放示例
│  ├─ workload/
│  │  ├─ deployment-frontend.yaml
│  │  ├─ deployment-backend.yaml
│  │  └─ statefulset-db.yaml     # 用云数据库就不建
│  ├─ network/
│  │  ├─ service-frontend.yaml
│  │  ├─ service-backend.yaml
│  │  └─ ingress.yaml
│  └─ storage/
│     └─ pvc.yaml
├─ scripts/
│  ├─ start.sh                    # 拉起已构建的服务
│  ├─ stop.sh                     # 优雅停止
│  ├─ deploy.sh                   # 构建 → 迁移 → 启动 → 冒烟
│  ├─ rollback.sh                 # 应用与数据库回滚
│  └─ migrate.sh                  # 数据库迁移，可单独执行
└─ env/
   ├─ .env.dev                    # 真实值，整目录不入库
   ├─ .env.test
   └─ .env.prod
```

| 层 | 建的条件 |
|---|---|
| `docker/`、`scripts/` | **固定，都建** |
| `k8s/` | 真上集群；没上之前整个目录不建 |
| `env/` | 每个环境一份；环境少于三个按实际留 |

`nginx/` 这类配置归到使用它的平台目录下（如 `docker/nginx/`），不单列。

**环境变量不在项目根，全部在 `deploy/env/`**，应用与脚本都从那里读。整目录 gitignore，一份都不入库：

```gitignore
deploy/env/
```

**变量清单不靠示例文件**，靠 `docs/06-运维/01-服务详细情况.md`：写清每个环境要哪些变量、放在哪，值只在服务器上。

**`废弃/` 与 `发布/` 的版本号含义不同。** `废弃/PRD2/v1.0.0/` 的 `v1.0.0` 是 PRD2 的版本；`发布/v1.4.0/` 的 `v1.4.0` 是这次上线的版本，里面 PRD 可能是 `v1.2.0`。

**判断文档有效还是废弃，看位置不看状态字段。** 在工作目录里就是有效，在 `99-归档/废弃/` 里就是废弃。状态字段会忘记改，位置不会说谎。

**`99-归档/版本/` 里的旧链也是「已失效」，但原因不同**：它不是被取消，是被新版替代。工作目录里那套才是当前版；要引旧链必须写明「历史版本，仅供追溯」。

**归档只进不出。** 从 `99-归档/` 往外搬东西说明判断错了，要先说清为什么。要恢复旧版，正确做法是从归档里 `cp` 出来当新版本升号，不是把它搬回去顶替当前版。

### 5.1 链上产物全部同版本，项目级文档只记最后更新

**一条需求是一条链**：PRD → 页面规格 → 系统架构 → 架构图示 → 状态机 → 数据库设计 → ER 图 → ADR → TD → 实现记录 → TP → TR → CR。

**这条链上的每一份产物共用一个版本号，写进文件名。** 版本一变，整条链一起升，旧的整套进归档。

```text
PRD1_电商运管平台_v1.3_20261121.md
03-页面规格_v1.3_20261121.md
01-系统架构_v1.3_20261121.md
05-数据库设计_v1.3_20261121.md
TD1_电商运管平台_v1.3_20261121.md
TD1_电商运管平台_实现记录_v1.3_20261121.md
TP1_功能验证_电商运管平台_v1.3_20261121.md
TR1_功能验证_电商运管平台_v1.3_20261121.md
CR1_PRD审查_电商运管平台_v1.3_20261121.md
```

**一眼就能看出「这些是一套」**，不用每次审查都重算「PRD v1.0.3 对应 TD v1.1.0」。**没有单独的「本文修订」号**——链上一份文件的版本就是整条链的版本。

#### 5.1.1 哪些在链上，哪些不在

| 类 | 文档 | 文件名带版本 |
|---|---|---|
| **链上** | PRD、页面规格、系统架构、架构图示、状态机、数据库设计、ER 图、ADR、TD、实现记录、TP、TR、CR | ✅ 与链同版本 |
| **项目级** | BRD、MRD、术语表、设计系统、项目环境规范、代码规范、测试策略、服务详细情况、部署拓扑、运维手册、发布记录、审查清单 | ❌ 不带版本，文首写「最后更新」 |

**项目级为什么不带版本**：BRD 是立项时写的，跨所有链；代码规范和审查清单是长期约定，不随某条需求变。把它们卷进链版本没有意义。

**项目级文档改了就改了**，靠 `git log` 看历史，文首写「最后更新」。**它们不参与链版本对齐**——所以不存在「版本歪掉」的问题。

#### 5.1.2 升版本三步

```text
1. 链上全部产物一起 cp 到新版本号（一份都不能漏，含架构与数据库设计）
2. 内容真改的改内容；没改的只改文首的版本行
3. 旧的一整套立刻搬进 docs/99-归档/版本/<需求>/<旧版本>/
```

**工作目录永远只有当前一套。** 不并存、不靠「版本号最大的是当前版」这种判断。

**为什么不省这一步**：看起来「没改内容的也拷一份」是浪费，但**文件名是唯一能让人一眼看出「这些是一套」的地方**。不拷，就会出现「PRD v1.3、架构 v1.0、TD v1.0」——内容上没错，但没人看得出它们配对。存储空间不值钱，认错对象要命。

#### 5.1.3 审查范围：看版本，不看内容有没有改

| 情况 | 重审吗 |
|---|---|
| 链版本升了，这份产物也跟着升 | **要审**（哪怕内容只是改了个错别字，也要过一遍确认） |
| 链版本没升 | 不用审 |

**简单规则：填在审查报告里的版本号变了，就重审。** 不再区分「本文修订」与「链版本」——只有一个版本号。

#### 5.1.4 `废弃/` 与 `版本/` 的区别

| 目录 | 放什么 | 什么时候进 |
|---|---|---|
| `99-归档/版本/<需求>/<旧版本>/` | **被新版替代**的整条链 | 链版本一升 |
| `99-归档/废弃/<需求>/<版本>/` | **整条需求被取消**的链 | 需求不做了 |
| `99-归档/发布/<上线版本>/` | 一次上线的整批快照 | 真上线 |

**`废弃/` 不收「被新版替代」的旧版**——那是 `版本/` 的事。**`发布/` 只放真上线的**。

#### 5.1.5 版本登记处 + 分支策略

**必须登记在同一个地方（`docs/README.md` 第一节），否则版本自己会漂：**

```markdown
## 一、在途需求

| 链 | 需求短名 | 当前版本 | PRD | 页面规格 | 架构 | 数据库设计 | TD | TR | CR | 审了几轮 |
|---|---|---|---|---|---|---|---|---|---|---|
| PRD1 | 电商运管平台 | v1.3 | v1.3 | v1.3 | v1.3 | v1.3 | v1.3 | v1.3 | v1.3 | 2 |
```

**同一条链上的 `v1.3` 必须全部相同。** 有一格不一样，就说明有一份没跟着升。

**分支策略：`dev` 全量，`test` / `prod` 精简。**

| 分支 | 推什么 | 为什么 |
|---|---|---|
| `dev` | **整个项目全部内容**，含 `99-归档/` 与 `99-tmp/` 之外的一切 | 开发本地仓库，信息必须对等；别人拉下来就能看到完整历史和所有旧版本 |
| `test` | 只推当前版本 + 当次需要的产物，**不含 `99-归档/`** | 测试环境只需要跑当前这套，冗余会拖慢流水线 |
| `prod` | 只推运行需要的内容 + 当次发布快照 | 生产环境最小化，减少误操作面 |

**`99-归档/` 只在 `dev` 上有。** 这是有意的：归档是给人和 AI 查历史用的，不是给流水线用的。`test` / `prod` 上没有归档，不代表归档不存在——它在 `dev` 上完整保留。

### 5.2 每个目录只放白名单里的扩展名

**工具收据、临时产物、编辑器备份都不进 `docs/` 的业务目录。**

| 目录 | 允许的扩展名 | 不允许 |
|---|---|---|
| `01-产品/`、`04-开发/`、`05-测试/`、`07-审查/` | `.md` | 其它全部 |
| `03-架构/`、`06-运维/`（**根目录**） | `.md`、`.html` | **`.json` 一律不许** |
| `03-架构/03-状态机/`、`03-架构/06-ER图/`、`03-架构/02-架构图示/`、`06-运维/02-部署拓扑/` | **只有 Archify 产物 html** | **不许有 `.json`；不许有导航/索引 html** |
| `02-设计/02-原型图/` | `.html`、`assets/`、`.file-versions/` | 其它 |
| `02-设计/02-原型图/<端>/`（多端时） | `.html`、`assets/`、`.file-versions/` | 其它 |
| `99-tmp/`、`99-外部文档/`、`99-模板文档/`、`99-归档/` | 不受限 | — |

**`index.html` 只在 `02-设计/02-原型图/` 出现，别处一律不许**（详见 5.2.2）。图目录里不建导航页——图打开就是内容，文件名带版本号已经说清有几张；要看「哪张图讲什么」，去归属文档的表格，那里会被审查。

**Archify 的交付收据（`*.finalize.json` / `*.browser-check.json` / `*.delivery.json` / `*.finalize-summary.json`）一律进 `99-tmp/<角色>-<任务>/receipts/`。** 生成时用 `archify finalize --out-dir <那个目录>`，不要把收据落在业务目录里。

**为什么这条要写死**：这次测试中 `03-架构/` 下有 12 个收据 json、`06-运维/` 下 4 个，真正产物只有 3 个 html + 1 个 html。**产物和工具的副产物混在一起，人看不出哪些是要读的。**

### 5.2.1 多图归目录：两类触发条件不同，且都不建导航页

**同一类的图不止一张时，归一个目录，不堆在同一层。** 但「什么时候建目录」分两类：

| 类型 | 触发 | 例子 | 理由 |
|---|---|---|---|
| **恒为目录** | 不论几张 | `03-状态机/`、`06-ER图/` | 张数由「有状态的实体 / 物理表」决定，几乎必然增长；先平铺再迁移只会留历史包袱 |
| **阈值触发** | 超过单图可读上限才建 | `02-架构图示/`（>12 节点）、`06-运维/02-部署拓扑/`（>14 节点） | 通常是单张；超出后一张读不清 |

```text
✅ 03-架构/
   ├─ 02-架构图示.html        ← ≤12 节点，平铺
   ├─ 03-状态机/              ← 恒为目录
   │  ├─ 1-订单.html
   │  ├─ 2-发货单.html
   │  ├─ 3-售后单.html
   │  └─ 4-退款单.html
   ├─ 04-项目环境规范.md
   ├─ 05-数据库设计.md
   └─ 06-ER图/
      ├─ 1-账号与商品.html
      ├─ 2-订单与发货.html
      └─ 3-售后与审计.html

❌ 03-架构/
   ├─ 03-状态机-1-订单.html
   ├─ 03-状态机-2-发货单.html
   ├─ 04-项目环境规范.md        ← 被图挤在中间，找不到
   └─ 06-ER图-1-账号与商品.html
```

| 规则 | 说明 |
|---|---|
| **文件名带序号** | `1-订单.html`、`2-发货单.html`；序号就是阅读顺序，`ls` 出来一眼看得出有几张 |
| **目录名带序号** | `03-状态机/`、`06-ER图/`、`02-架构图示/`，与同层其他文档的编号不打架 |
| **一个目录一个 `diagram_type`** | 状态机目录只放 `lifecycle`，ER 目录只放 `erd`，不混放 |
| **拆图的命名按维度走** | 架构图示按域（`1-总览.html` + `2-<域>.html`）；部署拓扑按环境（`1-测试.html`、`2-生产.html`） |

**为什么**：这次测试里 `03-架构/` 变成 `01-*.md`、`02-*.html`、`03-状态机-1-*.html`、`03-状态机-2-*.html`、`04-*.md`、`05-*.md`、`06-ER图-1/2/3.html` 混排——**按文件名排序时序号被图打断，人找不到「环境规范」在哪一节**。

### 5.2.2 `02-原型图/` 的文件名由 OpenDesign 决定，不自己改

**OpenDesign 导出的入口文件名固定是 `index.html`，不能改。**

实证（demo 的 `.file-versions/index.html.artifact.json`）：

```json
{ "entry": "index.html", "title": "index.html", "renderer": "html",
  "exports": ["html", "pdf", "zip"] }
```

`.file-versions/<hash>/manifest.json` 里的 `fileName` 也是 `index.html`。**它是工具约定，不是我们起的名**——按「工具产物不改名」处理。

**单端时它是原型应用本身；多端时根目录那个是手写导航页。**

**多端时**（桌面 + 移动）：

```text
02-设计/02-原型图/
├─ index.html          ← 手写导航页，只在多端时出现；单端时它是原型本身
├─ desktop/  index.html + assets/ + .file-versions/   ← OpenDesign 导出，保持原名
└─ mobile/   index.html + assets/ + .file-versions/
```

**判断规则一句话**：`02-原型图/` 根目录下**有子目录**时，根 `index.html` 是导航页；**没有子目录**时，它就是原型本身。这是全项目唯一允许手写 `index.html` 的地方，且只在多端时。

### 5.3 `99-tmp` 不入库

临时区整目录加进 `.gitignore`：

```gitignore
docs/99-tmp/
```

**原因**：这次 `99-tmp` 提交了 3715 个文件，其中 3551 个是审查角色做变异检验时 `cp -R` 复制仓库产生的**嵌套副本**——最深 19 层目录、15 份同名的 880K html。

**跑变异检验、留探针、导出截图都放这里，但都不入库。** 需要长期保留的是结论（写进 CR 报告或 TD），不是原料。
