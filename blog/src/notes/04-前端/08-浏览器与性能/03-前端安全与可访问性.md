# 前端安全与可访问性

> 这篇从同源策略与威胁模型讲起，经过 XSS 的输出编码、CSRF 与 Cookie 策略、CSP 与安全响应头、CORS 与 SRI、WCAG 2.2 的键盘与读屏要求，最后落到 axe 自动化加手工检查的完整修复案例。
>
> 学完能在一个 Vue 3.5 管理后台上定位并修掉注入点、配出可上线的 CSP、把键盘与读屏主流程走通，并用 axe 和手工清单验收。

## 一、威胁模型与信任边界

前端安全的起点是**同源策略（Same-Origin Policy）**：协议、域名、端口三者完全相同才算同源，不同源的脚本读不到彼此的 DOM 与存储；Cookie 另受 Domain/Path 约束，且不按端口隔离。所有前端攻击本质上都是绕过或利用这条边界。

| 攻击 | 利用什么 | 防线 |
|---|---|---|
| XSS | 把脚本注入页面 | 输出编码、CSP、Trusted Types |
| CSRF | 浏览器自动带 Cookie | SameSite、CSRF token、Origin 校验 |
| 点击劫持 | 透明 iframe 覆盖 | `frame-ancestors`、`X-Frame-Options` |
| 供应链 | 第三方脚本被篡改 | SRI、锁版本、最小依赖 |
| CORS 误配 | 跨源读取响应 | 白名单 Origin，禁用通配符加凭证 |
| 敏感信息泄露 | 前端打包了密钥 | 密钥只放服务端，构建期扫描 |

### 1.1 前端不持有秘密

打包产物里的任何字符串都能被用户读到：API Key、内部地址、注释里的账号。**前端代码是公开代码**，密钥、签名逻辑、权限判断都必须放在服务端。

```ts
// 反例：密钥进包，任何人打开 DevTools 就能拿到
const client = createClient({ apiKey: 'sk-live-9f2c...' });

// 正例：浏览器只调自己的后端，由后端持有密钥
await fetch('/api/report', { method: 'POST', body });
```

管理后台还有一条特殊边界：**前端隐藏按钮不是权限控制**。菜单按角色隐藏、按钮按权限置灰都只是体验，接口必须逐个校验权限；否则改一个前端变量就能调接口。

### 1.2 可访问性与安全同属“谁能用”

安全决定“谁能访问”，可访问性决定“谁能使用”。两者都是质量属性，都要在交付前验收，都不能靠事后补丁。一个键盘不可达的审批按钮，对键盘用户等同于功能不存在；一个读屏器读不出名称的输入框，对读屏用户等同于没有标签。

## 二、XSS：注入面与输出编码

跨站脚本（Cross-Site Scripting，XSS）是把不可信数据当成代码执行。防御的核心不是“过滤关键字”，而是**在正确的上下文里做正确的编码**。

### 2.1 三类 XSS

| 类型 | 注入位置 | 触发方式 |
|---|---|---|
| 存储型 | 数据库（评论、昵称、订单备注） | 其他用户打开页面 |
| 反射型 | URL 参数回显到 HTML | 诱导点击特制链接 |
| DOM 型 | 前端脚本把不可信数据写入 DOM | 页面自身逻辑 |

DOM 型最容易被前端忽略：数据根本没经过服务端，`location.hash` 直接进了 `innerHTML`。

### 2.2 按上下文编码

同一条数据放进不同位置，需要的编码完全不同：

```html
<!-- 反例：不可信数据直接拼进 HTML -->
<div id="out"></div>
<script>
  out.innerHTML = '<span>' + location.hash.slice(1) + '</span>'; // DOM 型 XSS
</script>

<!-- 正例：用 textContent，浏览器负责转义 -->
<script>
  const span = document.createElement('span');
  span.textContent = location.hash.slice(1); // 尖括号被当文本，不会解析成标签
  out.replaceChildren(span);
</script>
```

| 上下文 | 正确做法 | 错误做法 |
|---|---|---|
| HTML 文本 | `textContent`、模板自动转义 | 拼字符串进 `innerHTML` |
| HTML 属性 | 引号包裹 + 属性编码 | 无引号拼接 |
| URL 参数 | `encodeURIComponent` | 直接拼进 `href` |
| JS 字符串 | `JSON.stringify` + 转义 `<` | 手动拼引号 |
| CSS | 白名单值 | 用户输入进 `style` |

`href` 与 `src` 还有协议陷阱：`javascript:` 伪协议在点击时执行。

```ts
// 反例：用户可控的链接
link.href = userInput;            // javascript:alert(1) 会被执行

// 正例：只允许 http/https/相对路径
const url = new URL(userInput, location.origin);
if (url.protocol === 'http:' || url.protocol === 'https:') link.href = url.href;
```

### 2.3 框架的自动转义边界

Vue 与 React 的插值默认转义，危险的是“显式要求原始 HTML”的 API：

```vue
<!-- 反例：v-html 绕过转义，等于 innerHTML -->
<div v-html="order.remark"></div>

<!-- 正例：默认插值，{{ }} 自动转义 -->
<div>{{ order.remark }}</div>
```

```tsx
<>
  {/* 反例：dangerouslySetInnerHTML 名字已经在提醒 */}
  <div dangerouslySetInnerHTML={{ __html: order.remark }} />

  {/* 正例：按纯文本渲染 */}
  <div>{order.remark}</div>
</>
```

确实需要富文本（公告、邮件模板）时，输入必须过白名单清洗：

```ts
import DOMPurify from 'dompurify';

// 只允许排版标签与安全属性，脚本、事件属性、iframe 全部剔除
const clean = DOMPurify.sanitize(rawHtml, {
  ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'ul', 'ol', 'li', 'a'],
  ALLOWED_ATTR: ['href', 'title'],
  // 禁止 data: 与 javascript: 链接
  ALLOWED_URI_REGEXP: /^(?:https?|mailto):/i,
});
```

> 边界：清洗至少要在**渲染前**做；入库时也清洗能减少脏数据，但渲染前仍要再清洗一次，因为历史数据和二次编辑都可能带回危险内容。清洗库要跟版本，历史版本出过绕过漏洞。

### 2.4 Trusted Types

Trusted Types 把“给 `innerHTML` 赋值”变成需要类型化的策略对象，从 API 层面堵住字符串拼接：

```ts
// 只在支持的环境启用；不支持时 DOMPurify 仍然生效
if (window.trustedTypes) {
  const policy = trustedTypes.createPolicy('app-html', {
    createHTML: (input) => DOMPurify.sanitize(input), // 唯一出口，集中审计
  });
  el.innerHTML = policy.createHTML(userHtml);
}
```

配合 CSP 的 `require-trusted-types-for 'script'`，任何直接把字符串赋给 `innerHTML` 的代码都会抛错。这是一条“默认拒绝”的防线，代价是要改掉所有直接赋值点。

## 三、CSRF 与 Cookie 策略

跨站请求伪造（Cross-Site Request Forgery，CSRF）利用“浏览器会自动带上目标站 Cookie”这一事实：用户登录了银行，访问恶意页面，页面里的表单自动向银行提交转账请求，Cookie 一并带上。

### 3.1 三种防御叠加

| 防御 | 拦住什么 | 局限 |
|---|---|---|
| `SameSite=Lax/Strict` | 跨站请求不带 Cookie | 老浏览器、同站子域 |
| CSRF token | 攻击者拿不到的一次性值 | 需要服务端配合 |
| `Origin`/`Referer` 校验 | 非白名单来源的写请求 | 代理可能改写 Referer |

```ts
// 服务端设置会话 Cookie 的标准属性
res.cookie('sid', token, {
  httpOnly: true,   // 脚本读不到，XSS 也偷不走
  secure: true,     // 只走 HTTPS
  sameSite: 'lax',  // 跨站 POST 不带 Cookie；顶层导航仍可用
  path: '/',
  maxAge: 8 * 60 * 60 * 1000,
});
```

`SameSite=Lax` 是 2026 年的默认值，能挡住绝大多数跨站表单提交；但同站不同子域（`a.example.com` 攻击 `app.example.com`）仍算同站，需要 token 兜底。

```ts
// 双提交：Cookie 里放随机值，请求头再带同一个值，服务端比对
const csrf = crypto.randomUUID();
document.cookie = `csrf=${csrf}; path=/; secure; samesite=strict`;
await fetch('/api/orders', {
  method: 'POST',
  headers: { 'X-CSRF-Token': csrf }, // 攻击者跨源读不到 Cookie，也就拼不出这个头
  body,
});
```

> 边界：`SameSite=None` 必须同时 `Secure`，否则浏览器直接拒收；跨站嵌入（支付回调、iframe 单点登录）确实需要 `None` 时，token 校验不能省。

## 四、CSP 与安全响应头

内容安全策略（Content Security Policy，CSP）用响应头声明“哪些来源的脚本、样式、图片可以加载执行”，是 XSS 的最后一道闸。

### 4.1 nonce 与 hash

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' https: data:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'none';
  object-src 'none'
```

```html
<!-- 每次响应生成新 nonce，内联脚本必须带上它才执行 -->
<script nonce="r4nd0m">
  window.__INIT__ = { user: "qa" };
</script>
```

实测（Chromium 14x，`script-src 'self' 'nonce-abc123'`）：

```text
内联脚本（无 nonce）：被拦截
securitypolicyviolation 事件：{ "directive": "script-src-elem", "blocked": "inline" }
带 nonce 的脚本：正常执行
```

`strict-dynamic` 让被信任脚本动态插入的脚本也放行，适合现代打包产物；代价是 `'self'` 白名单失效，审计点集中到“谁能插入 script”。

### 4.2 上线路径：先报告后拦截

直接上强制策略会把线上打挂。标准路径是三步：

```http
# 第一步：只报告不拦截，收集真实违规
Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'nonce-...'; report-uri /csp-report

# 第二步：按报告补白名单，观察一周
# 第三步：换成强制头，保留 report-uri 继续监控
```

```ts
// 前端收集违规，定位到具体资源
document.addEventListener('securitypolicyviolation', (e) => {
  navigator.sendBeacon('/api/csp-report', JSON.stringify({
    directive: e.violatedDirective,
    blocked: e.blockedURI,
    sample: e.sample,
  }));
});
```

### 4.3 其余安全响应头

| 响应头 | 值 | 作用 |
|---|---|---|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | 强制 HTTPS |
| `X-Content-Type-Options` | `nosniff` | 禁止 MIME 嗅探 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 限制 Referer 泄露 |
| `Permissions-Policy` | `camera=(), microphone=()` | 关闭不需要的能力 |
| `frame-ancestors` | `'none'` | 防点击劫持（CSP 内） |

`frame-ancestors` 优先于 `X-Frame-Options`，新项目只配前者；需要被嵌入的页面按域名白名单放开，不要用 `*`。

> 边界：`style-src 'unsafe-inline'` 在很多组件库里暂时无法避免（动态内联样式）。它的风险远小于 `script-src 'unsafe-inline'`，可以接受；但 `script-src 'unsafe-inline'` 会让 CSP 基本失效，除非同时用 nonce 或 hash。

## 五、CORS 与 SRI

### 5.1 预检与凭证

跨源请求分两类：简单请求直接发；带自定义头、`PUT/DELETE`、`application/json` 的请求先发 `OPTIONS` 预检。

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-csrf-token

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST, GET
Access-Control-Allow-Headers: content-type, x-csrf-token
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600
```

| 配置 | 结果 |
|---|---|
| `Allow-Origin: *` + `Allow-Credentials: true` | 浏览器直接拒绝 |
| 回显任意 `Origin` | 等于对全世界开放，禁止 |
| 缺 `Allow-Headers` | 预检失败，报 CORS 错误 |
| 缺 `Vary: Origin` | CDN 缓存串源响应 |

> 边界：CORS 是浏览器强制的，不是服务端鉴权。`curl` 不受 CORS 限制，接口必须自己校验身份与权限；CORS 只决定“浏览器里的跨源脚本能不能读响应”。

### 5.2 SRI 校验第三方资源

子资源完整性（Subresource Integrity，SRI）用哈希锁定外部脚本内容，CDN 被篡改时浏览器拒绝执行：

```bash
# 生成 sha384 哈希
curl -s https://cdn.example.com/lib.js | openssl dgst -sha384 -binary | openssl base64 -A
# 输出形如（示例）：K7gNU3sdo+OL0wNhqoVWhr3g6s1xYv72ol/pe/Unols=
```

```html
<!-- integrity 不匹配就不执行；crossorigin 是 CORS 请求 SRI 校验的前提 -->
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-K7gNU3sdo+OL0wNhqoVWhr3g6s1xYv72ol/pe/Unols="
        crossorigin="anonymous"></script>
```

SRI 的边界：脚本更新必须同步改哈希，频繁发版的库不适合；动态 `import()` 的模块无法用 SRI，这类依赖应改为自托管。

## 六、WCAG 2.2 与键盘、读屏

Web 内容可访问性指南（Web Content Accessibility Guidelines，WCAG）2.2 是 2023 年 10 月发布的现行版本，2026 年企业采购与合规验收普遍引用它。四条原则：可感知（Perceivable）、可操作（Operable）、可理解（Understandable）、健壮（Robust）。

| 等级 | 含义 | 常见要求 |
|---|---|---|
| A | 最低 | 替代文本、键盘可达、标签 |
| AA | 企业交付基线 | 对比度 4.5:1、焦点可见、目标尺寸 |
| AAA | 增强 | 对比度 7:1、手语、扩展描述 |

### 6.1 WCAG 2.2 新增的验收点

| 条款 | 等级 | 要求 |
|---|---|---|
| 2.4.11 焦点不被遮挡（最低） | AA | 键盘焦点元素不能被固定头/浮层完全盖住 |
| 2.5.7 拖动操作 | AA | 拖动要有单点替代方案 |
| 2.5.8 目标尺寸（最低） | AA | 可点击目标至少 24×24 CSS px |
| 3.3.7 重复输入 | A | 同流程里不重复要求填同一信息 |
| 3.3.8 无障碍认证（最低） | AA | 登录不强制认知测试，允许粘贴密码 |

2.4.11 最容易被固定布局破坏：滚动到表格某行时，行被 64px 的 sticky 表头盖住，键盘用户看不到焦点在哪。修法是给粘性头留出 `scroll-margin-top`：

```css
/* 焦点滚动时预留粘性头高度，保证元素完整可见 */
:focus-visible { scroll-margin-top: 80px; outline: 2px solid #1d4ed8; outline-offset: 2px; }

/* 反例：全局去掉轮廓，键盘用户彻底失去位置 */
*:focus { outline: none; }
```

### 6.2 键盘与焦点管理

键盘可访问的验收只看一件事：**不碰鼠标能否完成主流程**。

```ts
// 弹窗焦点管理：打开时进弹窗，关闭时回触发按钮
function openDialog(trigger: HTMLElement, dialog: HTMLDialogElement) {
  const focusable = dialog.querySelectorAll<HTMLElement>(
    'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
  );
  dialog.showModal();                 // 原生 dialog 自带焦点陷阱与 Esc 关闭
  focusable[0]?.focus();
  dialog.addEventListener('close', () => trigger.focus(), { once: true }); // 焦点归还
}
```

优先用原生 `<dialog>` + `showModal()`：焦点陷阱、`Esc` 关闭、背景不可交互都是浏览器实现的，自己用 `div` 模拟要处理一堆边界。确实要手写时，至少覆盖 Tab 循环、Esc、焦点归还三点。

### 6.3 读屏名称与状态

读屏器读的是可访问性树（accessibility tree），不是视觉。三个最常错的地方：

- 图标按钮没有名称 → `aria-label="关闭"`；
- 异步结果没有播报 → 容器 `role="status"` 或 `aria-live="polite"`；
- 展开状态不同步 → `aria-expanded` 随状态更新。

```html
<!-- 图标按钮：图标对读屏器无意义，必须给名称 -->
<button type="button" aria-label="关闭对话框">×</button>

<!-- 异步提示：role=status 是礼貌播报，不打断当前朗读 -->
<div role="status" aria-live="polite">已保存 3 条记录</div>

<!-- 折叠面板：状态与视觉同步 -->
<button type="button" aria-expanded="false" aria-controls="panel-1">高级筛选</button>
<div id="panel-1" hidden>...</div>
```

## 七、axe 自动化与手工检查

### 7.1 axe-core 接入

axe-core 能自动检出约 30%–50% 的可访问性问题，覆盖替代文本、标签、对比度、地标、标题顺序、ARIA 合法性。它是门槛检查，不是验收全部。

```bash
npm i -D axe-core
```

```js
// Playwright 里注入 axe 并只取违规项
const { chromium } = require('@playwright/test');
const fs = require('fs');

;(async () => {
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto('http://127.0.0.1:5173/orders');
  await page.addScriptTag({ content: fs.readFileSync(require.resolve('axe-core'), 'utf8') });

  const violations = await page.evaluate(async () => {
    const res = await axe.run(document, { resultTypes: ['violations'] });
    return res.violations.map((v) => ({ id: v.id, impact: v.impact, nodes: v.nodes.length }));
  });
  console.log(violations);
  await browser.close();
})().catch((err) => {
  console.error(err);
  process.exitCode = 1;
});
```

一个未修复的订单页实测输出（Chromium 14x + axe-core）：

```text
color-contrast   serious   2 nodes
heading-order    moderate  1 node
image-alt        critical  1 node
label            critical  1 node
landmark-one-main moderate 1 node
region           moderate  5 nodes
```

共 6 类规则、11 个节点。修复后同样脚本输出 `[]`。

### 7.2 自动化的盲区

axe 查不出“能不能用”：

| 问题 | axe 是否报告 | 检查方式 |
|---|---|---|
| `div` 加 `onclick` 当按钮 | 否 | 键盘 Tab + Enter 实测 |
| 焦点顺序与视觉不一致 | 否 | 只用键盘走一遍 |
| 弹窗焦点没锁住 | 否 | Tab 到背景元素 |
| 读屏语义是否通顺 | 否 | VoiceOver/NVDA 实听 |
| 拖动没有替代操作 | 否 | 2.5.7 人工核对 |

`div` 按钮是典型：axe 不报，因为 `div` 本来就不是按钮；但它对键盘用户完全不可用。修法是换回 `<button>`，而不是加 `tabindex` 和键盘事件去模拟。

### 7.3 手工检查清单

- Tab 走完主流程，焦点始终可见且不被遮挡；
- 每个图标按钮都有可读名称；
- 表单错误与字段关联，提交后焦点落到第一个错误；
- 弹窗打开锁焦点、Esc 关闭、关闭后焦点回到触发点；
- 200% 缩放后内容不重叠、不截断；
- 只用键盘能完成登录（可粘贴密码，无认知测试）。

## 八、现场手册

| 现象 | 最可能原因 | 第一条命令/动作 |
|---|---|---|
| 页面出现陌生脚本执行 | 存储型 XSS 注入点 | 搜 `v-html`/`innerHTML`/`dangerouslySetInnerHTML` |
| 内联脚本突然不执行 | CSP 未带 nonce | 看 Console 的 CSP 报错与 `securitypolicyviolation` |
| 跨源接口报 CORS | 预检缺头或 Origin 不匹配 | Network 看 OPTIONS 响应头 |
| 跨站请求被拒 | `SameSite` 与场景不符 | 检查是否跨站 iframe/回调 |
| 第三方脚本被浏览器拒绝 | SRI 哈希与内容不一致 | 重新生成 `sha384` 并核对 `crossorigin` |
| 键盘无法操作某按钮 | 用了 `div` + `onclick` | 换 `<button>` |
| 焦点被表头盖住 | 粘性定位无 `scroll-margin` | 补 `scroll-margin-top` |
| axe 全绿但用户仍用不了 | 自动化盲区 | 按 7.3 手工走一遍 |

## 九、最佳实践案例

### 9.1 案例背景

某 B2B 管理后台的订单页，技术栈 Vue 3.5 + Element Plus，运营需要在订单备注里支持富文本公告。上线后出现三件事：安全团队扫描发现备注字段可注入脚本；第三方 CDN 的图表库没有完整性校验；无障碍审计报告列出 6 类问题，键盘用户无法提交筛选。

约束：不能重写页面框架，只允许改安全配置、富文本渲染路径和局部的可访问性标记；CSP 必须先报告后强制，避免一次性打挂线上。

### 9.2 案例实操

**第一步：确认 XSS 注入点。** 全仓搜危险 API：

```bash
grep -rn "v-html\|innerHTML\|dangerouslySetInnerHTML" src | grep -v node_modules
# src/views/OrderDetail.vue:88:  <div v-html="order.remark"></div>
```

`v-html` 直接渲染用户备注，脚本可执行。改为清洗后再渲染，只保留排版标签：

```ts
// src/utils/rich-text.ts
import DOMPurify from 'dompurify';

export function renderRemark(raw: string) {
  // 白名单：无脚本、无事件属性、无 iframe；链接只允许 http/https/mailto
  return DOMPurify.sanitize(raw, {
    ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'ul', 'ol', 'li', 'a'],
    ALLOWED_ATTR: ['href', 'title'],
    ALLOWED_URI_REGEXP: /^(?:https?|mailto):/i,
  });
}
```

```vue
<!-- 清洗后的结果仍通过 v-html 渲染，但已无危险标签 -->
<div class="remark" v-html="renderRemark(order.remark)"></div>
```

**第二步：配 CSP，先报告。** 首周只发 `Report-Only`，收集违规来源：

```http
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-{{NONCE}}' 'strict-dynamic';
  style-src 'self' 'unsafe-inline';
  img-src 'self' https: data:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'none';
  report-uri /api/csp-report
```

违规事件用统一入口收集（实测事件字段：`directive`、`blockedURI`、`sample`）：

```ts
// src/security/csp-report.ts
document.addEventListener('securitypolicyviolation', (e) => {
  navigator.sendBeacon('/api/csp-report', JSON.stringify({
    directive: e.violatedDirective,   // 例如 script-src-elem
    blocked: e.blockedURI,            // 例如 inline
    page: location.pathname,
  }));
});
```

一周后把白名单外的来源逐个处理，再把 `Report-Only` 换成强制头，保留 `report-uri` 继续观察。

**第三步：给第三方脚本加 SRI。**

```bash
curl -s https://cdn.example.com/chart.umd.js | openssl dgst -sha384 -binary | openssl base64 -A
```

```html
<!-- 哈希由上面的命令生成，内容一变浏览器就拒绝执行 -->
<script src="https://cdn.example.com/chart.umd.js"
        integrity="sha384-<上一步输出>"
        crossorigin="anonymous"></script>
```

同时把可自托管的依赖迁到自己的 CDN，减少跨源依赖；SRI 只防篡改，不防恶意库，版本仍要锁。

**第四步：修可访问性。** 先跑 axe 拿到基线：

```bash
node axe.js
```

```text
color-contrast    serious   2 nodes
heading-order     moderate  1 node
image-alt         critical  1 node
label             critical  1 node
landmark-one-main moderate 1 node
region            moderate  5 nodes
```

按类别逐项修：

```vue
<template>
  <a class="skip-link" href="#main">跳到主内容</a>

  <header><h1>订单管理</h1></header>

  <main id="main">
    <h2>筛选</h2>
    <!-- alt 描述图片表达的信息，不是文件名 -->
    <img src="/chart.svg" alt="近 30 天订单量趋势，整体上升 12%">

    <form @submit.prevent="search">
      <label for="keyword">关键词</label>
      <input id="keyword" v-model="keyword" type="search">
      <!-- 用原生 button，键盘与读屏天然可用 -->
      <button type="submit">搜索</button>
    </form>

    <table>
      <caption>订单列表</caption>
      <thead>
        <tr><th scope="col">订单号</th><th scope="col">客户</th><th scope="col">操作</th></tr>
      </thead>
      <tbody>
        <tr v-for="o in orders" :key="o.id">
          <td>{{ o.id }}</td>
          <td class="muted">{{ o.customer }}</td>
          <td><button type="button" @click="remove(o)">删除</button></td>
        </tr>
      </tbody>
    </table>
  </main>
</template>
```

对比度调整（`#bbb` 在白底上约 1.9:1，远低于 4.5:1）：

```css
/* 改前 #bbb 对白底约 1.9:1；改后 #4b5563 约 7.5:1 */
.muted { color: #4b5563; }
```

**第五步：键盘与焦点验收。** 固定表头会遮挡焦点，补 `scroll-margin`；弹窗改用原生 `<dialog>`：

```css
/* 键盘滚动到表格行时，给 64px 粘性头留出空间（WCAG 2.4.11） */
:focus-visible { scroll-margin-top: 80px; outline: 2px solid #1d4ed8; outline-offset: 2px; }
```

**第六步：复跑。** axe 归零后，再按 7.3 的手工清单走键盘与读屏。

### 9.3 案例结果

| 项 | 改前 | 改后 | 口径 |
|---|---|---|---|
| axe 违规规则 | 6 类 / 11 节点 | 0 | Chromium 14x + axe-core |
| 备注注入 | `v-html` 直出可执行 | 白名单清洗 | 手工构造 `<img onerror>` 验证 |
| 内联脚本 | 无策略，全部执行 | 无 nonce 被拦截 | CSP 实测事件 `script-src-elem` |
| 键盘提交筛选 | 不可达（div 按钮） | 可达 | Tab + Enter 实测 |
| 焦点遮挡 | 表头盖住行 | 完整可见 | 2.4.11 手工核对 |
| 第三方脚本 | 无完整性校验 | SRI 校验通过 | 篡改测试被拒绝 |

失败模式复盘：

- 第一版 CSP 直接上强制模式，图表库的动态 `eval` 被拦，页面白屏；改为 `Report-Only` 收集一周，才发现有三个依赖需要换版本；
- 清洗最初放在保存时，历史数据仍带脚本；改为“入库清洗 + 渲染清洗”双保险后，老数据也被兜住；
- axe 归零后键盘验收仍失败：`div` 按钮 axe 不报，说明自动化只能当门槛；
- 对比度修改后视觉稿被要求还原，最终按设计系统新增了一档满足 4.5:1 的灰色，而不是逐个页面改颜色。

结论：安全与可访问性都不是“加一个库”就完成的事。XSS 要按上下文编码并清洗富文本，CSRF 靠 Cookie 属性加 token，CSP 必须灰度上线，SRI 锁住第三方；可访问性要用 axe 建基线、用键盘和读屏验收真实可用性。两者共同点：**验收标准写在交付前，证据必须是可复现的命令或实测结果。**
