# 包管理与依赖供应链

> 这篇从包管理器的四项职责讲起，经过版本范围与 lockfile、依赖类型、pnpm 的存储布局、版本冲突处理、workspace 单仓，最后落到供应链攻击面和 CI 门禁。
>
> 学完能独立用 pnpm 管理多包仓库，锁定可复现的依赖，并把审计、SBOM 和脚本拦截接进流水线。

## 一、包管理器的职责与三家差异

包管理器做四件事：把版本范围解析成具体版本、下载并校验包、在 `node_modules` 里排出可用的链接结构、用 lockfile 锁住整套结果保证可复现。四件事缺任何一件，都会在团队协作里变成“我这能跑、CI 挂了”。

2026 年的前端仓库在三个包管理器里选：

| 包管理器 | node_modules 布局 | 突出优势 | 常见场景 |
|---|---|---|---|
| pnpm | 符号链接 + 内容寻址存储 | 省磁盘、安装快、默认隔离 | 新项目、monorepo |
| npm | 扁平化 hoist | 无需额外工具 | 最小依赖的库 |
| yarn (berry) | PnP 或 hoist | 存量项目延续 | 早期迁移过来的仓库 |

pnpm 是 Vue 3、Vite 官方模板都支持的包管理器；单仓场景默认选它。npm 只在“只发一个零依赖小包”这类场景里占优；yarn 不建议新项目采用。

包管理器与构建器的边界必须分清：

- 装什么、装哪个版本、装到哪——包管理器；
- 源码怎么转译、怎么打包——构建器（Vite）；
- 依赖是否合规、有没有漏洞——包管理器提供数据，门禁在 CI。

> 边界：`npm install` 能装上不代表依赖是“好的”。安装成功只说明版本解析和下载成功，安全与合规是供应链章的事，不要指望安装环节替团队把关。

## 二、安装与最小验证

pnpm 10 由 Corepack 管理，不全局安装。Corepack 随 Node 22 分发，pnpm 由它按 `packageManager` 字段下载。先固定版本再写代码。

### 2.1 安装 pnpm

Ubuntu / Debian：

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
corepack enable pnpm
corepack prepare pnpm@10.19.0 --activate
```

Rocky / CentOS：

```bash
sudo dnf install -y nodejs
corepack enable pnpm
```

macOS：

```bash
brew install node@22
corepack enable pnpm
```

Windows：

```powershell
winget install OpenJS.NodeJS.LTS
corepack enable pnpm
```

版本固定在 `package.json` 里，Corepack 会在进入目录时自动切换：

```json
{
  "packageManager": "pnpm@10.19.0",
  "engines": { "node": ">=22.12.0", "pnpm": ">=10.0.0" }
}
```

`engines` 默认只是提示；要让 CI 拦住用错 Node 的人，需要 `.npmrc`：

```ini
engine-strict=true
```

### 2.2 最小验证

空目录里跑通“装、引、跑、锁”四步：

```bash
mkdir hello && cd hello
pnpm init
pnpm add dayjs --save-exact
node --input-type=module -e "import dayjs from 'dayjs'; console.log(dayjs('2026-11-13').format('YYYY-MM-DD'))"
pnpm list --depth 0
```

预期输出：

```text
2026-11-13
hello@1.0.0 /tmp/hello

dependencies:
dayjs 1.11.13
```

第四条命令确认锁文件生成：

```bash
ls pnpm-lock.yaml   # pnpm-lock.yaml
```

| 组件 | 版本 |
|---|---|
| Node | 22.x LTS |
| pnpm | 10.x |
| Corepack | 随 Node 22 附带 |

`--save-exact` 锁定精确版本只影响 `package.json` 里的写法；真正的可复现来自 lockfile。`package.json` 写 `^1.11.13` 而 CI 用 `--frozen-lockfile`，同样能复现，只是“允许升级到什么范围”的意图表达不同。

> 边界：`pnpm init` 生成的 `package.json` 没有 `"type": "module"`。写 ESM 的项目要补上，否则 `.js` 文件按 CommonJS 解析，`import` 语法直接报错。

## 三、版本范围与 lockfile

lockfile 是唯一事实源：`package.json` 表达意图，lockfile 记录结果。两份文件对不上时，安装行为就取决于谁来执行——这正是“本地正常、CI 挂”的来源。

### 3.1 版本范围怎么解析

| 写法 | 含义 | 解析到 |
|---|---|---|
| `1.2.3` | 精确版本 | 1.2.3 |
| `^1.2.3` | 兼容 1.x | 最新 1.x |
| `~1.2.3` | 修 bug 级别 | 1.2.x |
| `>=1.2 <2` | 区间 | 区间内最新 |
| `workspace:*` | 单仓本地包 | 源码链接 |

两个规则容易被忽略：

- `0.x` 没有兼容承诺：`^0.3.2` 只解析到 `0.3.x`，因为 0.x 阶段次版本号等同于大版本；
- `^` 允许跨越小版本，pnpm install 不带 lockfile 时会拿到新小版本，新版本有行为变化时问题就在“重新装了一次”时出现。

### 3.2 lockfile 的结构

pnpm 的 lockfile 分三层：importers 记录每个项目的直接依赖，packages 记录每个包的元数据，snapshots 记录每个包的依赖关系：

```yaml
importers:
  apps/admin:
    dependencies:
      vue:
        specifier: 3.5.45
        version: 3.5.45

packages:
  vue@3.5.45:
    resolution: {integrity: sha512-...}
    engines: {node: '>=18'}
    hasBin: false

snapshots:
  vue@3.5.45:
    dependencies:
      '@vue/compiler-dom': 3.5.45
```

`specifier` 是 `package.json` 里的写法，`version` 是解析后的结果。CI 里两者不一致就要失败，而不是悄悄重装：

```bash
pnpm install --frozen-lockfile
```

人为制造一次不一致——给 `apps/admin` 加一个 `dayjs` 但不提交 lockfile 更新——再跑冻结安装：

```text
Scope: all 4 workspace projects
 ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because
 pnpm-lock.yaml is not up to date with <ROOT>/apps/admin/package.json

Note that in CI environments this setting is true by default. If you still
need to run install in such cases, use "pnpm install --no-frozen-lockfile"

  Failure reason:
    specifiers in the lockfile don't match specifiers in package.json:
* 1 dependencies were added: dayjs@1.11.13
```

错误信息直接给出原因和改法。CI 里永远用 `--frozen-lockfile`；本地日常 `pnpm install` 会自动更新 lockfile，改完依赖要把 lockfile 和 `package.json` 一起提交。

| 场景 | 命令 | lockfile 行为 |
|---|---|---|
| 本地加依赖 | `pnpm add x` | 更新并写入 |
| 本地同步 | `pnpm install` | 有漂移则更新 |
| CI 安装 | `pnpm install --frozen-lockfile` | 不一致即失败 |
| 只想改 lockfile | `pnpm install --lockfile-only` | 只写文件不装包 |
| 升级到最新版本并改写范围 | `pnpm update --latest` | 更新范围并写 lockfile |

> 边界：lockfile 必须提交进仓库。“lockfile 是生成物不用提交”是 npm 时代的老习惯，直接后果是每个环境各装各的，供应链审计也没有基线。`.gitignore` 里不应出现 `pnpm-lock.yaml`。

## 四、依赖类型的边界

依赖写在哪个字段，决定了谁能装到它、生产环境要不要它、别的项目能不能复用它。字段选错不影响本地运行，问题全在发布和部署时出现。

| 字段 | 谁会安装 | 放什么 |
|---|---|---|
| `dependencies` | 使用方 | 运行时需要的包 |
| `devDependencies` | 当前项目 | 构建、测试、类型 |
| `peerDependencies` | 使用方 | 宿主要提供的包 |
| `optionalDependencies` | 自动容错 | 装不上也能跑的包 |

### 4.1 应用和库的写法完全不同

应用（Vite 项目、Nuxt 项目）把 `vue`、`element-plus` 放 `dependencies`，把 `vite`、`vitest`、`typescript` 放 `devDependencies`——镜像里只需要前者的产物，后者的存在只是为了让构建机工作。

库（要被别人 `pnpm add` 的包）把 `vue` 放 `peerDependencies`：

```json
{
  "name": "@acme/ui",
  "peerDependencies": { "vue": "^3.4.0" },
  "devDependencies": { "vue": "3.5.45" }
}
```

`peerDependencies` 的含义是“我需要 vue，但不带自己的副本，由使用方提供”。这样宿主和库里只存在一份 vue，`instanceof`、`provide/inject` 才不会因为两个副本而失效。

不声明 peer 的代价在运行时爆发：

```text
Vue received a Component that was made a reactive object...
```

这类“两份 Vue 实例”报错的根源就是库自己打包了一份 vue。修法是回到 `package.json` 声明 peer，而不是在代码里 try/catch。

### 4.2 幽灵依赖

幽灵依赖（phantom dependency）指代码里 `import` 了一个没有在任何字段里声明的包，它之所以能解析，是因为扁平化布局把别的包的依赖抬到了顶层。

npm/yarn 的扁平布局掩盖幽灵依赖；pnpm 的链接布局让它在装依赖那一刻就暴露：

```text
ERROR  Unable to resolve dependency vue-router
```

这是 pnpm 的优点而不是缺点：错误提前到安装期，而不是上线前两天。修复方式只有一种——把用到的包写进 `package.json`，不要抄别人的依赖树。

```bash
# 确认某个包到底被谁依赖
pnpm -F @acme/admin why vue
```

```text
Legend: production dependency, optional only, dev only

@acme/admin@1.0.0 /repo/apps/admin

dependencies:
vue 3.5.45
```

> 边界：`@types/*` 这类类型包放 `devDependencies`。发布 TS 库时类型走 `.d.ts` 产物，使用方不需要再装库的类型依赖。

## 五、pnpm 的存储与 node_modules 布局

pnpm 把“包的真实文件”和“项目的依赖视图”分开管理：真实文件只存一份，项目里全是链接。理解这个布局，才能理解 pnpm 的速度、隔离性和报错。

三层结构：

```text
~/.local/share/pnpm/store/v10     # 内容寻址存储，全局一份（macOS 为 ~/Library/pnpm/store/v10）
<repo>/node_modules/.pnpm/         # 硬链接到 store 的真实结构
<repo>/node_modules/vue           # 指向 .pnpm/vue@3.5.45/... 的符号链接
```

验证：

```bash
pnpm store path
# /Users/jim/Library/pnpm/store/v10

pnpm -F @acme/admin exec node -e "console.log(require.resolve('vue/package.json'))"
# /repo/node_modules/.pnpm/vue@3.5.45/node_modules/vue/package.json
```

解析结果落在 `.pnpm/vue@3.5.45/` 里，说明 `apps/admin` 里的 `vue` 是穿过两级链接到达唯一副本的。同一个包在十个项目里用，磁盘上只有一份；这是 pnpm 比 npm 快和省的核心原因。

一个最小 workspace（3 个项目、23 个包）的实测安装输出：

```text
Progress: resolved 23, reused 0, downloaded 23, added 23, done

Done in 3.8s using pnpm v10.19.0
```

第二次安装同一项目时 `reused` 会接近全部数字——store 命中后不再下载。

### 5.1 什么时候放宽布局

两种真实场景需要放宽：

- 依赖了不规范的包，它去 require 同级的传递依赖（幽灵依赖的包版）；
- Docker 构建层需要极端简单的目录结构。

```ini
# .npmrc
node-linker=hoisted
```

`node-linker=hoisted` 放弃隔离换兼容，node_modules 变回 npm 的扁平结构，pnpm 只剩安装速度优势。先试 `pnpm.overrides` 补依赖，把 hoisted 当最后手段，因为它重新打开了幽灵依赖的大门。

`shamefully-hoist=true` 效果类似，名字本身就是警告。

> 边界：硬链接不能跨文件系统。store 在机械盘、项目在外置盘时，pnpm 会退化为复制，速度掉回 npm 水平。Docker 里给 store 一个命名卷、或用 `pnpm fetch` 预热，见第八节容器化部分。

### 5.2 store 维护

```bash
pnpm store prune   # 清理不再被引用的包，安全
pnpm store status  # 检查 store 完整性
```

`prune` 不会破坏正在使用的项目：内容寻址存储的引用计数保证只删无主文件。

## 六、版本冲突：overrides、patch、packageExtensions

同一个包出现多个版本是常态，是否要修取决于“是不是同一份实例被共享”。判断顺序：先看是不是 peer 冲突，再看是不是意外多版本，最后才动 overrides。

### 6.1 谁需要同版本

需要强制同版本的只有“单例类”依赖：`vue`、`react`、`pinia` 这类持有全局状态的包。工具库（`lodash-es`、`dayjs`）多一个副本只是多几 KB，不值得为它写 overrides。

```json
{
  "pnpm": {
    "overrides": {
      "vue": "3.5.45",
      "element-plus>vue": "3.5.45"
    }
  }
}
```

第一行全局钉死；第二行只钉 `element-plus` 的 vue 子依赖，范围更小、影响更可控。npm 的写法在 `overrides` 字段（不带 `pnpm` 前缀），yarn 用 `resolutions`，三家的语义相同：重写依赖图的解析结果。

改完必须重装并检查：

```bash
pnpm install && pnpm -r why vue
```

所有 importers 都指向同一个 `3.5.45` 才算生效。

### 6.2 补包的缺失声明

包没声明自己实际用到的 peer 时，用 `packageExtensions` 补：

```json
{
  "pnpm": {
    "packageExtensions": {
      "some-old-lib": {
        "peerDependencies": { "dayjs": "*" }
      }
    }
  }
}
```

比 overrides 温和：不改变版本，只补声明。等上游修复后删掉即可。

### 6.3 patch：改别人的代码

上游 bug 卡进度时才用 patch，且要有退出时间：

```bash
pnpm patch some-lib@1.2.3
# pnpm 会输出一个临时目录，在里面改代码

pnpm patch-commit /private/var/.../pnpm-patch-1234
```

`patch-commit` 生成 `patches/some-lib@1.2.3.patch` 并在 `package.json` 里登记：

```json
{
  "pnpm": {
    "patchedDependencies": {
      "some-lib@1.2.3": "patches/some-lib@1.2.3.patch"
    }
  }
}
```

patch 文件要提交进仓库。每次 `pnpm install` 都会重新应用；版本一旦升级，patch 不再匹配，pnpm 会直接报错——这是好事，强迫在升级时重新审视这个补丁。

> 边界：patch 的风险是上游不认。每个 patch 必须对应一个上游 issue 链接，写进 patch 文件顶部的注释；没有上游出口的 patch 是技术债的复利。

## 七、workspace 单仓

前端单仓（monorepo）把管理后台、移动端 H5、共享组件库放进一个仓库，用 workspace 协议互相引用，不发 npm 包就能本地联调。

### 7.1 结构与解析

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

```text
repo/
  apps/admin/        # 管理后台（Vite）
  apps/h5/           # 移动端
  packages/ui/       # 组件库
  packages/request/  # 请求封装
  pnpm-workspace.yaml
  pnpm-lock.yaml     # 整个仓库只有一份
```

内部依赖用 `workspace:` 协议：

```json
{
  "name": "@acme/admin",
  "dependencies": {
    "@acme/ui": "workspace:*",
    "vue": "3.5.45"
  }
}
```

`workspace:*` 在开发时解析成符号链接——改 `packages/ui` 的源码，`apps/admin` 的 dev server 立即热更新；发布时才把协议替换成真实版本号。

```bash
npx -y pnpm@10.19.0 install
```

```text
Scope: all 5 workspace projects
...
Done in 3.8s using pnpm v10.19.0
```

安装日志的 `Scope` 行列出全部项目（含根项目），确认 workspace 识别正常；`packages/*` 少匹配一个目录时，这里会立刻少一个。

### 7.2 过滤操作

`--filter` 是单仓里的核心操作符：

```bash
pnpm -F @acme/admin dev              # 只起 admin 的 dev server
pnpm -F @acme/admin add dayjs        # 只给 admin 加依赖
pnpm -F @acme/ui test                # 只跑 ui 的测试
pnpm -r --filter ./apps/** test      # apps 下所有项目跑测试
pnpm -F @acme/admin... build          # admin 及其依赖先构建
```

`@acme/admin...` 带三个点表示“连同它的内部依赖一起”，依赖图顺序由 pnpm 排，不需要手写 build 顺序脚本。

### 7.3 版本统一：catalog

多个项目各自声明版本，半年后就是 `admin` 用 vue 3.5、`h5` 用 3.4。catalog 把版本收敛到 workspace 文件里：

```yaml
# pnpm-workspace.yaml
catalog:
  vue: 3.5.45
  element-plus: 2.14.8
```

```json
{
  "dependencies": {
    "vue": "catalog:",
    "element-plus": "catalog:"
  }
}
```

所有写 `catalog:` 的项目解析到同一版本，升级只改一处。lockfile 里记录解析结果，发布时 pnpm 会替换成真实版本号。

### 7.4 发布链

```bash
pnpm -r publish --no-git-checks     # 按依赖顺序发布所有包
```

发布前要保证三件事：`workspace:` 已被替换（pnpm 自动做）、`files` 字段只包含产物、`.npmrc` 指向正确的 registry。多包仓库的版本管理用 changesets 维护，它根据变更记录生成 changelog 并按依赖传播版本号。

> 边界：workspace 不是免费的。仓库超过十几个包后，CI 要按 `--filter` 拆分增量任务，否则每次提交都全量构建；`pnpm -F` 与 CI 的路径过滤（如 GitHub Actions 的 `dorny/paths-filter`）配合使用。

## 八、供应链安全

供应链攻击利用的是“安装即执行”。npm 生态的攻击面：账号劫持后向正常包发恶意版本、抢注相似包名（typosquatting）、传递依赖里夹带恶意代码、postinstall 脚本直接执行任意命令、公有 registry 混入内网包名（dependency confusion）。

### 8.1 攻击面与对策

| 攻击面 | 对策 | 工具 |
|---|---|---|
| 新版本恶意代码 | 冻结 lockfile + 延迟升级 | CI 冻装、Renovate 定期 |
| 安装脚本 | 默认拦截，白名单放行 | `onlyBuiltDependencies` |
| 抢注包名 | 只装锁定的包 | lockfile 审查 |
| 内网包名被公网抢注 | scope 指向私有源 | `.npmrc` |
| 漏洞传递依赖 | 审计 + 门禁 | `pnpm audit` |
| 无法追溯 | SBOM 存档 | `syft`（pnpm 11+ 可用 `pnpm sbom`） |

pnpm 10 默认不执行依赖的 postinstall 类脚本，需要执行的包在 `pnpm-workspace.yaml` 里显式放行：

```yaml
onlyBuiltDependencies:
  - esbuild
  - sharp
```

命令行交互放行的入口是 `pnpm approve-builds`，输出会写回配置文件。esbuild、sharp 这类用脚本安装二进制的包不放开就不能工作，其他依赖保持默认拦截。

### 8.2 私有源与依赖混淆

```ini
# .npmrc
# @acme 前缀的包走内网源，其余走公网
@acme:registry=https://npm.corp.acme.com/
```

只加这一行还不够：公网上任何人都能发布 `@acme/xxx` 时，内网源临时故障会让 npm 回退到公网，拿到攻击者的包。彻底的防法是 CI 里禁用公网回退（内网源代理公网流量），并在审计里核对每个包的 resolved URL。

### 8.3 审计

```bash
# npm 项目
npm audit --omit=dev
# pnpm 项目
pnpm audit --prod
```

下面是一段 npm 项目的真实输出（一个装了 `request@2.88.0` 的项目），用于说明报告结构；pnpm 的字段格式不同，退出码语义一致。

```text
# npm audit report

form-data  <=2.5.5
Severity: critical
form-data uses unsafe random function in form-data for choosing boundary - https://github.com/advisories/GHSA-fjxv-7rqg-78g4
No fix available
node_modules/form-data
  request  *
  Depends on vulnerable versions of form-data
  Depends on vulnerable versions of qs
  Depends on vulnerable versions of tough-cookie
  node_modules/request

qs  <=6.15.4
Severity: moderate
qs's arrayLimit bypass in its bracket notation allows DoS via memory exhaustion - https://github.com/advisories/GHSA-6rw7-vpxm-498p
No fix available
```

审计有漏洞时退出码非零（实测 1），可以直接当 CI 门禁：

```yaml
- name: audit
  run: pnpm audit --prod --audit-level=high
```

`--audit-level=high` 只挡 high 和 critical，低危噪音交给 Renovate 的定期 PR 处理。`--prod`（npm 里是 `--omit=dev`）的理由：devDependencies 不进产物，攻击者无法通过线上应用触达它们。

`No fix available` 表示没有可升级的修复版本，只能换库。`request` 这类 2018 年就停止维护的库，正确动作是迁移到 `undici` 或原生 `fetch`，而不是压制告警。

### 8.4 SBOM 与自动升级

交付给甲方的系统越来越多要求 SBOM（软件物料清单）。pnpm 10 没有内置 sbom 命令，用 Syft 直接读锁文件（pnpm 11 起可用 `pnpm sbom --sbom-format cyclonedx`）：

```bash
syft dir:. -o cyclonedx-json > sbom.json
```

输出是 CycloneDX JSON，`metadata` 记录生成时间，`components` 列出全部传递依赖，随发布产物归档。

自动升级用 Renovate（或 Dependabot）：

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "rangeStrategy": "bump",
  "schedule": ["before 6am on Monday"],
  "packageRules": [
    {
      "matchUpdateTypes": ["minor", "patch"],
      "automerge": true
    },
    {
      "matchUpdateTypes": ["major"],
      "automerge": false
    }
  ]
}
```

minor 和 patch 自动合并的前提是测试足够（见 Vitest 篇），major 一律人工评审。自动化升级把“半年不敢动”变成“每周小步走”，供应链事件的响应时间也从周降到天。

> 边界：审计和 SBOM 都基于包名和版本，绕过不了“包发布后被替换”这种攻击。发布方有 sigstore 签名时验证 provenance 才有意义；没启用时，冻结 lockfile + 私有源代理是现实里的底线。

## 九、排障手册

| 现象 | 最可能原因 | 第一条命令 |
|---|---|---|
| CI 装依赖失败 OUTDATED_LOCKFILE | lockfile 与 package.json 不同步 | `git diff pnpm-lock.yaml` |
| `ERR_PNPM_PEER_DEP_UNMET` | peer 没装或版本不够 | `pnpm why <peer包>` |
| 代码里 import 报无法解析 | 幽灵依赖 | `pnpm add <包>` |
| 运行时两份 Vue 实例告警 | 库没把 vue 声明为 peer | 查库的 `package.json` |
| esbuild/sharp 运行报缺二进制 | 安装脚本被拦截 | `pnpm approve-builds` |
| 装得极慢、store 报错 | store 跨盘或损坏 | `pnpm store status` |
| workspace 项目互相看不见 | 目录不在 packages 匹配范围 | `pnpm -r list --depth 0` |

### 9.1 peer 冲突

```text
ERR_PNPM_PEER_DEP_UNMET  @acme/ui@1.0.0 requires vue@^3.4.0 but vue@3.5.45...
```

先确认这是真冲突还是声明太旧。库声明 `^3.4.0` 而宿主用 3.5 本应满足；报错说明版本范围写死了。宿主侧能用 `pnpm.peerDependencyRules.allowedVersions` 压制误报，库侧的正解是放宽范围并修复。

### 9.2 幽灵依赖在 CI 爆发

本地 npm 装的旧项目迁到 pnpm 后全量报错，因为扁平布局里“顺手 import”的包没有被声明。批量定位：

```bash
pnpm -r exec node -e "console.log(1)" 2>&1 | grep "Unable to resolve"
```

把报错的包补进对应项目的 `package.json`，不要用 `node-linker=hoisted` 一掩了之。

### 9.3 store 跨盘

Docker 或外置盘场景下安装变慢，先确认 store 与项目同盘：

```bash
pnpm store path
df -h .  # 对比挂载点
```

不同盘就把 store 移到项目所在盘：`pnpm config set store-dir /path/on/same/disk/store`。

## 十、最佳实践案例

### 10.1 案例背景

某公司的订单管理后台和移动端 H5 原来是两个仓库，各自用 npm，`package-lock.json` 经常合并冲突，共享组件靠手工复制，出现过两次“组件改了 A 仓库忘了 B 仓库”的线上事故。供应链层面没有任何门禁：postinstall 脚本畅通无阻、审计没人跑、甲方开始要求 SBOM。

目标：合并为 pnpm workspace，建立“锁文件冻结 + 脚本白名单 + 审计门禁 + SBOM 归档”的交付链，两周内完成且不阻塞日常迭代。

### 10.2 案例实操

第一步，搭建单仓结构：

```text
repo/
  apps/admin/     # 管理后台（Vite + Vue 3.5）
  apps/h5/        # 移动端 H5
  packages/ui/    # 组件库
  packages/request/
  pnpm-workspace.yaml
  .npmrc
```

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
catalog:
  vue: 3.5.45
  vue-router: 5.5.0
```

第二步，把两个仓库的依赖合并进各自 `package.json`，共享包抽到 `packages/ui` 并用 `workspace:*` 引用：

```json
{
  "name": "@acme/admin",
  "dependencies": {
    "@acme/ui": "workspace:*",
    "vue": "catalog:",
    "vue-router": "catalog:"
  }
}
```

第三步，一次性安装并验证内部链接：

```bash
npx -y pnpm@10.19.0 install
```

```text
Scope: all 5 workspace projects
...
Done in 3.8s using pnpm v10.19.0
```

这是冷装的关键片段；实际输出会逐行打印 `resolved / reused / downloaded` 的进度。

合并过程里 pnpm 报出 7 个幽灵依赖——两个仓库都在 import 没声明的 `dayjs`、`qs` 和 `lodash-es`，逐一补进声明。npm 时代它们靠扁平布局侥幸工作。

第四步，接脚本白名单和私有源：

```yaml
# pnpm-workspace.yaml 追加
onlyBuiltDependencies:
  - esbuild
  - sharp
```

```ini
# .npmrc
@acme:registry=https://npm.corp.acme.com/
engine-strict=true
```

第五步，CI 门禁。`.github/workflows/ci.yml`：

```yaml
name: ci
on: [push, pull_request]

jobs:
  install-and-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 10.19.0 }
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      # 冻装：lockfile 与 package.json 不一致直接失败
      - run: pnpm install --frozen-lockfile
      # 审计：只挡 high 及以上，dev 依赖不进产物不挡
      - run: pnpm audit --prod --audit-level=high
      # 测试全量；构建只跑 admin 及其内部依赖
      - run: pnpm -r test
      - run: pnpm -F @acme/admin... build
```

第六步，SBOM 归档加进发布流水线：

```bash
# 发布机需预装 syft
syft dir:. -o cyclonedx-json > sbom.json
tar czf dist-with-sbom.tgz dist sbom.json
```

### 10.3 案例结果

| 指标 | 迁移前 | 迁移后 | 说明 |
|---|---|---|---|
| 安装时间（CI 冷装） | 96 s | 31 s | 示例，四项目单仓冷装口径 |
| lockfile 合并冲突 | 每周 2–3 次 | 0 | 单一 lockfile + catalog |
| 幽灵依赖 | 7 个沉默存在 | 0 | 安装期暴露并补声明 |
| postinstall 脚本 | 全部放行 | 白名单 2 个 | esbuild、sharp |
| 供应链门禁 | 无 | 冻装 + 审计 + SBOM | 高危即失败 |

失败模式一：迁移时用 `node-linker=hoisted` 兼容幽灵依赖，一周后新的幽灵依赖又静默混入，等于没迁。正确做法是让 pnpm 报错、逐个补声明。

失败模式二：`pnpm audit --audit-level=low` 上线第一天就红了，低危告警淹没团队后门禁被整体注释掉。审计门禁必须从 high 起步，低危走 Renovate 周期处理。

失败模式三：catalog 统一了版本却没管 `apps/h5` 的构建器版本，Vite 大版本不一致导致共享包产物不兼容。catalog 里应当连 vite、vitest 一起收敛。

复盘：包管理是工程的地基，地基的可复现性靠“单一 lockfile + 冻装 + 脚本白名单”三件事，缺一个都会在团队规模上去之后复发。供应链门禁不追求一步到位，先把“高危漏洞挡在合并前”和“每次交付有 SBOM”两件事做实。
