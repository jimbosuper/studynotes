# 系统测试

## 一、系统测试的边界

测试知识分两层：**测试体系**（分层、自动化框架、长期质量度量）在 `06-测试` 方向；**一个版本的测试怎么组织**在本文。

| 环节 | 负责 | 不负责 |
|---|---|---|
| 07-系统测试（本文） | 测试方案、用例、执行、缺陷、放行结论 | 不讲框架选型和长期质量体系 |
| 测试方向（`06-测试`） | 测试分层、自动化体系、覆盖率、质量度量 | 不讲单个版本怎么排 |
| 06-系统实现 | 单测、自测、代码评审 | 不做系统级验证 |
| 08-系统部署与维护 | 上线、灰度、回滚 | 不替测试下放行结论 |

一句话：**开发证明代码对，测试证明系统能用，运维保证上线不出事**。三者不能互相替代。

## 二、测试方案四要素

测试方案不是几十页的计划书，是四件事说清楚：

| 要素 | 要回答 | 常见错误 |
|---|---|---|
| 范围 | 测什么、不测什么、为什么 | 什么都测，最后什么都没测透 |
| 环境与数据 | 在哪测、数据从哪来 | 用生产数据不脱敏 |
| 方法 | 手工/自动化/探索式，各占多少 | 全部自动化，或全凭手感 |
| 退出标准 | 什么条件下可以放行 | 「测完了」不是标准 |

### 2.1 范围：按风险排，不按功能清单排

一个版本有 50 个改动点，不可能平均用力。按两个维度排序：

- **影响面**：改的是核心链路（下单、支付）还是边缘功能（帮助页）；
- **变更程度**：新功能 > 改逻辑 > 改文案。

| 象限 | 策略 |
|---|---|
| 高影响 + 大变更 | 重点测：用例 + 探索 + 自动化回归 |
| 高影响 + 小变更 | 回归为主，确认没碰坏 |
| 低影响 + 大变更 | 用例覆盖，抽测 |
| 低影响 + 小变更 | 冒烟即可 |

### 2.2 环境与数据

| 环境 | 用途 | 数据 |
|---|---|---|
| 开发环境 | 开发自测 | 造数脚本 |
| 测试环境 | 功能测试、集成测试 | 脱敏数据 + 造数 |
| 预发环境 | 上线前验证 | 生产数据脱敏，配置同生产 |
| 生产 | 灰度验证 | 真实数据 |

三条铁律：**测试不用真实个人信息**（脱敏或造数）、**环境配置与生产一致**（否则测了也白测）、**预发环境必须能连外部依赖的沙箱**（支付、短信）。

### 2.3 退出标准

没有退出标准的测试，永远「快测完了」。可用的标准：

| 维度 | 标准 | 谁定 |
|---|---|---|
| 用例执行 | P0/P1 用例 100% 执行，通过率 ≥ 95% | 测试 |
| 缺陷 | 无 P0/P1 未关闭，P2 有明确处理计划 | 测试 + 产品 |
| 回归 | 核心链路自动化回归全绿 | 测试 |
| 性能 | 关键接口达到 SLO | 开发 + 测试 |
| 安全 | 无高危漏洞 | 安全 |

**退出标准要在提测前定**，不能测完了再商量「差不多就发吧」。

## 三、分层与取舍

### 3.1 三层各测什么

| 层 | 测什么 | 谁写 | 跑多久 | 占比（经验值） |
|---|---|---|---|---|
| 单元测试 | 函数/类的逻辑 | 开发 | 秒级 | 60-70% |
| 集成测试 | 模块间接口、数据库、外部依赖 | 开发/测试 | 分钟级 | 20-30% |
| 端到端 | 用户主流程 | 测试 | 十分钟级 | 5-10% |

金字塔不是教条。三种系统的比例完全不同：

| 系统类型 | 调整 | 原因 |
|---|---|---|
| 纯后端服务 | 单测为主，E2E 很少 | 逻辑在代码里，接口稳定 |
| 中后台系统 | 集成测试为主 | 大量逻辑在页面和接口之间 |
| C 端产品 | E2E 比例上升 | 用户路径长，页面状态多 |
| 数据/报表 | 以数据校验为主 | 逻辑在 SQL 里，单测难覆盖 |

### 3.2 什么该自动化

| 该自动化 | 不该自动化 |
|---|---|
| 核心链路回归（下单、支付、登录） | 一次性验证 |
| 接口契约测试 | 界面视觉细节 |
| 数据校验（金额、状态） | 需求还在变的功能 |
| 冒烟测试 | 探索式测试 |

判断标准：**这条用例会不会跑第二次以上**。只跑一次的用例，写自动化的时间比手工还长。

### 3.3 自动化的维护成本

自动化不是写完就完了。UI 自动化最容易被低估：页面改一个选择器，几十条用例全挂。

| 类型 | 维护成本 | 稳定性 | 建议 |
|---|---|---|---|
| 接口自动化 | 低 | 高 | 优先做 |
| 单元测试 | 低 | 高 | 必须做 |
| UI 自动化 | 高 | 低 | 只覆盖核心路径 |

一个可用的比例：**接口自动化 : UI 自动化 ≥ 5 : 1**。UI 自动化超过这个比例，维护成本会吃掉收益。

## 四、用例设计：三种方法够用

### 4.1 等价类：把无穷输入变成有限几类

1. 找出每个输入的取值范围和约束；
2. 切成若干等价类，同类内任取一个值行为应一致；
3. 每类分有效/无效，都要有用例；
4. 每类选一个代表值。

| 输入 | 有效等价类 | 无效等价类 |
|---|---|---|
| 金额 | > 0 且 ≤ 100000，两位小数 | ≤ 0、> 100000、超过两位小数 |
| 会员等级 | NORMAL/VIP/SVIP | 空、未知值 |
| 优惠券 | 有效券、无券 | 过期券、未知券、已使用 |

### 4.2 边界值：错误集中在边界上

等价类取中间值，边界值取两侧。每个边界取三个点：**边界值、边界 -1、边界 +1**。

金额满 200 减 20：

| 用例 | 金额 | 预期 |
|---|---|---|
| 边界下 | 199.99 | 不减 |
| 边界 | 200.00 | 减 20 |
| 边界上 | 200.01 | 减 20 |

**浮点金额的边界要特别小心**：`199.99` 在 float 里可能是 `199.9899999`，判等会出错。这也是金额要用 Decimal 的原因。

### 4.3 判定表：多条件组合

条件和动作的对应关系超过三种时，用判定表把组合列全。判定表的每一列就是一条用例。

画法：纵轴列条件，横轴是规则列（R1、R2…），列内填 Y/N/—，表底写每列的动作；一列一条用例，`—` 表示该条件不影响结果。

| 条件 \ 规则 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| 是会员 | Y | Y | N | N |
| 有券 | Y | N | Y | N |
| 折扣 | 会员折 + 券 | 会员折 | 券 | 无 |

规则数是条件数的笛卡尔积，条件多了会爆炸。实际做法是先删掉不可能的组合，再合并结果相同的列。

### 4.4 用例表字段

| 字段 | 说明 |
|---|---|
| 编号 | TC-模块-序号 |
| 关联需求 | R-01 |
| 前置条件 | 登录状态、数据准备 |
| 步骤 | 可执行的操作序列 |
| 预期结果 | 可观察、可断言 |
| 优先级 | P0/P1/P2 |

**预期结果必须可断言**。「显示正常」不是预期，「显示订单号、状态为待支付、金额为 199.99」才是。

## 五、探索式测试

脚本用例只能验证「你已经想到的」，探索式测试用来找「你没想到的」。两者不是替代关系。

### 5.1 什么时候用

| 场景 | 为什么适合探索式 |
|---|---|
| 新功能第一次测 | 需求理解还不完整，边测边发现 |
| 复杂交互 | 组合太多，脚本覆盖不全 |
| 上线前最后一轮 | 快速找遗漏的边界 |
| 缺陷高发模块 | 说明设计有问题，需要人去找 |

### 5.2 怎么做

给 30-60 分钟的时间盒，围绕一个「测试章程」自由探索，边测边记录：

```text
章程：验证优惠券在跨店、跨品类、部分退款场景下的行为
时间：45 分钟
关注：金额计算、状态变化、重复使用
记录：发现的问题 + 操作路径 + 当时的订单号
```

探索式测试不是「随便点点」。它有目标、有时间盒、有记录，产出是缺陷和新的用例想法。

### 5.3 产出

- 新发现的缺陷；
- 补充到用例库的场景；
- 对需求模糊点的确认问题。

## 六、缺陷管理

### 6.1 分级

分级看两个维度：**影响**（多少人、多严重）和**紧急度**（有没有替代方案）。

| 级别 | 定义 | 例子 | 修复时限 |
|---|---|---|---|
| P0 | 系统不可用、数据错误、资金损失 | 支付重复扣款、订单丢失 | 立即，阻塞发布 |
| P1 | 核心功能不可用，无替代 | 下单失败、登录不了 | 24 小时内，阻塞发布 |
| P2 | 非核心功能异常，有替代 | 报表导出失败、筛选不准 | 本版本内或下版本 |
| P3 | 体验问题、文案错误 | 按钮错位、错别字 | 排期处理 |

**分级的争议通常在 P1 和 P2 之间**。判定标准：有没有替代方案。有替代方案（换个浏览器能用、手工能补），就是 P2。

### 6.2 修复优先级

缺陷级别不等于修复顺序。排序看三件事：影响面 × 发生概率 × 修复成本。

| 情况 | 处理 |
|---|---|
| 影响大、概率高 | 立刻修 |
| 影响大、概率低 | 修，或加监控 + 应急预案 |
| 影响小、概率高 | 修，用户天天碰到 |
| 影响小、概率低 | 排期，可能永远不修 |

### 6.3 缺陷怎么写

一份能修的缺陷报告包含：

```text
标题：VIP 用户订单满 200 使用 MINUS_20 券，实付金额多减 20
环境：测试环境，Chrome 120，账号 vip_test_01
步骤：
1. 加入商品 200 元
2. 选择 MINUS_20 券
3. 提交订单
预期：实付 170（200 × 0.95 - 20）
实际：实付 150（200 - 20 - 20，券减了两次）
附件：截图、订单号、trace id
```

标题要写「什么条件下、什么操作、什么结果不对」。标题写成「优惠券有问题」，开发还得来问一遍。

### 6.4 从现象到根因

测试的价值不止是「发现不对」，还包括「缩小范围」。定位三步：

1. **确认可复现**：固定环境、固定数据，能稳定复现；
2. **缩小范围**：换账号、换商品、换金额，看哪个条件触发；
3. **留下证据**：订单号、trace id、请求响应、日志时间点。

有了这三样，开发定位时间能从半天降到半小时。

几个高频现象的第一步：

| 现象 | 先查什么 | 怎么查 |
|---|---|---|
| 金额差一分 | 舍入口径 | 单独跑一次计算，看是在哪一步 quantize |
| 券没生效 | 门槛基准 | 打印折前/折后金额，确认判的是哪个 |
| 偶发失败 | 并发或重复提交 | 查 trace，看同一单是否被处理两次 |
| 只有部分用户出错 | 用户属性 | 对比出错用户与正常用户的等级/地区/版本 |

## 七、测试报告与放行

### 7.1 报告写什么

测试报告不是流水账，是**放行决策的依据**。一页纸够：

| 项 | 内容 |
|---|---|
| 版本与范围 | 测了哪些、没测哪些 |
| 执行情况 | 用例数、通过率、自动化覆盖 |
| 缺陷 | 按级别统计，未关闭的列出 |
| 风险 | 已知问题 + 影响 + 规避方案 |
| 结论 | 建议放行 / 有条件放行 / 不建议放行 |

### 7.2 放行结论

| 结论 | 条件 |
|---|---|
| 建议放行 | 退出标准全部满足 |
| 有条件放行 | 有 P2 未关闭，但有明确规避方案和修复计划 |
| 不建议放行 | 有 P0/P1 未关闭，或核心链路未验证 |

「有条件放行」要写清条件：哪个缺陷、影响谁、怎么规避、什么时候修。不写条件的「有条件放行」就是「放行」。

## 八、用例的维护成本

用例库不是越多越好。一个几千条用例的库，维护成本会超过它发现缺陷的价值。

| 问题 | 表现 | 处理 |
|---|---|---|
| 用例过期 | 功能改了，用例没改，执行时全是误报 | 每个版本清理一次 |
| 用例重复 | 同一个规则有 5 条相似用例 | 合并，保留边界和异常 |
| 用例太细 | 一个用例只点一个按钮 | 按业务场景重组 |
| 没有优先级 | 几千条全要跑 | 分 P0/P1/P2，回归只跑 P0/P1 |

**用例的价值 = 发现的缺陷 ÷ 维护成本**。长期不发现缺陷的用例，要么删掉，要么降级为抽测。

## 九、案例：一次版本测试

### 9.1 背景

电商结算模块改版：新增优惠券叠加、调整运费规则、修改税费计算。影响下单、支付、退款三个链路。版本周期两周，测试 1 人。

### 9.2 测试方案

| 要素 | 内容 |
|---|---|
| 范围 | 结算页、下单接口、退款金额计算；不测商品详情、物流 |
| 环境 | 测试环境 + 预发环境（配置同生产） |
| 方法 | 接口自动化回归（核心链路）+ 手工用例（新规则）+ 探索式（组合场景） |
| 退出标准 | P0/P1 用例 100% 通过，无 P0/P1 缺陷，核心接口压测达标 |

### 9.3 用例设计

- **等价类**：会员三档 × 券三种状态 × 金额三档；
- **边界值**：满减线 199.99/200/200.01，免邮线 98.99/99/99.01；
- **判定表**：会员折扣、券、运费、税的叠加顺序，共 12 条规则；
- **探索式**：跨店、部分退款、券退回后再用。

### 9.4 发现的问题

| 缺陷 | 级别 | 根因 |
|---|---|---|
| 券在部分退款后仍算已使用 | P1 | 退款逻辑没回滚券状态 |
| 税费按含运费金额计算 | P1 | 税基口径在需求里没写清 |
| 金额 199.99 时免邮判断错误 | P2 | float 精度问题 |
| 优惠券列表在 Safari 下错位 | P3 | CSS 兼容 |

「券状态」是探索式测试发现的，脚本用例只覆盖了规则、没覆盖状态迁移；「税基口径」是在列判定表时发现的——需求本身没定义运费算不算税基，属于需求缺口而不是实现缺陷。

### 9.5 结论

两个 P1 修复后回归通过，P2 带到下个版本（有规避方案：金额用 Decimal 重算），P3 排期。结论：建议放行。

教训：**规则用例要配状态用例**。只测「算得对不对」，不测「状态变得对不对」，会漏掉一半的问题。
