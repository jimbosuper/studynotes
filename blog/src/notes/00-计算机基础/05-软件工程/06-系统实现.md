# 系统实现

## 一、实现环节的边界

实现阶段的输入有三样，缺一样就会靠猜：

| 输入 | 来自 | 缺了会怎样 |
|---|---|---|
| 接口契约、表结构、异常清单 | 05-系统设计 | 字段、错误码、边界靠猜 |
| 业务规则原文 | 04-需求分析 | 口径各人理解不同 |
| 代码规范与既有实现 | 仓库 + 本文 | 风格漂移，评审全在吵格式 |

**边界**：实现不负责补设计缺口。发现设计没定义清楚（比如「金额」含不含税），停下来回设计确认，不要自己拍。界面实现按 `02-设计` 的交付物做；集成与端到端验证在 `06-测试`，不在这里重复。

一份可评审的提交包含四样：**变更代码 + 提交说明（为什么改）+ 自测证据 + 关联任务号**。缺哪样，评审人就得自己补哪样，评审时间翻倍。

## 二、规范的分工：工具管的 vs 人管的

企业里代码规范落地失败，多半是因为把机器能做的事写成了人的纪律。人的注意力有限，应该花在机器判断不了的地方。

### 2.1 交给工具，不要写进规范文档

| 事项 | 工具 | 在哪跑 |
|---|---|---|
| 缩进、引号、换行、import 排序 | formatter（Prettier/gofmt/black） | pre-commit + CI |
| 未使用变量、空代码块、可疑写法 | linter（ESLint/golangci-lint/ruff） | pre-commit + CI |
| 类型错误 | 类型检查（tsc/mypy） | CI |
| 圈复杂度、函数长度、重复代码 | 静态分析（SonarQube/CodeClimate） | CI |
| 依赖漏洞 | 依赖扫描（Dependabot/Trivy） | CI 定时 |
| 提交信息格式 | commitlint | pre-commit |

原则：**能在 CI 里失败的事，不要靠评审提醒**。评审提醒一次，下次还会犯；CI 拦一次，全组都记住。

工具规则要少而硬。一个开了 200 条规则的 linter，最后所有人都在 `// eslint-disable`。只保留会引发真实问题的规则，其余关掉。

### 2.2 只能靠人：四件事

| 事项 | 为什么工具管不了 | 怎么检查 |
|---|---|---|
| 命名是否表达意图 | 语法合法不等于语义清楚 | 读函数名能不能猜出做什么 |
| 注释是否解释了「为什么」 | 工具不知道业务背景 | 看注释有没有复述代码 |
| 错误处理是否完整 | 工具不知道哪些错误可以忽略 | 对异常清单逐条核 |
| 代码是否可测试 | 取决于依赖怎么注入 | 能不能不启动数据库就测 |

这四件事就是评审的重点，其余的都交给工具。

## 三、代码怎么写才可评审

### 3.1 命名

| 对象 | 规则 | 反例 → 正例 |
|---|---|---|
| 函数、变量 | 小写下划线/小驼峰，动词+名词 | `d()` → `calc_discount()` |
| 类、类型 | 大驼峰，名词 | `orderAmt` → `OrderAmount` |
| 常量 | 全大写 | `FreeLine` → `FREE_SHIPPING_LINE` |
| 布尔 | `is_/has_/can_` 前缀 | `flag` → `is_paid` |
| 集合 | 复数 | `list1` → `items` |
| 单位 | 带单位后缀 | `timeout` → `timeout_seconds` |

三条硬约束：

1. **不自造缩写**。`amt`、`calc` 只在团队共识时用；不确定就写全；
2. **不加类型前缀**。`str_name`、`i_count` 是历史包袱，IDE 已经告诉你类型了；
3. **同一概念全仓库一个词**。订单金额统一叫 `amount`，不要一半 `money` 一半 `fee`。

命名不是越长越好。`payable` 够了，`order_amount_after_all_discount_and_coupon` 读起来更累。

### 3.2 注释

注释只写代码说不出来的东西：

| 该写 | 例子 |
|---|---|
| 为什么这么做 | `# 走 Decimal，避免 float 把 199.99 算错` |
| 业务约束 | `# 折扣封顶 50 元，超出部分运营兜底` |
| 口径来源 | `# 税基不含运费，见需求 §4.2` |
| 已知坑 | `# 第三方可能对同一单重复推送` |

不该写的：复述代码（`// 把 qty 减 1`）、过期 TODO、注释掉的代码。注释掉的代码直接删，git 里有历史。

**过期注释比没有注释更危险**。改代码时顺手改注释，改不动就删掉。

### 3.3 函数与复杂度

圈复杂度、函数长度、嵌套层数交给静态分析工具报，人不需要手数。人要判断的是工具报出来之后怎么办：

| 信号 | 通常的原因 | 处理 |
|---|---|---|
| 圈复杂度 > 15 | 分支太多，规则混在一起 | 抽规则表/策略，或拆函数 |
| 函数 > 80 行 | 做了不止一件事 | 按「取数/计算/落库」拆 |
| 嵌套 > 3 层 | 缺少提前返回 | 用 guard clause 拍平 |
| 重复代码 > 5 行 | 复制粘贴 | 抽公共函数，但别过度抽象 |

**不要为了降复杂度拆成一堆一行函数**。拆分的标准是「能不能独立命名、独立测试」，不是数字好看。

### 3.4 错误处理与日志

企业代码里最常见的线上事故，不是算法错，是错误被吞掉。

三条规则：

1. **不吞异常**。`catch (e) {}` 是事故之源；至少记日志并向上抛，或者明确降级；
2. **错误分层**。业务错误（参数错、状态不允许）返回给用户，系统错误（超时、连接失败）记日志 + 告警，不要都包成 500；
3. **日志带上下文**。一条日志至少包含：什么操作、什么参数（脱敏后）、什么结果、追踪 ID。

```python
# 差：出问题查不到任何线索
try:
    charge(order)
except Exception:
    pass

# 好：区分业务失败和系统失败，带上下文
try:
    charge(order)
except PaymentDeclined as e:
    logger.warning("payment declined order_id=%s code=%s", order.id, e.code)
    raise BusinessError(4003, "支付被拒绝")
except TimeoutError:
    logger.error("payment timeout order_id=%s trace=%s", order.id, trace_id)
    raise SystemError(5001, "支付服务超时")
```

日志级别统一：DEBUG 只给开发、INFO 记关键业务动作、WARN 记可恢复异常、ERROR 记需要人介入的故障。ERROR 必须配告警，否则就是噪音。

## 四、单元测试写到什么程度

### 4.1 覆盖率是结果，不是目标

覆盖率能说明「哪些代码没被测过」，不能说明「测得好不好」。下面这段代码覆盖率 100%，但什么都没验证：

```python
def test_calc():
    calc_discount("VIP", 100, None)  # 不写断言
```

覆盖率的正确用法：

| 用法 | 合理 | 不合理 |
|---|---|---|
| 看未覆盖的分支 | 找出漏测的异常路径 | —— |
| 设门槛 | 新增代码 ≥ 60%，整体不低于基线 | 要求整体 90% |
| 做考核 | —— | 按覆盖率发奖金 |

**覆盖率门槛只对新增代码有意义**。要求一个十年老项目整体达到 80%，只会逼出大量无断言的测试。

### 4.2 该测什么

按「错了会不会有人半夜被叫起来」排序：

| 优先级 | 测什么 | 例子 |
|---|---|---|
| 高 | 金额、权限、状态迁移 | 折扣计算、越权访问、订单取消 |
| 高 | 边界值 | 0、负数、上限、空集合 |
| 中 | 异常路径 | 第三方超时、重复回调 |
| 低 | 纯 getter/setter、框架代码 | —— |

一个可用的经验值：**核心业务规则的测试应占单测总量的 60% 以上**。如果单测里全是 controller 的 mock 测试，说明测错了地方。

### 4.3 测试的可维护性

测试代码也是代码，也要评审。三条要求：

- **一个测试只验证一件事**。断言超过 5 个，失败时不知道哪条规则坏了；
- **测试名说清场景和预期**。`test_vip_over_200_gets_20_off` 比 `test1` 有用；
- **不依赖执行顺序和共享状态**。测试之间互相影响，最后没人敢删任何一个。

集成测试和端到端测试的取舍见 `06-测试`。这里只强调一句：单测跑得慢（> 10 分钟），团队就会跳过它，等于没有。

## 五、提交与 PR

### 5.1 PR 多大算合适

| 规模 | 行数 | 评审质量 | 建议 |
|---|---|---|---|
| 小 | < 200 | 能认真看完 | 理想 |
| 中 | 200-500 | 能看完，容易漏细节 | 可接受 |
| 大 | 500-1000 | 只看个大概 | 拆 |
| 超大 | > 1000 | 基本是走过场 | 必须拆 |

拆 PR 的方法：按「重构 / 功能 / 测试」拆，或者按「接口 / 实现 / 接入」拆。**重构和功能不要放在同一个 PR**——评审分不清哪些是行为改变。

### 5.2 提交信息

格式：`类型: 说明`，类型用 `feat/fix/refactor/test/docs/chore`。

```text
feat: 订单支持优惠券叠加
fix: 修复并发下单导致库存为负
refactor: 抽出金额计算，行为不变
```

三条要求：**说清为什么改**（改了什么 diff 里能看到）、**一个提交一件事**、**不写「update」「fix bug」这种无信息量的说明**。

### 5.3 PR 描述

模板四段，超过四段没人填：

```markdown
## 改了什么
一句话说明。

## 为什么
关联需求/缺陷号，或背景。

## 怎么验证
- [ ] 单测：xxx
- [ ] 手动：xxx

## 风险
影响范围、回滚方式。
```

「怎么验证」这一栏最重要。评审人先看这栏，能快速判断作者有没有自测。

## 六、代码评审

### 6.1 评审看什么

评审不是找茬，是**在合并前用最便宜的方式发现缺陷**。按投入产出排序：

| 看什么 | 为什么 | 怎么快速看 |
|---|---|---|
| 业务规则对不对 | 错了就是线上事故 | 对照需求/设计里的规则表 |
| 边界和异常 | 大部分 bug 在这里 | 看空值、0、超时、重复调用 |
| 有没有吞异常 | 出问题查不到 | 搜 `catch`、`except` |
| 能不能测 | 不能测的代码通常设计有问题 | 看依赖是不是硬编码 |
| 命名和注释 | 影响长期维护 | 读一遍能不能懂 |

**不看的**：格式、缩进、import 顺序——这些工具已经管了。评审里出现「这里少个空格」，说明 CI 没配好。

### 6.2 评审 SLA

没有 SLA 的评审，PR 会挂三天，作者只能去干别的，上下文一切换就是半天。

| 团队规模 | 首次响应 | 完成评审 |
|---|---|---|
| < 10 人 | 4 小时 | 1 个工作日 |
| 10-30 人 | 8 小时 | 1 个工作日 |
| 跨时区 | 1 个工作日 | 2 个工作日 |

配套规则：

- 作者指定评审人，不要「谁有空谁看」；
- 评审人忙不过来时明确转交，不要让 PR 挂着；
- 超过 SLA 未评审，自动升级到 tech lead；
- 紧急修复可以事后评审，但要留记录。

### 6.3 遗留代码怎么办

老代码不符合规范是常态，不要试图一次改完。

| 场景 | 策略 |
|---|---|
| 要改的文件 | 顺手把改到的函数整理干净（童子军规则） |
| 不改的文件 | 不动，不要为了「统一风格」全量格式化 |
| 核心遗留模块 | 先补测试，再重构；没测试的重构是赌博 |
| 准备废弃的模块 | 不投入，只修 P0 缺陷 |

全量格式化的 PR 会把真正的改动淹没在 diff 里，且容易引入冲突。**格式化和功能改动永远分开提交**。

### 6.4 评审意见怎么提

| 说法 | 问题 | 改法 |
|---|---|---|
| 「这里不对」 | 作者不知道哪里不对 | 「这里并发下会重复扣减，建议加幂等键」 |
| 「重写吧」 | 否定人不否定事 | 「这个函数做了三件事，能不能拆成取数/计算/落库」 |
| 「随便看看」 | 评审人也不知道看什么 | 用 6.1 的清单 |

区分 **must fix**（阻断合并）和 **nit**（建议，不阻断）。不区分的话，作者会为了一个空格改三轮。

## 七、缺陷修复

### 7.1 缺陷分类

| 类型 | 例子 | 修复方式 |
|---|---|---|
| 功能缺陷 | 折扣算错、状态不对 | 改代码 + 补单测 |
| 边界缺陷 | 空列表报错、金额为 0 崩溃 | 补边界处理 + 补用例 |
| 并发缺陷 | 重复下单、超卖 | 加锁/幂等，压测验证 |
| 性能缺陷 | 列表加载 10 秒 | 定位慢查询，加索引/缓存 |
| 数据缺陷 | 历史数据不一致 | 写修复脚本，先备份 |

### 7.2 修复流程

1. **先复现**。复现不了就不要改代码，先加日志；
2. **写一个失败的测试**。测试先红，改完变绿，这条缺陷才算被网住；
3. **改最小范围**。修 bug 不要顺手重构，混在一起无法回滚；
4. **回归**。跑相关模块的单测 + 手工验证原路径；
5. **记录根因**。同一个模块一个月内出三次同类缺陷，说明设计有问题，要立项改，不要继续打补丁。

## 八、案例：结算模块的一次实现与评审

### 8.1 背景

结算服务新增「订单金额计算」：输入商品行、会员等级、优惠券，输出小计、折扣、运费、税、应付。规则：VIP 95 折、SVIP 9 折（封顶 50）；满 200 减 20 在折后金额上判；折后满 99 免运费；税率 6%，税基不含运费。

### 8.2 实现要点

- 金额统一 `Decimal` + `ROUND_HALF_UP`，不用 float；
- 拆成四个纯函数：`member_discount`、`coupon_discount`、`shipping`、`tax`，每个只做一件事；
- 规则参数放配置表，不写死在代码里（折扣率、封顶、免邮线会变）；
- 主流程只做编排：算折扣 → 算运费 → 算税 → 汇总。

```python
def calc_payable(items, level, coupon):
    subtotal = sum(i.price * i.qty for i in items)
    discount = member_discount(subtotal, level) + coupon_discount(subtotal, coupon)
    payable = subtotal - discount
    shipping = 0 if payable >= FREE_SHIPPING_LINE else SHIPPING_FEE
    tax = (payable * TAX_RATE).quantize(CENT, ROUND_HALF_UP)
    return payable + shipping + tax
```

### 8.3 单测

四组测试，共 23 条：

| 组 | 覆盖 | 条数 |
|---|---|---|
| 会员折扣 | 三档等级、封顶、边界金额 | 8 |
| 优惠券 | 满减门槛、叠加顺序、互斥 | 7 |
| 运费 | 免邮线两侧、折扣后金额判定 | 4 |
| 税 | 税基不含运费、四舍五入 | 4 |

### 8.4 评审发现的问题

- 折扣叠加顺序没写清：需求说「会员折后金额满 200」，代码用的却是原价，属于口径错，must fix；
- `coupon_discount` 里对未知券静默返回 0，应该抛错，否则用户以为用上了券；
- 税的计算用了 `float`，虽然当前金额小看不出来，但属于隐患；
- 单测里有一条只断言「不抛异常」，没有断言金额，等于没测。

### 8.5 结果

修改后合并。上线后第一次大促，折扣规则临时调整（VIP 改 9 折），因为参数在配置表里，改配置 10 分钟生效，没有发版。

教训：**把会变的规则抽成配置，比把代码写得多优雅更有价值**。
