# 服务通信与消息

> 这篇从一次同步调用链如何在超时后自我放大讲起，经过同步与异步的取舍、RPC 与 REST 的契约、消息投递语义、Schema 演进、超时预算、重试、熔断、背压、服务发现和分区消费，最后落到一次大促前的通信链路改造决策。
>
> 学完能为一条跨服务链路定通信方式、算超时预算、收敛重试、设计消息契约，并在积压与抖动时按指标定位到具体环节。

## 一、通信方式决定系统形状

通信方式不是实现细节，它决定服务之间的时间耦合、失败传播范围和数据一致性边界；选错通信方式，后面加多少中间件都补不回来。

同步调用（Synchronous Call）要求调用方在等待期内保持连接和线程，被调方不可用时失败立刻向上传播。异步消息（Asynchronous Messaging）把调用方与提供方在时间上解耦，失败被推迟到消费侧，代价是链路变长、结果不再即时。

| 维度 | 同步调用 | 异步消息 |
|---|---|---|
| 时间耦合 | 强，双方必须同时可用 | 弱，消费方可延迟处理 |
| 失败传播 | 立即，沿调用链上浮 | 延迟，转为积压或死信 |
| 结果获取 | 直接返回 | 回调、轮询或事件 |
| 链路追踪 | 一次请求一个 Trace | 跨消息需显式传播上下文 |
| 适用 | 需要即时结果、强校验 | 可延后、可补偿、削峰 |

判断用哪种，问四个问题：调用方是否必须拿到结果才能继续；失败能否延后处理；上下游是否需要独立扩容；重复执行是否可接受。四个问题里有两个指向异步，才值得引入消息。

### 1.1 四种组合

现实系统不是“同步或异步”二选一，而是四种组合并存。

| 组合 | 形态 | 典型场景 |
|---|---|---|
| 同步请求、同步响应 | RPC / REST | 查库存、算价格 |
| 同步请求、异步处理 | 受理后返回任务号 | 导出报表、批量开票 |
| 异步事件 | 发布事实，多方订阅 | 订单已支付、库存已变更 |
| 异步请求、异步响应 | 消息加回复队列 | 跨组织对账指令 |

第二种最容易被做成“同步等很久”。正确形态是接口在 200 毫秒内返回任务号，客户端轮询或等待回调；而不是把 HTTP 超时设成 30 分钟。第三种要求事件是事实描述，不是命令，否则发布方会隐含依赖订阅方的行为。

### 1.2 三条硬约束

任何跨进程通信都必须同时具备三样东西：超时、有限重试、幂等。缺一样，故障时就会从“慢”变成“错”。

- 没有超时：线程和连接被永久占用，故障沿调用链扩散；
- 没有有限重试：瞬时抖动直接变成用户可见失败；
- 没有幂等：重试把一次操作执行多次，数据错乱。

幂等不是通信层能单独提供的。它要么靠业务唯一键，要么靠去重表，要么靠状态机的条件更新。中间件宣称的“精确一次”只在它自己的边界内成立，跨出边界仍是至少一次。

### 1.3 常见反模式

- 用消息队列模拟 RPC：请求方发消息后阻塞等回复队列，把异步做成了更慢的同步。
- 全链路异步化：所有调用都改成事件，结果没有任何一处能回答“这单现在到哪了”。
- 同步链路过长：一次用户请求串行经过七个服务，可用性是七个 99.9% 的乘积。
- 用共享库代替契约：所有服务依赖同一个 DTO jar，改一个字段要全量发版。

> 边界：异步不是性能银弹。引入消息就引入了重复、顺序、积压、死信四类新问题；没有对应的消费幂等和积压告警，异步化只是把故障从接口挪到了队列。

## 二、同步调用：RPC 与 REST

同步调用只有两种主流形态：以 gRPC 为代表的二进制 RPC，和以 HTTP + JSON 为代表的 REST；选择依据是契约强度、调用方类型和延迟要求，不是团队偏好。

gRPC 基于 HTTP/2 和 Protobuf，支持四种流式模式，天然带截止时间（Deadline）和结构化错误码。REST 基于 HTTP 语义，资源用 URI 表达，方法表达动作，浏览器和任何语言都能直接调用。

| 维度 | gRPC | REST / JSON |
|---|---|---|
| 契约 | `.proto`，强类型 | OpenAPI，弱类型 |
| 序列化 | Protobuf，体积小 | JSON，可读 |
| 流式 | 支持双向流 | 需 SSE 或分块传输 |
| 浏览器 | 需 gRPC-Web 代理 | 原生支持 |
| 调试 | 需专用工具 | curl 即可 |
| 适用 | 内部高频、低延迟 | 开放接口、弱网、前端 |

### 2.1 契约先行的写法

契约是双方共同遵守的文档，不是服务端实现的副产品。先写 `.proto` 或 OpenAPI，再生成代码，最后写实现；顺序反过来，契约会跟着实现漂移。

```proto
syntax = "proto3";
package stock.v1;

service StockService {
  rpc Reserve(ReserveRequest) returns (ReserveResponse);
}

message ReserveRequest {
  string request_id = 1;        // 幂等键，重试必须复用
  string sku_id = 2;
  int32 quantity = 3;
  int64 deadline_unix_ms = 4;   // 绝对截止时间，跨进程传递预算
}

message ReserveResponse {
  enum Status {
    STATUS_UNSPECIFIED = 0;     // 必须有 0 值，兼容旧客户端
    RESERVED = 1;
    REJECTED = 2;
  }
  Status status = 1;
  string reservation_id = 2;
}
```

`request_id` 放在请求体而不是由服务端生成，是因为重试发生在客户端，只有客户端知道“这是同一次业务动作”。`deadline_unix_ms` 用绝对时间而不是相对毫秒，避免每一跳重新计时导致预算被无限续期。

### 2.2 REST 的方法语义

REST 的幂等性由方法定义，不由实现决定。

| 方法 | 幂等 | 语义 | 典型用途 |
|---|---|---|---|
| GET | 是 | 读取资源 | 查询订单 |
| PUT | 是 | 全量替换 | 更新配置 |
| DELETE | 是 | 删除资源 | 取消草稿 |
| POST | 否 | 创建或执行 | 下单、支付 |

把“扣库存”做成 `POST /stock/deduct` 且不带幂等键，是重试事故的常见起点。要么改成 `PUT /stock/{sku}/reservation/{request_id}`，要么在 POST 上带 `Idempotency-Key` 并在服务端落去重表。

状态码也要按语义用：`400` 参数错、`401` 未认证、`403` 无权限、`404` 不存在、`409` 状态冲突、`429` 限流、`503` 暂时不可用。全用 `200` 加业务码，会让网关、重试策略和监控全部失效。

### 2.3 超时与错误码的映射

gRPC 的状态码比 HTTP 更细，跨协议网关要建立固定映射，否则重试策略会误判。

| gRPC | HTTP | 是否可重试 | 含义 |
|---|---|---|---|
| UNAVAILABLE | 503 | 是 | 暂时不可用 |
| DEADLINE_EXCEEDED | 504 | 视幂等 | 超时，结果未知 |
| RESOURCE_EXHAUSTED | 429 | 是，带退避 | 限流 |
| INVALID_ARGUMENT | 400 | 否 | 参数错误 |
| ABORTED | 409 | 否 | 并发冲突 |

`DEADLINE_EXCEEDED` 标“视幂等”是关键：读请求可以重试，写请求必须先查结果。把超时一律当可重试，等于给重复写入开绿灯。

### 2.4 边界

对外开放的 API 用 REST + JSON，因为调用方不可控，可读性和通用性优先。内部高频短调用用 gRPC，省带宽、省序列化、天然支持流。长耗时任务两种都不合适，应改成“受理 + 任务号 + 查询”。

> 边界：不要在同一组服务之间同时维护 gRPC 和 REST 两套等价接口。双份契约意味着双份兼容性负担，最终总有一套先腐坏。

## 三、异步消息：投递语义与顺序

消息系统只提供三种投递语义，选择哪一种决定了消费端必须做什么；宣称“精确一次”的方案，本质上都是至少一次加去重。

### 3.1 三种语义

| 语义 | 保证 | 失败后果 | 消费端要求 |
|---|---|---|---|
| 至多一次 | 不重复，可能丢 | 业务缺失 | 可接受丢失 |
| 至少一次 | 不丢，可能重复 | 重复处理 | 必须幂等 |
| 精确一次 | 不丢不重 | 无 | 边界内自动，跨系统仍需幂等 |

“精确一次”只在消息系统内部成立。Kafka 的事务能保证“读 Kafka、写 Kafka、提交位点”原子，但写外部数据库不在事务内，跨出去仍然是至少一次。因此工程上默认按至少一次设计，把幂等当成必选项。

### 3.2 顺序的边界

消息系统通常只保证分区内有序，不保证主题内全局有序。Kafka 的一个分区同一时刻只有一个消费者在处理，跨分区并行。

要顺序就选键：同一订单的事件用订单号做分区键，保证同一订单的事件按序；不同订单之间无序。全局有序需要单分区，吞吐直接锁死在一个消费者上，除极少数场景外不该选。

```text
topic: order-events        partitions: 24
key:   SO202611130001      → partition = hash(key) % 24
效果：同一订单的事件有序；不同订单并行
```

分区键还必须稳定。用随机数或时间戳做键，同一订单的事件会散到不同分区，顺序保证失效。

### 3.3 事件与命令

事件描述已经发生的事实，用过去式命名，发布方不关心谁消费；命令描述期望发生的动作，用祈使式命名，通常点对点发送。

| 类型 | 命名 | 投递 | 失败处理 |
|---|---|---|---|
| 事件 | `order.paid` | 订阅，多方 | 消费方自行重试 |
| 命令 | `reserve-stock` | 点对点 | 发送方决定补偿 |

把命令伪装成事件（`order.pay-requested` 发给所有订阅者），会让多个服务同时执行同一动作，是重复扣款的结构性原因。

### 3.4 队列与日志

| 维度 | 队列（RabbitMQ 类） | 日志（Kafka 类） |
|---|---|---|
| 消费后消息 | 删除 | 保留到期 |
| 重放 | 困难 | 重置位点即可 |
| 顺序 | 单队列有序 | 分区内有序 |
| 吞吐 | 万级 | 十万级以上 |
| 适用 | 任务分发、复杂路由 | 事件流、审计、重放 |

需要“事后重放”才能修的链路选日志型；只需要“把任务分给一个工人”的选队列型。

> 边界：消息体不要超过 1MB。大对象存对象存储，消息里放引用；否则 broker 的页缓存和网络都会被单条消息拖垮。消息也不适合做请求-响应，需要结果就用同步调用或“受理 + 查询”。

## 四、契约设计：Schema 与版本兼容

契约的兼容性由“旧消费者能否读懂新消息”和“新消费者能否读懂旧消息”共同定义；任何一方读不懂，都是一次线上故障。

### 4.1 兼容性方向

| 模式 | 含义 | 允许的变更 |
|---|---|---|
| 向后兼容 | 新 Schema 读旧数据 | 加可选字段 |
| 向前兼容 | 旧 Schema 读新数据 | 删可选字段、加字段 |
| 全兼容 | 双向都可读 | 只加可选字段，不删不改 |
| 无兼容 | 不保证 | 任意，但需停机切换 |

消息场景通常要求全兼容，因为生产者和消费者的发布节奏不同，任何时刻都存在新旧版本并存。

### 4.2 Protobuf 的编号规则

Protobuf 靠字段编号识别字段，不靠名字。编号一旦分配就不能复用，删除字段要同时锁编号和名字。

```proto
message OrderPaid {
  reserved 4, 7;                 // 已删除字段的编号永久作废
  reserved "old_amount";         // 名字也锁住，防止被重新定义

  string order_no = 1;
  int64 amount_cent = 2;         // 整数分，避免浮点误差
  string currency = 3;
  optional string coupon_id = 5; // 新增可选字段，旧消费者忽略
}
```

复用编号是最危险的变更：新字段会覆盖旧消费者解析出的旧字段，且编译期不报错，只有线上数据错乱时才暴露。

### 4.3 枚举与未知字段

旧消费者遇到新枚举值，必须走默认分支而不是抛异常；否则每次新增状态都会打挂一半消费者。Protobuf 的 `UNSPECIFIED = 0` 就是为此准备的兜底值。

JSON 契约同理：消费端要忽略未知字段，生产端不得因为多了一个字段就拒收。严格校验只放在入口，内部消费要宽容。

### 4.4 版本策略

| 方式 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| URI 版本 | `/v1/orders` | 直观，易路由 | 版本散落在路径 |
| Header 版本 | `Accept: application/vnd.order.v2+json` | 路径稳定 | 调试不直观 |
| Schema 版本 | 消息内 `schema_version` | 消息可并存 | 消费端要分支 |

消息契约优先用 Schema 版本加注册中心，不用 URI。注册中心（Schema Registry）负责存版本、校验兼容性，常见配置是 `BACKWARD` 或 `FULL`。把兼容模式设成 `NONE`，等于放弃了发布前的最后一道检查。

### 4.5 消费者驱动契约测试

提供方改契约时，最怕“自己测试通过、调用方解析失败”。消费者驱动契约（Consumer-Driven Contract）由消费方声明期望，提供方在 CI 里验证这些期望。

适用判断：服务数量多、发布不同步、跨团队。代价是要维护契约文件和验证流水线。两个服务由同一团队同日发布，用它收益不大。

> 边界：不要用共享 DTO jar 代替契约。共享 jar 把编译期耦合带进运行时，一个字段改名就要所有服务同时发版，版本兼容的讨论被绕过去了。

## 五、超时预算

超时不是一个数字，而是一份从入口分配到数据库的预算；每一跳只能花掉剩余预算的一部分，不能各自重新计时。

端到端超时的来源是用户体验或 SLO。假设订单详情页要求 P99 在 1 秒内，入口预算就是 1,000 毫秒；往下每一层都要留出处理和网络开销，子调用必须显著小于父预算。

### 5.1 预算表

| 层 | 预算 | 主要开销 |
|---|---|---|
| 客户端 | 1,000ms | 渲染与网络 |
| 网关 | 850ms | 鉴权、限流、路由 |
| 订单服务 | 650ms | 编排与本地逻辑 |
| 库存服务 | 300ms | 校验与条件更新 |
| 数据库 | 80ms | 索引查询 |

每层留 15% 到 20% 的余量。库存服务 300ms 的预算，数据库给 80ms，剩下 220ms 覆盖序列化、连接池等待和重试。若把子调用设成和父预算一样大，父层超时后子层还在跑，工作白做，连接还占着。

### 5.2 截止时间的传递

只设客户端超时不够，服务端不知道自己还剩多少时间。传递方式有两种：gRPC 的 Deadline 自动随请求传播；HTTP 用自定义头传剩余毫秒。

```http
POST /v1/stock:reserve HTTP/1.1
x-request-id: 7f3c2a91
x-request-deadline-ms: 240
```

服务端收到后，用 `min(本地配置, 剩余预算 - 安全边界)` 作为下游超时。剩余预算小于 20 毫秒时直接快速失败，不再发起下游调用，避免“注定超时的调用”继续占用资源。

### 5.3 连接超时与读超时

| 超时类型 | 作用 | 典型值 |
|---|---|---|
| 连接超时 | TCP/TLS 建连 | 200ms |
| 读超时 | 等待响应 | 按预算分配 |
| 总截止时间 | 含排队与重试 | 入口 SLO |
| 空闲超时 | 连接池回收 | 30s 到 60s |

连接超时设得比读超时还长，是常见的配置错误。建连失败通常意味着网络或对端不可达，应该快速失败，而不是陪它等几秒。

### 5.4 超时之后做什么

超时不等于失败。写请求超时后，结果可能是成功、失败或仍在处理，必须按业务单号查询，不能直接重试或补偿。

```text
超时 → 查支付单/订单状态 → 已成功：按成功处理
                          → 明确失败：可重试或补偿
                          → 未知：保持中间态，交给巡检与对账
```

### 5.5 边界

超时设得过短，会把正常慢请求变成失败并触发重试，等于人为放大流量；设得过长，故障时连接和线程堆积，恢复更慢。基线应来自压测的 P99.9，而不是拍脑袋。没有压测数据时，先用 P99 的 2 到 3 倍，并在上线后按实际分布调整。

> 边界：超时预算不能跨团队口头约定。调用方按 300ms 设计、提供方按 3s 设计，双方都“符合自己的规范”，合起来就是故障。

## 六、重试与放大

重试只能在最外层做一次，并且必须带预算；每一层都重试，会把一次故障放大成一场雪崩。

放大倍数是各层尝试次数的乘积。客户端、网关、服务各尝试 3 次，最坏情况一次用户请求变成 27 次下游调用；如果这 27 次都打在同一条已经过载的链路上，服务端永远缓不过来。

### 6.1 放大计算

| 层 | 尝试次数 | 累计调用 |
|---|---|---|
| 客户端 | 3 | 3 |
| 网关 | 3 | 9 |
| 服务 | 3 | 27 |

把重试收敛到入口后，同样三次尝试只产生 3 倍流量。服务内部对下游只做“快速失败 + 上层决策”，不自行重试。

### 6.2 重试预算

重试预算（Retry Budget）限制重试流量占总流量的比例，常见做法是令牌桶：每个成功请求补充令牌，重试消耗令牌，令牌不足时直接失败。

```yaml
retryBudget:
  ratio: 0.1          # 重试最多占成功请求的 10%
  minPerSecond: 10    # 低流量时保底，避免小流量下无法重试
  ttl: 10s
```

没有预算的重试，在故障时的行为是“越失败越重试，越重试越失败”。预算把重试从无界行为变成有界资源。

### 6.3 哪些错误可以重试

| 错误 | 可重试 | 原因 |
|---|---|---|
| 连接失败、连接重置 | 是 | 请求未到达 |
| 读超时 | 仅幂等请求 | 结果未知 |
| 429 限流 | 是，带退避 | 稍后可成功 |
| 503 不可用 | 是，带退避 | 实例可能已恢复 |
| 400 参数错误 | 否 | 重试结果相同 |
| 409 状态冲突 | 否 | 需重新读状态 |
| 业务规则拒绝 | 否 | 重试无意义 |

“读超时 + 非幂等写”是最危险的一类：请求可能已经执行，重试会重复执行。正确做法是带幂等键重试，或先查询结果。

### 6.4 退避与抖动

固定间隔重试会让所有失败客户端在同一时刻再次冲击服务端。指数退避加随机抖动把重试打散。

```text
sleep = min(cap, base × 2^attempt) × random(0.5, 1.0)
base = 100ms, cap = 2s
第 1 次：50–100ms
第 2 次：100–200ms
第 3 次：200–400ms
```

抖动必须作用在每一次等待上，而不是只加一次固定偏移。同步重试（所有客户端同一节奏）在故障恢复瞬间会形成第二波峰值。

### 6.5 幂等键的设计

幂等键要满足三点：全局唯一、由发起方生成、在重试期间保持不变。

- 下单：客户端生成 `request_id`，服务端建唯一索引；
- 支付：业务订单号加支付请求号；
- 消息消费：`event_id` 加消费者标识。

把时间戳或随机数当幂等键，每次重试都会生成新键，去重表形同虚设。

### 6.6 边界

重试解决的是瞬时抖动，不解决容量不足。下游已经过载时，重试只会延长故障。判断标准：错误率在 1 分钟内快速回落，说明是抖动；持续高位，说明是容量或依赖故障，应该熔断和降级，而不是重试。

> 边界：批量任务的重试要单独设计。逐条重试会把一次批量失败变成 N 次单条调用，既慢又容易触发限流；应按批次重试，并记录失败条目。

## 七、熔断、隔离与背压

熔断解决“下游已经坏了还要继续打”的问题，隔离解决“一个依赖拖垮全部线程”的问题，背压解决“上游生产速度超过下游消费速度”的问题；三者解决的是三种不同的失控。

### 7.1 熔断的三个状态

熔断器（Circuit Breaker）在关闭、打开、半开之间切换，用统计窗口内的失败比例决定是否切断流量。

| 状态 | 行为 | 迁移条件 |
|---|---|---|
| 关闭（Closed） | 正常放行，统计失败率 | 超阈值 → 打开 |
| 打开（Open） | 直接失败，不发请求 | 等待期结束 → 半开 |
| 半开（Half-Open） | 放行少量探测请求 | 成功 → 关闭；失败 → 打开 |

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 100          # 统计最近 100 次调用
        minimumNumberOfCalls: 20        # 样本不足不熔断，避免低流量误判
        failureRateThreshold: 50        # 失败率超过 50% 打开
        slowCallRateThreshold: 60       # 慢调用占比超过 60% 打开
        slowCallDurationThreshold: 800ms
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 10
```

`minimumNumberOfCalls` 是最容易被忽略的参数。设成 100 而实例每分钟只有 20 次调用，熔断器永远不会触发，故障期间流量照打。低流量服务要把样本门槛降到与真实 QPS 匹配的量级。

### 7.2 隔离

隔离（Bulkhead）把资源按依赖切分，一个依赖耗尽自己的线程或连接，不影响其他依赖。

| 方式 | 隔离粒度 | 代价 |
|---|---|---|
| 线程池隔离 | 每个依赖独立线程池 | 线程多，上下文切换 |
| 信号量隔离 | 并发计数 | 无法中断阻塞调用 |
| 连接池隔离 | 每个依赖独立连接池 | 连接数上限需精算 |
| 实例隔离 | 核心与非核心分集群 | 部署与成本 |

线程池隔离适合阻塞式 IO 且延迟不可控的依赖；信号量隔离适合低延迟、非阻塞调用。连接池要按“下游并发上限 × 单请求时长”估算，池子小于并发就会出现排队超时，池子过大则把压力全推给下游。

### 7.3 背压

背压（Backpressure）的本质是让生产速度可见地降下来，而不是把消息堆在内存里。无界队列不是缓冲，是把崩溃从“立刻”推迟到“内存耗尽”。

| 机制 | 做法 | 适用 |
|---|---|---|
| 有界队列 | 队列满即拒绝，返回 429 | 线程池入口 |
| 拉模式消费 | 消费方按能力拉取 | 消息队列 |
| 并发上限 | 限制同时处理的请求数 | 下游保护 |
| 自适应限流 | 按延迟与并发动态调上限 | 流量波动大 |
| 消费降速 | 暂停分区或降低批次 | 积压时保护数据库 |

```yaml
server:
  tomcat:
    threads:
      max: 200
    accept-count: 100        # 有界等待队列，满则拒绝
```

队列长度要配合超时：请求在队列里等 2 秒，而入口预算是 1 秒，排队本身就注定超时。队列容量的估算方式是“可接受排队时长 ÷ 单请求处理时长 × 并发数”。

Kafka 消费侧的背压由拉模式天然提供：`max.poll.records` 控制单批条数，消费线程数控制并发，处理不过来时位点不前进，lag 上升，触发告警和扩容。把 `max.poll.records` 调到几万条，看似吞吐高，实际是一次 poll 处理超时，触发 rebalance，整批重放。

### 7.4 边界

熔断不是限流。限流保护自己不被压垮，熔断保护自己不被下游拖垮；一个在入口，一个在出口。只配其中一个，另一半仍然会失控。

半开状态放行的请求要选“代表性请求”，不能只放健康检查。健康检查通过但业务查询超时的服务很常见，用健康检查探活会让熔断器误判恢复。

> 边界：熔断打开后必须有降级返回。没有降级，熔断只是把“慢失败”换成“快失败”，用户仍然拿不到结果。

## 八、服务发现与负载均衡

服务发现（Service Discovery）解决“实例地址会变”，负载均衡（Load Balancing）解决“请求分给谁”；两者都依赖健康状态，而健康状态的判定标准决定了故障时的实际可用性。

### 8.1 注册与发现

| 环节 | 动作 | 失败后果 |
|---|---|---|
| 注册 | 实例启动后写入地址与元数据 | 新实例收不到流量 |
| 心跳 | 定期续约，证明存活 | 过期被摘除 |
| 订阅 | 调用方拉取或监听实例列表 | 使用过期地址 |
| 摘除 | 心跳超时或主动下线 | 流量打到死实例 |

Nacos 2.x 用长连接加心跳，Consul 用健康检查，Kubernetes 用 EndpointSlice 加探针。三者的共同点是：注册中心只反映“实例自称的状态”，不反映“实例能否正确处理业务”。

### 8.2 健康检查的分层

| 探针 | 检查什么 | 失败动作 |
|---|---|---|
| 启动探针 | 进程是否完成初始化 | 重启容器 |
| 就绪探针 | 是否可接收流量 | 从 Endpoint 摘除 |
| 存活探针 | 进程是否卡死 | 重启容器 |

就绪探针不能只查端口。依赖数据库连接池未初始化、配置未加载完成时，端口已经监听，但请求必然失败。就绪检查要覆盖“关键依赖可用”这一层，同时避免把下游故障当成自身不健康，否则一次数据库抖动会把所有实例同时摘除。

### 8.3 负载均衡的位置

| 位置 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| 客户端 | SDK 内选实例 | 少一跳，延迟低 | 多语言重复实现 |
| 服务端 | 独立 LB / 网关 | 集中治理 | 多一跳，可能成瓶颈 |
| 服务网格 | Sidecar 代理 | 语言无关，策略统一 | 运维复杂度上升 |

没有服务网格的团队，客户端负载均衡加注册中心足够；跨语言、多协议、需要统一 mTLS 和流量切分时，服务网格的收益才抵得上成本。

### 8.4 算法与摘除延迟

| 算法 | 特点 | 适用 |
|---|---|---|
| 轮询 | 均匀，忽略负载 | 实例同构、请求均匀 |
| 加权 | 按容量分配 | 实例规格不同 |
| 最少请求 | 按在途数分配 | 请求耗时差异大 |
| 一致性哈希 | 同键落同实例 | 缓存亲和、有状态 |
| 延迟优先 | 按观测延迟选 | 多机房 |

摘除延迟是可用性的隐形杀手。心跳 TTL 10 秒、摘除再等 10 秒，故障实例会继续收 20 秒流量。缩短 TTL 会增加心跳压力，常见的折中是 3 到 5 秒 TTL，配合调用方熔断兜底。

优雅停机同样重要：实例收到终止信号后先从注册中心摘除，等待一个心跳周期，再停止接收新请求，最后处理完在途请求。缺少 `preStop` 等待，滚动发布期间必然出现一批 502。

> 边界：DNS 做服务发现时，TTL 决定了摘除速度，客户端还会缓存解析结果。TTL 设 30 秒，故障流量就会多打 30 秒；把 TTL 压到 1 秒，DNS 查询量又会压垮解析器。

## 九、分区、消费组与积压治理

消息系统的并行度由分区数决定，消费组的每个分区同一时刻只能被一个消费者处理；不理解这一点，扩容消费者往往没有效果。

### 9.1 分区与消费者的关系

```text
topic: order-events   partitions: 12
group: fulfillment    consumers: 6   → 每个消费者分 2 个分区
group: analytics      consumers: 12  → 每个消费者分 1 个分区
```

消费者数超过分区数，多出来的消费者空闲。想让 12 个消费者都工作，分区至少要 12 个。分区数只能增不能减，且增加后同一 key 的路由可能变化，顺序保证会被打破。

### 9.2 顺序与扩容的冲突

扩分区会改变 `hash(key) % partitions` 的结果，同一订单的新旧事件可能落到不同分区，消费端看到的顺序就乱了。

需要扩分区又需要顺序时，正确做法是新建一个分区更多的主题，双写一段时间，让消费者先追平旧主题再切到新主题，最后停掉旧主题。直接对在线主题扩分区，是一次无声的顺序破坏。

### 9.3 积压的判断与处理

积压（Lag）等于最新位点减去消费位点。只看总 lag 不够，还要看增长速度：lag 稳定说明消费能力与生产速度匹配，lag 持续上升说明消费端已经跟不上。

```bash
kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --describe --group order-fulfillment
```

```text
GROUP              TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
order-fulfillment  order-events   0          812340          812340          0
order-fulfillment  order-events   1          798112          930441          132329
order-fulfillment  order-events   2          801233          801240          7
```

单分区 lag 高、其他分区正常，通常是该分区有热点 key 或消费阻塞；全分区同时高，才是整体消费能力不足。

| 处置 | 做法 | 代价 |
|---|---|---|
| 扩消费者 | 加到不超过分区数 | 受分区上限约束 |
| 提高批次 | 调大 poll 条数与并发 | 单批耗时上升，可能超时 |
| 降级处理 | 跳过非关键逻辑 | 数据不完整 |
| 转死信 | 跳过毒消息 | 需人工补偿 |
| 扩分区 | 新建主题迁移 | 破坏顺序，周期长 |

毒消息（Poison Message）是积压的常见原因：一条消息反序列化失败，消费端不断重试，位点永不前进。必须配置死信主题和重试上限，让坏消息离开主链路。

### 9.4 位点提交与重复窗口

先处理后提交位点，失败会重复消费；先提交后处理，失败会丢消息。默认选前者，用幂等消化重复。

```yaml
spring:
  kafka:
    consumer:
      max-poll-records: 200
      properties:
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
      enable-auto-commit: false
```

自动提交会在处理完成前提交位点，进程崩溃就丢消息。关闭自动提交，处理成功后手动提交，重复窗口由业务幂等兜住。

`CooperativeStickyAssignor` 做增量再均衡，避免每次 rebalance 停掉所有分区。配合静态成员（static membership），滚动发布时可以减少无谓的再均衡。

### 9.5 边界

顺序和并行是互斥的。要求全局顺序，就只能单分区单消费者，吞吐上限锁死；要求高吞吐，就必须接受分区内有序、跨分区无序，并在业务上保证不依赖全局顺序。

> 边界：积压时不要盲目扩消费者。消费者数已经等于分区数，再加只会多出空闲进程；此时要么提高单条处理速度，要么扩分区并接受迁移成本。

## 十、可观测与排障手册

通信故障的定位依赖三样东西：指标定位环节、Trace 串起跨服务与跨消息、日志给出具体参数；缺一样，排障就只能靠猜。

### 10.1 指标

| 指标组 | 内容 | 用途 |
|---|---|---|
| RED | 速率、错误率、延迟 | 服务级健康 |
| USE | 利用率、饱和度、错误 | 资源瓶颈 |
| 消息 | 生产速率、消费速率、lag | 积压判断 |
| 连接 | 建连失败、池占用、等待时长 | 连接池问题 |

延迟必须看分位数，不看平均值。P99 从 200ms 涨到 2s、平均值只从 80ms 涨到 120ms 的情况很常见，平均值会把长尾完全掩盖。

### 10.2 跨同步与异步的追踪

同步调用用 W3C Trace Context 的 `traceparent` 头传播；消息要把同样的字段写进消息头或属性，消费端取出后作为父上下文继续。

```json
{
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "event_id": "0f1c9a7e-6d2b-4c1a-9f30-5b7e2d8c4411"
}
```

异步链路的消费不是请求的子调用，而是由消息触发的新执行。用 Span Link 关联生产与消费，比强行挂成父子关系更准确，否则 Trace 会出现一个跨越数小时的长父 Span。

### 10.3 日志字段

每条跨服务日志至少带 `trace_id`、`span_id`、`request_id`、`attempt`、`peer.service`。`attempt` 用来区分首次调用与重试，缺了它，重复调用的日志会看起来像两次独立业务。

### 10.4 排障顺序

| 现象 | 第一条查询 | 判断 |
|---|---|---|
| 接口 P99 突增 | 按下游拆分的延迟分位 | 哪个依赖变慢 |
| 错误率上升但延迟正常 | 错误码分布 | 业务拒绝还是技术失败 |
| 重试量暴涨 | 重试预算消耗、attempt 分布 | 哪一层在重试 |
| 消息不消费 | 消费者组 lag 与实例数 | 无消费者还是消费卡住 |
| 502 / 连接拒绝 | 实例就绪状态、注册中心列表 | 摘除是否及时 |
| 超时但下游成功 | 按业务单号查下游状态 | 是否结果未知 |

### 10.5 采样

高流量链路必须采样，但普通随机采样会丢掉长尾。头采样按比例决定是否记录，尾采样在请求结束后按“是否错误、是否超时”决定保留，后者更适合排障。

> 边界：采样率降低后，错误率的绝对值仍然可用，但单条个案的完整链路可能不存在。资金类链路要对错误请求全量保留，不能按比例采样。

## 十一、选型与失败模式

通信选型先定交互形态，再定协议，再定治理策略；顺序反了，就会在错误的形态上做精细优化。

### 11.1 决策顺序

1. 调用方是否必须立即拿到结果？是，同步；否，异步。
2. 需要流式或双向推送？是，gRPC 流；否，单向 RPC 或 REST。
3. 调用方是浏览器或第三方？是，REST + JSON；否，gRPC 优先。
4. 失败能否延后？能，消息加消费幂等；不能，同步加超时预算。
5. 链路是否需要跨团队治理？是，契约加注册中心或服务网格；否，SDK 足够。

### 11.2 方案矩阵

| 场景 | 通信方式 | 关键治理 |
|---|---|---|
| 内部高频查询 | gRPC | 截止时间、熔断 |
| 开放 API | REST + JSON | 版本、限流、鉴权 |
| 事件广播 | 日志型消息 | 分区键、Schema |
| 任务分发 | 队列型消息 | 死信、重试上限 |
| 长耗时任务 | 受理 + 轮询 | 任务状态机 |
| 跨组织通知 | 最大努力通知 | 重试节奏、对账 |

### 11.3 失败模式

- 同步链路过长：七跳串行，可用性被乘积拉低。
- 每层都重试：故障时流量放大十几倍，恢复无望。
- 超时不传递：下游不知道剩余预算，做注定超时的工作。
- 无幂等重试：一次超时变成两次扣款。
- 契约无兼容检查：新增必填字段，旧消费者集体解析失败。
- 无界队列：内存耗尽前一切看起来正常。
- 消费者数超过分区数：扩容无效，误判为消费能力不足。
- 异步链路不传 Trace：出问题只能按时间猜。

### 11.4 决策清单

1. 这次交互需要即时结果吗，失败能否延后？
2. 端到端预算是多少，每一跳分到多少？
3. 重试在哪一层做，预算多少，是否幂等？
4. 下游故障时返回什么，降级路径是什么？
5. 契约如何演进，兼容模式是什么，谁验证？
6. 分区键是什么，顺序要求到哪一级？
7. 积压多少算异常，第一条命令是什么？

## 十二、最佳实践案例

### 12.1 案例背景

一家区域零售企业的订单中心有 12 个服务，大促期间下单主链路串行经过网关、订单、价格、优惠、库存、风控、支付七个环节。日常 P99 约 600ms，大促峰值 P99 达到 2.4 秒，超时率 3.8%，入口重试与 SDK 重试叠加后，下游实际流量约为入口的 9 倍（示例数据）。

故障表现有三类：库存服务偶发慢查询时，订单线程池被占满，连查询接口也不可用；支付回调重复到达，产生重复入账；积分与通知同步调用失败，导致订单创建整体回滚。消息侧另有一个问题：履约事件积压峰值 200 万条，恢复耗时超过 3 小时。

目标是六周内把下单 P99 压到 500ms 以内，超时率降到 0.3% 以下，重试放大控制在 2 倍以内，积压恢复时间压到 1 小时以内。约束有四项：不能停机；第三方支付只提供同步接口，单次调用预算 800ms；移动端存在弱网；团队 14 人，没有服务网格运维经验。

### 12.2 案例实操

第一步是给链路分级，而不是先调参数。团队把 12 个服务按“是否阻塞下单结果”分成三类，结论是只有订单、库存、支付必须同步，价格与优惠可以前置批量查询，积分、通知、推荐、报表可以异步。

| 选项 | 改造量 | 主要风险 | 判断 |
|---|---|---|---|
| 全链路异步化 | 大 | 结果不可查，链路难追踪 | 否 |
| 只扩容实例 | 小 | 成本线性，故障仍放大 | 否 |
| 引入服务网格 | 中 | 团队无运维经验 | 否 |
| 分层改造 | 中 | 需逐链路梳理预算 | 是 |

决策是分层改造：同步链路从七跳压到三跳，非关键动作改事件，治理策略统一放在 SDK 与网关，不引入新组件。理由是故障的主因是链路长度与重试放大，不是缺少流量治理能力。

超时预算按入口 SLO 反推，并写进接口契约，由网关注入剩余毫秒。

| 环节 | 改造前 | 改造后 |
|---|---|---|
| 客户端 | 3,000ms | 1,000ms |
| 网关 | 3,000ms | 850ms |
| 订单 | 2,500ms | 600ms |
| 库存 | 2,000ms | 250ms |
| 支付 | 2,000ms | 700ms |

价格与优惠改成网关注入的批量预取，一次调用取回全部规则，耗时从两次 200ms 合并为一次 120ms。库存的 250ms 里给数据库 80ms，剩余覆盖连接池等待与序列化。

重试收敛到入口：关闭 SDK 的自动重试，网关只对幂等 GET 重试一次，写请求一律不自动重试，由业务带幂等键决策。入口加 10% 的重试预算，故障时重试流量不再无限增长。

```yaml
retry:
  budgetRatio: 0.10
  minPerSecond: 10
  maxAttempts: 2
  backoff:
    base: 100ms
    cap: 2s
    jitter: 0.5
```

库存与支付各自独立线程池，核心链路 120 线程，非核心 40 线程，队列上限 200，满则拒绝并返回 429。这样库存慢查询只会耗尽自己的池子，不会拖垮订单查询。

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        slidingWindowSize: 50
        minimumNumberOfCalls: 20
        failureRateThreshold: 50
        slowCallDurationThreshold: 300ms
        slowCallRateThreshold: 60
        waitDurationInOpenState: 20s
```

熔断打开后的降级是返回“库存校验中”的中间态，由订单状态机在 30 秒内异步确认，而不是直接失败。支付熔断则返回明确的“稍后重试”，因为支付不能凭中间态继续。

消息侧先解决契约，再解决积压。履约事件的主题从 12 个分区扩到 24 个，但没有直接改在线主题，而是新建 `order-events-v2`，双写两周，消费者追平后切换，最后停写旧主题。这样既扩了并行度，又没有破坏同一订单的顺序。

事件契约统一为六个字段，`schema_version` 由注册中心校验，兼容模式设为 `FULL`。

```json
{
  "event_id": "5c8f1d20-9a4e-4b71-8f02-2d6a7e91c334",
  "event_type": "order.paid",
  "schema_version": 3,
  "occurred_at": "2026-11-13T10:21:33.412+08:00",
  "producer": "order-service",
  "payload": { "order_no": "SO202611130001", "amount_cent": 12800, "currency": "CNY" }
}
```

消费端关闭自动提交，`max.poll.records` 设为 200，消费线程数 24，与分区数对齐。位点处理成功后提交，重复由 `(consumer, event_id)` 去重表消化。死信主题保留 7 天，重试 5 次仍失败的消息转人工，不再阻塞主链路。

服务发现侧补了优雅停机：实例下线时先反注册，等待 5 秒，再停止接收新请求，最后等待在途请求完成。就绪探针加入数据库连接池与配置加载检查，存活探针只查进程，避免依赖抖动导致全量重启。

灰度按 10% → 30% → 60% → 100% 四批，每批观察 P99、超时率、重试量、lag 四个指标。压测用生产流量的 1.2 倍回放，持续时间 40 分钟，覆盖库存慢查询与支付超时两个故障注入场景。

### 12.3 案例结果

上线后的大促数据如下（示例，取自监控周报口径）。

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 下单 P99 | 2.4s | 420ms |
| 超时率 | 3.8% | 0.12% |
| 重试放大 | 9 倍 | 1.4 倍 |
| 峰值积压 | 200 万 | 4.7 万 |
| 积压恢复 | 3 小时 | 40 分钟 |

可用性从 99.95% 升到 99.98%，库存慢查询期间订单查询接口未再受影响。异步化的积分与通知日均处理 260 万条，重复消费 11 条，全部被去重表拦下。改造没有新增中间件，运维对象数量不变。

失败模式与复盘：

第一，关闭 SDK 重试后的第一周，错误率从 0.3% 升到 0.7%。原因是原先被自动重试掩盖的瞬时连接重置暴露出来。修复不是恢复每层重试，而是在入口按预算重试一次，并把连接池的空闲检测打开。结论是重试要“显式且有界”，不能依赖 SDK 默认值。

第二，熔断器最初按 100 次调用统计，两个低流量实例整场大促都没触发过熔断。把样本门槛降到 20 并加入慢调用比例后，库存抖动时能正常打开。阈值必须按实例真实 QPS 校准，照抄文档参数等于没配。

第三，异步链路的 Trace 在消息处断裂，履约延迟只能按日志时间猜。补上消息头传播 `traceparent`、消费端用 Span Link 关联后，才能看出“生产到消费”的实际排队时长。

第四，双写切换期间有消费者仍按旧 Schema 解析，新增的必填字段导致整批失败并积压。注册中心当时是 `BACKWARD`，挡不住“新消费者读旧数据”的方向。改成 `FULL` 并把新字段改为可选后恢复。契约兼容不是发布前的一次检查，而是注册中心的持续约束。

复盘的核心结论：这次改造的收益主要来自三件事——缩短同步链路、把重试收敛到一处、给每个依赖独立资源池。三者都不需要新中间件，但都需要先把链路和预算画清楚。通信治理的难点不在工具，而在“谁在等谁、等多久、失败了谁负责”这三个问题有没有明确答案。
