# 分布式事务与最终一致性

> 这篇从一次跨服务扣减为什么会留下半成品讲起，经过一致性目标、两阶段提交、TCC、Saga、事务性发件箱、事务消息、对账与幂等，最后落到一致性状态机、选型矩阵和一次履约链路的改造决策。
>
> 学完能为一条跨库业务链路选出事务方案，写出补偿、消息契约和对账规则，并把不一致收敛到可查询、可告警、可人工兜底的状态机上。

## 一、问题的边界

分布式事务要解决的从来不是“让两台数据库一起提交”，而是**一次业务动作跨过进程边界、失败发生在中间时，数据允许停在哪一个状态**。

本地事务（Local Transaction）的 ACID 只在同一个数据库连接内成立。订单服务写订单库、库存服务写库存库，两次提交之间没有共同的提交点，因此必然存在“订单已创建、库存未扣减”的可见窗口。这个窗口不是 bug，是跨进程调用的固有属性；方案的价值在于把窗口压到多短、暴露给谁、由谁收敛。

三个真实断点：

| 断点 | 现象 | 是否真不一致 | 处理方向 |
|---|---|---|---|
| 上游提交后进程崩溃 | 订单存在，下游未调用 | 是 | 事件重放或对账补单 |
| 下游成功、响应丢失 | 库存已扣，订单未落 | 是 | 幂等重试，先查结果 |
| 下游超时但最终成功 | 调用方判定失败 | 是（判断错） | 结果查询，禁止盲目补偿 |

第三种断点最容易被写错。调用方超时后立刻发补偿，而下游其实已经成功，补偿会把一次正确扣减压成零，再被后续重试扣一次。跨服务调用只要可能超时，就必须提供按业务单号查询结果的能力，补偿只能建立在“确认失败”之上。

> 边界：单库多表仍应使用本地事务。把同一个库的两张表拆给两个服务，再用分布式事务补回来，是用架构复杂度换一个本来不存在的问题。

判断是否需要跨服务事务，按顺序问三个问题：

1. 能否收敛到单库？同一业务实体的强一致数据放在同一个库，用本地事务一次提交。
2. 能否用业务状态替代原子提交？预留、冻结、锁定、待确认都是把“原子”换成“可识别中间态”。
3. 不一致的敞口能否被对账覆盖？资金类链路即使做了事务方案，也必须有对账。

三个都为否，才进入方案选型。多数团队跳过前两问，直接比较 2PC 和 TCC，最后得到一个比业务本身复杂得多的系统。

### 1.1 局部成功为什么无法靠重试修好

重试只能修复“没执行”的动作，不能修复“执行了一半”的动作。订单已提交、库存未扣，重试扣库存可以把数据补回来；但如果库存已扣、优惠券已核销、支付已发起，重试整个业务动作就会重复扣减。区别在于**动作是否幂等**，而不在于重试次数。

因此，跨服务事务的第一个设计产物不是方案图，而是一张动作清单：每个动作是否可重复执行、是否可反向执行、失败后由谁负责。清单里出现“不可重复且不可反向”的动作，就必须把它放到流程最后，或者改成可识别的中间态。

### 1.2 一致性问题的三种表现

同一个根因会以三种形态出现，排障时先归类再动手：

| 形态 | 表现 | 例子 | 首选手段 |
|---|---|---|---|
| 中间态滞留 | 单据停在处理中 | 订单待履约超过 30 分钟 | 超时扫描 + 状态查询 |
| 数据缺失 | 一边有一边没有 | 支付成功、订单未更新 | 消息重放 + 对账补单 |
| 数据重复 | 同一动作执行多次 | 重复退款、重复发券 | 幂等键 + 唯一索引 |

“中间态滞留”经常被误判为死锁或性能问题，实际是状态机缺少超时迁移。第 9 章会把这类问题统一到状态机与巡检指标上。

## 二、一致性目标

一致性目标必须先于方案确定，写成可验收的等级和窗口；否则“最终一致”会变成“永远不一致”的托词。

强一致（Strong Consistency）指任何读都能看到最近一次成功写；最终一致（Eventual Consistency）指在没有新写入的前提下，系统在有限时间内收敛到同一结果。工程上真正要定义的是三件事：哪些数据必须强一致、允许的中间态持续多久、超出窗口后由什么机制兜底。

### 2.1 一致性等级

| 等级 | 保证 | 实现方式 | 主要代价 |
|---|---|---|---|
| L0 强一致 | 读到已提交结果 | 单库事务、共识协议 | 延迟与可用性 |
| L1 读己之写 | 用户看到自己的修改 | 粘性路由、写后读主库 | 路由与降级复杂 |
| L2 最终一致 | 窗口内收敛 | 消息、重试、状态机 | 中间态对外可见 |
| L3 对账兜底 | 按周期发现并修复 | 文件对账、冲正 | 时效与人工 |

等级按数据分配，不按系统分配。同一个订单系统里，库存扣减需要 L0 或强约束的 L2，订单列表展示可以接受 L2，历史订单导出可以接受 L3。把整个系统标成“最终一致”，等于没有目标。

### 2.2 业务不变量

不变量（Invariant）是任何时刻都必须成立的断言，它比“最终一致”更可验收。

| 不变量 | 校验点 | 破坏后果 |
|---|---|---|
| 库存可用量 ≥ 0 | 扣减语句的条件更新 | 超卖，履约失败 |
| 支付金额 = 订单应付 | 支付回调入账 | 资损 |
| 券核销数 ≤ 发行量 | 领券与核销 | 超发，成本失控 |
| 一个订单最多一笔成功支付 | 支付单唯一键 | 重复扣款 |

不变量的价值在于：它可以在数据库层用约束、条件更新、唯一索引直接守住，不依赖事务方案。库存扣减写成 `UPDATE stock SET available = available - ? WHERE sku_id = ? AND available >= ?`，影响行数为 0 就失败，这一条比任何分布式锁都可靠。

> 边界：不变量只能守单库内的断言。跨库的“订单金额 = 支付金额”无法用唯一索引表达，只能靠状态机校验加对账。

### 2.3 一致性窗口与损失

窗口要按故障级别分别定义，并给出检测手段。没有检测手段的窗口只是愿望。

| 场景 | 目标收敛时间 | 检测手段 | 兜底 |
|---|---|---|---|
| 正常波动 | 1 秒内 | 中间态存量监控 | 自动重试 |
| 单实例故障 | 1 分钟内 | 消息堆积、重试队列 | 重放 |
| 中间件故障 | 30 分钟内 | 投递延迟、对账批次 | 人工补单 |
| 渠道故障 | 次日 12 点前 | 渠道对账文件 | 冲正 |

损失模型用来决定投入。假设日均 80 万单、客单价 120 元、每万单出现 2 单不一致、其中 30% 产生资损（示例），日资损约 5,760 元；若自动收敛能把不一致压到每万单 0.2 单，日资损降到 576 元，一年差约 190 万元。这个数量级才支撑得起一套 TCC 加对账的改造。

反过来，内容社区的点赞数不一致，损失接近零，用对账兜底即可。用同一套方案覆盖两者，是把成本花在看不见的地方。

### 2.4 目标怎么写

一条可验收的一致性目标包含五个要素：

```text
对象：订单履约链路（订单、库存、优惠券、支付）
不变量：库存不为负；一个订单最多一笔成功支付
等级：库存 L0，订单状态 L2，券 L2
窗口：正常 1s，单实例故障 60s，渠道故障次日 12:00
兜底：T+1 全量对账，差异自动冲正，失败转人工
```

这五行写不出来，说明还没到选方案的时候。

## 三、两阶段提交与 XA

两阶段提交（Two-Phase Commit，2PC）用协调者统一收集参与者的准备结果，再统一发出提交或回滚；它提供强一致，代价是同步阻塞和协调者单点。

2PC 的前提是参与者都支持 XA 协议（eXtended Architecture）：数据库暴露 `xa_start`、`xa_end`、`xa_prepare`、`xa_commit`、`xa_rollback`，由事务管理器（Transaction Manager，TM）驱动。MySQL 8.4 的 InnoDB 支持 XA，Java 侧通过 JTA 接入。

### 3.1 两个阶段的动作与失败后果

| 阶段 | 协调者动作 | 参与者动作 | 失败后果 |
|---|---|---|---|
| 准备 | 持久化事务日志，发 prepare | 执行并持锁，写 prepare 日志 | 参与者阻塞，资源被占用 |
| 提交 | 收齐 yes 后发 commit | 提交并释放锁 | 部分收到 commit，暂时不一致 |
| 回滚 | 任一 no 或超时后发 rollback | 回滚并释放锁 | 同左，需重试到全部确认 |

准备阶段之后，参与者已经“可以提交但还没提交”，锁一直持有到第二阶段结束。这是 2PC 性能问题的根源：事务时长等于最慢参与者的时长，期间行锁、连接、undo 都不能释放。

### 3.2 四个典型故障

| 故障 | 现象 | 后果 | 处理 |
|---|---|---|---|
| 协调者 prepare 后宕机 | 参与者长期 in-doubt | 行锁不释放，业务堆积 | 查 XA RECOVER，人工裁决 |
| 参与者 commit 后未回 ack | 协调者反复重发 | 重复提交 | 提交必须幂等 |
| 网络分区 | 部分提交、部分回滚 | 启发式不一致 | 记录 heuristic 日志，对账修复 |
| 事务过长 | 锁等待超时 | 部分回滚 | 拆分事务，禁止长事务 |

in-doubt 事务是最难处理的状态：数据库不知道最终该提交还是回滚，只能等协调者恢复或人工介入。生产上必须监控 `information_schema.innodb_trx` 里长期处于 prepared 状态的事务，并设置告警。

### 3.3 AT 模式：2PC 的工程化改良

Seata 的 AT（Automatic Transaction）模式保留了全局锁和两阶段结构，但把一阶段的业务 SQL 直接提交，同时记录 undo log；二阶段提交只删 undo log，回滚则用 undo log 反向补偿。

| 维度 | XA | AT | TCC |
|---|---|---|---|
| 资源锁定 | 数据库锁，全程持有 | 全局锁，短暂持有 | 业务冻结，时长可控 |
| 业务侵入 | 无 | 无 | 高，需写三接口 |
| 隔离性 | 强 | 读未提交风险 | 由业务保证 |
| 适用时长 | 极短 | 短 | 中等 |

AT 的读未提交风险来自“一阶段已提交、全局锁未释放”：其他事务可能读到未全局提交的数据。对账或强隔离场景要配合 `SELECT ... FOR UPDATE` 或改用 TCC。

### 3.4 边界

2PC 适合同机房、短事务、参与者都支持 XA 的场景，例如一个应用写两个数据源。它不适合跨微服务的长业务流程：协调者是新的单点，事务时长受网络影响，参与方无法独立演进。跨组织调用更不能用 2PC，因为对端不会为调用方持有锁。

> 边界：把 2PC 当默认方案，会让系统的可用性等于所有参与者可用性的乘积。三个 99.9% 的参与者串在一个事务里，理论可用性已经降到 99.7%。

## 四、TCC

TCC（Try-Confirm-Cancel）把资源预留交给业务实现：Try 冻结资源，Confirm 确认扣减，Cancel 释放冻结；一致性由业务的三组接口和一张事务控制表共同保证。

TCC 的收益是锁的粒度由业务决定，事务时长不受数据库锁限制；代价是每个参与方都要实现三个接口，并处理空回滚、悬挂、重复这三类异常。

### 4.1 资源模型

库存从 `available` 转到 `frozen`，券从 `unused` 转到 `locked`，额度从 `available` 转到 `reserved`。Try 只做冻结，不做最终扣减；Confirm 把冻结转为已用；Cancel 把冻结退回可用。

```text
Try:     available -= n, frozen += n   （条件：available >= n）
Confirm: frozen -= n, used += n        （幂等，重复执行结果不变）
Cancel:  frozen -= n, available += n   （幂等，未冻结则直接成功）
```

这三条语句必须放在同一个本地事务里，并带条件判断。Try 的条件更新失败就返回业务失败，不进入全局事务。

### 4.2 事务控制表

```sql
CREATE TABLE tcc_transaction (
  xid          VARCHAR(64)  NOT NULL,   -- 全局事务号，由发起方生成
  branch_id    VARCHAR(64)  NOT NULL,   -- 分支号，标识参与方与动作
  status       VARCHAR(16)  NOT NULL,   -- TRYING / CONFIRMED / CANCELLED
  args_digest  CHAR(64)     NOT NULL,   -- 请求参数摘要，防同号不同参
  expires_at   DATETIME(3)  NOT NULL,   -- 预留超时，到期由巡检 Cancel
  version      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (xid, branch_id),
  KEY idx_status_expire (status, expires_at)
) ENGINE=InnoDB;
```

`args_digest` 不是可选项。同一个 xid 携带不同参数重试，说明上游拼接错误，必须拒绝而不是覆盖。`version` 用于状态迁移的 CAS，避免 Confirm 与 Cancel 并发时互相覆盖。

### 4.3 三类异常与防护

| 异常 | 触发顺序 | 现象 | 防护 |
|---|---|---|---|
| 空回滚 | Cancel 先于 Try | 无记录可回滚 | 无记录时插入 CANCELLED 占位 |
| 悬挂 | Try 晚于 Cancel | 冻结了已取消的资源 | Try 前查占位，存在则拒绝 |
| 重复执行 | 网络重试 | 重复扣减 | 唯一键 + 状态 CAS |

空回滚的正确做法不是“查不到就返回成功”，而是写入一条 `CANCELLED` 占位记录。否则后续迟到的 Try 会成功冻结资源，形成悬挂。悬挂检查发生在 Try 入口：按 `(xid, branch_id)` 查到已取消，直接返回成功但不做任何资源变更。

Confirm 与 Cancel 都必须幂等。重复 Cancel 时，第二次读到 `CANCELLED` 直接返回成功；不能用“更新行数为 0 就报错”的写法，那会把正常重试变成故障。

### 4.4 超时与巡检

Try 成功但全局事务未结束时，资源会一直冻结。必须有超时释放：`expires_at` 到期后，由巡检任务反查全局事务状态，确认未提交则调用 Cancel。巡检必须与正常 Cancel 共用同一套幂等逻辑，否则会出现“巡检释放了、上游又 Confirm”的双重变更。

### 4.5 边界

TCC 适合有明确预留语义的资源：库存、额度、权益、座位。它不适合无法预留的资源，例如第三方支付的扣款（只能退款冲正）、已发出的短信、已生成的物流单。对这类动作，TCC 退化为 Saga 的补偿。

TCC 的开发成本约为普通接口的三倍，且要求每个参与方都实现幂等与空回滚。团队没有统一的事务框架和代码模板时，不要选 TCC；手工实现三套接口的项目，最后往往只有 Try 是完整的。

## 五、Saga

Saga 把长事务拆成一串本地事务，每个正向步骤配一个补偿动作；某步失败时按逆序执行已成功步骤的补偿，把系统带回可接受状态。

Saga 不提供隔离性。中间状态对其他事务可见，因此必须用语义锁（Semantic Lock）把未完成的单据挡在业务视图之外：订单置为 `PENDING`，库存置为 `FROZEN`，对外查询默认过滤这些状态。

### 5.1 编排与协同

| 维度 | 编排（Orchestration） | 协同（Choreography） |
|---|---|---|
| 控制点 | 中心协调器 | 各服务监听事件 |
| 流程可见性 | 高，一处可读 | 低，分散在订阅关系里 |
| 耦合 | 协调器依赖各服务 | 服务只依赖事件 |
| 变更成本 | 改协调器 | 改多个订阅方 |
| 适用 | 步骤多、需人工介入 | 步骤少、事件天然广播 |

订单履约、支付、退款这类需要明确进度和人工兜底的流程用编排；积分、通知、搜索索引这类旁路动作可以用协同。

### 5.2 状态机定义

Saga 的实体必须是一台显式状态机，状态迁移由事件驱动，禁止在代码里散落 `if (status == ...)`。

| 当前状态 | 事件 | 守卫 | 下一状态 |
|---|---|---|---|
| CREATED | 库存已预留 | 全部明细齐 | STOCK_RESERVED |
| STOCK_RESERVED | 支付已授权 | 金额一致 | PAYMENT_AUTHORIZED |
| PAYMENT_AUTHORIZED | 履约已创建 | 仓库可分配 | FULFILLED |
| STOCK_RESERVED | 支付失败 | 可补偿 | COMPENSATING |
| COMPENSATING | 库存已释放 | 补偿全部成功 | CANCELLED |
| COMPENSATING | 补偿失败 | 超过重试上限 | MANUAL_REVIEW |
| CREATED | 超时未推进 | 超过 15 分钟 | MANUAL_REVIEW |

`MANUAL_REVIEW` 是正式状态，不是异常分支。没有人工兜底状态的状态机，遇到补偿失败就只能改数据库。

### 5.3 补偿的设计规则

补偿不是“反向执行原操作”，而是“抵消原操作的业务效果”。四条规则：

1. 补偿必须幂等，重复执行不产生额外效果；
2. 补偿必须可重试，失败进入重试队列而不是抛异常终止；
3. 补偿用业务语义，退款而不是删除支付记录，释放而不是删除订单；
4. 不可补偿的动作放到最后，作为 pivot，之前全部可补偿。

不可补偿动作包括已出库、已开票、已发送通知。把它们排在 pivot 之后，意味着一旦越过 pivot，失败只能向前修复（继续履约或人工处理），不能回退。

### 5.4 超时与重试

每个步骤都要有独立超时，超时后先查询结果，再决定补偿。Saga 协调器记录每一步的 `step_status`、`attempt`、`next_retry_at`，重试用指数退避，上限后转人工。

> 边界：Saga 的“最终一致”依赖补偿一定被执行。协调器本身宕机时，必须有独立的巡检任务扫描停滞的 Saga 实例，否则流程会永久停在中间态。

## 六、事务性发件箱与本地消息表

事务性发件箱（Transactional Outbox）把“业务数据变更”和“待发送事件”写在同一个本地事务里，再由独立中继投递；它解决的是“数据库提交了，消息没发出去”。

本地消息表（Local Message Table）是 Outbox 的一种落地形式：消息表与业务表同库，业务操作和插消息在一个事务内完成。两者的差别只在表的归属，机制相同。

### 6.1 表结构

```sql
CREATE TABLE outbox_event (
  event_id      CHAR(36)     NOT NULL,   -- 消费端幂等键
  aggregate_id  VARCHAR(64)  NOT NULL,   -- 聚合根，决定分区与顺序
  event_type    VARCHAR(64)  NOT NULL,   -- 契约里的类型名
  payload       JSON         NOT NULL,   -- 事件体，大对象只存引用
  status        TINYINT      NOT NULL DEFAULT 0,  -- 0 待投递 1 已投递 2 死信
  retry_count   INT          NOT NULL DEFAULT 0,
  next_retry_at DATETIME(3)  NOT NULL,
  created_at    DATETIME(3)  NOT NULL,
  PRIMARY KEY (event_id),
  KEY idx_dispatch (status, next_retry_at)
) ENGINE=InnoDB;
```

`event_id` 在业务事务里生成，不是投递时生成。这样即使中继重复投递，消费端拿到的仍是同一个键。

### 6.2 投递流程

```text
1. 业务事务：更新订单 + 插入 outbox_event(status=0)  → 一次本地提交
2. 中继轮询：SELECT ... WHERE status=0 AND next_retry_at <= now() LIMIT 200 FOR UPDATE SKIP LOCKED
3. 投递到消息中间件，等待 broker ack
4. ack 成功：status=1；ack 失败：retry_count+1，next_retry_at 指数退避
5. 消费端：以 event_id 去重，处理成功后才提交位点
```

`FOR UPDATE SKIP LOCKED` 让多个中继实例并行拉取而不互相阻塞，MySQL 8.0 以后可用。没有它，多实例轮询会重复投递同一条记录。

### 6.3 消费端去重

```sql
CREATE TABLE consumed_event (
  consumer    VARCHAR(64) NOT NULL,
  event_id    CHAR(36)    NOT NULL,
  consumed_at DATETIME(3) NOT NULL,
  PRIMARY KEY (consumer, event_id)
) ENGINE=InnoDB;
```

去重表与业务变更必须在同一个本地事务里提交。先写去重表再处理业务，处理失败会丢消息；先处理业务再写去重表，重复消费会重复处理。正确顺序是同一事务内：插去重记录（冲突即视为已处理）、执行业务、提交。

### 6.4 中继的两种实现

| 方式 | 延迟 | 数据库压力 | 复杂度 |
|---|---|---|---|
| 轮询 | 百毫秒到秒级 | 持续查询，需索引 | 低 |
| CDC 日志订阅 | 毫秒级 | 读 binlog，压力小 | 中，需运维组件 |

轮询实现简单，适合日订单百万级；CDC 用 Debezium 之类的组件读 binlog，延迟低，但引入额外运维对象和位点管理。无论哪种，投递语义都是至少一次（At-Least-Once），消费端必须幂等。

### 6.5 边界

Outbox 要求业务表与消息表在同一个数据库。跨库写 outbox 又回到了分布式事务，方案自相矛盾。事件体只存必要字段，大对象存引用；否则 outbox 表会膨胀到影响业务库性能。投递完成后要归档或删除，保留期按审计要求设定，常见 7 到 30 天。

顺序性按 `aggregate_id` 保证：同一聚合的事件进入同一分区，消费端串行处理。跨聚合不保证顺序，业务不能依赖。

## 七、事务消息

事务消息（Transactional Message）由消息中间件提供半消息与回查机制，让“发送消息”和“本地事务”达成原子；它解决 Outbox 需要自建中继和表的运维成本。

以 RocketMQ 5.3 为例，流程分四步：

```text
1. 生产者发送半消息（half message），broker 存储但对消费者不可见
2. broker 返回成功，生产者执行本地事务
3. 本地事务成功 → 提交消息；失败 → 回滚消息；结果未知 → 不表态
4. broker 定时回查生产者的本地事务状态，按回查结果提交或回滚
```

### 7.1 回查接口的约束

| 回查结果 | 生产者行为 | broker 行为 |
|---|---|---|
| COMMIT | 本地事务已提交 | 消息对消费者可见 |
| ROLLBACK | 本地事务已回滚 | 删除半消息 |
| UNKNOWN | 状态仍不确定 | 延迟后再查，超过上限丢弃 |

回查必须能按业务主键查到本地事务的最终状态，不能依赖内存变量。回查次数有上限，超过后 broker 丢弃消息，这条业务就永久丢失了事件，只能靠对账发现。因此本地事务表要保留足够长的状态，至少覆盖回查窗口。

### 7.2 与 Outbox 的对比

| 维度 | Outbox | 事务消息 |
|---|---|---|
| 依赖 | 数据库 | 支持事务消息的 MQ |
| 原子性来源 | 本地事务 | 半消息 + 回查 |
| 延迟 | 轮询或 CDC | 秒级 |
| 运维 | 自建中继与表 | 依赖 MQ 能力 |
| 顺序 | 按聚合自行分区 | 按队列或分区 |

### 7.3 Kafka 事务的边界

Kafka 4.0 的事务配合 `transactional.id` 与 `isolation.level=read_committed`，可以做到“读消息、处理、写消息、提交位点”在 Kafka 内部原子，即 Kafka 内的精确一次（Exactly-Once）。它不覆盖外部数据库：写数据库与写 Kafka 仍在两个系统里，需要 Outbox 或幂等消费补齐。

> 边界：事务消息只保证“本地事务成功则消息一定可投递”，不保证下游业务成功。下游失败仍要靠重试、补偿和对账。把事务消息当端到端方案，是这类方案最常见的误读。

## 八、对账、冲正与幂等

对账（Reconciliation）是最后一道防线：它不阻止不一致发生，但保证不一致在可接受的时间内被发现、被分类、被修复。

任何跨系统资金或权益链路都必须有对账，包括做了 TCC 或 Saga 的链路。事务方案降低发生概率，对账提供兜底，两者不是替代关系。

### 8.1 对账的三个层次

| 层次 | 对比对象 | 频率 | 主要发现 |
|---|---|---|---|
| 内部对账 | 订单与支付、库存与流水 | 小时级 | 状态不同步 |
| 渠道对账 | 内部账与渠道文件 | 日级 | 长短款、状态差异 |
| 财务对账 | 业务账与会计账 | 月级 | 科目与金额差异 |

### 8.2 对账表

```sql
CREATE TABLE recon_detail (
  batch_id       VARCHAR(32)   NOT NULL,  -- 对账批次，按日+渠道
  channel        VARCHAR(32)   NOT NULL,
  channel_no     VARCHAR(64)   NOT NULL,  -- 渠道流水号
  internal_no    VARCHAR(64)   NULL,      -- 内部单号，可能为空
  amount         DECIMAL(18,2) NOT NULL,
  channel_state  VARCHAR(16)   NOT NULL,
  internal_state VARCHAR(16)   NULL,
  diff_type      VARCHAR(16)   NULL,      -- LONG/SHORT/AMOUNT/STATE/DUP
  PRIMARY KEY (batch_id, channel, channel_no)
) ENGINE=InnoDB;
```

差异类型只有五类，处理方式固定，才能自动化：

| 差异 | 含义 | 自动处理 | 人工介入条件 |
|---|---|---|---|
| LONG 长款 | 渠道有、内部无 | 补单 | 金额超阈值 |
| SHORT 短款 | 内部有、渠道无 | 查询后冲正 | 已履约 |
| AMOUNT 金额不符 | 两边金额不同 | 挂起 | 全部 |
| STATE 状态不符 | 成功与失败冲突 | 以渠道为准修正 | 已发货 |
| DUP 重复 | 同一流水多条 | 撤销多余 | 已分账 |

### 8.3 冲正与补单

冲正不是删除记录，而是生成一笔反向流水，保留完整审计链。补单必须复用正常下单入口，带唯一业务键，避免补出重复单。

对账任务本身要幂等：同一批次重复跑，结果一致；差异处理重复执行，只产生一条有效冲正。实现方式是为每个差异生成 `(batch_id, channel_no, action)` 唯一键的处理记录。

### 8.4 幂等的四种实现

幂等（Idempotency）不是加一个 `if`，而是让“同一业务动作执行多次”与“执行一次”产生相同结果；四种实现按成本从低到高排列，能覆盖绝大多数链路。

| 实现 | 机制 | 适用 | 失效点 |
|---|---|---|---|
| 唯一索引 | 业务键冲突即拒绝 | 创建类动作 | 键设计错误 |
| 去重表 | 消费前插入键 | 消息消费 | 与业务不同事务 |
| 状态 CAS | 带前置状态更新 | 状态迁移 | 状态被并发修改 |
| 令牌 | 一次性凭证 | 提交类接口 | 令牌可重放 |

唯一索引是最可靠的一层，因为它由数据库保证，不依赖应用逻辑。去重表的风险在事务边界：去重记录与业务变更必须同一个本地事务提交，否则要么漏判、要么误判。状态 CAS 要求所有写路径都带前置状态，任何一处直接 `UPDATE ... SET status = ...` 都会绕过保护。令牌适合防重复提交，不适合防重试，因为重试方通常拿不到新令牌。

判断幂等键是否合格，用一条标准：同一个业务动作在任意次重试中，键必须完全相同。下单用客户端生成的请求号，支付用订单号加支付请求号，消费用 `event_id` 加消费者标识。用时间戳、随机数、自增 ID 生成键，去重表就是摆设。

### 8.5 最大努力通知

对第三方渠道，通常无法要求对方重试到成功，只能用最大努力通知（Best Effort Notification）：按递增间隔反复通知，超过次数后停止，转为主动查询和对账。通知次数、间隔、终止条件要写进接口契约，不能靠调用方猜测。

### 8.6 边界

对账修复不了不可逆的副作用。券已核销、货已发出、积分已兑换，冲正只能补钱，不能补回业务状态。这类动作要在正向流程里加校验，而不是指望对账。

对账还受文件到达时间约束。渠道文件晚到时，批次要能等待并重跑，不能因为“当天没文件”就标记为无差异。

## 九、一致性状态机与运行手册

所有不一致最终都表现为状态机上的非法状态或停滞状态；把状态机设计好，排障就从“查数据”变成“查状态”。

### 9.1 状态机的四条规则

1. 单一写者：一个聚合实例在同一时刻只有一个服务能改它的状态；
2. 迁移受控：所有迁移走同一张迁移表，禁止散落的更新语句；
3. 迁移带守卫：每次迁移校验前置状态和业务条件，用 CAS 更新；
4. 中间态可枚举：每个非终态都有超时和下一跳。

```sql
UPDATE order_flow
   SET status = 'STOCK_RESERVED', version = version + 1
 WHERE order_no = ?
   AND status = 'CREATED'
   AND version = ?;
```

影响行数为 0 表示状态已被其他动作改变，调用方必须重新读取再决策，不能当作成功。

### 9.2 运行指标

| 指标 | 含义 | 告警阈值（示例） |
|---|---|---|
| 中间态存量 | 停留在非终态的单据数 | > 500 持续 10 分钟 |
| 中间态停留 P99 | 从进入到离开的时长 | > 5 分钟 |
| 补偿成功率 | Cancel 成功占比 | < 99% 持续 5 分钟 |
| 对账差异率 | 差异单 / 总单 | > 0.05% |
| 人工单量 | 转人工的工单数 | > 20 单/日 |

中间态存量要看“年龄分布”，不能只看总数。总数稳定但老单据堆积，说明有新单据在正常流转、老单据卡死，平均值会掩盖问题。

### 9.3 排障顺序

| 现象 | 第一条查询 | 判断 | 动作 |
|---|---|---|---|
| 订单停在待履约 | 查状态机迁移记录 | 最后事件是什么 | 重放事件或补单 |
| 库存与订单不符 | 查冻结流水与 outbox | 事件是否投递 | 重投或对账 |
| 重复扣款 | 查支付唯一键与去重表 | 幂等键是否一致 | 冲正 |
| 补偿一直失败 | 查补偿重试次数与错误码 | 参数错还是下游错 | 修参数或转人工 |

> 边界：不要在故障时手工改状态。手工改状态绕过了迁移守卫和版本号，会让后续事件无法判断当前状态，把小故障扩成数据事故。人工介入只能通过带审计的运维接口。

## 十、选型与失败模式

选型的顺序是“先缩小问题，再比较方案”，不是先列技术清单。

### 10.1 决策顺序

1. 能单库解决吗？能，用本地事务，结束。
2. 能用业务状态替代吗？预留、冻结、待确认能覆盖，用状态机加补偿。
3. 参与方都支持 XA 且事务短吗？是，考虑 2PC 或 AT。
4. 资源可预留吗？是，TCC；否，Saga。
5. 事件必须可靠外发吗？加 Outbox 或事务消息。
6. 资金或权益链路吗？无论前面选什么，加对账。

### 10.2 方案矩阵

| 方案 | 一致性 | 侵入性 | 适用场景 |
|---|---|---|---|
| 2PC / XA | 强 | 低 | 同机房短事务、多数据源 |
| TCC | 强（业务保证） | 高 | 可预留的库存、额度、权益 |
| Saga | 最终 | 中 | 长流程、跨组织、可补偿 |
| Outbox | 最终 | 中 | 可靠事件外发 |
| 事务消息 | 最终 | 低 | 已有事务消息中间件 |
| 对账 | 事后 | 低 | 所有资金与权益链路 |

### 10.3 失败模式

- 把最终一致当强一致用：下单后立刻查库存，读到旧值，判定为超卖。
- 没有幂等键：重试一次多扣一次，最后靠退款平账。
- 补偿写成反向业务：退款变删除支付单，审计链断裂。
- 只对金额不对状态：金额一致但一边成功一边失败，长期无人发现。
- 中间态没有超时：单据永久停在处理中，指标看不出来。
- 用消息队列当数据库：把消息当唯一事实源，重放后数据漂移。
- 全局事务跨了五个服务：任一抖动全链路回滚，可用性被乘积拉低。

### 10.4 决策清单

1. 不变量是什么，能否用数据库约束守住？
2. 允许的中间态和窗口分别是多少，谁检测？
3. 每个动作可重复吗，可反向吗，谁负责补偿？
4. 事件如何可靠外发，消费端如何去重？
5. 对账对比什么，差异分几类，哪类自动处理？
6. 人工兜底的入口在哪，是否有审计？

## 十一、最佳实践案例

### 11.1 案例背景

一家区域零售企业的订单履约链路覆盖订单、库存、优惠券、支付四个服务，日订单 80 万，峰值 1,200 TPS。改造前，订单创建与库存扣减在一个同步调用里完成，券核销紧随其后，支付走第三方渠道的异步回调。

现状是三类问题每月重复：大促超时后订单已创建但库存未扣，导致超卖；支付回调重复到达，产生重复入账；券核销成功但订单取消，券没有退回。运营每天花约 4 小时手工核对，财务每月对账差异在 0.3% 左右（示例数据）。

目标是六周内把不一致单量压到每日 20 单以内，人工处理降到 1 小时以内，且不能停机改造。约束有四项：第三方支付不支持 TCC，只能退款冲正；库存必须支持预留；优惠券可以回滚；财务要求 T+1 出对账结果。团队 9 人，其中熟悉事务框架的只有 2 人。

### 11.2 案例实操

第一步是收敛问题边界。团队把四个服务的数据按“是否必须强一致”重新分类，结论是库存扣减与订单状态必须强约束，券可以最终一致，支付只能异步加对账。原本计划的“全链路 TCC”被否掉，因为支付渠道无法预留，且 9 人团队维护四套 TCC 接口的风险高于收益。

| 选项 | 一致性 | 改造量 | 主要风险 |
|---|---|---|---|
| 全链路 2PC | 强 | 大，需 XA 改造 | 支付渠道不支持，长事务锁表 |
| 全链路 TCC | 强 | 很大，四个服务三接口 | 团队经验不足，支付无法预留 |
| 混合：TCC + Saga + Outbox | 分级 | 中 | 状态机与对账需自建 |
| 只加对账 | 事后 | 小 | 资损与客诉仍在 |

决策是混合方案：库存与券用 TCC 预留；订单到履约用 Saga 编排；订单状态变更事件用 Outbox 外发；支付走异步回调加主动查询，用对账兜底。理由是每个子问题用最便宜的手段解决，而不是让一个方案覆盖全部。

状态机先定，代码后写。履约单只允许八个状态，迁移表如下。

| 当前状态 | 事件 | 守卫 | 下一状态 |
|---|---|---|---|
| CREATED | 库存与券已预留 | 全部明细成功 | RESERVED |
| RESERVED | 支付已受理 | 金额一致 | PAYING |
| PAYING | 支付成功 | 渠道流水唯一 | PAID |
| PAYING | 支付失败 | 已确认失败 | COMPENSATING |
| PAID | 履约单已创建 | 仓库可分配 | FULFILLED |
| COMPENSATING | 库存与券已释放 | 补偿全部成功 | CANCELLED |
| 任意非终态 | 停滞超过 15 分钟 | 巡检触发 | MANUAL_REVIEW |

关键设计是把 `PAYING` 独立出来。支付受理后既不能算成功也不能算失败，必须有独立状态承载“等待渠道结果”，否则超时只能二选一，选错就是资损。

TCC 的控制表按第 4 章的结构建，库存分支的 Try 用条件更新冻结，Confirm 把冻结转已用，Cancel 退回可用。券分支复用同一张表，用 `branch_id` 前缀区分。空回滚写入 `CANCELLED` 占位，悬挂检查放在 Try 入口，两个逻辑共用一段状态迁移代码。

补偿动作先于代码定稿，每个正向动作都必须能查到对应的反向动作和失败去向。

| 正向动作 | 补偿动作 | 幂等键 | 补偿失败去向 |
|---|---|---|---|
| 冻结库存 | 释放冻结 | 订单号 + SKU | 重试 5 次后人工 |
| 锁定券 | 解锁券 | 订单号 + 券号 | 重试 5 次后人工 |
| 创建履约单 | 取消履约单 | 订单号 | 已出库转人工 |
| 发起支付 | 查单后冲正 | 支付请求号 | 次日对账批次 |

Outbox 与订单表同库，`aggregate_id` 用订单号，保证同一订单的事件进入同一分区。中继用轮询，每 200 毫秒拉一批 200 条，`FOR UPDATE SKIP LOCKED` 支持两个实例并行。事件契约固定六个字段，`version` 是聚合版本，消费端拒收版本回退的事件。

```json
{
  "event_id": "0f1c9a7e-6d2b-4c1a-9f30-5b7e2d8c4411",
  "event_type": "order.reserved",
  "aggregate_id": "SO202611130001",
  "version": 3,
  "occurred_at": "2026-11-13T10:21:33.412+08:00",
  "payload": { "stock_status": "FROZEN", "coupon_status": "LOCKED" }
}
```

消费端为每个消费者建去重表，`(consumer, event_id)` 为主键，与业务更新同事务提交。重复事件撞主键即视为已处理，直接提交位点，不再执行业务。

支付侧不接 TCC，改为三段：发起支付时落支付单（唯一键为订单号加支付请求号），回调按渠道流水号幂等入账，超过 30 秒未收到回调则主动查询渠道，查询仍无结果则保持 `PAYING` 并交给 T+1 对账。对账表按第 8 章的结构建，差异分五类，长短款自动补单或冲正，金额不符与已履约的短款转人工。

灰度按 5% → 20% → 50% → 100% 四批推进，每批观察三个指标：中间态存量、补偿成功率、对账差异率。任何一批的补偿成功率低于 99%，暂停并回滚开关。开关控制的是“是否走新链路”，不是数据开关，回滚后老链路的在途单由巡检继续处理。

演练做了四次：库存 Confirm 超时、券 Cancel 重复到达、Outbox 中继停机 10 分钟、支付回调重复。前两次验证幂等与空回滚，第三次验证积压恢复后的顺序与去重，第四次验证支付唯一键。每次演练都记录实际状态迁移序列，与设计表逐条比对。

### 11.3 案例结果

上线三个月后的数据如下（示例，来自内部周报口径）。

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 日不一致单量 | 约 300 | 8 到 15 |
| 人工处理时长 | 4 小时/日 | 0.4 小时/日 |
| 对账差异率 | 0.30% | 0.015% |
| 中间态停留 P99 | 无统计 | 780ms |
| 自动收敛占比 | 无 | 96% |

超卖从每月 3 到 5 起降到 0 起；重复入账未再发生；券未退回的工单从每月 40 单降到 2 单。代价是链路多了一次预留和一次确认，下单 P99 从 210ms 升到 290ms，仍在 300ms 的 SLO 内。

失败模式与复盘：

第一，首轮灰度出现悬挂。Cancel 先到并写入占位，Try 后到但没有查占位，冻结了一笔已取消的库存。修复是在 Try 入口加占位查询，并把演练用例补成“Cancel 先于 Try”的乱序场景。这类问题只能在设计阶段用状态表覆盖，测试很难自然触发。

第二，Outbox 中继停机 10 分钟后恢复，消费端出现重复处理。原因是去重表漏了一个消费者，该消费者只做了业务幂等，没有做事件幂等。补建去重表后，历史重复数据用对账脚本修正。结论是去重键必须由平台统一发放，不能由各消费者自行决定。

第三，支付主动查询把“渠道处理中”误判为失败，触发了一次不必要的补偿。修复是把渠道返回码映射成三态：成功、失败、未知，未知只能等待，不能进入补偿。这条规则后来写进了所有外部调用的接入规范。

第四，对账初期只对了金额，没有对状态，导致“金额一致但一边成功一边失败”的差错漏了两周。补上状态比对后，差异类型从三类扩到五类，人工单量先升后降。

复盘的核心结论是：混合方案的成本主要不在事务框架，而在状态机、幂等键和对账规则这三样“看起来不是事务”的东西。它们决定了故障时能否自动收敛，也决定了团队能不能在没有原作者的情况下继续维护。
