# 架构决策与ADR

> 这篇从“什么决策值得记录”讲起，经过 ADR 模板、状态生命周期、评审方式、治理指标和追溯链，再落到复审淘汰与组织落地，最后用一个完整治理案例收束。
>
> 学完能建立一套可评审、可追溯、可复审的决策记录机制，并在审计或人员更替时还原“当时为什么这样选”。

## 一、什么决策值得记录

架构决策记录（Architecture Decision Record，ADR）只记录“改了会很贵、后人会反复问为什么”的决策；把所有会议纪要都塞进去，等于没有记录。

### 1.1 决策的三个层级

同一个项目里的决策影响范围差别很大，记录方式也应不同。

| 层级 | 影响范围 | 寿命 | 记录方式 |
|---|---|---|---|
| 架构决策 | 多团队、多系统 | 季度到年 | ADR |
| 设计决策 | 单模块、单服务 | 周到月 | 设计文档、ADR 可选 |
| 实现决策 | 单文件、单函数 | 天 | 代码注释、提交信息 |

判断落在哪一层，看变更时需要谁参与：需要跨团队协调、需要改数据模型、需要改部署形态，基本属于架构层。

> 边界：架构层不等于“技术含量高”。选消息队列是架构决策，选某个队列客户端版本不是；定数据归属是架构决策，定表索引不是。

### 1.2 决策门槛四问

四个问题里任意两个为“是”，就值得写 ADR。

| 问题 | 判断依据 |
|---|---|
| 影响多个团队吗 | 需要跨团队排期或改接口 |
| 改错后难回退吗 | 涉及数据迁移、公开契约、客户端兼容 |
| 成本显著吗 | 超过一个人月或持续产生费用 |
| 后人会问为什么吗 | 存在多个合理选项，结论不显然 |

反例：日志级别从 INFO 调到 WARN、把超时从 3 秒调到 5 秒、选择 JSON 序列化库。这些改动可逆、影响单模块，写进提交信息即可。

正例：数据库从单库改为分库分表、公开 API 增加版本、服务边界重划、引入事件驱动替代同步调用、多租户从共享库改为独立库。

### 1.3 记录成本与不记录的代价

一条 ADR 的写作成本约 30 到 60 分钟，评审约 15 分钟。不记录的代价在半年后出现：新人重提已被否决的方案、事故复盘找不到原始假设、审计无法证明决策经过评估。

| 项目 | 有 ADR | 无 ADR |
|---|---|---|
| 决策形成 | 30 到 60 分钟 | 会议照开，结论不留 |
| 重复讨论 | 可引用历史结论 | 每季度重来一次 |
| 新人上手 | 按索引读 5 到 10 条 | 口头传承，版本不一 |
| 审计举证 | 直接导出 | 翻聊天记录 |
| 事故复盘 | 可对照假设 | 只能猜 |

数字为经验值。真正的差距在“重复讨论”：一个 10 人团队每季度为同一议题开两次会，一年就是 80 人时，足够写几十条 ADR。

### 1.4 ADR 与设计文档的分工

ADR 记录一个决策及其理由，设计文档描述一个方案怎么实现。两者不能互相替代。

| 文档 | 回答 | 长度 | 变更方式 |
|---|---|---|---|
| ADR | 为什么选它，放弃了什么 | 1 到 2 页 | 新增取代，不改写历史 |
| 设计文档 | 怎么实现，接口与数据 | 5 到 30 页 | 随实现迭代 |
| 运行手册 | 怎么部署、怎么排障 | 按需 | 随环境更新 |

ADR 不写类图和完整接口定义；设计文档不承担“为什么否决另外三个方案”的职责。混在一起，两份都会过期。

## 二、ADR 模板

模板的价值是保证关键信息不缺项，不是保证每篇都一样长；背景、决策、备选、后果四块不能省。

### 2.1 最小可用模板

```markdown
# ADR-0007 订单查询采用读写分离

- 状态：已接受（Accepted）
- 日期：2026-11-13
- 决策者：订单平台组
- 关联：OPS-142、PR-318

## 背景

订单查询 P99 在峰值达到 800 ms，主库 CPU 长期高于 80%。
查询与写入比为 12:1，数据量 400 GB，未来 12 个月预计增长 60%。

## 决策

查询流量走只读副本，写入走主库。
副本延迟超过 3 秒时，查询降级读主库。
写后立即读的请求显式路由到主库。

## 备选方案

1. 加缓存：订单状态变化频繁，命中率预计低于 60%。
2. 分库分表：当前数据量未到瓶颈，迁移需要 3 个月。
3. 读写分离：改造 3 周，能覆盖读多写少的主要矛盾。

## 后果

- 需要处理副本延迟与读一致性，增加降级逻辑。
- 需要监控复制延迟、降级次数、主库回切流量。
- 数据量继续增长后仍需分库分表，本决策不替代后续拆分。
```

四块内容对应四个问题：发生了什么、选了什么、还考虑过什么、要付出什么。

### 2.2 背景写事实与约束

背景只写可核实的事实：指标、数据量、时间点、合同要求、团队规模。不写“系统比较慢”“业务发展迅速”这类判断。

| 写法 | 问题 | 改法 |
|---|---|---|
| 系统性能很差 | 无法验证 | P99 800 ms，峰值 200 QPS |
| 业务增长很快 | 无法量化 | 12 个月数据增长 60% |
| 团队人手不足 | 无边界 | 后端 6 人，无专职运维 |
| 必须高可用 | 形容词 | 合同要求月度可用率 99.9% |

背景里要写明约束来源：合同、法规、预算、遗留系统、组织架构。约束来源决定后续能不能推翻这条决策。

### 2.3 决策写一句可执行的话

决策段用主动语态写“做什么、做到什么范围、例外怎么处理”，不写“建议考虑”“倾向于”。

| 要素 | 示例 |
|---|---|
| 动作 | 查询走只读副本 |
| 范围 | 订单查询 API 的列表与详情 |
| 例外 | 写后 5 秒内的读走主库 |
| 降级 | 副本延迟超过 3 秒切主库 |

“采用读写分离”不是决策，是方向；“查询走只读副本，写后 5 秒内读主库，副本延迟超过 3 秒全量降级”才是可执行、可验收的决策。

### 2.4 备选方案写清代价

备选段不是凑数，要写清每个方案被否决的具体原因。至少两个备选，包含“什么都不做”。

| 备选 | 保留原因 | 否决原因 |
|---|---|---|
| 加缓存 | 改造成本最低 | 命中率不稳定 |
| 分库分表 | 彻底解决容量 | 周期长，当前未到瓶颈 |
| 读写分离 | 成本与收益匹配 | 选中，代价是延迟与一致性 |
| 维持现状 | 无改造风险 | 峰值已影响下单 |

否决原因要能对应背景里的约束。如果否决理由只是“感觉不合适”，说明调研还没完成。

### 2.5 后果写代价与后续

后果段同时写正面、负面和后续动作。只写好处的 ADR 不可信，后人也无法判断什么时候该复审。

| 类型 | 内容 |
|---|---|
| 正面 | 读压力从主库移出，查询 P99 下降 |
| 负面 | 引入副本延迟与读不一致 |
| 运维 | 新增复制延迟、降级次数监控 |
| 后续 | 数据量到 1 TB 时启动分库分表评估 |

### 2.6 模板选型

| 模板 | 结构 | 适用 |
|---|---|---|
| Nygard | 背景、决策、状态、后果 | 快速起步 |
| MADR | 增加备选、比较、确认 | 需要评审留痕 |
| 自定义 | 按组织字段扩展 | 有审计要求 |

MADR（Markdown Any Decision Records）是 2026 年仍常用的开源模板，核心结构与 Nygard 一致，多了“备选方案”和“决策驱动因素”两段。

```markdown
# ADR-0012 采用事件驱动同步库存

- 状态：提议（Proposed）
- 日期：2026-11-13
- 决策者：库存组、订单组
- 驱动因素：峰值解耦、下游可重放、发布独立

## 背景与问题

大促峰值下单 5,000 单/分钟，同步扣减库存在 3 个下游服务上串行等待，
P99 从 180 ms 上升到 1.2 s，任一下游超时都会导致下单失败。

## 决策驱动因素

- 下单成功率必须高于 99.9%
- 库存不允许超卖
- 下游新增不能修改下单主流程

## 备选方案

1. 同步调用加长超时：实现简单，故障放大。
2. 本地消息表加事件：最终一致，需幂等。
3. 直接引入事件溯源：改造成本最高。

## 决策

下单只写本地库存与发件箱，库存变更事件异步投递；
下游按订单号幂等消费；超卖由库存预占与对账兜底。

## 后果

- 正面：下单与下游解耦，峰值不再被下游拖垮。
- 负面：下游数据存在秒级延迟，需要一致性对账。
- 风险：重复消费、消息积压、事件契约变更。
```

模板确定后不要频繁改字段。字段每变一次，历史 ADR 的可比性就下降一次。

## 三、状态与生命周期

ADR 的状态表达“这条决策现在是否有效”，不是文档的编辑进度；状态错了，比没有状态更危险。

### 3.1 五个状态

| 状态 | 含义 | 是否可执行 |
|---|---|---|
| 提议（Proposed） | 已提交，未评审完 | 否 |
| 已接受（Accepted） | 评审通过，生效 | 是 |
| 已拒绝（Rejected） | 评审否决 | 否 |
| 已弃用（Deprecated） | 仍有效但不再推荐 | 是，逐步退出 |
| 被取代（Superseded） | 已被新 ADR 替代 | 否，看新 ADR |

“已弃用”和“被取代”容易混。弃用是决策仍然有效、但计划退出；被取代是新决策已经生效、旧决策失效。前者保留过渡期，后者必须给出新编号。

### 3.2 状态转换规则

| 从 | 到 | 条件 | 谁操作 |
|---|---|---|---|
| 提议 | 已接受 | 评审通过并记录意见 | 决策者 |
| 提议 | 已拒绝 | 评审否决并写明原因 | 决策者 |
| 已接受 | 已弃用 | 出现更好方案但未切换 | 决策者 |
| 已接受 | 被取代 | 新 ADR 生效 | 新 ADR 作者 |
| 已弃用 | 被取代 | 替代方案落地 | 新 ADR 作者 |
| 任何状态 | 提议 | 不允许，另开新 ADR | 无 |

不允许把“被取代”改回“已接受”。历史结论可以纠正，但要用新 ADR 说明纠正理由，不能改写旧记录。

### 3.3 取代关系与编号

编号一经分配不复用，即使 ADR 被拒绝或删除。编号是追溯锚点，复用会让工单、代码注释、审计记录指向错误对象。

```text
ADR-0007 订单查询采用读写分离        状态：被取代
  superseded-by: ADR-0021
ADR-0021 订单查询改为分库分表        状态：已接受
  supersedes: ADR-0007
```

双向链接必须同时写。只写单向链接，从旧记录找不到新结论，从新记录也说不清替代了什么。

### 3.4 状态漂移

状态漂移是“文档写着已接受，实际方案已经换了”的状态。它比没有 ADR 更有害，因为读者会相信错误结论。

| 漂移表现 | 检测方式 | 修复 |
|---|---|---|
| 代码与决策不符 | 架构守护测试失败 | 补新 ADR 或回退代码 |
| 状态长期为提议 | 超过评审 SLA 未处理 | 排期评审或关闭 |
| 已弃用无替代 | 索引中无 superseded-by | 补替代方案或恢复 |
| 被取代仍被引用 | 检索旧编号的引用 | 更新引用与文档 |

治理动作是每月跑一次状态巡检：提议超过 14 天、已接受超过 12 个月未复审、被取代缺少链接，三类都列入清单。

### 3.5 状态与发布同步

ADR 状态变更应与发布流程绑定，而不是靠记忆。

- 决策评审通过后，状态改“已接受”，同时创建实施工单；
- 实施完成并验证后，在 ADR 追加上线日期与验证结果；
- 方案回退时，状态改“已弃用”，写明回退原因；
- 新方案上线当周，旧 ADR 改“被取代”，补双向链接。

把这几步写进发布检查清单，状态漂移会显著减少。

## 四、ADR 的评审

评审的目标是暴露约束冲突和未验证假设，不是让所有人同意；没有评审的 ADR 只是个人笔记。

### 4.1 评审触发条件

| 条件 | 评审形式 |
|---|---|
| 跨两个以上团队 | 正式评审，30 分钟 |
| 涉及数据迁移或公开契约 | 正式评审加数据方案 |
| 成本超过一个人月 | 正式评审加预算确认 |
| 单团队内部、可逆 | 异步评审，48 小时窗口 |
| 紧急故障处置 | 先执行，48 小时内补 ADR |

紧急决策不能因为“来不及写”而跳过记录。补记时要区分“当时已知”和“事后补充”，避免把事后合理化写进背景。

### 4.2 角色与时间盒

| 角色 | 职责 | 时间 |
|---|---|---|
| 决策者 | 提出方案，最终拍板 | 全程 |
| 记录人 | 维护 ADR 与评审纪要 | 全程 |
| 受影响团队代表 | 提出约束与成本 | 30 分钟 |
| 平台或运维 | 评估运行与值班影响 | 30 分钟 |
| 安全或合规 | 评估数据与审计要求 | 按需 |

正式评审控制在 30 分钟：5 分钟讲背景，10 分钟讲选项与取舍，10 分钟提问，5 分钟确认结论与待办。超过 45 分钟通常说明背景材料没提前发。

### 4.3 评审清单

1. 要解决的问题是否有数据支撑，而不是感受？
2. 约束是否完整：预算、人力、合规、遗留系统、时间窗口？
3. 是否至少有两个真实备选，包含“维持现状”？
4. 每个备选的代价是否量化，谁承担？
5. 决策是否可执行，范围和例外是否写清？
6. 失败信号是什么，多久能看到？
7. 回退方案是否存在，回退需要多久？
8. 数据迁移与兼容性是否评估？
9. 运维、监控、值班影响是否确认？
10. 状态、负责人、复审时间是否确定？

十条里任意三条答不上来，结论应是“补充材料后再评审”，不是“先通过再说”。

### 4.4 轻量评审与 ATAM

ATAM（Architecture Tradeoff Analysis Method）是重量级架构权衡分析方法，适合高风险、多利益方的系统。日常 ADR 用轻量评审即可。

| 维度 | 轻量评审 | ATAM |
|---|---|---|
| 时长 | 30 分钟 | 1 到 3 天 |
| 参与 | 3 到 6 人 | 10 人以上 |
| 输入 | 一条 ADR | 质量属性场景集 |
| 输出 | 结论与待办 | 风险、敏感点、权衡点 |
| 适用 | 日常决策 | 核心系统、重大改造 |

判据是“决策错了会不会影响一个季度以上”。会，用 ATAM 或至少做一次完整场景评审；不会，轻量评审足够。

### 4.5 分歧处理

评审不需要达成一致，但必须明确谁拍板、谁保留意见、何时复核。

| 情况 | 处理 |
|---|---|
| 技术分歧无数据 | 设一周原型验证，带数据再议 |
| 成本分歧 | 拆成最小可行范围，分期决策 |
| 团队利益冲突 | 上升到共同上级，记录各方意见 |
| 合规一票否决 | 合规意见优先，记录约束来源 |
| 仍无法决定 | 选可逆性最高的方案，设复审点 |

“不同意但执行”（disagree and commit）要写进 ADR：保留意见、保留人、复核条件。没有复核条件，保留意见会变成长期消极抵抗。

### 4.6 评审记录

评审结论写进 ADR 的“评审记录”段，不另开会议纪要。

```markdown
## 评审记录

- 2026-11-13 评审通过，参与：订单组、DBA、SRE。
- 保留意见：DBA 认为副本延迟告警阈值 3 秒偏松，建议 1 秒。
- 结论：阈值先按 3 秒上线，两周后按实际延迟分布调整。
- 待办：补复制延迟看板（OPS-151），两周后复审。
```

保留意见与待办是复审的输入。只写“评审通过”，等于把评审过程丢了。

## 五、治理指标

治理指标用来判断 ADR 机制是否在工作，不用来考核个人；指标一旦变成考核，记录就会变成表演。

### 5.1 指标集

| 指标 | 定义 | 用途 |
|---|---|---|
| 覆盖率 | 符合条件的决策中有 ADR 的比例 | 判断机制是否落地 |
| 决策前置时间 | 从提出到状态确定的中位天数 | 判断评审效率 |
| 复审及时率 | 到期 ADR 按期复审的比例 | 判断是否过期 |
| 取代率 | 每年被取代的 ADR 占比 | 判断假设是否失效 |
| 引用率 | 被工单、代码、文档引用的比例 | 判断是否有人用 |

指标不求多，五个足够。超过十个，采集成本会超过收益。

### 5.2 定义与采集

| 指标 | 采集方式 | 口径 |
|---|---|---|
| 覆盖率 | 架构评审清单对照 | 季度抽样 |
| 前置时间 | ADR 日期与状态变更时间 | 中位数，不看均值 |
| 复审及时率 | 索引中的复审日期 | 到期 30 天内 |
| 取代率 | 状态为被取代的数量 | 滚动 12 个月 |
| 引用率 | 检索 ADR 编号 | 抽样 20 条 |

覆盖率最难采集，建议用“季度架构变更清单”反查：列出当季跨团队变更，逐条看是否有 ADR。抽样比全量统计更可持续。

### 5.3 阈值与动作

| 指标 | 健康区间 | 低于区间 | 高于区间 |
|---|---|---|---|
| 覆盖率 | 70% 到 90% | 补培训与模板 | 可能记录过细 |
| 前置时间 | 3 到 10 天 | 评审过轻 | 流程太重 |
| 复审及时率 | 80% 以上 | 设季度复审日 | 复审形式化 |
| 取代率 | 10% 到 30% | 假设未复核 | 方向不稳定 |
| 引用率 | 40% 以上 | 索引与培训不足 | 可能过度引用 |

区间为经验值。覆盖率 100% 通常意味着把设计决策也算进去了，反而稀释了架构记录的价值。

### 5.4 反指标

以下信号说明机制在空转，需要调整而不是加码：

- ADR 数量增长快，但引用率接近零；
- 评审全员举手，没人提约束；
- 每条 ADR 都写“无备选方案”；
- 状态长期停在提议，无人处理；
- 复审记录只有“仍然有效”四个字。

反指标比正指标更早暴露问题。看到“无备选方案”反复出现，先查模板是否要求了备选，再查评审是否真的在看。

## 六、追溯

追溯要能回答“这个需求为什么变成这段代码、这个监控为什么存在”；断在任何一环，审计和复盘都要靠人回忆。

### 6.1 追溯链

```text
需求 / 质量属性场景
  → ADR（决策与取舍）
    → 设计文档 / 接口契约
      → 代码 / 配置 / 基础设施定义
        → 测试 / 监控 / 告警
          → 事故复盘 / 复审记录
```

链路不需要每个环节都双向引用，但 ADR 必须能向上找到需求或场景，向下找到实施工单与验证证据。

### 6.2 仓库布局

ADR 与代码同仓，评审和变更才能在同一套权限与历史里完成。

```text
repo/
├── docs/
│   └── adr/
│       ├── README.md          # 索引与状态总表
│       ├── template.md        # 模板
│       ├── 0001-record-architecture-decisions.md
│       ├── 0007-read-write-split.md
│       └── 0021-shard-order-table.md
├── src/
└── deploy/
```

文件名用“编号加短横线加英文短语”，避免中文文件名在不同系统上的编码差异。标题可以是中文，文件名保持可检索。

### 6.3 命名与索引

索引表是追溯入口，必须随 ADR 增删同步更新。

| 编号 | 标题 | 状态 | 复审日期 |
|---|---|---|---|
| 0001 | 采用 ADR 记录架构决策 | 已接受 | 2027-11 |
| 0007 | 订单查询采用读写分离 | 被取代 | 已由 0021 替代 |
| 0021 | 订单查询改为分库分表 | 已接受 | 2027-06 |

索引只放四列，详细信息在各自文件里。索引超过一屏，检索价值会下降。

### 6.4 关联工单、代码与监控

| 关联对象 | 写法 | 作用 |
|---|---|---|
| 工单 | ADR-0007 | 实施背景可查 |
| 代码 | 注释引用 ADR 编号 | 修改前先读决策 |
| 配置 | 注释写约束来源 | 防止参数被随意改 |
| 监控 | 告警说明链接 ADR | 解释阈值依据 |
| 事故 | 复盘引用 ADR | 判断是假设错误还是执行偏差 |

代码里只引用编号，不复制整段理由。复制会过期，编号不会。

### 6.5 检索与审计

```bash
# 查出所有仍有效的决策
grep -rl "状态：已接受" docs/adr | sort

# 找出被取代但缺少新编号的旧记录
grep -rl "状态：被取代" docs/adr | xargs grep -L "superseded-by"

# 找出到期未复审的 ADR（按索引日期人工核对）
grep "复审" docs/adr/README.md
```

审计场景通常要求三样东西：决策时间、参与人、备选方案。ADR 模板里的日期、决策者、备选段正好对应；缺一项，举证就要靠补充说明。

## 七、复审与淘汰

ADR 不是一次性文档；假设变化后不复审，旧结论会以“历史决定”的名义阻止正确变更。

### 7.1 复审触发条件

| 触发 | 说明 | 响应 |
|---|---|---|
| 到期 | 索引中的复审日期到达 | 季度批量复审 |
| 容量变化 | 数据量或流量超出假设 50% | 30 天内复审 |
| 组织变化 | 团队合并、拆分、外包 | 60 天内复审 |
| 技术变化 | 依赖版本停止维护 | 立即评估 |
| 事故 | 故障根因涉及该决策 | 复盘时同步复审 |

时间是兜底，事件才是主触发。只靠年度复审，容量早就翻倍了。

### 7.2 复审流程

复审控制在 30 分钟，输出三种结论之一：继续有效、修订、取代。

1. 读背景与假设，确认哪些已变化；
2. 对照当前指标，判断假设是否仍成立；
3. 检查后果是否出现，监控是否覆盖；
4. 给出结论与下一步，更新状态与复审日期；
5. 需要取代时，当场指定新 ADR 负责人与截止时间。

复审记录写在原 ADR 末尾，保留历史，不覆盖原文。

```markdown
## 复审记录

- 2027-05-20 复审：数据量 780 GB，未达 1 TB 触发线。
- 结论：继续有效，复审日期调整为 2027-11。
- 备注：副本延迟告警阈值已从 3 秒调整为 1 秒。
```

### 7.3 淘汰与取代

淘汰分三种：被取代、弃用后删除、转为普通设计文档。

| 方式 | 适用 | 处理 |
|---|---|---|
| 被取代 | 有新决策生效 | 双向链接，旧记录保留 |
| 弃用 | 方案退出但无替代 | 状态改弃用，写下线与日期 |
| 转文档 | 不再是架构决策 | 移入设计文档，ADR 标弃用 |

ADR 原则上不删除。删除会让历史工单和代码注释指向空链接。确需清理时，保留文件并在首行标注“已归档，内容不再维护”。

### 7.4 归档

归档解决索引膨胀，不解决有效性判断。

- 超过 5 年且已失效的 ADR 移入 `archive/` 子目录；
- 索引保留一行，状态标“已归档”；
- 归档文件不参与日常检索，但保留完整内容；
- 归档前确认没有代码或监控仍在引用。

## 八、组织落地

ADR 机制失败通常不是模板问题，而是没有固定节奏和明确 owner；先跑通一条决策，再推广。

### 8.1 五周落地计划

| 阶段 | 动作 | 产出 |
|---|---|---|
| 第 1 周 | 选一个正在进行的决策做试点 | 一条完整 ADR |
| 第 2 周 | 定模板、编号、仓库位置 | 模板与索引 |
| 第 3 周 | 建 30 分钟评审节奏 | 评审日历 |
| 第 4 周 | 回填 3 到 5 条历史决策 | 初始索引 |
| 第 5 周 | 收集反馈，调整字段 | 模板 v2 |

回填只选仍会影响当前工作的决策，不要试图补齐三年历史。回填十条里八条没人看，是常见浪费。

### 8.2 角色分工

| 角色 | 职责 | 投入 |
|---|---|---|
| 架构负责人 | 定门槛、主持评审、处理分歧 | 每周 2 小时 |
| 记录人 | 维护模板、索引、状态 | 每周 1 小时 |
| 团队 Tech Lead | 提出 ADR、执行评审结论 | 按需 |
| 平台组 | 评估运维与成本影响 | 评审时 30 分钟 |

不需要专职架构师。40 人规模下，架构负责人每周 2 小时足够维持机制；再少，评审会排不上。

### 8.3 常见阻力

| 阻力 | 真实原因 | 对策 |
|---|---|---|
| 没时间写 | 模板太重 | 用最小模板，先写四段 |
| 写了没人看 | 没有索引与引用 | 发布检查清单加引用 |
| 评审变批斗 | 角色不清 | 明确决策者与时间盒 |
| 结论总是通过 | 没有问题清单 | 用十条清单逐项问 |
| 历史包袱太多 | 试图全量回填 | 只回填仍有效的 |

“没时间”通常不是时间问题，是不知道写什么。给一个填好的例子，比再发一次规范有效。

### 8.4 模板治理

模板每半年评审一次，改动遵循三条：

- 只加被证明缺失的字段，不因个别案例加字段；
- 新字段必须能对应一个评审问题；
- 模板变更不追溯修改历史 ADR。

模板版本写在 `template.md` 顶部，历史 ADR 保持原样。模板频繁变更会让索引无法比较。

## 九、失败模式与检查清单

ADR 的价值在“可追溯的取舍”，不在文档数量；以下失败模式比缺文档更常见。

### 9.1 失败模式

| 失败模式 | 表现 | 纠正 |
|---|---|---|
| 会议纪要化 | 记录讨论过程，没有结论 | 只留决策、备选、后果 |
| 只写好处 | 后果段为空 | 强制写负面与风险 |
| 没有备选 | 只有一条路 | 补维持现状与替代方案 |
| 状态漂移 | 文档与代码不符 | 月度巡检与守护测试 |
| 评审形式化 | 全员同意，无人提问 | 用清单逐项确认 |
| 编号复用 | 新旧记录指向同一编号 | 编号只增不复用 |
| 过度记录 | 每个参数都写 ADR | 用四问门槛过滤 |
| 归档即删除 | 历史链接失效 | 归档保留文件 |

### 9.2 上线前检查清单

1. 背景是否有数据与约束来源？
2. 决策是否写了范围、例外与降级？
3. 是否至少两个备选，包含维持现状？
4. 后果是否写了负面与后续动作？
5. 状态、决策者、复审日期是否齐全？
6. 是否与相关工单、代码、监控建立链接？
7. 受影响团队是否评审并留下意见？
8. 失败信号与回退方案是否明确？
9. 索引是否更新？
10. 是否安排了首次复审时间？

十项全过再合并。缺项不是格式问题，是后人无法判断决策是否仍成立。

## 十、最佳实践案例

### 10.1 案例背景

一家支付清结算平台，25 名工程师分 3 个小组，18 个月内经历两次核心改造。决策长期散落在即时消息、会议纪要和代码注释里，同一议题平均每月重复讨论 5 次；一次数据库选型在半年内被推翻两次，但没人说得清第一次为什么被否。

外部审计要求：涉及资金与个人信息的架构变更，必须能提供决策时间、参与人、备选方案与风险评估。现状是 6 项无法举证。团队没有专职架构师，代码托管在自建 GitLab，三个小组分布在两个时区。

约束是：不能增加专职岗位；评审时间每周不超过 1 小时；历史决策只回填仍影响当前工作的部分；审计截止在 3 个月内。

审计方的取证要求可以写成一条可验证场景：

```text
来源：外部审计员
刺激：抽查一次数据库选型变更
制品：架构决策记录库
环境：决策已上线 8 个月，原参与人已转岗
响应：提供决策时间、参与人、备选方案、风险与验证记录
度量：10 分钟内完成检索与举证，缺失项为 0
```

### 10.2 案例实操

候选方案对比：

| 选项 | 代价 | 主要风险 |
|---|---|---|
| 建 Wiki 决策库 | 低 | 与代码分离，易过期 |
| 设架构委员会 | 高 | 排期慢，成为瓶颈 |
| 仓库内 ADR 加周评审 | 中 | 依赖记录人坚持 |
| 只补审计材料 | 低 | 解决一次，机制不成立 |

决策是仓库内 ADR 加每周 30 分钟评审，不设委员会；架构负责人由清算组 Tech Lead 兼任，每周投入 2 小时。

执行步骤：

1. 采用 Nygard 四段模板，增加“决策者、关联工单、复审日期”三个字段；模板控制在 1 页内。
2. 在 `docs/adr/` 建目录与索引，编号从 0001 开始，文件名用英文短语。
3. 选正在进行的“结算批次改为事件驱动”做试点，完整走一遍提出、评审、接受、实施、验证。
4. 回填 8 条仍影响当前工作的历史决策，其中 3 条补写时明确标注“事后整理”，与当时记录区分。
5. 把 ADR 编号写进发布检查清单：涉及跨团队接口或数据变更的合并请求，必须引用 ADR。
6. 每月最后一周做状态巡检：提议超过 14 天、已接受超过 12 个月、被取代缺链接，三类列清单。
7. 每季度末用 30 分钟批量复审到期 ADR，结论只有继续有效、修订、取代三种。

评审采用十条清单，重点问三个问题：约束是否完整、备选是否真实、失败信号是什么。第一次评审时，“结算批次改事件驱动”因缺少重复消费预案被退回补充，第二次才通过。

### 10.3 案例结果

运行 6 个月后的指标如下，均为示例数据：

| 指标 | 实施前 | 实施后 |
|---|---:|---:|
| 决策前置时间 | 9 天 | 3 天 |
| 同一议题月均重复讨论 | 5 次 | 1 次 |
| 审计可举证项 | 14/20 | 20/20 |
| ADR 覆盖率 | 0 | 88% |
| 到期复审及时率 | 无 | 82% |
| 被引用 ADR 占比 | 0 | 46% |

复盘有四点。第一，收益最大的是索引与引用，不是模板；工程师在合并请求里看到编号，才会去读。第二，回填 8 条中有 2 条从未被引用，说明“仍影响当前工作”的判断偏乐观，回填范围还应更窄。第三，首版模板要求写“决策驱动因素”，实际填写率只有 30%，第二版并入背景段后填写率升到 90%。第四，季度复审一度变成“仍然有效”的盖章，后来要求每次复审必须带一个当前指标，才恢复有效性。

失败模式也记录在案：上线第二个月，一条“已接受”的 ADR 与代码不一致，原因是实施时改了方案但没更新记录；巡检发现后补了新 ADR 取代旧记录，并把“方案变更必须同步 ADR”写进发布检查清单。另有一次评审因参与人缺席导致两次流会，之后改为提前 48 小时发材料、缺席默认异步留言，评审不再因一人改期。
