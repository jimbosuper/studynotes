# 应用安全架构

> 这篇从资产识别与信任边界讲起，经过 STRIDE 威胁建模、身份认证、会话管理、多租户授权、数据分级与密钥管理、审计日志，最后落到供应链门禁和一次完整的安全架构决策案例。
>
> 学完能为一个系统画出信任边界、建出威胁模型、定义认证授权与密钥方案，并留下一张可执行的安全上线清单。

## 一、资产与信任边界

安全架构的第一步不是选工具，是回答"保护什么、防谁"。资产识别和信任边界划分决定后面所有机制的位置。

### 1.1 资产识别：先列清单再谈防护

没有资产清单的安全设计是空转。一张最小资产表至少覆盖：数据资产（用户资料、订单、支付凭据）、凭据资产（密钥、令牌、证书）、能力资产（管理员操作、资金操作）、可用性资产（核心交易链路）。

| 资产类型 | 示例 | 泄露后果 | 篡改后果 |
|---|---|---|---|
| 用户身份数据 | 手机号、身份证号 | 隐私违规、撞库 | 冒充他人 |
| 支付凭据 | 卡号、协议号 | 资损 | 资损 |
| 业务数据 | 订单、库存 | 竞争损失 | 错误发货、对账失败 |
| 系统凭据 | 数据库口令、API Key | 内网横移 | 数据被改 |
| 核心链路可用性 | 下单、支付 | 收入损失 | 超卖、重复支付 |

> 边界：资产识别不做完，渗透测试和告警都会漏。清单不要求一次列全，但每季度要和业务对一次，新业务上线时必须先过这张表。

### 1.2 信任边界：攻击面在哪里，边界就在哪里

信任边界（Trust Boundary）是"数据或控制的信任程度发生变化"的位置：从公网进入内网、从网关进入服务、从用户会话进入后台任务、从服务进入数据库，每跨一次边界都要有校验。跨边界的数据默认不可信，这就是零信任（Zero Trust）的出发点。

一个典型电商系统的信任边界与校验点：

| 边界 | 位置 | 必须校验 |
|---|---|---|
| 互联网 → CDN/WAF | 入口 | IP 信誉、请求合法性 |
| CDN → 网关 | 网关 | TLS、请求签名、限流 |
| 网关 → 微服务 | 服务间 | 身份令牌、权限 |
| 服务 → 数据库 | 存储 | 最小权限账号、SQL 审计 |
| 内网 → 第三方 | 出口 | 出站白名单 |

> 最容易错在两处：一是把内网当作可信，服务间调用不校验身份，一台失陷主机横移全内网；二是把第三方回调当作可信，直接信任回调报文里的金额。

## 二、威胁建模：STRIDE

威胁建模（Threat Modeling）回答"攻击者会怎么打这个系统"。STRIDE 把威胁分成六类，按数据流图逐个边界过一遍，比凭经验想更全。

### 2.1 STRIDE 六类威胁与对策

| 威胁 | 字母 | 违反的属性 | 示例 | 首选对策 |
|---|---|---|---|---|
| 假冒 Spoofing | S | 认证 | 拿到别人的会话令牌 | 强认证、短时效令牌 |
| 篡改 Tampering | T | 完整性 | 改请求里的金额 | 签名、HMAC、事务 |
| 抵赖 Repudiation | R | 不可否认 | 管理员删了数据不认 | 审计日志 |
| 信息泄露 Information | I | 机密性 | 接口返回别人的订单 | 授权检查、脱敏 |
| 拒绝服务 DoS | D | 可用性 | 恶意刷短信接口 | 限流、配额、验证码 |
| 提权 Elevation | E | 授权 | 普通用户调管理员 API | 服务端授权、最小权限 |

### 2.2 按 DFD 建模的操作步骤

先画数据流图（Data Flow Diagram，DFD）：进程、数据存储、外部实体、数据流；再对每条跨越信任边界的数据流套 STRIDE 六问；最后按风险排序，只修"发生概率 × 影响"值得修的项。

操作顺序：

1. 画图：进程（服务）、存储（DB/缓存/对象存储）、外部（用户/第三方）、数据流。
2. 标边界：把第一章的信任边界画在数据流上。
3. 六问：对每个进程和每条跨界数据流，问 STRIDE 各类有没有可能发生。
4. 定级：用高/中/低排威胁优先级，明确"接受"的项。
5. 落 ADR：对策（限流、签名、授权）进需求和上线清单。

一次支付下单链路的建模结果（示例）：

| 编号 | 威胁 | 类别 | 对策 | 状态 |
|---|---|---|---|---|
| T1 | 网关重放下单请求多扣款 | 篡改/DoS | 幂等键 + 时间窗口 | 已落地 |
| T2 | 支付回调伪造 | 假冒 | 验签 + 白名单回调源 | 已落地 |
| T3 | 订单号遍历查他人订单 | 泄露 | 资源级授权 + 脱敏 | 已落地 |
| T4 | 短信接口被刷 | DoS | 图形验证码 + 每日配额 | 已落地 |
| T5 | 内部员工导出全量手机号 | 泄露 | 数据分级 + 行级审批 | 已落地 |
| T6 | 后台操作无法追责 | 抵赖 | 审计日志不可删改 | 已落地 |

> 边界：威胁建模不是文档仪式。做完后必须留下两样东西：威胁清单（含已接受风险）和进入上线清单的对策项。威胁建模在架构评审时做一次，大改版再更新。

### 2.3 威胁建模的时机与产出

威胁建模不是一次性文档，它在四个时点触发：新系统架构评审、新增外部接口、新增数据出境/导出、重大依赖变更。每次产出一张威胁清单和一张对策表，对策必须落到需求编号和上线清单项。

| 时点 | 关注 | 产出 |
|---|---|---|
| 架构评审 | 信任边界、数据流 | 威胁清单 v1 |
| 新外部接口 | 假冒、篡改 | 验签与限流方案 |
| 数据导出 | 泄漏、抵赖 | 分级与审批 |
| 依赖大改 | 供应链 | SBOM 与扫描门禁 |

## 三、身份认证：证明你是谁

认证（Authentication）解决"这个请求来自哪个主体"。架构上关心的不是某个登录页怎么写，而是身份凭证的强度、流转和生命周期。

### 3.1 认证因子的组合

认证因子分三类：所知（口令）、所有（手机、令牌、证书）、所是（生物特征）。企业系统的底线是口令系统本身要按 OWASP ASVS 的要求实现，而不是自己发明加密。

| 场景 | 最低要求 | 增强手段 |
|---|---|---|
| C 端登录 | 口令 bcrypt/argon2 哈希、防撞库 | 短信/OTP 二次因子 |
| 管理后台 | 口令 + TOTP 动态码 | 硬件密钥（FIDO2） |
| 服务对服务 | mTLS 或密钥 | 证书轮换 + 白名单 |
| 服务对用户 | 令牌（JWT/Opaque Token） | 短时效 + 刷新机制 |
| 内部员工 | 统一 SSO | 按敏感度加 MFA |

### 3.2 令牌选型：JWT 还是 Opaque Token

会话令牌的两种主流形态，取舍点在吊销、状态和网关开销：

| 维度 | JWT | Opaque Token |
|---|---|---|
| 存储 | 无状态，带签名自校验 | 有状态，集中查缓存 |
| 吊销 | 难，需要黑名单 | 容易，删除即失效 |
| 网关开销 | 只验签名，不查存储 | 每次访问校验服务 |
| 携带信息 | 自带用户属性 | 需反查 |
| 适用 | 服务间短时效令牌 | C 端可吊销会话 |

经验取舍：C 端会话用不透明令牌（Opaque Token）存 Redis，可强制下线；服务间用短时效（15 分钟以内）JWT，吊销风险由时效兜底；JWT 里只放标识和租户 ID，不放敏感信息——令牌会被打进日志。

> 最容易错的三处：JWT 用 `alg: none` 或对称密钥随前端分发；令牌放 localStorage 被 XSS 一次性偷走（用 HttpOnly Cookie 时要同时防 CSRF）；刷新令牌长期不轮换，泄漏后等于永久后门。

### 3.3 会话生命周期管理

会话的四个环节都有架构决策：签发（令牌格式、有效期）、传递（Header 还是 Cookie）、刷新（滑动过期还是绝对过期）、终止（登出、改密、异地登录时的全端失效）。

| 参数 | 推荐值（示例） | 说明 |
|---|---|---|
| 访问令牌 TTL | 15–30 分钟 | 泄漏影响窗口 |
| 刷新令牌 TTL | 7–14 天，使用即轮换 | 检测重放 |
| 并发会话数 | 限制并告警 | 代理检测 |
| 改密后 | 全部会话失效 | 快速止损 |

### 3.4 协议选型：OIDC、OAuth2、SAML

| 协议 | 场景 | 特点 | 不建议用于 |
|---|---|---|---|
| OIDC | 现代 Web/移动登录 | 基于 OAuth2，返回 ID Token | 老旧企业 IdP 对接 |
| OAuth2 | 第三方授权、API 访问 | 授权委托，不认证 | 当作登录协议单独用 |
| SAML 2.0 | 企业 SSO 对接 | 成熟、XML 重 | 新移动端 |
| mTLS | 服务间、设备 | 双向证书 | C 端浏览器 |

选型规则：新系统对外登录用 OIDC；需要接客户已有 IdP 时保留 SAML；服务间用 mTLS 或 SPIFFE 身份。OAuth2 的授权码模式必须配 PKCE，隐式模式已经淘汰。

## 四、授权：你能做什么

授权（Authorization）是"主体能否对资源执行操作"的判定。越权（BOLA/IDOR）常年排在 OWASP Top 10 前列，因为它出在架构分层而不是具体语言。

### 4.1 授权模型按复杂度选

| 模型 | 判定逻辑 | 适用 |
|---|---|---|
| ACL | 用户 → 资源 | 资源少的内部系统 |
| RBAC | 用户 → 角色 → 权限 | 管理后台，覆盖八成场景 |
| ABAC | 属性规则 | 需要"工作时间内、本部门数据"这类条件 |
| ReBAC | 关系图 | 文档协作、社交关系 |

判定逻辑放的位置：网关做粗粒度（这个路径要不要登录），业务服务做细粒度（这个订单是不是这个用户的）。不能只有网关检查——BOLA 的本质就是应用层忘了做资源归属校验。

### 4.2 授权判定的三层顺序

授权判定必须固定顺序：租户 → 资源归属 → 功能权限。顺序颠倒会让越权判定依赖角色，角色一多就漏。

| 层 | 判定 | 失败返回 | 漏判后果 |
|---|---|---|---|
| 租户 | 令牌租户 = 资源租户 | 404 | 跨租户泄漏 |
| 归属 | 资源属于该主体 | 403 | 横向越权 |
| 功能 | 角色含该动作 | 403 | 越权操作 |

把顺序写成策略配置，而不是散落在每个接口里：

```yaml
# 片段：策略声明式配置，归属校验不可被单个接口关闭
policy:
  resource: order
  evaluationOrder: [tenant, ownership, role]
  actions:
    read:
      roles: [order_viewer, tenant_admin]
      requireOwnership: true
    export:
      roles: [tenant_admin]
      requireOwnership: true
      audit: true
      stepUpAuth: true
```

> 最容易错：用"页面上没这个按钮"代替服务端授权。前端隐藏只是体验，攻击者直接调 API。服务端必须独立完成全部判定，前端只负责渲染。

### 4.3 权限数据的缓存与失效

权限判定在每次请求上，性能压力集中在角色和资源归属查询。缓存可以加，但必须能失效：角色变更、租户迁移、资源转移三种事件要主动清缓存，TTL 只做兜底。

| 缓存对象 | TTL 建议 | 失效触发 |
|---|---|---|
| 用户角色集合 | 5 分钟 | 角色变更事件 |
| 资源归属 | 60 秒 | 资源转移事件 |
| 策略配置 | 30 秒 | 发布事件 |

> 边界：授权缓存不能长于令牌有效期，否则会出现"已撤权但仍可访问"的窗口。撤权要求立即生效时，走令牌黑名单而不是等缓存过期。

## 五、多租户：授权最大的坑

多租户（Multi-tenancy）隔离是 SaaS 和企业系统的第一安全约束，也是数据泄漏事故的常见根源。租户过滤必须是架构级机制，不能靠每条 SQL 自觉。

### 5.1 隔离级别选型

| 方案 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|
| 共享库 + 租户列 | 弱，靠代码过滤 | 低 | 大量小租户 |
| 独立 Schema | 中 | 中 | 中等数量租户 |
| 独立实例 | 强 | 高 | 金融、医疗大客户 |

主流选择是"共享库 + 租户列 + 行级强制过滤"：成本可控，但必须把租户条件做进框架层，比如 MyBatis-Plus 的租户插件或 PostgreSQL 的行级安全（RLS），让漏加条件的 SQL 直接报错或被改写。

```sql
-- 片段：PostgreSQL 行级安全，把租户隔离下沉到数据库，绕过应用的裸 SQL 也被拦
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

### 5.2 租户数据的判定顺序

判定顺序必须是"租户 → 角色 → 资源"，跳过租户直接判角色是越权的常见成因。所有资源 ID 都必须能反查租户，跨租户操作（平台管理员）走单独角色和单独审计。

### 5.3 租户生命周期

租户隔离不只发生在查询时，开通、迁移、注销三个阶段各有一个安全决策。

| 阶段 | 决策点 | 常见事故 |
|---|---|---|
| 开通 | 租户标识生成、配额初始化 | 租户 ID 可预测被枚举 |
| 运行 | 数据、配额、密钥按租户隔离 | 共享缓存串数据 |
| 迁移 | 目标库提前建好 RLS 策略 | 迁移期间双写无校验 |
| 注销 | 数据保留期与删除证明 | 注销后数据仍能恢复，违反合规 |

缓存也要带租户前缀：共享 Redis 里裸用 `order:{id}` 做键，A 租户写入的数据会被 B 租户读到。正确写法是 `t:{tenantId}:order:{id}`，前缀缺失在代码评审里算阻断项。

## 六、数据分级与脱敏

数据分级（Data Classification）决定"哪些数据能被谁看到、能存多久、能不能出网"。没有分级，脱敏和审计就缺少判据，只能全量加密或全量放行。

### 6.1 四级分法与处置要求

| 级别 | 示例 | 存储 | 展示 | 出网 |
|---|---|---|---|---|
| L1 公开 | 商品标题 | 明文 | 原样 | 允许 |
| L2 内部 | 库存、成本 | 明文 + 权限 | 按角色 | 审批 |
| L3 敏感 | 手机号、地址 | 加密/脱敏 | 掩码 | 禁止 |
| L4 极敏感 | 身份证、卡号、密钥 | 加密 + 分库 | 不可回显 | 禁止 |

分级的落地不是一个标签，而是三条硬约束：L3 以上字段默认脱敏返回；L4 字段禁止进日志和消息体；跨级导出必须走审批并留审计。

### 6.2 脱敏的实现位置

脱敏放在序列化层（统一拦截），而不是每个接口手写。

```yaml
# 片段：统一脱敏规则，按字段名匹配，避免每个 DTO 手写
masking:
  rules:
    - field: phone
      strategy: keep-prefix-suffix   # 138****8000
      keep: 3
    - field: idCard
      strategy: hash                 # 不可逆，保留查询能力
    - field: bankCard
      strategy: full-mask
  excludeRoles: [pii_viewer]         # 只有该角色看原文，且操作入审计
```

> 边界：脱敏不是加密。脱敏后数据不可还原，适合展示；需要还原的场景（如对账）用加密存储 + 授权解密。把脱敏当加密用，会在需要原值时被迫全量落明文。

### 6.3 加密字段的查询取舍

字段一旦加密，等值查询和模糊查询都会失效。三种方案对应不同需求：

| 方案 | 能力 | 泄露风险 | 适用 |
|---|---|---|---|
| 明文 | 全部查询 | 高 | 不适用 L3/L4 |
| 盲索引（HMAC） | 等值查询 | 中，可被字典攻击 | 手机号精确查 |
| 确定性加密 | 等值查询 | 中高 | 不推荐 L4 |

盲索引（Blind Index）的思路：另存一列 `phone_idx = HMAC(key, phone)`，查询走索引列，原文只走解密展示。字典攻击的缓解是给 HMAC 加一层"每租户盐"，让相同手机号在不同租户下索引值不同。

> 边界：加密解决"库被拖"的场景，不解决"应用有漏洞被查"的场景。应用层授权仍是第一道防线，加密是最后一道。

## 七、密钥与信封加密

密钥管理（Key Management）是安全架构里最容易"看起来做了、实际没做"的部分。核心原则：密钥不出 KMS、数据密钥随用随解、主密钥定期轮换。

### 7.1 信封加密的结构

信封加密（Envelope Encryption）用两级密钥：主密钥（KEK）常驻 KMS 不导出，数据密钥（DEK）由 KMS 生成并加密后随数据存储。解密时先用 KEK 解出 DEK，再解数据。这样轮换 KEK 不需要重加密全部业务数据。

```text
写入：明文 → 生成 DEK → 用 DEK 加密数据 → 用 KEK 加密 DEK → 存 {密文, 加密后的DEK, KEK版本}
读取：取加密DEK → KMS 用 KEK 解出 DEK → 用 DEK 解数据 → DEK 丢弃
轮换：只换 KEK 版本，旧版本保留解密能力，新写入用新版本
```

### 7.2 密钥的生命周期与存放

| 环节 | 要求 | 常见错误 |
|---|---|---|
| 生成 | KMS/HSM，禁止自写随机 | 用时间戳做种子 |
| 存放 | 密钥管理服务，不进代码库 | 写进配置文件提交 Git |
| 使用 | 按需解密，用完即弃 | DEK 缓存在进程内存不清理 |
| 轮换 | KEK 定期轮换，DEK 按数据分类 | 永不轮换，泄漏无法止损 |
| 销毁 | 保留解密旧数据的窗口后销毁 | 直接删，历史数据打不开 |

应用侧只持有"访问 KMS 的身份"，不持有主密钥。K8s 场景用 External Secrets Operator 或 Vault Agent 注入短期凭据，避免把长期密钥写进 Secret。

```yaml
# 片段：External Secrets 从 Vault 拉取，Pod 内只见短期凭据
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-db
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
  target:
    name: order-db-secret
  data:
    - secretKey: password
      remoteRef:
        key: prod/order/db
        property: password
```

> 最容易错：把密钥放在环境变量里就以为安全。环境变量会进崩溃转储、进 `docker inspect`、被子进程继承。生产密钥应通过文件挂载或工作负载身份（如 K8s ServiceAccount + Vault）短期获取。

### 7.3 密钥轮换的操作顺序

轮换的目标是"不中断业务、不重加密全量数据、旧数据可解"。按以下顺序执行，任一步失败都可停在上一步。

1. 在 KMS 生成新版本 KEK，旧版本保持启用状态。
2. 应用发布：写入统一用最新版本，读取按记录里的版本号选择 KEK。
3. 观察 24 小时，确认没有"版本不存在"的解密失败。
4. 后台任务重加密 DEK（只重加密 DEK，不动业务数据）。
5. 确认旧版本 KEK 近 30 天无解密调用后，禁用它；保留 90 天再销毁。

| 检查点 | 通过判据 |
|---|---|
| 双版本并存 | 新旧 KEK 都能解密 |
| 写入版本 | 新记录全部带新版本号 |
| 失败率 | 解密失败率 < 0.01% |
| 回退 | 旧版本仍启用，可回退发布 |

> 最容易错：先禁用旧 KEK 再切写入，导致历史数据全部解不开；或者只轮换不记录版本号，事后无法判断某条数据用的哪把密钥。

## 八、审计与可观测

审计（Audit）回答"谁在什么时候对什么做了什么"，它同时承担合规、追责和入侵检测三个职责。审计日志与应用日志必须分开，前者不可删改，后者可以采样。

### 8.1 审计事件的必填字段

| 字段 | 示例 | 为什么必须 |
|---|---|---|
| 主体 | user_id + 租户 + 角色 | 追责到人 |
| 动作 | order.export | 区分读写与导出 |
| 对象 | 订单 ID 范围 | 定位影响面 |
| 结果 | 成功 / 拒绝 / 失败原因 | 识别越权尝试 |
| 上下文 | IP、UA、请求 ID、时间 | 关联排查与取证 |

审计记录写入独立存储（如对象存储 + WORM 或专用审计库），业务账号无删除权限。审计日志本身也要脱敏，否则审计库成了泄漏源。

### 8.2 告警规则：从审计里抓异常

| 现象 | 规则 | 处置 |
|---|---|---|
| 越权尝试激增 | 403 次数 5 分钟 > 阈值 | 临时封禁 + 通知 |
| 敏感数据批量导出 | 单账号日导出 > 阈值 | 阻断 + 审批 |
| 异地同时登录 | 同账号多地令牌 | 强制下线 |
| 密钥访问异常 | 非工作时段解密 | 告警 + 复核 |

> 边界：审计日志不是越多越好。把全量请求体写进审计，既贵又制造新的泄漏面；只记录安全相关动作和判定结果，请求体做字段白名单。

### 8.3 审计与隐私的平衡

审计日志本身含敏感信息，必须同时满足"可追溯"和"最小化"。三条规则：

- 只记字段白名单，不记完整请求体；
- 对象记 ID 与范围，不记内容；
- 审计日志的访问也要审计，谁能查审计本身要审批。

保留期按合规要求定：一般操作日志 180 天，资金与权限变更 1 年以上，日志归档后只读。

## 九、供应链安全

供应链（Supply Chain）攻击的入口是依赖、构建和发布，不是运行时。防护要点是把"引入的东西"和"产出的东西"都变成可验证的清单。

### 9.1 三道门禁

| 环节 | 门禁 | 工具形态 |
|---|---|---|
| 引入 | 依赖漏洞扫描 + 来源锁定 | Dependabot、Trivy、私有仓库 |
| 构建 | 锁文件、可复现构建、SBOM | Maven/Gradle lock、Syft |
| 发布 | 制品签名、镜像扫描 | Sigstore/cosign、Trivy |

依赖混淆（Dependency Confusion）是高频手法：攻击者把内部包名发布到公共仓库，构建时优先拉到恶意版本。对策是私有仓库代理 + 作用域锁定（npm scope、Maven groupId 白名单），并在 CI 里禁止直连公网仓库。

```bash
# 片段：生成 SBOM 并扫描高危漏洞，CI 里失败即阻断
syft packages registry.example.com/order:1.8.2 -o spdx-json > sbom.json
trivy sbom sbom.json --severity HIGH,CRITICAL --exit-code 1
# 预期输出：HIGH/CRITICAL 数量 > 0 时退出码为 1，流水线中断
```

### 9.2 制品签名与验证

```bash
# 片段：用无密钥签名（OIDC 身份）签署镜像，部署前验签
cosign sign --yes registry.example.com/order:1.8.2
cosign verify registry.example.com/order:1.8.2 \
  --certificate-identity-regexp '.*ci@example.com' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

> 边界：签名只证明"制品来自谁"，不证明"制品没漏洞"。签名和扫描必须同时做；只签名不扫描，等于给有洞的包盖章。

### 9.3 一条可落地的 CI 门禁链

```yaml
# 片段：GitHub Actions 的安全门禁顺序，先快后慢，失败即停
jobs:
  security:
    steps:
      - run: gitleaks detect --source . --redact --exit-code 1        # 密钥扫描，10 秒级
      - run: mvn -q dependency-check:check -DfailBuildOnCVSS=7        # 依赖 CVE，且只拦高危
      - run: semgrep ci --config p/owasp-top-ten                       # SAST，按 OWASP 规则
      - run: syft packages dir:. -o spdx-json > sbom.json              # 产出 SBOM 作为交付物
      - run: trivy image --severity HIGH,CRITICAL --exit-code 1 $IMAGE # 镜像扫描
      - run: cosign verify $IMAGE --certificate-identity-regexp '.*ci@example.com' \
               --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

门禁顺序按耗时排：密钥扫描最先（秒级、误报低），依赖与 SAST 次之，镜像扫描最后。把 SBOM 作为发布产物归档，出事时能在分钟级回答"哪些线上服务用了这个受影响的包"。

| 门禁 | 阻断条件 | 豁免方式 |
|---|---|---|
| 密钥扫描 | 检出任何密钥 | 不允许 |
| 依赖 CVE | CVSS ≥ 7 且无补丁 | 安全负责人审批 |
| SAST | 高危规则命中 | 逐条基线化 |
| 镜像扫描 | HIGH/CRITICAL | 不允许 |
| 验签 | 签名不匹配 | 不允许 |

## 十、安全上线清单与失败模式

安全架构的产出不是文档，是能挂进发布流程的门禁清单。清单要绑定"谁检查、在哪一步、不通过怎么办"。

### 10.1 发布前清单

| 检查项 | 判据 | 阻断级别 |
|---|---|---|
| 信任边界 | 每条跨界流有校验点 | 必须 |
| 认证 | 无匿名可调的管理接口 | 必须 |
| 授权 | 资源归属校验在服务端 | 必须 |
| 租户隔离 | 漏加租户条件的查询会失败 | 必须 |
| 数据分级 | L3+ 字段有脱敏规则 | 必须 |
| 密钥 | 无硬编码密钥，KMS 可轮换 | 必须 |
| 审计 | 敏感动作有审计且不可删 | 必须 |
| 供应链 | 无高危漏洞，制品已签名 | 建议 |

### 10.2 失败模式

- 只在网关做鉴权，业务层不校验资源归属，出现 BOLA；
- 把内网当可信区，服务间调用不带身份，一台机器失陷就横向移动；
- 多租户靠代码自觉加 `tenant_id`，一条漏写就是跨租户泄漏；
- 密钥写进配置、镜像或环境变量，仓库一泄漏全线失守；
- 审计日志和业务日志混在一个库，出事时被一起清掉；
- 只在上线前做一次渗透测试，没有持续扫描和门禁。

### 10.3 凭据泄漏的应急顺序

凭据泄漏是安全架构里唯一必须背下来的流程：先遏制，再取证，最后根除。顺序错一步，攻击者就会在你排查时继续使用旧凭据。

| 步骤 | 动作 | 时限（示例） |
|---|---|---|
| 1 遏制 | 吊销凭据、封禁来源、下线受影响通道 | 15 分钟内 |
| 2 取证 | 拉取该凭据的使用日志，确定时间窗与范围 | 2 小时内 |
| 3 根除 | 轮换关联凭据（往往不止一把） | 24 小时内 |
| 4 恢复 | 灰度恢复，确认无异常调用 | 按业务 |
| 5 复盘 | 找到泄漏路径，补门禁 | 一周内 |

> 边界：只轮换泄漏的那一把密钥不够。同一份配置文件里常有数据库口令、对象存储 AK、第三方 token，泄漏一个往往意味着全部暴露；要按"同一来源"整体轮换。

## 十一、最佳实践案例

### 11.1 案例背景

一家做企业采购 SaaS 的公司，2025 年从单体迁到多租户微服务，客户数从 40 涨到 900。迁移后三个月内出现两次安全事件：一次是 A 客户通过改 URL 里的订单 ID 看到了 B 客户的订单（BOLA）；一次是测试环境把生产数据库口令提交进了 Git 仓库，虽然及时删除，但凭据已暴露 6 小时。

目标是六个月内在不阻断业务迭代的前提下，把这两类问题变成"发布流水线里过不去"的硬约束。约束有三条：团队 12 人、没有专职安全工程师；不能停机；不能为每个租户单独部署（成本不允许）。现状是：网关统一登录，服务间裸 HTTP 调用，数据库单库单表带 `tenant_id` 列但过滤靠手写，密钥在 `application-prod.yml`。

### 11.2 案例实操

第一步，画信任边界并做 STRIDE。团队用半天把 7 条跨界数据流画出来，标出 4 个校验缺口（服务间、回调、导出、运维通道），形成威胁清单。

| 边界 | 现状 | 威胁 | 对策 |
|---|---|---|---|
| 网关 → 服务 | 裸 HTTP，无令牌 | 假冒、提权 | 内部 JWT + mTLS |
| 第三方回调 | 信任报文金额 | 篡改 | 验签 + 幂等 |
| 服务 → DB | 共用高权限账号 | 泄露、篡改 | 按服务分账号 |
| 运维 → 生产 | 共享跳板机口令 | 抵赖 | 堡垒机 + 审计 |
| 服务 → 对象存储 | 长期 AK | 泄露 | 短期 STS 凭据 |

第二步，把租户隔离下沉到框架层。选型对比后选了共享库 + PostgreSQL 行级安全（RLS），而不是独立 Schema：900 租户下独立 Schema 的迁移和连接池成本过高。改造前先盘了依赖表，确认改动波及面：

| 改动 | 依赖它的服务 | 改造方式 |
|---|---|---|
| RLS 策略 | 订单、合同、报表共 11 个服务 | 统一 DBA 变更单 |
| 授权 SDK | 全部业务服务 | 灰度按服务分批接入 |
| Vault 接入 | 所有部署单元 | 先测试环境一周 |
| 审计流 | 导出、权限、解密三类动作 | 只加不改 |

依赖表决定了执行顺序：授权 SDK 波及面最大，放最后一批；RLS 是数据库层改动，对服务透明，放最前。

| 选项 | 隔离强度 | 改造成本 | 结论 |
|---|---|---|---|
| 手写 tenant_id 过滤 | 弱 | 低 | 否决，已出事故 |
| MyBatis-Plus 租户插件 | 中 | 低 | 过渡 |
| PostgreSQL RLS | 强 | 中 | 采用 |
| 独立 Schema | 强 | 高 | 大客户专用 |

RLS 落地时踩了一个坑：连接池复用连接，`app.tenant_id` 会串。改为在事务开始时 `SET LOCAL`，并用拦截器强制每个请求必须设置租户变量，未设置直接拒绝。

```sql
-- 片段：会话级设置租户，事务结束自动失效，避免连接池串租户
BEGIN;
SET LOCAL app.tenant_id = '9f1c...';
-- 此后所有查询被 RLS 强制过滤
COMMIT;
```

第三步，密钥治理。把 `application-prod.yml` 里的口令全部移除，接入 Vault + External Secrets，Pod 只拿短期凭据；数据库启用信封加密存 L4 字段（身份证、银行账号），KEK 在 KMS，轮换周期 90 天。同时在 CI 加 `gitleaks` 扫描，提交历史里出现密钥直接失败。

```yaml
# 片段：CI 密钥扫描门禁
- name: secret-scan
  run: gitleaks detect --source . --redact --exit-code 1
```

第四步，授权改造。网关只验令牌，业务服务统一接入一个授权 SDK：先从令牌取 `tenant_id`，再用资源 ID 反查归属，最后判角色。SDK 里内置"未调用归属校验就返回敏感字段"的断言，开发环境直接抛异常。

```yaml
# 片段：策略即配置，功能权限与资源归属分开声明，避免开发者漏写
policy:
  resource: order
  actions:
    read:
      roles: [order_viewer, tenant_admin]
      requireOwnership: true        # 归属校验不可关
    export:
      roles: [tenant_admin]
      requireOwnership: true
      audit: true                   # 导出必须留审计
      stepUpAuth: true              # 二次认证
```

第五步，审计与告警。敏感动作（导出、改权限、解密）写独立审计流，落到只写对象存储；对 403 激增、批量导出、非工作时段解密设三条告警。

第六步，发布门禁。把清单前十项做成流水线检查：SAST、依赖扫描、SBOM、镜像扫描、cosign 验签，全部通过才允许部署生产。

### 11.3 案例结果

六个月后（示例数据）：跨租户越权从季度 2 起降到 0 起；密钥泄漏类事件 0 起，`gitleaks` 在 CI 阶段拦截 14 次；发布流水线平均增加 6 分 40 秒，没有因安全门禁导致发布失败超过 1 次/月；900 个租户的数据访问全部经过 RLS，渗透测试中 BOLA 类问题从 5 个降到 0 个。

代价与失败模式也要记录：RLS 让复杂报表查询慢了约 15%，最终用只读副本 + 预聚合解决；授权 SDK 上线初期有 3 个服务因为"资源不存在时未做归属校验"被断言拦下，暴露了原来的静默越权；Vault 接入让本地开发多了一步登录，团队用 mock 身份提供器缓解。

复盘三条：第一，租户隔离必须做成"漏写就报错"的机制，不能靠 code review；第二，密钥治理的收益不在加密算法，而在"没有长期凭据可偷"；第三，安全清单只有挂进流水线才算落地，写在 Confluence 里的清单三个月后没人看。
