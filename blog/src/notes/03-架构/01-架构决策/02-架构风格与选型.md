# 架构风格与选型

> 这篇从架构风格的约束本质讲起，经过单体、模块化单体、微服务、事件驱动、Serverless 和六边形架构的适用边界，再落到选型矩阵、团队容量、迁移代价，最后用一个完整决策案例收束。
>
> 学完能针对给定业务与团队约束，排出候选风格、算出迁移代价，并给出可被评审的选型结论。

## 一、风格选择的判断单位

架构风格不是审美偏好，而是一组关于部署单元、数据所有权、通信方式和团队映射的约束；选型的本质是选择接受哪一组代价。

### 1.1 风格由五个约束轴定义

同一个词在不同团队嘴里经常指不同东西。把风格拆成五个可观察的约束轴，争论才有共同对象。

| 约束轴 | 单体 | 微服务 |
|---|---|---|
| 部署单元 | 一个制品整体发布 | 每个服务独立发布 |
| 数据所有权 | 共享 schema | 每服务私有数据 |
| 通信方式 | 进程内方法调用 | 网络调用 |
| 团队映射 | 多团队共用一个制品 | 团队拥有服务 |
| 故障域 | 整个进程一起失效 | 单服务或单副本失效 |

五条轴不需要同时改变。只把部署单元拆开、数据仍然共享，得到的是“多个制品连同一个库”，通常比原单体更难维护；只把数据拆开、发布仍然锁步，得到的是“分布式单体”。

> 边界：风格名只描述主要约束，不描述全部约束。判断一个系统是不是微服务，看服务是否独立部署、数据是否私有、故障是否隔离，不看用了几个仓库。

### 1.2 先算约束，再谈风格

选型顺序是约束排查，不是风格比较。三条约束会直接排除大部分选项。

| 约束 | 判断问题 | 通常排除 |
|---|---|---|
| 团队容量 | 能否为每个服务配齐开发、值班、平台支持 | 超出团队数的微服务 |
| 一致性边界 | 是否存在必须跨模块的强事务 | 无补偿设计的微服务 |
| 运维能力 | 是否具备灰度、追踪、集中日志、告警 | 大规模微服务、Serverless |

示例：6 名后端、1 名兼职运维、没有集中日志。这个组合可以做好模块化单体，做不了 20 个微服务；不是技术能力问题，是值班和排障的人力问题。

### 1.3 风格是光谱，通信是另一个维度

风格之间不是互斥选项，而是约束逐步增加的光谱。事件驱动描述通信方式，Serverless 描述运行形态，六边形描述代码依赖方向，三者与前四种风格正交。

| 维度 | 可选值 | 主要影响 |
|---|---|---|
| 部署形态 | 单体、服务化、微服务、FaaS | 发布粒度、故障域 |
| 通信方式 | 同步调用、事件、批处理 | 耦合、一致性、延迟 |
| 代码结构 | 分层、六边形、模块化 | 可测试性、替换成本 |
| 数据归属 | 共享库、私有库、多副本 | 事务、对账、迁移 |

一个系统可以是“模块化单体 + 内部事件 + 六边形代码结构”，也可以是“微服务 + 同步调用 + 分层结构”。把通信方式当成风格替代品，会在选型表里制造伪选项。

## 二、单体与模块化单体

单体在边界不清、团队不大、流量可预测时仍然是成本最低的选择；模块化单体把边界放进代码，而不是提前放进网络。

### 2.1 单体的成立条件

单体是单个部署单元、单个数据库 schema、单个进程的架构形态。它的优势来自进程内调用和本地事务，不是“简单”两个字。

| 条件 | 判据 | 不满足的后果 |
|---|---|---|
| 边界可讨论 | 领域专家能在一张图上达成一致 | 拆出来的模块仍互相渗透 |
| 团队规模有限 | 发布不需要跨三个以上团队协调 | 发布排队，责任不清 |
| 流量形态平稳 | 峰值与均值差距在可扩容范围内 | 只能整机扩容，成本高 |
| 一致性强 | 大量操作需要跨实体事务 | 提前拆分会引入补偿逻辑 |

单体真正的成本不在代码量，而在变更耦合：任何一次发布都带着所有模块的回归范围。团队能接受这个成本时，单体是合理选择。

### 2.2 模块化单体：边界在代码里

模块化单体是一个部署单元内，由若干高内聚模块组成，模块之间只通过公开接口通信，不直接访问对方的表。

```text
src/main/java/com/example/order/
├── order/
│   ├── api/                 # 对外公开的接口与 DTO
│   ├── domain/              # 订单聚合、领域服务
│   └── infrastructure/      # 仓储实现、消息发送
├── inventory/
│   ├── api/
│   ├── domain/
│   └── infrastructure/
└── payment/
    ├── api/
    ├── domain/
    └── infrastructure/
```

依赖规则只有一条：模块只能依赖对方的 `api` 包；`domain` 和 `infrastructure` 对外不可见。跨模块查询通过接口，不通过 SQL join 对方的表。

| 手段 | 强制力 | 成本 |
|---|---|---|
| 包结构约定 | 低 | 低 |
| 构建模块拆分 | 中 | 中 |
| ArchUnit 规则 | 中高 | 低 |
| 独立 schema | 高 | 中高 |
| 独立数据库实例 | 最高 | 高 |

ArchUnit 这类字节码规则测试能在 CI 里拦住“新代码直接 import 对方 domain”的退化。规则宜少而硬，超过二十条通常没人维护。

Spring Modulith 在 2026 年仍是 Java 生态里做模块化单体的常用支撑：它按包识别模块、校验依赖、把模块内事件转为事务性发件箱。工具不是边界本身，边界仍是包与接口的设计。

### 2.3 单体的失效模式

单体变坏通常不是因为“用了单体”，而是因为边界从未被定义，也没有任何机制阻止侵蚀。

| 现象 | 可观察指标 | 处理 |
|---|---|---|
| 大泥球 | 跨包 import 数持续上升 | 先画边界，再谈拆分 |
| 锁步发布 | 一次发布涉及 3 个以上团队 | 按变更频率切模块 |
| 资源争抢 | 单个报表拖垮整个进程 | 隔离线程池或抽独立进程 |
| 扩容粗糙 | 峰值只能整机扩容 | 找出真正吃资源的模块 |
| 回归范围失控 | 每次发布回归用例数翻倍 | 建立模块级测试边界 |

### 2.4 该拆分的信号

拆分信号来自组织与运行数据，不来自代码行数。

| 信号 | 判据 | 动作 |
|---|---|---|
| 独立扩容 | 某模块资源占用是其他的 5 倍以上 | 抽成独立服务 |
| 发布冲突 | 两团队每周互相等待发布窗口 | 按团队边界拆 |
| 故障隔离 | 单模块故障导致全站不可用 | 先做进程隔离 |
| 合规隔离 | 数据必须落在独立边界 | 独立服务与独立库 |
| 技术异构 | 某模块需要不同运行时 | 独立部署 |

“代码有 30 万行”“招聘要求微服务”不是拆分信号。前者只说明需要模块化，后者只说明简历市场。

## 三、微服务

微服务用网络边界换取独立部署与独立扩容，代价是分布式系统的全部复杂度；只有当前置能力齐备时，收益才会出现。

### 3.1 微服务交换的是什么

| 获得 | 付出 |
|---|---|
| 独立发布，故障不连坐 | 网络延迟、超时、重试、熔断 |
| 按服务扩容 | 每服务一套流水线、监控、值班 |
| 团队自治，技术异构 | 跨服务一致性、对账、补偿 |
| 边界清晰，替换成本低 | 分布式追踪、服务目录、契约管理 |
| 细粒度权限与审计 | 平台团队与基础设施成本 |

收益与代价不是同时到账。团队数少于服务数时，收益通常先到；值班和排障能力不足时，代价后到，而且更贵。

### 3.2 拆分的前置能力

微服务不是拆完再补能力，而是能力齐备才拆。

| 能力 | 最低标准 | 缺失后果 |
|---|---|---|
| 持续交付 | 单服务 10 分钟内可回滚 | 发布变慢，故障恢复靠人 |
| 可观测性 | Trace、指标、结构化日志可关联 | 跨服务问题无法定位 |
| 服务目录 | 负责人、SLA、依赖可查 | 变更影响面靠猜 |
| 数据所有权 | 每服务独占写入路径 | 共享库导致锁步变更 |
| 平台支持 | 网关、配置、密钥、流水线模板 | 每团队重复造轮子 |
| 值班机制 | 明确一线与升级路径 | 故障无人认领 |

这份清单可以直接当评审表用：任意两项不达标，拆分计划应先补能力，而不是先拆服务。

### 3.3 服务粒度与边界判定

服务边界优先按业务能力与限界上下文（Bounded Context）划，其次按事务边界，最后才按团队。按技术层拆（订单 Controller 服务、订单 DAO 服务）会制造大量同步调用，属于反模式。

| 判据 | 倾向独立服务 | 倾向留在模块内 |
|---|---|---|
| 数据 | 拥有独立聚合与写入 | 与相邻实体强事务 |
| 变更频率 | 与邻居明显不同 | 总是一起改 |
| 团队 | 有明确 owner | 无固定 owner |
| 调用 | 以异步或粗粒度同步为主 | 需细粒度同步往返 |
| 生命周期 | 可独立下线 | 与主流程同生共死 |

粒度经验值：一个服务由一个团队拥有，团队能说清它的数据边界和 SLA；服务数超过团队数两倍时，维护质量通常开始下降。这个比例是经验值，不是定律。

### 3.4 分布式单体

分布式单体是“服务已拆开、耦合仍按单体运行”的状态：共享数据库、共享库版本锁步、发布必须一起、调用链深度超过三层。

| 症状 | 检测方式 | 后果 |
|---|---|---|
| 共享表 | 统计跨服务访问的表数量 | 任何表变更都要多方协调 |
| 共享库 | 多个服务依赖同一内部库 | 升级必须整体发布 |
| 同步长链 | 采样 Trace 的最大深度 | 尾延迟叠加，故障放大 |
| 联合发布 | 发布单里固定绑定多个服务 | 独立部署名存实亡 |
| 共享事务 | 跨服务直接读未提交数据 | 一致性无法保证 |

治理顺序是先消除共享表，再消除共享库，最后缩短同步链。直接上服务网格不会解决这些问题，只会让调用图更漂亮。

### 3.5 服务数量的成本曲线

平台成本随服务数近似线性增长，协调成本增长更快。

| 服务数 | 流水线 | 月基础设施 | 平台人力 |
|---:|---:|---:|---:|
| 10 | 10 | 1.0 倍基数 | 2 人 |
| 30 | 30 | 1.8 倍基数 | 4 人 |
| 100 | 100 | 4.5 倍基数 | 9 人 |

数字为示例，用于说明趋势：服务数翻三倍，平台人力通常不止翻倍，因为服务目录、告警治理、版本升级、证书轮换都要按服务重复。选型时把这笔长期成本写进对比表，能过滤掉大量“先拆了再说”的方案。

## 四、事件驱动

事件驱动解决的是跨边界副作用与削峰，不解决强一致读；用之前必须先接受重复、乱序与最终一致。

### 4.1 三种事件用法

| 用法 | 事件内容 | 适用 | 风险 |
|---|---|---|---|
| 通知事件 | 只说明发生了什么 | 触发下游动作 | 下游要回查 |
| 状态转移事件 | 携带变更后的关键字段 | 下游直接消费 | 契约变更影响大 |
| 事件溯源 | 事件即事实来源 | 审计、回放、复杂状态 | 建模与运维门槛高 |

多数业务只需要通知事件或状态转移事件。事件溯源适合账务、审批、库存流水这类需要完整历史的场景；把它当默认存储模式会显著增加查询与迁移成本。

### 4.2 何时该用异步

| 场景 | 判断 | 理由 |
|---|---|---|
| 跨边界副作用 | 是 | 下游失败不应回滚主流程 |
| 峰值削峰 | 是 | 队列吸收瞬时流量 |
| 长流程 | 是 | 编排或编舞比同步等待稳 |
| 多消费者 | 是 | 一次发布多方订阅 |
| 同步查询结果 | 否 | 最终一致会破坏交互 |
| 强事务写 | 否 | 需要本地事务或补偿设计 |

判断标准是“调用方是否需要立即拿到结果”。需要，就同步；不需要，再评估异步的运维成本。

### 4.3 异步的必备能力

| 问题 | 机制 | 验证方式 |
|---|---|---|
| 重复投递 | 消费端幂等键 | 重放同一事件，结果不变 |
| 乱序 | 按聚合键分区 | 同键事件顺序消费 |
| 事务与发件 | 发件箱模式 | 断网时不丢事件 |
| 毒消息 | 重试上限加死信队列 | 注入坏消息可告警 |
| 契约演进 | schema 注册与兼容规则 | 新旧消费者并行 |
| 排障 | 事件 ID 贯穿日志与 Trace | 按事件 ID 还原链路 |

没有幂等键的消费者，在至少一次投递语义下一定会重复处理。这不是概率问题，是时间问题。

### 4.4 事件契约的演进规则

事件是公开接口，按公开 API 的标准管理。

| 变更 | 兼容性 | 处理 |
|---|---|---|
| 新增可选字段 | 兼容 | 消费者忽略未知字段 |
| 新增必填字段 | 不兼容 | 升版本，双发过渡 |
| 删除字段 | 不兼容 | 先停用，再删除 |
| 改字段类型 | 不兼容 | 新事件类型 |
| 改语义 | 不兼容 | 新事件类型加文档 |

主题命名带业务含义与版本，例如 `order.order-placed.v2`。禁止用 `order-events` 这类无版本主题承载所有变更。

### 4.5 事件链路的运行指标

| 指标 | 含义 | 告警阈值示例 |
|---|---|---|
| 消费延迟 | 最新消息与消费位点差 | 持续 5 分钟超 1 万条 |
| 死信率 | 进入死信的消息占比 | 超过 0.1% |
| 重复率 | 幂等命中占比 | 突增 3 倍 |
| 消费者利用率 | 处理时间占轮询周期 | 超过 80% |
| 积压恢复时间 | 峰值后回到基线 | 超过 30 分钟 |

阈值为示例，应按业务容忍度设定。事件链路的排障入口是消费延迟与死信，不是应用日志。

## 五、Serverless

Serverless 适合事件触发、短时、突发、低运维的场景；把它用在长连接或稳态高负载上，成本与延迟都会反向。

### 5.1 适用边界

函数即服务（Function as a Service，FaaS）的运行特征决定了适用面：无状态、有超时上限、按调用与时长计费、并发受配额限制。

| 特征 | 适配 | 不适配 |
|---|---|---|
| 流量 | 突发、间歇、不可预测 | 稳态高吞吐 |
| 任务时长 | 秒级到分钟级 | 小时级批处理 |
| 状态 | 无状态，外置存储 | 本地缓存、长连接 |
| 延迟 | 可接受冷启动 | P99 敏感交互 |
| 运维 | 希望零服务器管理 | 需要内核级调优 |

### 5.2 不适用场景

- WebSocket 长连接与高频双向推送；
- 持续高负载的 API，按量计费高于常驻实例；
- 需要大内存或 GPU 的推理；
- 单次执行超过平台上限的批处理；
- 依赖本地磁盘或进程内缓存的逻辑；
- 对冷启动尾延迟有硬性 SLA 的同步接口。

这些场景不是“不能做”，是成本或工程约束不划算。判断时用月度成本与 P99 两个数字，不用偏好。

### 5.3 成本模型

按量计费由请求数、执行时长、内存规格共同决定，另有网络与存储费用。

```text
月成本 ≈ 请求数 × (单次执行秒数 × 内存GB × 单价 + 每请求单价)

示例参数：
请求数        3,000 万/月
平均执行      120 ms
内存          512 MB
计算单价      0.000167 元/GB·秒
请求单价      0.0000002 元/次

计算部分 = 3000万 × 0.12 × 0.5 × 0.000167 ≈ 300 元
请求部分 = 3000万 × 0.0000002 = 6 元
```

| 月请求量 | 平均时长 | Serverless 月成本 | 常驻实例月成本 |
|---:|---:|---:|---:|
| 300 万 | 80 ms | 约 21 元 | 约 600 元 |
| 3,000 万 | 120 ms | 约 306 元 | 约 900 元 |
| 3 亿 | 150 ms | 约 3,820 元 | 约 2,700 元 |

数字为示例，单价以实际云厂商为准。趋势是：低请求量时按量计费明显便宜，高请求量时常驻实例反超；拐点取决于单价与利用率。

### 5.4 冷启动与延迟工程

冷启动来自运行时初始化、依赖加载、连接建立。治理手段按收益排序：

| 手段 | 作用 | 代价 |
|---|---|---|
| 预置并发 | 消除大部分冷启动 | 按预留容量计费 |
| 缩小包体 | 缩短初始化 | 构建拆分成本 |
| 选择轻运行时 | 降低启动耗时 | 生态与团队熟悉度 |
| 连接池外置 | 避免每次建连 | 需要代理层 |
| 定时预热 | 降低概率 | 不保证命中 |

冷启动要看 P99 与初始化耗时分布，不看平均值。把 P50 当达标依据，会在流量突增时集中暴露。

### 5.5 运行边界与锁定

Serverless 的锁定不在语言，在事件源、权限模型、部署描述和可观测性接口。降低锁定的做法是把业务逻辑放在与运行时无关的模块里，入口函数只做协议转换。

| 关注点 | 风险 | 缓解 |
|---|---|---|
| 事件源 | 绑定厂商消息服务 | 适配层隔离 |
| 权限 | 厂商 IAM 模型 | 策略即代码，集中管理 |
| 本地开发 | 模拟器行为差异 | 容器化运行同一入口 |
| 配额 | 并发与超时上限 | 压测确认配额 |
| 观测 | 厂商追踪格式 | OpenTelemetry 导出 |

## 六、六边形架构

六边形架构（Hexagonal Architecture，也称端口与适配器）解决的是依赖方向：业务核心不依赖框架、数据库和外部协议。

### 6.1 端口与适配器

端口是业务核心定义的接口，适配器是实现该接口的技术组件。依赖倒置保证核心只依赖自己的抽象。

| 组件 | 归属 | 例子 |
|---|---|---|
| 领域模型 | 核心 | 订单、库存、金额 |
| 应用服务 | 核心 | 下单用例、取消用例 |
| 入站端口 | 核心定义 | 下单接口、查询接口 |
| 入站适配器 | 外层 | HTTP Controller、消息监听 |
| 出站端口 | 核心定义 | 仓储、支付网关、发件箱 |
| 出站适配器 | 外层 | JPA 实现、HTTP 客户端 |

### 6.2 结构与依赖规则

```text
com.example.order/
├── domain/                  # 实体、值对象、领域服务，无框架依赖
├── application/
│   ├── port/in/             # 用例接口
│   ├── port/out/            # 仓储与外部服务接口
│   └── service/             # 用例编排，事务边界
└── adapter/
    ├── in/web/              # Controller，只做协议转换
    ├── in/mq/               # 消息消费者
    └── out/persistence/     # 仓储实现
```

依赖方向只能由外向内。`domain` 不 import 框架注解，`application` 不 import 适配器，适配器之间不互相调用。

### 6.3 与分层架构的差别

| 维度 | 分层架构 | 六边形架构 |
|---|---|---|
| 依赖方向 | 上层依赖下层 | 外层依赖内层 |
| 数据库地位 | 业务依赖数据层 | 数据库是适配器 |
| 测试 | 常需数据库 | 核心可用内存实现测试 |
| 替换成本 | 换存储要改业务 | 换适配器即可 |
| 复杂度 | 低 | 中 |

六边形不是替代单体或微服务的风格，它描述单个服务内部的代码组织。一个模块化单体的每个模块都可以是六边形。

### 6.4 使用边界

不是每个增删改查都需要端口。以下信号出现时，六边形的收益才明显：

- 同一业务核心有多种入口（HTTP、消息、定时任务）；
- 外部依赖需要替换或需要契约测试；
- 核心逻辑需要在无数据库环境下快速测试；
- 存储或第三方接口预计会变更。

反例是“一张表一个仓储接口、一个服务接口、一个实现类”的机械套用。层数增加但没有替换需求，只会提高阅读成本。

## 七、选型矩阵与团队容量

选型要把业务约束、团队容量和长期成本放在同一张表里打分；单看技术特性，任何风格都能找到支持理由。

### 7.1 选型维度与权重

| 维度 | 说明 | 权重示例 |
|---|---|---|
| 交付节奏 | 发布频率、变更独立性、峰值弹性 | 40% |
| 团队容量 | 开发、值班、平台人力、长期成本 | 30% |
| 一致性 | 强事务与对账要求 | 30% |

流量形态折进交付节奏：峰值越高，独立扩容的权重越大。运维能力与基础设施成本折进团队容量：能力越弱、预算越紧，可维护性权重越高。三个维度足以拉开差距，维度再多，打分反而变成拍脑袋。

权重由业务定，不由架构师偏好定。合规行业的“一致性”权重往往高于“交付节奏”，增长型业务相反。

### 7.2 风格对比矩阵

| 风格 | 部署单元 | 数据归属 | 团队映射 | 主要代价 |
|---|---|---|---|---|
| 单体 | 一个 | 共享 schema | 多团队共用 | 变更耦合、整机扩容 |
| 模块化单体 | 一个 | 模块私有 schema | 模块有 owner | 边界靠纪律与测试 |
| 微服务 | 每服务 | 每服务私有 | 团队拥有服务 | 分布式复杂度、平台成本 |
| 事件驱动 | 随宿主 | 按聚合划分 | 按事件契约协作 | 最终一致、重复与顺序 |
| Serverless | 每函数 | 外置存储 | 按能力划分 | 冷启动、配额、锁定 |

事件驱动与 Serverless 可以和前三种组合，矩阵中的“部署单元”只表示其典型形态。

### 7.3 团队容量模型

康威定律（Conway's Law）指出系统结构会复制组织沟通结构。选型必须回答“谁来拥有、谁来值班”。

| 团队规模 | 可维护服务数 | 必需平台能力 |
|---:|---:|---|
| 5 人 | 1 到 3 | 托管流水线、基础监控 |
| 15 人 | 4 到 8 | 服务目录、集中日志、告警 |
| 40 人 | 10 到 20 | 平台组、网关、契约管理 |
| 100 人 | 25 到 50 | 多集群、成本分摊、治理 |

数值为经验区间，取决于自动化程度。一个可用的估算公式是：可维护服务数 ≈ 后端人数 ÷ 每服务最低人力，每服务最低人力包含开发、值班、升级维护，通常不低于 2 人。

平台人力配比常用 1 名平台工程师支撑 8 到 10 名产品工程师。低于这个配比，平台能力会成为拆分的瓶颈。

### 7.4 加权打分示例

场景：40 名工程师的 B2B SaaS，强事务集中在订单与库存，发布每月两次，运维 3 人。

| 风格 | 交付 | 容量 | 一致性 | 加权分 |
|---|---:|---:|---:|---:|
| 单体 | 2 | 5 | 5 | 3.8 |
| 模块化单体 | 4 | 5 | 5 | 4.6 |
| 微服务 | 5 | 2 | 2 | 3.2 |
| 事件驱动 | 4 | 3 | 2 | 3.1 |
| Serverless | 3 | 4 | 2 | 3.0 |

分数 1 到 5，加权分 = Σ 维度分 × 权重。示例结论是模块化单体优先，事件驱动用于通知类副作用；这个结论依赖权重，换一组业务约束可能不同。

> 边界：打分用于暴露分歧，不用于代替决策。两个方案分数接近时，选可逆性更高的那个；分数差距来自权重争议时，先把权重谈拢。

## 八、迁移代价

迁移成本由数据迁移、双跑验证、组织协调和回退能力四项构成；只算开发工日，通常会低估一半以上。

### 8.1 四条迁移路径

| 路径 | 风险 | 适用 |
|---|---|---|
| 一次性切换 | 高 | 小系统、可停机 |
| 绞杀者 | 中 | 单体逐步外移 |
| 分支抽象 | 中低 | 同进程内替换实现 |
| 并行运行 | 低 | 账务、核心链路 |

### 8.2 绞杀者模式的执行顺序

1. 在入口加路由层，按路径或租户分流；
2. 选定一个可独立的能力，先复制读路径；
3. 读流量切到新实现，比较结果差异；
4. 写路径双写或变更数据捕获（CDC）同步；
5. 对账通过后切写流量；
6. 观察一个完整业务周期，再下线旧路径。

顺序不能颠倒。先切写再补对账，会把数据修复成本留到上线后。

### 8.3 数据迁移的控制点

| 阶段 | 主要风险 | 控制手段 |
|---|---|---|
| 双写 | 两边不一致 | 幂等键、版本号、补偿任务 |
| 增量同步 | 延迟与丢失 | CDC 位点监控、延迟告警 |
| 全量校验 | 样本偏差 | 分片校验、金额汇总比对 |
| 切读 | 旧数据未同步 | 读灰度、差异率阈值 |
| 切写 | 回退窗口不足 | 保留双写、限时回退 |
| 下线 | 隐藏依赖 | 依赖扫描、流量清零确认 |

### 8.4 迁移成本估算

| 工作项 | 人日 | 说明 |
|---|---:|---|
| 边界梳理 | 15 | 领域事件、表依赖、调用图 |
| 模块改造 | 40 | 接口化、去共享表 |
| 新服务开发 | 30 | 含测试与契约 |
| 数据同步与对账 | 25 | 双写、CDC、校验工具 |
| 观测与告警 | 10 | 指标、追踪、看板 |
| 双跑与演练 | 15 | 故障注入、回退演练 |
| 培训与文档 | 5 | 值班手册、ADR |
| 合计 | 140 | 约 7 人月 |

数字为示例。隐藏成本主要在双跑与回退演练；省掉这两项，故障时的恢复时间会把节省的工日全部吃掉。

### 8.5 迁移的停止条件

迁移不是必须完成的项目。出现以下情况应暂停或改为模块化：

- 目标服务没有明确 owner；
- 数据对账差异率连续两周无法降到阈值内；
- 平台能力缺口导致新服务无法独立排障；
- 迁移成本超过三年预计收益；
- 业务方向变化使目标边界失效。

模块化单体本身就可以是迁移终点。把“拆成微服务”当成功标准，会让团队为架构标签付出不必要成本。

## 九、决策清单与失败模式

选型结论要能回答约束、选项、代价、验证四个问题；答不上来的部分，通常是还没调研。

### 9.1 选型决策清单

1. 当前最痛的问题是交付、容量、一致性还是故障隔离，证据是什么？
2. 团队规模、值班能力、平台人力能否支撑目标风格？
3. 至少三个候选方案分别是什么，代价项是否量化？
4. 数据边界与事务边界是否一致，跨边界操作如何补偿？
5. 迁移路径与回退窗口是什么，回退演练做过没有？
6. 目标风格的可逆性如何，多久能回到上一状态？
7. 用什么指标验证成功，观察期多长？
8. 哪些决策需要写成 ADR，谁批准，何时复审？

### 9.2 常见失败模式

| 失败模式 | 表现 | 纠正 |
|---|---|---|
| 追新 | 以招聘或行业声量为依据 | 用约束与成本表重做选型 |
| 过度拆分 | 服务数远超团队数 | 合并或回到模块化 |
| 分布式单体 | 共享库、联合发布 | 先消除共享表与共享库 |
| 忽视运维 | 上线后无追踪、无值班 | 补平台能力再扩服务 |
| 只算开发成本 | 不含双跑、培训、回退 | 用全生命周期成本 |
| 一次到位 | 大爆炸迁移 | 改绞杀者，分批切 |
| 无验证 | 上线即宣布成功 | 设指标与观察期 |

## 十、最佳实践案例

### 10.1 案例背景

一家 B2B 供应链 SaaS 公司，40 名工程师分 6 个小组，主力系统是运行 6 年的 Java 单体：约 80 万行代码、一个 MySQL 库、每月发布 2 次。月订单约 120 万，大促峰值查询 P99 为 1.8 秒，主库 CPU 峰值 85%。

痛点是发布排队：订单组与库存组每周互相等待窗口；一次发布回归范围覆盖全部模块；大促时整机扩容，成本按 3 倍峰值准备。目标是在 12 个月内把发布周期降到每周、订单查询 P99 降到 500 毫秒以内，且不能停机迁移。

约束是团队没有服务网格、平台组只有 3 人、合同承诺大促期间可用率 99.9%、预算只能增加 20%。这些约束直接排除了“全面微服务”。

改造目标写成一条质量属性场景：

```text
来源：大促期间的运营用户
刺激：以 200 QPS 并发查询最近 90 天订单
制品：订单查询 API
环境：峰值流量，只读副本可用
响应：返回分页结果，副本延迟超标时降级主库
度量：P99 ≤ 500 ms，错误率 < 0.1%，持续 30 分钟
```

### 10.2 案例实操

第一步是边界梳理。用事件风暴列出 9 个业务能力，统计表访问关系，发现订单、库存、结算三个模块共享 14 张表，跨模块 SQL 有 60 多处。结论是先做模块化，而不是先拆服务。

候选方案对比：

| 选项 | 代价 | 主要风险 |
|---|---|---|
| 保持单体，只做扩容 | 低 | 发布排队不解决，成本随峰值上涨 |
| 全面微服务 | 高 | 平台人力不足，分布式单体 |
| 模块化单体加按需抽取 | 中 | 边界执行不到位会退化 |
| 直接换云托管架构 | 高 | 迁移停机，合同不允许 |

决策是模块化单体为主，抽取两个服务：库存查询服务与通知服务；订单事件通过发件箱加消息队列异步发布；不引入服务网格。

执行顺序：

1. 按业务能力重划包结构，模块只暴露 `api` 包；引入 ArchUnit 规则，跨模块 import 在 CI 直接失败。
2. 14 张共享表按写入方归属拆分 schema，跨模块查询改为接口调用；对无法立即拆的 3 张表设半年期限。
3. 库存查询读路径先抽服务，走 CDC 同步，读流量按租户灰度，差异率低于 0.01% 后全量。
4. 通知服务独立，消费订单事件；消费端以订单号加事件类型做幂等键。
5. 建统一 Trace、消费延迟看板与死信告警；平台组从 3 人补到 4 人。
6. 做两次回退演练：一次库存服务回切单体读路径，一次消息链路降级为同步发送。

### 10.3 案例结果

上线 9 个月后的指标如下，均为示例数据：

| 指标 | 改造前 | 改造后 |
|---|---:|---:|
| 发布频率 | 2 次/月 | 2 次/周 |
| 变更前置时间 | 18 天 | 5 天 |
| 订单查询 P99 | 1.8 s | 420 ms |
| 主库 CPU 峰值 | 85% | 52% |
| 基础设施月成本 | 1.0 倍 | 1.18 倍 |
| 发布失败率 | 18% | 7% |

复盘有四点。第一，收益主要来自模块化与共享表拆分，微服务只贡献了库存查询的独立扩容；原计划抽 6 个服务，实际 2 个就够。第二，通知服务独立后价值有限，但事件链路为后续结算对账提供了基础。第三，ArchUnit 规则上线首月出现 40 多次构建失败，团队补了 6 条例外，规则才稳定；没有例外机制的规则会被整体关闭。第四，事件重复导致过两次重复通知，补幂等键后消失；这类问题在双跑阶段没有暴露，因为当时流量太小。

失败模式也记录在案：库存服务切读时，CDC 延迟一度达到 8 秒，灰度差异率升到 0.3%，回退到单体读路径后恢复；根因是同步位点未纳入告警。后续把复制延迟纳入一级告警，并把回退开关做成配置项，不再依赖发版。
