# 存储选型与分库分表

> 这篇从“一条数据该放在哪种存储里”讲起，经过关系库、文档库、宽表、搜索引擎和对象存储的边界，冷热分离，分片键与路由，全局 ID，跨分片查询的约束，最后落到平滑扩容、迁移对账和一次完整的订单库分库分表决策。
>
> 学完能为一类数据选出权威存储并说明理由，能设计可扩容的分片方案，能写出不停机迁移的步骤、校验和回滚预案。

## 一、存储选型先定数据形状

存储选型的顺序是：先定权威源，再定访问模式，最后才比较产品。反过来做——先挑一个流行数据库再找理由——是大多数存储返工的开始。

三个问题按顺序回答：

1. 这条数据的权威源是谁？只允许一个系统对它有写权限，其余都是派生副本。
2. 读写比例和查询形状是什么？按主键点查、按范围扫、按多个条件组合过滤、全文检索，对应的存储完全不同。
3. 能容忍多少丢失和多少延迟？这决定同步复制还是异步复制，也决定能不能用最终一致的搜索索引。

| 数据形状 | 典型访问 | 首选存储 | 不选它的理由 |
|---|---|---|---|
| 交易与账务 | 单行读写、事务 | 关系库 | 无 |
| 聚合根整体读写 | 按 ID 取整棵文档 | 文档库 | 跨文档事务弱 |
| 写入密集的时序/日志 | 按 key + 时间范围 | 宽表 | 组合查询弱 |
| 多条件检索与排序 | 任意字段过滤 | 搜索引擎 | 不是权威源 |
| 图片、备份、归档文件 | 按 URL 取整块 | 对象存储 | 不支持随机改写 |

### 1.1 五类存储的分工

关系库（Relational Database）负责需要事务和强约束的核心数据；文档库（Document Database）负责结构多变、以聚合根为单位读写的业务数据；宽表（Wide-Column Store）负责写入量大、按 key 和时间访问的数据；搜索引擎（Search Engine）负责多条件检索；对象存储（Object Storage）负责不可变的大块数据。

分工的判据是“这条数据会不会被两种访问模式同时需要”。会，就拆成权威源加派生索引；不会，就不要为了“技术栈统一”硬塞进一个库。

边界：一个系统里出现五种存储不稀奇，稀奇的是同一个业务事实有两个可写副本。多存储的前提是写路径唯一。

### 1.2 选型矩阵

按需求给候选打分，比“熟悉哪个用哪个”可靠。下表是某订单系统的实际评分（1–5 分，示例）。

| 需求 | 关系库 | 文档库 | 宽表 | 搜索引擎 |
|---|---|---|---|---|
| 事务与唯一约束 | 5 | 3 | 1 | 1 |
| 按主键点查延迟 | 5 | 5 | 5 | 4 |
| 多条件组合查询 | 4 | 3 | 1 | 5 |
| 水平写入扩展 | 2 | 4 | 5 | 4 |
| 运维与人才储备 | 5 | 3 | 2 | 4 |
| 合计 | 21 | 18 | 14 | 18 |

矩阵只解决“往哪个方向想”，不替人做决定。关系库合计最高，但当写入达到单机上限时，第 4 行的 2 分会变成硬约束，这时才需要分片或换存储。

边界：评分权重必须来自业务。报表系统会把“组合查询”权重调到 5，交易系统会把“事务”权重调到 5，同一张表得出相反结论是正常的。

### 1.3 权威源与派生索引

搜索引擎、缓存、宽表里的数据都必须是派生副本，写路径只写权威源，再通过变更日志（Change Data Capture，CDC）同步。派生副本可以随时重建，这是它和权威源最重要的区别。

```text
写请求 → 订单库（权威源） → binlog → CDC → Elasticsearch（派生索引）
                                      → Redis（派生缓存）
```

同步链路的三个必备能力：

- 可重放：binlog 位点可回溯，重建索引时能从某个时间点重新消费。
- 可幂等：同一条消息重复消费不产生副作用，用主键覆盖而不是追加。
- 可观测：消费延迟有指标，延迟超过阈值告警，而不是等用户发现搜不到。

边界：不要让写请求同时写权威源和搜索索引并等待两者都成功。搜索失败不该让下单失败；正确做法是写库成功后发事件，索引失败重试。

## 二、关系库的容量边界

关系库能撑到多大，不由“单表多少万行”这个流传的数字决定，而由索引高度、单行大小、缓冲池命中率、备份恢复时长和 DDL 时长共同决定。

### 2.1 单表容量的真实约束

InnoDB 的聚簇索引把整行存在主键 B+ 树的叶子页上，二级索引的叶子存的是主键值。页大小 16KB，非叶子节点每条记录约 14 字节（主键 8 字节加页号 6 字节），一页约存 1170 条。

```text
两层非叶子：1170 × 1170 ≈ 137 万 个叶子页
叶子页存 16 行（单行约 1KB）：137 万 × 16 ≈ 2190 万 行
```

也就是说，单行 1KB 的表，三层 B+ 树大约到 2000 万行；行更小能到 5000 万行以上，行更大（含大字段）可能 1000 万行就回落磁盘。行数不是关键，**索引总大小是否能放进缓冲池**才是。

| 信号 | 阈值（示例） | 该做什么 |
|---|---|---|
| 单表行数 | > 2000 万且持续增长 | 评估归档或分片 |
| 单表数据+索引 | > 100GB | 拆分或归档 |
| 缓冲池命中率 | < 99% | 加内存或拆表 |
| 备份恢复耗时 | > RTO 的一半 | 减小单库体积 |
| DDL 时长 | > 业务低峰窗口 | 用 gh-ost/pt-osc 或分片 |

```sql
-- 查单表体积与索引体积，判断是数据大还是索引大
SELECT table_name,
       ROUND(data_length / 1024 / 1024 / 1024, 2) AS data_gb,
       ROUND(index_length / 1024 / 1024 / 1024, 2) AS index_gb,
       table_rows
FROM information_schema.tables
WHERE table_schema = 'order_db'
ORDER BY data_length + index_length DESC
LIMIT 10;
```

预期输出是一张按体积排序的表。若 `index_gb` 超过 `data_gb` 的一半，说明索引建多了，先删低效索引比拆库便宜。

边界：`table_rows` 是估算值，InnoDB 的统计信息有误差，精确行数要用 `COUNT(*)` 或 `information_schema` 配合采样。用估算值做容量决策时要留 20% 余量。

### 2.2 读写分离解决什么

读写分离（Read-Write Splitting）只解决读压力，不解决写压力，也不解决单表体积。

| 瓶颈 | 读写分离有效 | 分库分表有效 |
|---|---|---|
| 读 QPS 高 | 是 | 是 |
| 写 TPS 高 | 否 | 是 |
| 单表体积大 | 否 | 是 |
| 备份恢复慢 | 部分 | 是 |
| 索引维护成本 | 否 | 是 |

复制延迟是读写分离的固有代价。MySQL 半同步复制（semi-synchronous replication）只能保证至少一个副本收到日志，不保证副本已应用；组复制（Group Replication）能提供更强保证，但写延迟上升。

```sql
-- 在只读副本上确认延迟，超过阈值应把读请求切回主库
SHOW REPLICA STATUS\G
-- 关注 Seconds_Behind_Source 与 Retrieved_Gtid_Set / Executed_Gtid_Set 的差
```

边界：写完立刻读的场景必须显式走主库。这类查询靠“默认路由到副本”一定会出错，而且只在低概率下出错，测试很难覆盖。

### 2.3 分区表能做什么不能做什么

分区表（Partitioned Table）把一个大表按分区键切成多个物理文件，对 SQL 透明。它能加速按分区键的范围删除和扫描，但不能提升并发写入能力，因为所有分区仍在同一个实例上。

MySQL 8.4 的关键限制：

- 所有唯一索引（含主键）必须包含分区键，否则无法建表。
- 分区表不支持外键。
- 分区数过多会增加打开文件和元数据开销，建议不超过 100 个。
- 跨分区查询会扫描所有分区，分区裁剪只对分区键条件生效。

```sql
-- 按月份做范围分区；主键必须包含 create_time
CREATE TABLE order_archive (
  id          BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  create_time DATETIME NOT NULL,
  amount      DECIMAL(12,2) NOT NULL,
  PRIMARY KEY (id, create_time)
) PARTITION BY RANGE COLUMNS (create_time) (
  PARTITION p202601 VALUES LESS THAN ('2026-02-01'),
  PARTITION p202602 VALUES LESS THAN ('2026-03-01'),
  PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);
```

边界：分区表适合“按时间归档、按时间删除”的场景，不适合“按用户分散写入”的场景。把分区当分片用，最后会在单机上撞到同样的写上限。

## 三、文档、宽表、搜索引擎与对象存储

四类非关系存储在边界清晰时非常好用，边界模糊时会把一致性问题带进核心链路。

### 3.1 文档库：聚合根整体读写

文档库把一棵对象树存成一个文档，读一次拿全，适合商品详情、用户画像、表单配置这类“整体读写、字段经常变”的数据。

适用判据：

- 绝大多数查询按文档 ID 或少量索引字段命中；
- 一次业务操作只改一个文档，或能接受跨文档最终一致；
- 字段结构随业务演进，不想为每个新字段做 DDL。

不适用判据：

- 需要跨文档 join 和强事务（订单、账务、库存扣减）；
- 需要按任意字段组合做聚合统计；
- 文档会无限增长（评论列表塞进商品文档），导致文档体积失控。

MongoDB 8.x 的单文档大小上限是 16MB，超过就要拆集合。文档内数组无限追加是常见错误，正确做法是把子项放独立集合，用父 ID 关联。

### 3.2 宽表：按 key 和时间写入

宽表（Wide-Column Store，如 Cassandra 5.x、HBase 2.6、ScyllaDB）按分区键把数据分布到多个节点，写入是追加式的，适合日志、指标、消息、轨迹这类写多读少、按 key 加时间范围查询的数据。

| 能力 | 宽表表现 |
|---|---|
| 写入吞吐 | 线性扩展，随节点增加 |
| 按分区键点查 | 单节点命中，延迟低 |
| 按时间范围扫 | 同一分区内有序，效率高 |
| 多条件组合查询 | 需要预先建物化视图或额外索引 |
| 跨分区聚合 | 需要外部计算引擎 |
| 事务 | 单分区轻量事务，跨分区基本没有 |

数据建模的核心是“先定查询，再定主键”。Cassandra 的主键分成分区键和聚类键，分区键决定数据落在哪个节点，聚类键决定分区内排序。查询不带分区键就是全集群扫描，生产上必须禁止。

边界：宽表不适合做“运营后台随意筛选”。后台需求变化快，宽表的主键改一次就要重刷全量数据，代价极高。这类需求应该走搜索引擎或离线数仓。

### 3.3 搜索引擎：索引不是数据库

搜索引擎（Elasticsearch 8.x/9.x、OpenSearch）擅长多条件过滤、相关性排序和聚合分析，但它的写入是近实时的（默认 1 秒刷新），没有跨文档事务，也没有真正的权威性。

三条铁律：

1. 搜索索引永远不是权威源，丢了要能从权威源重建。
2. 写索引必须幂等，用业务主键做文档 ID，重复写入覆盖而不是新增。
3. 索引映射（mapping）要显式定义，禁止动态映射把数值猜成字符串。

```jsonc
// 显式映射片段：金额用 scaled_float，时间用 date，避免动态映射猜错类型
{
  "mappings": {
    "properties": {
      "order_id":  { "type": "keyword" },
      "user_id":   { "type": "keyword" },
      "amount":    { "type": "scaled_float", "scaling_factor": 100 },
      "status":    { "type": "keyword" },
      "created_at":{ "type": "date" }
    }
  }
}
```

深分页是搜索引擎的典型陷阱。`from + size` 超过 10000 会触发 `index.max_result_window` 限制，即使调大也会让协调节点内存暴涨。正确做法是 `search_after` 游标翻页，或限制用户只能看前 N 页。

边界：需要“精确一致”的列表页不要用搜索索引。订单列表这类必须反映最新状态的页面，应该查权威库；搜索只用于“模糊找”。

### 3.4 对象存储：不可变的大块数据

对象存储（Object Storage，如 S3、OSS、MinIO）以桶和对象组织数据，对象写入后整体替换，不支持随机偏移改写。适合图片、视频、备份、日志归档、数据湖文件。

| 特性 | 含义 | 影响 |
|---|---|---|
| 整体读写 | 不支持部分更新 | 小文件频繁改要换方案 |
| 强一致（S3 自 2020 起） | 写后读立即可见 | 可以做元数据主存 |
| 预签名 URL | 临时授权直传直读 | 业务服务不转发大文件 |
| 生命周期策略 | 到期转低频/归档/删除 | 冷热分离的主要工具 |
| 版本控制 | 保留历史版本 | 防误删，但成本上升 |

不要把它当文件系统：重命名是复制加删除，目录是前缀模拟，列目录在大桶上很慢。目录层级超过三层、单前缀对象超过百万，列表操作就会变慢。

边界：对象存储适合“一次写、多次读、很少改”。需要频繁修改的配置文件、需要按行查询的数据，都不该放这里。

### 3.5 组合使用的反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 双写数据库和搜索索引 | 一边失败就长期不一致 | 写库后发事件，异步建索引 |
| 用搜索索引做唯一性校验 | 近实时导致重复注册 | 唯一约束落在权威库 |
| 把大字段存进关系库 | 页分裂、备份膨胀 | 存对象存储，库存 URL |
| 用宽表做运营后台查询 | 全表扫描或频繁改主键 | 走搜索或离线数仓 |
| 缓存当唯一数据源 | 缓存淘汰即数据丢失 | 缓存只做加速 |

## 四、冷热分离

冷热分离（Hot-Cold Separation）按访问频率把数据分到不同介质，目标是在不牺牲热数据性能的前提下降低存储成本和备份窗口。

### 4.1 分层与判据

| 层级 | 数据年龄（示例） | 介质 | 查询延迟 | 相对成本 |
|---|---|---|---|---|
| 热 | 0–90 天 | 关系库主库+副本 | 毫秒 | 1.0 |
| 温 | 91–365 天 | 历史库/只读实例 | 十毫秒 | 0.4 |
| 冷 | 1–3 年 | 对象存储+Parquet | 秒级 | 0.05 |
| 归档 | 3 年以上 | 归档存储 | 分钟级 | 0.01 |

判据不是“数据多老”，而是“多久被访问一次”。先统计访问分布：如果 90 天以前的数据只占查询量的 2%，把它挪走对整体延迟几乎无影响；如果占 30%，挪走就是把问题搬家。

```sql
-- 统计订单查询的年龄分布，决定冷热分界线（示例库）
SELECT CASE
         WHEN create_time >= NOW() - INTERVAL 90 DAY  THEN '0-90d'
         WHEN create_time >= NOW() - INTERVAL 365 DAY THEN '91-365d'
         ELSE '365d+'
       END AS age_bucket,
       COUNT(*) AS cnt
FROM order_query_log
WHERE created_at >= NOW() - INTERVAL 7 DAY
GROUP BY age_bucket;
```

边界：冷热分界线要按业务定，不能照抄 90 天。电商订单的查询高峰集中在下单后 30 天，金融流水的查询由合规驱动，可能三年内的数据都必须在线可查。

### 4.2 三种落地方案

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 同库归档表 | 热表和归档表放同一实例 | 改造小，事务简单 | 不减少实例体积 |
| 独立历史库 | 归档数据搬到只读实例 | 隔离备份与故障 | 跨库查询要应用层合并 |
| 对象存储+元数据 | 明细转 Parquet，元数据入库 | 成本最低 | 查询要经过计算引擎 |

同库归档最容易被低估：它只是把行从一张表挪到另一张表，实例体积、备份时间、缓冲池压力都没变。真正的冷热分离要让冷数据离开热实例。

独立历史库的查询路径：

```text
按订单号查详情
  → 先查热库（覆盖 90 天内）
  → 未命中再查历史库
  → 仍未命中返回“已归档，请走客服工单”
```

这条路径必须设“不回写”：查历史库的结果不要写回热库，否则冷数据会被查询重新加热，冷热分离失效。

边界：冷数据要满足“可查、可删、可审计”三条。只搬到对象存储而没建索引，客服和合规都用不了；没有删除流程，个人信息保护要求无法满足；没有校验和，归档文件损坏无法发现。

### 4.3 成本与合规边界

以 10TB 订单明细为例（示例单价，按 2026 年公有云公开价量级）：

| 介质 | 单价（元/GB/月） | 10TB 月成本 | 适用 |
|---|---:|---:|---|
| 关系库 ESSD | 1.0 | 10,240 元 | 热数据 |
| 对象存储标准 | 0.12 | 1,228 元 | 温数据 |
| 对象存储归档 | 0.033 | 338 元 | 冷数据 |

成本差两个数量级，但归档存储有最短存储期和取回费用。存 30 天就删的数据放归档反而更贵。

合规边界要提前确认：

- 留存期：交易数据通常要求 5 年以上，具体按行业规定。
- 删除权：用户注销后要能定位并删除其全部冷数据，归档文件必须按用户可分片。
- 加密：冷数据同样要加密，密钥轮换周期要覆盖归档期。
- 审计：谁在什么时候查了哪条冷数据，要有日志。

## 五、分片键与路由

分片键（Shard Key）决定数据分布，也决定哪些查询能路由到单分片。选错分片键，后面所有优化都是在补这个洞。

### 5.1 好分片键的四个条件

一个可用的分片键同时满足四条：

1. 高基数：取值足够多，单值数据量可控。
2. 分布均匀：不会因为业务特征集中在少数值上。
3. 查询覆盖：绝大多数在线查询都带这个条件。
4. 不可变：创建后不更新，避免跨分片搬数据。

四条里最容易忽略的是第 3 条。分片键选得再均匀，如果 80% 的查询不带它，每次查询都要广播到所有分片，分片就只剩存储收益。

### 5.2 候选键评估

| 候选键 | 基数 | 均匀性 | 查询覆盖 | 主要风险 |
|---|---|---|---|---|
| 用户 ID | 高 | 好 | 用户维度查询全覆盖 | 大卖家/大客户热点 |
| 订单 ID | 极高 | 好 | 只覆盖按订单号查 | 用户订单列表要广播 |
| 商户 ID | 中 | 差（头部集中） | 商户后台全覆盖 | 头部商户打爆单分片 |
| 创建时间 | 低 | 差（当前月集中） | 范围查询好 | 写入全压最新分片 |
| 自增 ID | 极高 | 差（尾部集中） | 点查 | 写入热点，扩容难 |

订单系统的常见解法是“基因法”：订单号里嵌入用户 ID 的低位，让订单号和用户 ID 指向同一分片。

```text
order_id = 时间戳(41bit) << 23 | user_id 低 10bit << 13 | 序列(13bit)
路由：shard = (order_id >> 13) & 0x3FF  等价于 user_id 的低 10 位
```

这样按订单号查和按用户查都能单分片命中。代价是订单号长度增加，且用户 ID 位宽固定后不能随意改分片数。

边界：基因法适合“一个用户的数据必须同分片”的场景。如果业务要求按商户聚合，而订单同时属于用户和商户，就要选一个主维度，另一个维度用冗余表解决。

### 5.3 路由算法

| 算法 | 扩容影响 | 范围查询 | 适用 |
|---|---|---|---|
| 取模 | 扩容要重分布大部分数据 | 差 | 分片数固定 |
| 范围 | 只影响边界分片 | 好 | 按时间/ID 段 |
| 目录表 | 灵活，可手动调度 | 好 | 大客户单独分片 |
| 一致性哈希 | 只迁移相邻数据 | 差 | 缓存节点 |

数据库分片优先用“逻辑分片 + 目录映射”，不要直接用一致性哈希。一致性哈希解决了缓存节点的增减问题，但打散了范围查询，而数据库恰恰需要范围扫描。


路由表存在配置中心或元数据库，应用启动时加载并监听变更。路由规则必须能热更新，否则扩容要重启全部应用。

### 5.4 热点与大客户

均匀的分片键也会出现热点，因为业务分布本身不均匀。SaaS 系统里 1% 的租户可能产生 40% 的写入。

三种处理方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| 大客户上浮 | 单独库或单独分片 | 路由要支持例外 |
| 二次拆分 | 热点键加后缀散列 | 查询要聚合多片 |
| 写入削峰 | 队列缓冲、批量合并 | 延迟上升 |

二次拆分会破坏“同键同片”，只适合可合并的写多读少场景（如计数器、日志）。订单这类需要按用户聚合的数据，优先用大客户上浮。

边界：热点判断要靠监控，不要靠猜。按分片统计 QPS 和体积，偏差超过 30% 就说明分布有问题。

### 5.5 逻辑分片与物理分片

一次性把物理分片数定死，后续扩容只能重分布。标准做法是先定较多逻辑分片，再映射到较少的物理库表：

```text
逻辑分片：1024 个（2 的幂，便于位运算和翻倍）
物理库：   16 个（每个库 64 个逻辑分片）
物理表：   每库 4 张（每张表 16 个逻辑分片）
```

扩容时把逻辑分片成组迁移：16 库扩到 32 库，每库迁出一半逻辑分片，迁移单位是 32 个逻辑分片而不是单行数据。逻辑分片数量在系统生命周期内不变，物理布局可以变。

边界：逻辑分片数不是越多越好。1024 个逻辑分片意味着每张物理表都要能容纳 1/64 的数据，单表体积下限被抬高；数据量小的系统用 256 或 64 就够。

## 六、全局 ID

分片之后自增主键不再全局唯一，必须在写入前生成 ID。ID 方案影响索引局部性、号段长度和可用性。

### 6.1 ID 的需求

| 需求 | 说明 | 不满足的后果 |
|---|---|---|
| 全局唯一 | 多分片并发生成不冲突 | 主键冲突，写入失败 |
| 趋势递增 | 新 ID 大于旧 ID | 随机主键导致页分裂 |
| 不可猜测 | 不能从 ID 推出总量 | 泄露业务规模 |
| 高可用 | 生成服务不能是单点 | 写链路整体不可用 |
| 长度可控 | 8 字节以内 | 索引膨胀 |

“趋势递增”比“严格递增”更容易满足，也更实用。同一毫秒内的顺序不重要，重要的是新数据落在 B+ 树右侧，而不是随机插入中间。

### 6.2 方案对比

| 方案 | 有序性 | 长度 | 依赖 | 主要风险 |
|---|---|---|---|---|
| 数据库自增 | 严格 | 8B | 单库 | 分片后不唯一 |
| UUIDv4 | 无序 | 16B | 无 | 页分裂，索引膨胀 |
| UUIDv7 | 趋势有序 | 16B | 无 | 长度仍是 16B |
| Snowflake | 趋势有序 | 8B | 时钟+workerId | 时钟回拨 |
| 号段模式 | 趋势有序 | 8B | 数据库 | 号段浪费 |
| Redis INCR | 严格 | 8B | Redis | 持久化风险 |

UUIDv4 做主键的问题值得单独说：16 字节随机值让每次插入都落在 B+ 树随机位置，页分裂和缓冲池污染会把写入吞吐拉低一个数量级。UUIDv7 把时间戳放在高位，解决了顺序问题，但 16 字节的长度仍然让二级索引变大。

边界：对外暴露的 ID 和对内主键可以分开。对内用 Snowflake 保证索引效率，对外用短码或加密 ID 防止遍历，两套 ID 用映射表关联。

### 6.3 Snowflake 与时钟回拨

Snowflake 把 64 位切成三段的经典分配是：41 位毫秒时间戳、10 位机器号、12 位序列号。41 位可用约 69 年，10 位支持 1024 个节点，12 位支持单节点每毫秒 4096 个 ID。

时钟回拨是它唯一的硬伤。服务器 NTP 校时可能把时钟往回拨几十毫秒，这时生成的 ID 会重复。

```java
// 片段：时钟回拨的处理策略，回拨小于 5ms 等待，超过则拒绝并告警
long now = System.currentTimeMillis();
if (now < lastTimestamp) {
    long offset = lastTimestamp - now;
    if (offset <= 5) {
        // 小幅回拨：等到时间追上，避免生成重复 ID
        Thread.sleep(offset << 1);
        now = System.currentTimeMillis();
    } else {
        // 大幅回拨：宁可让这次写入失败，也不能发出重复 ID
        throw new IllegalStateException("clock moved backwards: " + offset + "ms");
    }
}
```

生产上还要做两件事：workerId 由配置中心统一分配并持久化，不能靠 IP 自动推导（容器重建后 IP 会变）；对 ID 生成服务做多实例部署，单实例故障时由其他实例接管号段。

边界：Snowflake 依赖系统时钟，虚拟机迁移、容器漂移、NTP 配置错误都会触发回拨。不能接受写入失败的核心链路，应该改用号段模式。

### 6.4 号段模式

号段模式（Segment Mode）从数据库一次取一批 ID 缓存在内存，用完再取。它不依赖时钟，数据库只承担低频的号段分配。

```sql
-- 号段表：每个业务一行，step 是每次分配的批量大小
CREATE TABLE id_segment (
  biz_tag    VARCHAR(64)  NOT NULL PRIMARY KEY,
  max_id     BIGINT       NOT NULL,
  step       INT          NOT NULL DEFAULT 1000,
  updated_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 一条语句原子推进并取回号段结束值；LAST_INSERT_ID 是连接级变量，避免并发读到别人的值
UPDATE id_segment
SET max_id = LAST_INSERT_ID(max_id + step), updated_at = NOW()
WHERE biz_tag = 'order';
SELECT LAST_INSERT_ID() AS segment_end;
```

本次可用区间是 `[segment_end - step + 1, segment_end]`。进程只把这个区间缓存在内存，不逐条访问数据库。

双 buffer 是它的关键优化：当前号段用到 20% 时异步加载下一个号段，避免每次切换都等数据库。两个 buffer 都耗尽时才阻塞，这时数据库不可用会直接影响写入。

边界：号段模式生成的 ID 在进程重启后会跳一段（未用完的号段丢弃），这是可接受的；但不能接受 ID 不连续的业务（如流水号）要另行处理。

### 6.5 业务 ID 与主键分离

订单号、支付流水号这类对外可见的编号，不要直接等于数据库主键。分开的理由：

- 业务编号有格式要求（前缀、日期、校验位），主键没有；
- 业务编号可能要在创建前预占，主键只能在插入时生成；
- 业务编号泄露的信息比主键多，需要单独控制。

```text
主键 id       = 1839204756102930432   （Snowflake，仅内部使用）
业务单号 no   = SO2026111300012345    （对外展示，可读、可检索）
```

两者用唯一索引互相映射，查询走哪个都能命中。

## 七、跨分片查询的约束

分片之后，“写 SQL 让数据库想办法”这条路走不通了。跨分片的 join、排序、分页、事务都要在应用层或中间件层显式处理。

### 7.1 五类查询的处理方式

| 查询类型 | 分片后的处理 | 代价 |
|---|---|---|
| 带分片键的点查 | 直接路由单分片 | 无 |
| 带分片键的范围查 | 路由单分片内范围扫 | 无 |
| 不带分片键的查询 | 广播到全部分片再归并 | 分片数倍放大 |
| 跨分片 join | 拆成两次查询，应用层拼装 | 代码复杂度 |
| 跨分片聚合 | 预聚合表或离线计算 | 数据延迟 |

广播查询必须有硬限制：只允许运营后台使用，带分页上限，走独立限流。C 端接口出现广播查询，说明分片键选错了。

### 7.2 分页与排序

跨分片分页的正确做法是“各分片取前 N 条，归并后再截取”：

```sql
-- 在第 1..16 个分片上分别执行，取回 16 组结果后在应用层归并
SELECT id, user_id, amount, created_at
FROM order_00
WHERE status = 'PAID'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
```

第 2 页要把 `OFFSET` 变成 20，每个分片取 40 条，归并后丢掉前 20 条。页数越深，每个分片返回的行越多，代价线性上升。

深分页的正确解法是游标：用上一页最后一条的 `(created_at, id)` 作为下一页的起点，每个分片取 `> 游标` 的前 N 条。这样无论翻到第几页，每个分片都只返回 N 条。

边界：需要“跳页”的后台列表不要做真分页，改成“上一页/下一页”或导出。页码越大，跨分片归并的成本越不可控。

### 7.3 分布式事务

分片后的事务策略按优先级排：

1. 让事务落在单分片：把需要一起改的数据设计成同一分片键。
2. 单分片本地事务 + 本地消息表：跨分片的部分异步补偿。
3. Saga：把长事务拆成多个本地事务，每步有补偿动作。
4. XA/两阶段提交：只在极少数强一致场景用，性能和可用性代价高。

```text
下单（单分片事务）：
  BEGIN
    INSERT order (...);
    INSERT order_item (...);   -- 同一 user_id，同一分片
  COMMIT
  发事件 → 扣库存（另一服务，Saga 补偿）
```

边界：跨分片强一致几乎总是错误需求。真正需要的是“最终一致 + 可对账”，而不是“分布式锁 + 两阶段提交”。

### 7.4 全局唯一约束

分片表的唯一索引只在单分片内生效。要全局唯一，只有三条路：

| 方式 | 做法 | 适用 |
|---|---|---|
| 由 ID 保证 | 唯一值就是全局 ID | 主键、订单号 |
| 独立索引表 | 唯一键单独一张不分片的表 | 手机号、邮箱 |
| 分片键绑定 | 唯一键与分片键同值 | 用户名即用户 ID |

独立索引表是最常用的方案：一张小表存 `unique_key -> shard_id`，插入前先抢占。这张表会成为写入瓶颈，所以只放真正需要全局唯一的字段，不要把所有唯一索引都搬上去。

```sql
-- 全局唯一索引表：唯一键做本地唯一约束，value 存分片号
CREATE TABLE global_unique (
  uk_type  VARCHAR(32)  NOT NULL,
  uk_value VARCHAR(128) NOT NULL,
  shard_id INT          NOT NULL,
  PRIMARY KEY (uk_type, uk_value)
);
```

边界：索引表本身不能分片，否则又回到同样的问题。它的容量要按“唯一字段数量”估算，通常远小于业务表。

## 八、平滑扩容与数据迁移

扩容的目标不是“把数据搬过去”，而是“在不停机、不丢数据、可回滚的前提下把读写切过去”。

### 8.1 迁移的六个阶段

| 阶段 | 动作 | 校验 | 回滚点 |
|---|---|---|---|
| 0 评估 | 盘点表、索引、SQL、定时任务 | 全量 SQL 清单 | 无 |
| 1 建新库 | 建分片表、双写开关 | 表结构一致性 | 关开关 |
| 2 双写 | 写旧库成功后写新库 | 写入成功率、延迟 | 关开关 |
| 3 全量+增量 | 历史数据搬迁、binlog 追平 | 行数、校验和 | 停同步 |
| 4 影子读 | 双读比对，只返回旧结果 | 差异率 | 关双读 |
| 5 切读 | 按比例/用户灰度读新库 | 错误率、P99 | 切回旧库 |
| 6 切写 | 写新库为准，旧库停写 | 对账、业务指标 | 回滚窗口内切回 |

阶段之间必须有明确的“退出条件”，不满足就不进入下一阶段。最常见的失败是“双写还没稳定就切读”，结果读到的数据缺一块。

### 8.2 双写的实现要点

双写的顺序固定为“先旧后新”，旧库成功才算业务成功：

```text
1. 写旧库，失败 → 整体失败，返回错误
2. 旧库成功，写新库
3. 新库失败 → 记录到补偿表，返回成功（业务不感知）
4. 补偿任务按主键幂等重放
```

反过来“先新后旧”会让旧库失败时新库已有数据，回滚时要清理新库，代价大得多。

幂等键用业务主键，不用自增 ID。补偿任务重复执行时必须覆盖而不是插入，否则会产生重复行。

边界：双写只适合过渡期，必须有结束日期。长期双写的系统会出现“两边都能写、两边都不准”的状态，比单写更危险。

### 8.3 全量与增量

历史数据用批量搬迁，搬迁期间的新变更用 binlog 追平：

```bash
# 片段：用 Debezium 订阅 MySQL binlog，输出到 Kafka 供迁移程序消费
curl -X POST http://debezium:8083/connectors -H 'Content-Type: application/json' -d '{
  "name": "order-source",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "old-mysql",
    "database.server.id": "184054",
    "database.include.list": "order_db",
    "table.include.list": "order_db.orders",
    "topic.prefix": "cdc",
    "schema.history.internal.kafka.bootstrap.servers": "kafka:9092"
  }
}'
```

全量搬迁按主键区间分批，每批 1000–5000 行，批间休眠，避免把旧库 IO 打满。每批记录最大主键，断点续传。

```sql
-- 分批搬迁：按主键区间取，避免大事务和长锁
SELECT id, user_id, amount, status, created_at
FROM orders
WHERE id > ? AND id <= ?
ORDER BY id
LIMIT 2000;
```

边界：搬迁期间不要执行 DDL。DDL 会改变 binlog 结构，轻则解析失败，重则数据错位。迁移窗口内对源库冻结 DDL，是硬性要求。

### 8.4 切读与切写

切读按“百分比 → 用户白名单 → 全量”三步：

```yaml
# 片段：路由开关，支持按百分比和用户白名单灰度
order_route:
  read_new_ratio: 5          # 5% 的读流量走新库
  write_new: false           # 写仍走旧库
  whitelist_user_ids: [1001, 1002]
  fallback_on_error: true    # 新库异常时自动回旧库
```

切写比切读危险得多，因为写错了要修数据。切写前必须满足：

- 连续 3 天对账差异率为 0；
- 双写补偿表的积压为 0；
- 新库的主从延迟在阈值内；
- 回滚脚本演练过一次。

### 8.5 回滚

回滚要能在 5 分钟内完成，且不丢数据。三个前提：

1. 旧库在回滚窗口内保持可写（通常 7 天）；
2. 切写后旧库的写入由补偿任务同步，不能停；
3. 回滚脚本和正向脚本一起写、一起测。

```text
回滚检查表：
□ 停止新库写入（或降为只读）
□ 打开旧库写入开关
□ 校验旧库数据完整（对账）
□ 回放新库独有数据到旧库
□ 确认应用无新库残留连接
```

边界：超过回滚窗口后，旧库会被清理，此时回滚只能靠备份恢复，RTO 从分钟级变成小时级。窗口长度要写进变更单，不能靠记忆。

## 九、对账与一致性校验

迁移期间唯一可信的结论来自对账，不来自“看起来正常”。

### 9.1 三层对账

| 层级 | 比对内容 | 频率 | 能发现的问题 |
|---|---|---|---|
| 行数 | 每分片 count | 每小时 | 漏搬、重复 |
| 聚合 | sum/分组统计 | 每天 | 字段错位、精度丢失 |
| 明细 | 抽样逐行比对 | 每天 | 内容不一致 |

行数对账最快，但只能发现“数量不对”；聚合对账能发现“数量对但内容错”；明细抽样成本最高，用于定位具体问题。

### 9.2 校验和 SQL

MySQL 没有跨行校验和函数，用 `BIT_XOR(CRC32(...))` 对主键区间做摘要：

```sql
-- 在新旧库分别执行，比较同一主键区间的摘要值
SELECT COUNT(*) AS cnt,
       BIT_XOR(CRC32(CONCAT_WS('#', id, user_id, amount, status,
                               DATE_FORMAT(created_at, '%Y-%m-%d %H:%i:%s')))) AS digest
FROM orders
WHERE id BETWEEN 1000000 AND 1999999;
```

`CONCAT_WS` 用固定分隔符，避免字段拼接产生歧义；时间格式化到秒，避免微秒精度差异造成假阳性。

边界：`CRC32` 有碰撞概率，但用于发现“批量错位”足够。真正定位问题还是要拉明细。金额字段要先转成最小货币单位再参与摘要，避免浮点表示差异。

### 9.3 差异修复

修复原则：以权威源为准，修复动作幂等，每次修复留记录。

```text
1. 差异表记录 (主键, 差异类型, 旧值摘要, 新值摘要)
2. 修复任务按主键从权威源读取整行
3. 幂等 upsert 到目标库
4. 修复后重新对账该区间
5. 差异率归零才算完成
```

不要做“按差异表逐字段 update”，字段级修复会漏掉并发更新。整行覆盖更安全。

### 9.4 对账的边界

- 对账有窗口：T+1 的对账不能覆盖当天的新写入，要按“已封账”的时间点比。
- 软删除要参与对账：`deleted_at` 不同步会导致行数对不上。
- 时钟不同步会造成假差异：服务器时区、`timestamp` 与 `datetime` 的转换都要统一。
- 对账本身要限流：全表校验和会扫全表，放在从库或低峰执行。

## 十、失败模式与检查清单

### 10.1 现象与处置

| 现象 | 最常见原因 | 第一条动作 |
|---|---|---|
| 写入延迟尖刺 | 跨分片事务或热点分片 | 看分片级 QPS 与锁等待 |
| 查询变慢但 CPU 不高 | 广播查询打满连接 | 抓慢日志确认是否无分片键 |
| 主键冲突 | ID 生成重复或 workerId 冲突 | 查 ID 服务日志与机器号分配 |
| 迁移后数据少一截 | binlog 断点或 DDL 中断 | 比对 binlog 位点与行数 |
| 对账差异持续不收敛 | 双写补偿积压 | 看补偿表积压与重试失败原因 |
| 扩容后部分请求 404 | 路由表未刷新 | 检查配置中心推送与客户端缓存 |

### 10.2 上线检查清单

- [ ] 分片键能覆盖 95% 以上的在线查询；
- [ ] 逻辑分片数是 2 的幂，且预留了翻倍空间；
- [ ] 全局 ID 方案演练过时钟回拨和号段耗尽；
- [ ] 跨分片查询有白名单和限流，C 端接口没有广播；
- [ ] 双写有补偿表、有对账、有结束日期；
- [ ] 每个迁移阶段都有退出条件和回滚脚本；
- [ ] 回滚窗口写进变更单，旧库在窗口内保持可写；
- [ ] 对账覆盖行数、聚合、明细三层；
- [ ] 冷数据可查、可删、可审计；
- [ ] 分片监控按库、按表、按逻辑分片三个维度都有。

## 十一、最佳实践案例

### 11.1 案例背景

一家做企业采购 SaaS 的公司，订单库单实例 MySQL 8.4，`orders` 表 8.2 亿行、约 1.1TB（含索引），日均新增 180 万行，峰值写入 6000 TPS、读 24000 QPS。大促期间订单列表 P99 达到 900ms，主库 CPU 长期 85%，备份恢复一次要 3 小时 40 分钟。

约束条件：

- 已做读写分离，读副本 2 个，复制延迟峰值 8 秒；
- 团队 5 人，没有人做过分库分表；
- 不能停机，业务 7×24；
- 合规要求订单明细在线可查 3 年，3 年以上可归档但不可删除；
- 预算只够一次中等改造，改造周期 6 个月。

目标是 12 个月内支撑 3 倍增长：写入 18000 TPS，订单列表 P99 ≤ 300ms，备份恢复 ≤ 60 分钟，迁移过程零停机、零丢单。

### 11.2 案例实操

第一步是把选项摆出来，用同一组指标打分（1–5 分，5 最好，示例）。

| 选项 | 改造周期 | 停机风险 | 3 倍增长支撑 | 综合 |
|---|---|---|---|---|
| A 只扩容硬件 | 2 周 | 低 | 2 | 12 |
| B 归档+分区表 | 6 周 | 低 | 2 | 13 |
| C 分库分表+冷热分离 | 5 个月 | 中 | 5 | 17 |
| D 迁文档库 | 7 个月 | 高 | 4 | 12 |

综合分包含团队可控性：团队对 A、B 最熟悉，对 C 只有理论经验，对 D 没有经验。

选项 A 的问题是把 1.1TB 的单库放到更大机器上，备份时间仍按体积线性增长，恢复 3 小时的 RTO 不变。选项 B 能缓解备份和查询，但写入仍集中在单主库，6000 TPS 已经是这套硬件的上限，3 倍增长必然撞墙。选项 D 要改全部 SQL 和事务语义，团队没有对应经验。

决策：C，分库分表 + 冷热分离，但分两期做。第一期只做冷热分离和逻辑分片改造，第二期做物理扩容。

分片设计：

| 维度 | 决策 | 理由 |
|---|---|---|
| 分片键 | `user_id`（买家） | 覆盖 96% 的在线查询 |
| 订单号 | 基因法嵌入 user_id 低 10 位 | 按订单号查也能单分片 |
| 逻辑分片 | 1024 | 2 的幂，可扩到 2048 |
| 物理布局 | 16 库 × 4 表 | 单表控制在 1200 万行 |
| 全局 ID | 号段模式，步长 2000 | 不依赖时钟，团队可控 |
| 大客户 | 写入超过 5% 的租户单独库 | 避免热点分片 |

迁移按六阶段推进，每一步的退出条件写进变更单：

| 阶段 | 周期 | 关键动作 | 退出条件 |
|---|---|---|---|
| 0 评估 | 3 周 | 收集全量 SQL，标记无分片键的查询 | 广播查询清单 < 20 条 |
| 1 建库 | 2 周 | 建 16 库 64 表，部署路由层 | 路由单测通过 |
| 2 双写 | 3 周 | 写旧成功后写新，失败进补偿表 | 双写成功率 99.99%，补偿积压 < 100 |
| 3 搬迁 | 5 周 | 分批全量 + binlog 追平 | 行数与摘要一致 |
| 4 影子读 | 2 周 | 双读比对，只返回旧结果 | 差异率 < 0.001% |
| 5 切读 | 3 周 | 5% → 30% → 100% | 错误率与 P99 达标 |
| 6 切写 | 2 周 | 按租户白名单切写 | 连续 3 天对账差异为 0 |

冷热分离与迁移并行：90 天前的订单迁移到独立历史库，只保留 `order_id`、`user_id`、`amount`、`status`、`created_at` 五个字段，其余明细转 Parquet 存对象存储，历史库保留索引供客服查询。3 年以上的数据只留对象存储，元数据登记在归档表。

切写阶段的路由配置：

```yaml
# 片段：切写灰度配置，按租户白名单逐步放量
order_write:
  new_cluster: true
  tenant_whitelist: [T1001, T1002, T1003]
  ratio: 0
  dual_write: true          # 过渡期仍然双写，保留回滚能力
  rollback_window_days: 7
```

风险预案：

- 若新库写入成功率低于 99.9%，自动关闭 `new_cluster`，写回旧库；
- 若对账差异率超过 0.01%，暂停扩量，只修数据；
- 旧库在切写后保留 7 天可写，补偿任务持续把新库独有数据回灌旧库。

### 11.3 案例结果

上线 6 个月后的实测数据（示例，来自内部监控）：

| 指标 | 改造前 | 改造后 | 目标 |
|---|---:|---:|---:|
| 订单列表 P99 | 900ms | 180ms | ≤ 300ms |
| 峰值写入 | 6000 TPS | 17500 TPS | 18000 TPS |
| 单表最大行数 | 8.2 亿 | 1150 万 | ≤ 2000 万 |
| 备份恢复 | 3h40m | 38min | ≤ 60min |
| 主库 CPU 峰值 | 85% | 52% | ≤ 70% |
| 存储月成本 | 基线 | +18% | ≤ +30% |

迁移期间零停机，切写灰度用了 11 天，回滚开关触发过 1 次（某租户写入延迟超过阈值，自动回旧库，23 分钟后恢复扩量）。对账最终差异率 0.0003%，共 2.1 万行，全部由“双写补偿表重试超时”导致，整行覆盖修复后归零。

三个失败模式值得记下来：

1. 初期按 `order_id` 分片，用户订单列表变成 16 分片广播，P99 反而升到 1.2 秒。改成基因法后广播查询从 34 条降到 6 条。
2. 一个大客户占写入 12%，单分片被打到 90% CPU。加了“大客户上浮”规则，把该租户迁到独立库，热点消失。
3. 搬迁第 4 周执行了一次加索引 DDL，binlog 解析错位，增量同步延迟 40 分钟。此后迁移窗口内冻结 DDL，并把 DDL 检查加入发布流水线。

复盘结论：分库分表真正的成本不在拆表，而在“查询约束的重新设计”和“迁移期的对账能力”。如果重做一次，会先花两周把所有不带分片键的 SQL 找出来并改造，再开始建库，而不是边迁边改。
