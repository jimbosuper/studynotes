# 全栈笔记导读

> 从一台计算机怎么执行指令，一直写到一个大模型应用怎么上线。
> 219 篇，一条完整的交付链：**计算机基础 → 产品 → 设计 → 架构 → 前端/后端 → 测试 → 运维 → 移动端 → 大模型**。

---

## 一、这是什么

这是一套**工程笔记**，不是教程合集。

写它的出发点很朴素：网上讲一个技术的文章很多，但大多数停在「它能做什么」，很少回答三个真正卡住人的问题——

1. 装好了怎么确认它真的能用？
2. 出了事，第一条命令敲什么？
3. 这套东西放到真实项目里，边界在哪、会踩什么坑？

所以这里的每一篇都按同一条标准写：**先划边界，再给最小可运行验证，最后落到一个完整案例**。看完一篇，你应该能从「听说过」变成「敢在项目里用，坏了知道先看哪」。

它面向的人：

- **想系统补全知识面的工程师**——不想靠碎片文章拼出一套体系
- **需要跨域协作的人**——后端要懂产品怎么定需求，产品要懂架构为什么要拆服务，设计要懂前端怎么落地
- **准备带项目的人**——从立项、需求、设计、架构、实现、测试到上线，每个环节都有可交付物清单
- **正在转方向的人**——Java 转 Go、前端转全栈、传统开发转 AI 应用，都有对应路径

它不面向的人：只想背面试题的人、只想要一段能复制的代码的人。这里信息密度高，但不轻松。

### 2.2 后端分区为什么占三分之一

74 篇是整库最大的一块，按**语言 → 层次**两级组织，五门语言用同一套骨架，便于横向对照：

```text
05-后端/
├── 01-Java    (20)  语法 → 常用库 → 工程化 → 数据库 → 常用框架 → 微服务
├── 02-Python  (10)  语法 → 常用库 → 工程化 → 数据库 → 常用框架
├── 03-Go      (13)  语法 → 常用库 → 工程化 → 数据库 → 常用框架 → 微服务
├── 04-Cpp      (6)  语法 → 常用库 → 工程化
├── 05-Rust     (9)  语法 → 常用库 → 工程化 → 常用框架
├── 06-数据库   (5)  SQL 基础、MySQL、PostgreSQL、MongoDB、SQLite
├── 07-中间件   (6)  Redis、RabbitMQ、Kafka、Elasticsearch、MinIO、XXL-Job
├── 08-Web与API (3)  OpenAPI 契约、WebSocket 与 SSE、文件与对象存储
└── 09-安全     (2)  认证与授权、输入校验与注入
```

每门语言的层次目录含义固定，同样的位置在不同语言讲同一件事：`01-语法` 讲类型与流程控制，`02-常用库` 讲集合、并发、错误处理，`03-工程化` 讲构建与依赖，`04-数据库` 讲 ORM 与连接池，`05-常用框架` 讲 Web 服务搭建，`06-微服务` 讲注册发现、调用、网关、限流、分布式事务。

**横向对照是这块的主要用法**：同样做「服务注册与发现」，Java 篇是 Nacos，Go 篇是 Consul + gRPC 解析器，读的时候能看清两者解决同一问题的不同取舍。

## 三、结构约定

### 3.1 编号规则

```text
00-计算机基础/01-数据结构/01-绪论.md
│             │              └─ 篇序号（同目录内从 1 连续）
│             └──────────────── 二级分类序号
└────────────────────────────── 分区序号（00–09，决定阅读顺序）
```

- 分区、分类、篇目**全部两位数字编号**，排序不依赖文件系统或编辑器
- 文件名 = 主题名，不含序号以外的装饰（少数历史文件例外，见第七节）
- 一篇一个文件，不放子目录（除 `assets/`）

### 3.2 配图规则

- 图片放在**同目录的 `assets/`** 下，正文用相对路径引用：`![说明](./assets/xxx.svg)`
- 因此**必须整目录拷贝或整体 clone**，单独拷一个 `.md` 出来图片会全部丢失
- 结构性关系优先用 Mermaid 内联（无需外部文件），视觉类主题用 SVG 手绘

### 3.3 阅读时每篇会看到什么

一篇标准的技术笔记，结构固定如下：

| 位置 | 内容 | 解决什么问题 |
|---|---|---|
| 标题 | 主题名（编号在文件名里，不在标题里） | — |
| 第 1–2 句引用块 | 「这篇从 X 讲起，经过 A、B、C，最后落到 E」 | 告诉你路线，决定要不要读 |
| 第 2 句引用块 | 「学完能 F，并能按现象定位 G」 | 告诉你产出，判断是否达标 |
| `## 一、定位与边界` | 它解决什么、不解决什么、和相邻技术怎么分工 | 防止用错工具 |
| `## 二、环境与最小验证` | 版本基线 + 一条能跑通的命令 + **预期输出** | 确认「装好了」不是自我感觉 |
| `## 三、…` 到 `## N-1、…` | 每个概念一段取舍判断 + 可运行片段 + `> 边界：…` 提醒 | 正文主体 |
| `## N、最佳实践案例` | 背景（带量化现状）→ 实操（完整源码）→ 结果对比表 → 失败模式复盘 | 从知识变成经验 |

其中两个标记值得专门留意：

- **`> 边界：…`**（全库 1556 处）——不是补充说明，是「什么情况下**不要**这么用」。这类内容最容易在真实项目里救命。
- **`预期输出`**（97 篇有）——命令跑完应该看到什么。没有它，读者只能靠猜自己是不是配错了。

### 3.4 版本基线

技术篇文首标注：

> 版本基线（2026-11）：Go 1.24+，示例在 1.27.x 上验证；`slices`、`maps` 需要 1.21+，`maps.Keys` 迭代器需要 1.23+。

写法上强调**分水岭**：哪个小版本加了什么 API、哪些行为变了、哪些要额外装依赖。因为技术笔记最容易失效的地方就是版本，与其含糊，不如写死。

## 四、怎么读

### 4.1 按角色选路线

不同起点的人不必从头读到尾。下面是四条经过取舍的路线：

**转行 / 应届，想补全栈地基**

```text
00-计算机基础（数据结构 → 操作系统 → 网络）
  → 04-前端/01-语言基础（HTML/CSS/JS/TS）
  → 05-后端/一门语言（选 Java 或 Go，走完 语法→框架）
  → 06-测试/01-测试基础
  → 07-运维/01-Linux + 02-Docker
```

理由：先有「计算机怎么工作」的直觉，写代码时才不会把内存、进程、网络当成黑盒；语言只选一门走通全链，比五门都读一遍更有效。

**后端工程师，补架构与交付**

```text
05-后端/06-数据库 + 07-中间件（先把存储与消息吃透）
  → 03-架构（服务拆分 → 一致性 → 容量 → 容灾）
  → 07-运维（容器编排 → 可观测性 → 故障应急）
  → 06-测试（契约测试 + 性能测试）
```

理由：后端往上走的分水岭不是会写更多框架，而是能判断「这个服务该不该拆、数据归谁、出问题怎么在 5 分钟内定位」。

**前端工程师，补工程化与服务端**

```text
04-前端（02-Vue3 或 03-React 任选一条走完）
  → 04-前端/06-构建与规范 + 08-浏览器与性能（工程化与性能是分水岭）
  → 02-设计/02-交互与设计系统（能读懂设计稿的意图）
  → 04-前端/03-React生态/03-Nextjs16全栈与RSC（进入服务端）
  → 05-后端/08-Web与API（接口契约）
```

**产品 / 设计与研发协作**

```text
01-产品（需求分层与验收标准）
  → 02-设计（后台规范 + 设计系统）
  → 00-计算机基础/05-软件工程/01-软件工程图典（按岗位找图，一次看懂各角色在画什么）
  → 03-架构/01-架构决策（为什么有些需求注定做不快）
```

**做 AI 应用**

```text
09-大模型/01-模型接入 → 02-Prompt与结构化 → 03-RAG → 04-Agent
  → 09-大模型/04-Agent/04-AI应用追踪与评估（不评估就没法上线）
  → 09-大模型/06-AI安全
```

同时建议并行读 `05-后端/01-Java/05-Java常用框架`（如果走 Java）或 `05-后端/03-Go/05-Go常用框架`，因为 RAG 与 Agent 最终要挂在业务服务上。

### 4.2 三种查法

- **按问题查**：搜「排障」「失败模式」「现场手册」「先看哪」。技术篇都带故障清单，且第一条命令具体到可复制。
- **按决策查**：搜「边界」「选型」「取舍」「什么时候不要」。这类段落的价值高于任何「最佳实践」。
- **按链路查**：从 `01-产品` 的某篇需求出发，顺着同一个业务（订单/报销/库存）往后翻，看它在设计、架构、实现、测试、运维里分别变成什么形态。

### 4.3 单篇读法建议

1. 先读两段引用块，判断这篇要不要现在读
2. 读第一章「边界」，确认自己没把工具用错位置
3. 跟着第二章的命令跑一遍，看到「预期输出」再往下
4. 中间各章按需跳读，但**`> 边界` 段落不要跳**
5. 末章案例照着做一遍，失败模式复盘逐条对照自己踩过的坑

## 八、来源

全部内容来自个人学习整理。

### 8.1 整理方式

这些笔记不是一次性写完的，而是按「学一门、跑一遍、记一篇」的方式长期积累：

- **先读再做**。每个技术点先看官方文档与规范，动手跑通一遍，能解释清楚原理和边界之后才动笔；
- **示例以可执行为准**。命令与代码尽量在本地或容器里执行过，文中「预期输出」是对应环境的实际回显；
- **案例自己搭**。各篇末尾的实践案例是按真实项目形态搭的练习工程，用来串起整篇的知识点；
- **边写边对照**。同一技术在不同语言、不同框架里的写法互相印证，发现冲突就回头查文档修正。

### 8.2 内容取舍

一篇笔记主要保留三样东西：

1. **能复现的操作**——装什么版本、敲什么命令、看到什么算对；
2. **容易踩错的边界**——文中 `> 边界：…` 系列，写的是「什么情况下不要这么用」；
3. **一次完整的落地过程**——从现状、约束到结果对比和失败复盘。

取舍上偏向「少而准」：说不清的原理不硬写，没跑过的结论不当作定论，需要读者再验证一遍的内容尽量不留在正文里。

### 8.3 局限

- **版本有时效**。各篇标注的版本基线是写作当时的环境，技术迭代后行为可能变化，以官方文档最新说明为准；
- **案例数据分两类，要看表头口径**。一类标注了「本地实测」，是本人机器或容器里跑出来的真实回显与计时；另一类标注「示例」，是按典型业务量级构造的示意数据，用来说明量级差异与改造方向，不能当作基准测试结论使用；
- **机器与环境不同，数字不可直接搬运**。同一份代码在核数、内存带宽、磁盘类型不同的机器上结果差异明显，例如并行版本受内存带宽限制时加速比会明显低于线程数；
- **覆盖面不等于深度**。十个分区的目标是建立完整认知框架与可上手路径，个别主题的深度不及专门专著，遇到深入问题仍应查官方规范与源码。

### 8.4 使用建议

- 用于入门与建立体系：按第四节的路线读，效果最好；
- 用于查问题：直接跳到对应篇的排障章节，第一条命令通常就能缩小范围；
- 用于团队传阅：建议先按分区拆开，按角色分发，不要整库推给一个人。
