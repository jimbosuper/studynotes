# 移动端工程化与发布

> 这篇从移动端交付链讲起，经过构建环境、签名与密钥、版本号、CI/CD 流水线、应用商店分发，最后落到灰度、热更新、回滚与构建排障。
>
> 学完能把一个手工打包的 Android/iOS 工程改造成可重复的流水线产物，并独立完成签名、版本管理、灰度发布和线上回滚。

## 一、移动端交付链与手工发布的代价

移动端发布不是一个"打包"动作，而是一条链：**构建 → 签名 → 分发 → 审核 → 灰度 → 更新/回滚**。链上任何一环靠手工，都会在版本变多后失控。

| 环节 | Android | iOS | 小程序 |
|---|---|---|---|
| 构建 | Gradle | Xcode/fastlane | 平台编译器 |
| 签名 | keystore | 证书 + 描述文件 | 平台账号 |
| 分发 | APK/AAB | IPA/TestFlight | 上传后审核 |
| 审核 | 商店审核 | App Review | 平台审核 |
| 回滚 | 旧包重发 | 下架版本 | 回退版本 |

三条判断决定工具选型：**Android 可以完全脱离图形界面构建**，因此 CI 成本最低；**iOS 构建必须跑在 macOS 上**，CI 要么买 macOS Runner，要么自建 Mac 构建机；**小程序没有热更新**，只能整包审核发版，所以远程配置要把"能改的"提前抽出来。

> 边界：个人项目、单次交付的原型可以手工打包；一旦有测试包、灰度、多渠道或多团队协作，就必须上流水线，否则签名和版本号一定出错。

## 二、环境与最小可发布构建

版本基线 2026-11：JDK 21 LTS、Android SDK API 36、Gradle 8.9+（以 AGP 要求为准）、Kotlin 2.x、fastlane 当前版、Node 20/22（跨平台工程用）。

| 工具 | 版本基线 | 用途 |
|---|---|---|
| JDK | 21 LTS | Gradle/AGP 编译 |
| Android SDK | API 36 | 编译与目标版本 |
| Gradle | 8.9+ | 构建 |
| fastlane | 当前稳定版 | iOS 构建与上传 |
| Node | 20/22 LTS | 跨平台工程 |

| 环境 | 安装 |
|---|---|
| Windows 10/11 | `winget install EclipseAdoptium.Temurin.21.JDK` |
| macOS | `brew install --cask temurin@21`，`brew install fastlane` |
| Ubuntu 24.04 | `sudo apt install -y openjdk-21-jdk`，SDK 用 commandline-tools |
| Rocky/CentOS 9 | `sudo dnf install -y java-21-openjdk-devel` |

Android SDK 命令行安装（CI 与无图形界面服务器通用）：

```bash
# 只装构建需要的平台与工具，不装模拟器，节省 2GB 以上
yes | sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
```

最小发布构建：

```bash
./gradlew :app:assembleRelease
```

预期输出（关键片段）：

```text
> Task :app:minifyReleaseWithR8
> Task :app:packageRelease
> Task :app:assembleRelease

BUILD SUCCESSFUL in 1m 42s
```

产物在 `app/build/outputs/apk/release/app-release.apk`。未配置签名时这个包是 unsigned，装不上真机，下一节处理。

iOS 用 fastlane 的最小闭环：

```bash
cd ios && fastlane init   # 生成 Fastfile 与 Appfile
bundle exec fastlane build
```

> 边界：`assembleRelease` 默认开启 R8 代码压缩，反射、序列化、JNI 相关类必须配 keep 规则；调试包不混淆，所以"debug 正常、release 崩溃"九成是混淆或签名问题。

### 2.1 构建变体与产物裁剪

一个应用通常要出多个变体：正式、预发、渠道、免费/付费。用 `buildTypes` 管环境差异，用 `productFlavors` 管渠道差异，两者交叉生成变体，不要为每个变体复制一份工程。

```kotlin
android {
    buildTypes {
        create("staging") {
            initWith(getByName("release"))   // 预发沿用正式包的混淆与签名配置
            applicationIdSuffix = ".staging" // 包名不同，可与正式包共存
            versionNameSuffix = "-staging"
            matchingFallbacks += listOf("release")
        }
    }
    flavorDimensions += "channel"
    productFlavors {
        create("official") { dimension = "channel" }
        create("huawei") { dimension = "channel" }
    }
}
```

产物裁剪按收益从高到低做三件事：只保留需要的语言资源、按 ABI 拆包、开启资源压缩。

```kotlin
android {
    defaultConfig {
        // 只保留中英文，去掉依赖库里带的几十种语言
        resourceConfigurations += listOf("zh", "en")
        ndk { abiFilters += listOf("arm64-v8a", "armeabi-v7a") }
    }
    buildTypes {
        release {
            isShrinkResources = true   // 删除未被引用的资源，依赖 R8 的引用分析
        }
    }
    splits {
        abi {
            isEnable = true
            reset()
            include("arm64-v8a", "armeabi-v7a")
            isUniversalApk = false     // 不额外产出全量包，避免误发
        }
    }
}
```

| 手段 | 典型收益 | 代价 |
|---|---|---|
| 语言裁剪 | 200–800 KB | 需列出支持语言 |
| ABI 拆分 | 单包减少 30% 以上 | 商店需支持多 APK |
| 资源压缩 | 5%–15% | 动态引用资源要配 keep |
| 图片转 WebP | 20%–50% | 构建耗时增加 |

验证裁剪没有误删：

```bash
./gradlew :app:assembleOfficialRelease
unzip -l app/build/outputs/apk/official/release/app-official-arm64-v8a-release.apk | tail -5
```

```text
---------                   -------
   18432000  18432000 files
```

> 边界：`isShrinkResources` 依赖 R8，反射或 `getIdentifier` 动态取资源时会被误删，必须在 `res/raw/keep.xml` 里声明；ABI 拆分后要确认统计 SDK 能正确归因，否则渠道数据会对不上。

## 三、签名与密钥管理

Android 的签名密钥（keystore）是应用的身份，丢失后无法给已上架应用发更新，只能换包名重新上架。密钥必须进密钥管理系统，不能进 Git。

```bash
# 生成 keystore，有效期 25 年以上，算法用当前推荐
keytool -genkeypair -v \
  -keystore release.jks \
  -alias app \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass "$STORE_PASS" -keypass "$KEY_PASS" \
  -dname "CN=Example, OU=Mobile, O=Example Inc, L=Shanghai, C=CN"
```

预期输出：

```text
Generating 2,048 bit RSA key pair and self-signed certificate (SHA256withRSA)
[Storing release.jks]
```

Gradle 从环境变量读取，仓库里只提交占位配置：

```kotlin
// app/build.gradle.kts
android {
    signingConfigs {
        create("release") {
            // 路径与口令都来自环境变量，CI 与本机共用一套逻辑
            storeFile = file(System.getenv("KEYSTORE_PATH") ?: "release.jks")
            storePassword = System.getenv("STORE_PASS")
            keyAlias = System.getenv("KEY_ALIAS") ?: "app"
            keyPassword = System.getenv("KEY_PASS")
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")
            isMinifyEnabled = true          // 开混淆，减小包体并增加逆向成本
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
        }
    }
}
```

验证签名，发布前必须做：

```bash
apksigner verify --print-certs app-release.apk
```

```text
Signer #1 certificate DN: CN=Example, OU=Mobile, O=Example Inc, L=Shanghai, C=CN
Signer #1 certificate SHA-256 digest: 3f2a...9c1d
```

iOS 的身份是证书加描述文件（provisioning profile），由 Apple Developer 账号签发，fastlane match 把证书加密存进私有仓库，团队共享同一份：

```bash
bundle exec fastlane match appstore --readonly
```

> 边界：Android 调试签名（debug.keystore）每台机器不同，用它打的包不能覆盖安装正式包，报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`；iOS 描述文件过期会让所有构建突然失败，到期前 30 天要换。

## 四、版本号与构建号

版本由两个数字组成：**对用户可见的版本名**和**对系统递增的构建号**。前者用于运营和商店展示，后者用于判断新旧，每次上传必须递增，否则商店拒收。

| 平台 | 版本名 | 构建号 | 规则 |
|---|---|---|---|
| Android | `versionName` | `versionCode` | code 单调递增整数 |
| iOS | `CFBundleShortVersionString` | `CFBundleVersion` | build 单调递增 |
| 小程序 | 上传版本号 | 无 | 与 tag 对应 |

```kotlin
// 版本号集中在一处，避免 app 与各 module 不一致
android {
    defaultConfig {
        versionCode = 42          // CI 用提交次数或流水线号自增
        versionName = "3.7.0"     // 语义化：主版本.次版本.修订
    }
}
```

```bash
# CI 里用流水线号自增，避免人工忘记改
./gradlew :app:assembleRelease -PversionCode=$GITHUB_RUN_NUMBER
```

语义化约定：修 bug 升修订号，加功能升次版本，不兼容改动升主版本。`versionCode` 与 `versionName` 不要混用同一个数字，否则回滚和灰度时无法区分"同名不同包"。

> 边界：`versionCode` 一旦上传就占用，不能复用；Google Play 允许跳过号段，国内商店多数也允许，但不要回退到更小的号，否则老用户收不到更新。

## 五、CI/CD 流水线

流水线的目标不是"能构建"，而是"每次提交都能产出可追溯、可复现、可回滚的包"。缓存依赖、固定 JDK、密钥注入、产物归档四件事缺一不可。

```yaml
# .github/workflows/android.yml
name: android-release
on:
  push:
    tags: ['v*']          # 只在打 tag 时出正式包，避免每次提交都占构建额度

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'   # 与本地、AGP 要求保持一致

      - uses: actions/cache@v4
        with:
          path: |
            ~/.gradle/caches
            ~/.gradle/wrapper
          key: gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}

      - name: Decode keystore
        run: echo "${{ secrets.KEYSTORE_BASE64 }}" | base64 -d > release.jks
        # 密钥只在这一步落盘，任务结束随 runner 销毁

      - name: Build
        env:
          KEYSTORE_PATH: release.jks
          STORE_PASS: ${{ secrets.STORE_PASS }}
          KEY_ALIAS: app
          KEY_PASS: ${{ secrets.KEY_PASS }}
        run: ./gradlew :app:assembleRelease --no-daemon

      - uses: actions/upload-artifact@v4
        with:
          name: app-release
          path: app/build/outputs/apk/release/*.apk
          retention-days: 30   # 保留一个月，覆盖灰度与回滚窗口
```

`--no-daemon` 让 Gradle 在一次性容器里不常驻，减少内存占用和残留进程。缓存的 key 用 Gradle 文件哈希，依赖变更时自动失效。

iOS 的 job 必须用 macOS runner：

```yaml
  ios:
    runs-on: macos-15
    steps:
      - uses: actions/checkout@v4
      - run: bundle install
      - run: bundle exec fastlane beta   # 内部走 match + gym + pilot
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
          APP_STORE_CONNECT_API_KEY: ${{ secrets.ASC_KEY }}
```

预期输出（关键片段）：

```text
[14:22:31]: Match: All certificates and profiles are installed
[14:25:02]: Gym: Build succeeded
[14:27:40]: Pilot: Successfully uploaded build 128 to TestFlight
```

| 流水线环节 | 失败后果 | 检查点 |
|---|---|---|
| 密钥解码 | 包未签名 | `apksigner verify` |
| 构建 | 无产物 | Gradle 日志首行错误 |
| 测试 | 带缺陷发版 | 单测/冒烟结果 |
| 归档 | 无法回滚 | artifact 保留期 |

> 边界：GitHub 托管的 macOS runner 按分钟计费且排队，团队量大时自建 Mac mini 构建机更稳；密钥用 OIDC 或云厂商密钥管理服务，不要长期放在 secrets 里明文可读。

### 5.1 依赖与构建缓存治理

依赖版本统一在版本目录（Version Catalog）里管理，module 不允许写裸版本号，否则同一个库会出现多个版本并行。

```toml
# gradle/libs.versions.toml —— 版本只在这一处出现
[versions]
kotlin = "2.1.20"
compose-bom = "2026.09.00"
retrofit = "2.11.0"

[libraries]
retrofit = { module = "com.squareup.retrofit2:retrofit", version.ref = "retrofit" }
compose-bom = { module = "androidx.compose:compose-bom", version.ref = "compose-bom" }

[plugins]
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
```

```kotlin
// app/build.gradle.kts —— 只引用，不写版本
dependencies {
    implementation(platform(libs.compose.bom))
    implementation(libs.retrofit)
}
```

锁定依赖的传递版本，保证每次构建拿到的依赖一致：

```bash
./gradlew dependencies --write-locks   # 生成 gradle.lockfile，随仓库提交
./gradlew build                        # 后续构建严格按锁文件解析
```

构建缓存开启后，未变更的任务产物直接复用，CI 冷构建能省一半以上时间：

```properties
# gradle.properties
org.gradle.caching=true            # 任务级缓存，命中则跳过执行
org.gradle.configuration-cache=true # 配置阶段缓存，大工程省 10-30 秒
org.gradle.jvmargs=-Xmx4g          # 给足堆，避免中途 GC 卡顿
```

| 治理项 | 命令 | 频率 |
|---|---|---|
| 依赖版本检查 | `./gradlew dependencyUpdates` | 每迭代 |
| 锁定更新 | `--update-locks` | 升级时 |
| 缓存命中率 | 构建日志 `FROM-CACHE` | 每次构建 |
| 许可证扫描 | 依赖报告插件 | 每迭代 |

> 边界：配置缓存对自定义 Task 的输入输出要求严格，升级 Gradle 后首次构建会报错，这是预期行为，按报错补齐注解即可，不要直接关掉。

## 六、分发与应用商店

Android 用 AAB 上 Google Play，用 APK 发国内商店和自有渠道。AAB 由商店按设备生成 APK，体积更小，但不能直接安装，测试要用 bundletool 转出。

```bash
# 从 AAB 生成一组按设备配置拆分的 APK，用于本地验证
bundletool build-apks --bundle=app-release.aab --output=app.apks \
  --ks=release.jks --ks-key-alias=app
bundletool install-apks --apks=app.apks
```

| 渠道 | 产物 | 审核要点 |
|---|---|---|
| Google Play | AAB | 隐私政策、数据安全表 |
| 国内应用商店 | APK | 软著、备案、隐私合规 |
| TestFlight | IPA | 测试信息、出口合规 |
| 企业内部分发 | APK/IPA | MDM 或签名描述文件 |

国内上架的共同门槛：软件著作权、ICP 备案（涉及网络服务）、隐私政策、权限最小化说明。隐私政策必须逐项对应实际收集的权限，多声明一个权限就可能被驳回。

小程序分发在上一层的 uni-app 篇已展开，这里只强调工程侧：版本号与 Git tag 对齐，上传后的体验版用于验收，正式版走审核。

> 边界：Google Play 的 AAB 不能再直接改签名重签分发；国内商店大多要求 APK 且各自有加固要求，加固会改签名，必须用加固平台的重签功能，不能拿加固前的包去校验签名。

### 6.1 隐私合规与上架材料

上架被拒的原因大多与功能无关，而是材料不齐或声明不实。把材料当成构建产物的一部分，随版本归档，比每次临时找要快。

| 材料 | 适用 | 常见问题 |
|---|---|---|
| 隐私政策 | 全平台 | 收集项与实际权限不符 |
| 权限清单 | 国内商店 | 多申请了定位/通讯录 |
| 软件著作权 | 国内商店 | 名称与安装包不一致 |
| 备案号 | 涉及网络服务 | 未在页面展示 |
| 数据安全表 | Google Play | 未声明第三方 SDK 收集 |

第三方 SDK 是合规的重灾区。统计、推送、广告 SDK 都会收集设备信息，必须在隐私政策里逐项披露，并在首次启动时取得同意后才初始化。

```kotlin
// 合规的初始化顺序：用户同意前不初始化任何采集类 SDK
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        initCrashReporter()             // 崩溃采集属于必要功能，可先行
        if (consentStore.hasAgreed()) { // 其余 SDK 等同意后再初始化
            initAnalytics()
            initPush()
            initAd()
        }
    }
}
```

隐私政策要能从 App 内打开，且不能是一个死链。审核员会点开看，链接 404 直接判拒。

> 边界：隐私政策不是法务一次性写完就结束的文档；新增一个 SDK、新增一个权限，都要同步更新版本号和收集清单，否则属于"声明不实"。

## 七、灰度、热更新与回滚

灰度发布把新版本先给 5% 用户，观察崩溃率和核心转化，再逐步放量。没有灰度能力的渠道，用功能开关在服务端控制行为，等价于"代码已发、功能未开"。

```text
5%  ──▶ 观察 30 分钟（崩溃率、启动成功率）
20% ──▶ 观察 2 小时
50%  ──▶ 观察 12 小时
100% ──▶ 全量
```

判断是否继续放量的门槛要提前写死，不能凭感觉：

| 指标 | 阈值 | 动作 |
|---|---|---|
| 崩溃率 | 高于基线 0.5 倍 | 暂停放量 |
| 启动成功率 | 低于 99.5% | 回滚 |
| 核心转化 | 下降 5% | 回滚 |
| 新增 ANR | 明显上升 | 暂停 |

热更新的现实约束：Android 热修复受商店政策限制，主流商店要求"能修复但不改变功能"，且必须可下架；iOS 的 JSPatch 类方案早被禁止；React Native 的 CodePush 只更新 JS bundle，不能改原生代码；小程序完全不支持热更新。

```js
// 功能开关：配置在服务端，出问题先关开关再发版
if (remoteConfig.enableNewCheckout && userInBucket('checkout_v2')) {
  renderNewCheckout()
} else {
  renderOldCheckout()
}
```

回滚策略按平台不同：Android 保留上一个版本的 APK/AAB，商店后台可直接切回旧版本；iOS 只能下架新版本并提交旧版本重新审核，恢复慢，所以 iOS 更依赖服务端开关；小程序在后台回退到历史版本，即时生效。

> 边界：灰度分桶要按设备或用户稳定哈希，不能每次请求随机，否则同一用户一会儿新一会儿旧，指标不可信；分桶比例变更要记录时间点，便于归因。

### 7.1 远程配置与开关治理

远程配置是"不改代码就能改行为"的手段，也是灰度的真正载体。配置必须有默认值、有版本、有生效确认，否则一次错误的下发就是一次全量事故。

```http
GET /api/v1/config?appVersion=3.7.0

{
  "configVersion": 42,
  "checkout_v2": { "enabled": true, "rollout": 5, "salt": "uid" },
  "maxRetry": 3,
  "forceUpgrade": null
}
```

```json
{
  "configVersion": 42,
  "appliedAt": "2026-11-13T10:00:00Z"
}
```

客户端按 `salt + 用户ID` 做稳定分桶，`rollout` 是比例；服务端只发配置和盐值，分桶在客户端算，请求不感知分桶。

| 治理项 | 规则 |
|---|---|
| 默认值 | 代码里必须有本地默认值 |
| 生效确认 | 客户端回传已应用版本 |
| 灰度开关 | 上限 100%，可一键全关 |
| 审计 | 每次变更记录人、时间、理由 |

> 边界：远程配置只改变行为参数，不改变业务逻辑的完整性；开关打开时新旧两条代码路径都要有测试覆盖，否则灰度只是在选择哪种方式坏。

## 八、现场手册：构建与审核排障

构建问题的第一条命令永远是看完整错误，而不是最后一行。Gradle 的 `What went wrong` 段、Xcode 的 `error:` 行、fastlane 的最早失败步骤，才是根因。

| 现象 | 最可能原因 | 第一条检查 |
|---|---|---|
| 包装不上 | 签名不一致 | `apksigner verify` |
| release 崩溃 | R8 混淆 | 看堆栈类名是否被混淆 |
| Gradle 报 JDK 版本 | `JAVA_HOME` 指向旧 JDK | `./gradlew -version` |
| 上传被拒 | versionCode 未递增 | 对比商店后台 |
| iOS 描述文件失效 | 证书过期 | `security find-identity -v` |
| 审核被拒 | 隐私/权限/类目 | 审核回复原文 |

```bash
# 确认 Gradle 实际使用的 JDK，而不是 shell 里 java -version 的结果
./gradlew -version

# 查看设备上已安装包的签名，和待装包对比
adb shell dumpsys package com.example.app | grep -A2 signatures
```

release 崩溃但 debug 正常的定位办法：保留 mapping 文件，用 R8 的 retrace 还原堆栈。

```bash
# mapping 在 build/outputs/mapping/release/，每次发版都要归档
retrace app/build/outputs/mapping/release/mapping.txt crash.txt
```

```text
com.example.app.OrderRepo -> a.b.c:
    java.lang.NullPointerException
        at com.example.app.OrderRepo.load(OrderRepo.kt:42)
```

审核被拒的处理原则：先按回复原文改，再考虑申诉；隐私政策缺失、权限说明不清、诱导下载这三类占国内驳回的大多数，属于"改了就能过"，不要浪费申诉次数。

> 边界：不要用"换个包名重新上架"绕过封禁，账号会被关联处罚；签名密钥泄露后的正确动作是联系商店走密钥轮换流程，而不是重新生成 keystore。

## 九、最佳实践案例

### 9.1 案例背景

一个 8 人团队的电商 App，Android 端此前由一名开发在本地打包，每周发一次版。现状是：签名文件放在开发者电脑桌面，换人打包就出现签名不一致；版本号手工改，出现过两次商店拒收；没有测试包通道，测试同学靠群里发 APK；一次线上支付崩溃后无法快速回滚，靠紧急发版折腾了 6 小时。目标是两周内建成"打 tag 即出包、可灰度、可回滚"的流水线，覆盖 Google Play 与两个国内渠道。

### 9.2 案例实操

第一步把签名迁到密钥管理，仓库里只留读取逻辑。keystore 用 base64 存进 CI secrets，本地开发通过环境变量注入，任何人拿不到明文。

```bash
# 迁移一次性执行，执行后从个人电脑删除明文 keystore
base64 -i release.jks | pbcopy    # macOS
base64 -w0 release.jks            # Linux，输出到 CI secret
```

```kotlin
// 统一从环境变量取，缺任何一个就在配置阶段失败，避免打出未签名包
val storePath = System.getenv("KEYSTORE_PATH")
    ?: error("KEYSTORE_PATH is required")
```

第二步统一版本来源。用 tag 推导版本名，用流水线号推导构建号，二者都写进 `BuildConfig`：

```kotlin
android {
    defaultConfig {
        // tag v3.7.0 -> versionName 3.7.0；没有 tag 时用 dev 后缀标识非正式包
        versionName = System.getenv("GIT_TAG")?.removePrefix("v") ?: "3.7.0-dev"
        versionCode = (System.getenv("GITHUB_RUN_NUMBER") ?: "1").toInt()
    }
    buildFeatures { buildConfig = true }
}
```

第三步建三渠道产物，用 productFlavors 区分商店，渠道信息进 `BuildConfig` 供统计：

```kotlin
flavorDimensions += "store"
productFlavors {
    create("google") { dimension = "store"; applicationIdSuffix = "" }
    create("huawei") { dimension = "store"; applicationIdSuffix = "" }
    create("xiaomi") { dimension = "store"; applicationIdSuffix = "" }
}
```

```bash
# 一次构建三个渠道包，产物按渠道分目录
./gradlew assembleGoogleRelease assembleHuaweiRelease assembleXiaomiRelease
```

第四步流水线加"发布前门禁"：单测、lint、签名校验、包体积阈值，任一失败即阻断。

```yaml
      - name: Verify signature
        run: apksigner verify --print-certs app/build/outputs/apk/google/release/*.apk

      - name: Size gate
        run: |
          SIZE=$(stat -c%s app/build/outputs/apk/google/release/*.apk)
          # 超过 45MB 阻断，防止误引入大资源
          test "$SIZE" -lt 47185920
```

第五步灰度。Google Play 用分阶段发布，国内渠道用服务端开关兜底：

```bash
# 用 fastlane supply 把已上传的 AAB 推进到 5% 灰度轨道
bundle exec fastlane supply --aab app-release.aab --track production --rollout 0.05
```

预期输出：

```text
[15:02:11]: Supply: Uploading app bundle
[15:04:38]: Supply: Successfully set rollout to 5%
```

### 9.3 案例结果

流水线落地后，打 tag 到产出三渠道包平均 11 分钟（示例，GitHub 托管 runner，含缓存命中），签名不一致问题归零，版本号错误归零。灰度期间发现一次支付回调的崩溃率从 0.12% 升到 0.9%，在 5% 阶段暂停放量并关闭新收银台开关，影响面控制在 5% 用户内，回滚耗时 8 分钟。

复盘出的失败模式：一是最初把 keystore 直接 base64 写进 workflow 文件，被代码扫描告警，改为 secrets；二是 `--no-daemon` 漏写导致 runner 内存不足，构建在 80% 处被 OOM 杀掉；三是国内渠道包用了 Google 渠道的 `applicationIdSuffix` 配置，包名冲突，改为按 flavor 分别配置。遗留风险是 iOS 仍靠人工触发 fastlane，尚未接入 tag 自动构建，主要卡在证书轮换的审批流程。
