# 安全测试与依赖扫描

> 这篇从安全测试要覆盖的威胁面讲起，经过 ZAP 的被动与主动扫描、越权与业务逻辑验证、依赖与镜像扫描、密钥泄露检查，最后落到 CI 门禁、漏洞治理和一个订单系统的完整加固案例。
>
> 学完能把 DAST、SCA、密钥扫描接进流水线，独立验证越权漏洞，并按严重级别和修复窗口管理漏洞。

## 一、安全测试的目标与威胁模型

安全测试不是“扫一遍工具”，而是用攻击者视角验证三类问题：谁能访问什么、系统信任了哪些不该信任的输入、依赖和配置里有没有已知弱点。工具只能覆盖已知模式，业务逻辑漏洞必须靠设计和手工验证。

### 1.1 安全测试与渗透测试的分工

| 类型 | 目标 | 频率 | 产出 |
|---|---|---|---|
| SAST 静态分析 | 源码中的危险模式 | 每次提交 | 代码位置与规则 |
| DAST 动态扫描 | 运行中应用的已知漏洞 | 每次部署 | 告警与请求证据 |
| SCA 依赖扫描 | 第三方组件的已知 CVE | 每次构建 | 组件、版本、修复版 |
| 密钥扫描 | 凭据是否进入代码库 | 每次提交 | 文件、提交、泄露类型 |
| 渗透测试 | 组合利用与业务逻辑 | 季度/上线前 | 可利用链条与报告 |

SAST 和 DAST 都查不到“用户 A 能看用户 B 的订单”这类逻辑问题，因为请求本身完全合法。越权、支付绕过、优惠券叠加必须有明确的测试用例和双账号验证。

> 边界：自动化扫描通过不等于安全。扫描器擅长已知签名，不擅长多步业务绕过和权限设计缺陷。

### 1.2 OWASP Top 10 的测试映射

| 类别 | 典型问题 | 主要验证手段 |
|---|---|---|
| A01 访问控制失效 | 水平/垂直越权、目录遍历 | 双账号手工 + 自动化 |
| A02 加密机制失效 | 明文传输、弱哈希、硬编码密钥 | 配置检查 + 密钥扫描 |
| A03 注入 | SQL/命令/模板注入 | DAST + 参数化代码审查 |
| A04 不安全设计 | 缺少限流、可枚举、信任客户端 | 威胁建模 + 滥用用例 |
| A05 安全配置错误 | 默认口令、调试端口、CORS 过宽 | 配置基线 + DAST |
| A06 易受攻击组件 | 过期依赖、镜像基础层 CVE | SCA + 镜像扫描 |
| A07 身份认证失效 | 会话固定、弱口令、JWT 校验缺失 | 认证用例 + DAST |
| A08 数据完整性失效 | 不验签的反序列化、供应链 | 签名校验 + SBOM |
| A09 日志监控失效 | 关键事件无审计、告警缺失 | 日志检查 + 演练 |
| A10 SSRF | 服务端请求任意 URL | 出网限制 + 手工验证 |

这张表用于分配测试资源，不是检查清单。每一类都要落到具体接口、具体角色和具体数据。

### 1.3 风险排序

漏洞优先级由可利用性、影响面和暴露面共同决定，不能只看工具给的等级：

```text
优先级 ≈ 可利用性 × 影响 × 暴露面
```

- 互联网可达、无需认证、可批量利用 → 立即修；
- 内网可达、需要高权限、影响单租户 → 按迭代修；
- 需要物理接触或仅测试环境 → 记录并接受；
- 无修复版本但有补偿控制（WAF、网络隔离）→ 限期复核。

CVSS 分数是输入，不是结论。一个 9.8 分的组件漏洞如果代码路径不可达，实际风险可能低于一个 6.5 分的越权。

### 1.4 测试边界与授权

- 只测已授权资产，扫描前确认域名、IP、时间窗；
- 主动扫描会发攻击载荷，禁止对生产直接执行；
- 越权测试使用自建双账号和测试数据，不碰真实用户；
- 发现可用漏洞先走内部通道，不在工单里贴利用细节；
- 扫描流量要能被观测和熔断，避免误伤依赖方。

## 二、环境与工具准备

这一章解决“工具能跑、靶场能扫、结果能看”。版本基线：OWASP ZAP 2.15+、Trivy 0.58+、gitleaks 8.x、JDK 21。三者分别覆盖动态、依赖、密钥三个面。

### 2.1 OWASP ZAP 安装

ZAP 提供桌面版、命令行脚本和容器镜像。CI 用容器最稳定：

```bash
# 生产流水线把 stable 换成具体版本标签，保证结果可复现
docker pull ghcr.io/zaproxy/zaproxy:stable
docker run --rm ghcr.io/zaproxy/zaproxy:stable zap.sh -version
# 2.15.0 或更高
```

macOS 桌面版：

```bash
brew install --cask zap
```

Ubuntu / Rocky 用官方安装包或容器。Windows 从 zaproxy.org 下载安装器。桌面版用于探索和调试，流水线用 `zap-baseline.py`、`zap-full-scan.py`、`zap-api-scan.py`。

> 边界：ZAP 是代理式扫描器，默认不执行复杂 JavaScript。单页应用的关键接口要提供 OpenAPI 或通过认证上下文导入，否则扫不到真实 API。

### 2.2 Trivy 安装

```bash
# macOS
brew install trivy

# Ubuntu / Debian：官方 release 二进制，不依赖第三方仓库
curl -sSL https://github.com/aquasecurity/trivy/releases/download/v0.58.0/trivy_0.58.0_Linux-64bit.tar.gz \
  | sudo tar -xz -C /usr/local/bin trivy

# Rocky / CentOS：直接安装 release 的 rpm
sudo dnf install -y https://github.com/aquasecurity/trivy/releases/download/v0.58.0/trivy_0.58.0_Linux-64bit.rpm

# Windows
winget install AquaSecurity.Trivy

# 容器方式，不依赖本机
docker run --rm aquasec/trivy:0.58.0 --version
```

Trivy 首次运行会下载漏洞库，离线环境要预置缓存：

```bash
trivy image --download-db-only
trivy image --cache-dir /var/lib/trivy --offline-scan myapp:1.0.0
```

```bash
brew install gitleaks                 # macOS
# Linux（Ubuntu/Rocky 通用）：release 二进制
curl -sSL https://github.com/gitleaks/gitleaks/releases/download/v8.21.2/gitleaks_8.21.2_linux_x64.tar.gz \

# 8.21.2
```

### 2.4 最小验证：扫一个本地服务

启动一个带已知问题的 Spring Boot 服务（示例用 `http://127.0.0.1:8080`），执行基线扫描：

```bash
mkdir -p zap-out
docker run --rm --network host \
  -v "$(pwd)/zap-out:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://127.0.0.1:8080 -r baseline.html -J baseline.json
```

预期输出（关键片段）：

```text
PASS: Cookie No HttpOnly Flag [10010]
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 3
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 2
FAIL-NEW: 0
WARN-NEW: 5
Report written to /zap/wrk/baseline.html
```

退出码：`0` 成功，`1` 至少一个 FAIL，`2` 只有 WARN 且无 FAIL，`3` 执行失败。默认所有告警都按 WARN 处理，未配置规则时基线扫描通常返回 2；CI 中先用 `-I` 让 WARN 不返回失败，等告警清零后再收紧。

> 边界：`--network host` 让容器直接访问宿主机端口；macOS 的 Docker Desktop 用 `host.docker.internal` 代替。不要把 `127.0.0.1` 写进容器内的目标地址。

## 三、ZAP 扫描

ZAP 的价值在于把“发请求—看响应—匹配规则”标准化。被动扫描看响应头、Cookie、信息泄露，主动扫描发注入载荷。两者要分开跑，主动扫描必须限定范围和强度。

### 3.1 三种扫描模式

| 模式 | 是否攻击 | 耗时 | 适用阶段 |
|---|---|---|---|
| Baseline 被动 | 否 | 1–3 分钟 | 每次部署 |
| Full 主动 | 是 | 10–60 分钟 | 预发/夜间 |
| API 扫描 | 可配置 | 5–30 分钟 | 有 OpenAPI 时 |

Baseline 只爬取和观察，不修改数据，可以放在每次部署后。Full 会尝试 SQL 注入、XSS、路径遍历等，只能在预发或专用靶场执行。

```bash
# 主动扫描，限制只测指定 URL，避免爬虫跑出范围
docker run --rm --network host -v "$(pwd)/zap-out:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-full-scan.py -t http://127.0.0.1:8080 \
  -m 5 -T 20 -r full.html -J full.json
```

`-m 5` 限制爬虫最多 5 分钟，`-T 20` 限制主动扫描最多 20 分钟；两者都是时间上限，不是并发。主动扫描的并发要单独在 ZAP 配置里收紧，否则容易把预发打挂，结果也不可信。

### 3.2 API 扫描

有 OpenAPI 文档时，API 扫描比爬虫准确：

```bash
docker run --rm --network host -v "$(pwd)/zap-out:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py -t http://127.0.0.1:8080/v3/api-docs \
  -f openapi -r api.html -J api.json
```

预期输出：

```text
Total of 42 URLs
PASS: 30
WARN-NEW: 8
FAIL-NEW: 4
```

API 扫描只覆盖文档里声明的接口。文档缺失、参数未标注、鉴权头未声明，都会导致漏扫。

### 3.3 认证扫描

未认证扫描只能看到登录页。要扫业务接口，必须给 ZAP 配置认证上下文：

```yaml
# zap.yaml（只展示 contexts 片段，spider/activeScan 的 jobs 省略）
env:
  contexts:
    - name: order-api
      urls:
        - http://127.0.0.1:8080
      authentication:
        method: json
        parameters:
          loginUrl: http://127.0.0.1:8080/api/login
          loginRequestData: '{"username":"perf01","password":"***"}'
      sessionManagement:
        method: cookie
      users:
        - name: tester
          credentials:
            username: perf01
            password: "***"
```

用 Automation Framework 执行：

```bash
docker run --rm --network host -v "$(pwd):/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap.sh -cmd -autorun /zap/wrk/zap.yaml
```

> 边界：认证账号必须是专用测试账号，权限与真实角色一致但不含生产数据。用管理员账号扫普通接口会掩盖越权问题。

### 3.4 规则阈值与误报

ZAP 的告警分 High/Medium/Low/Informational。团队要维护一份规则文件，把确认的误报标为 IGNORE，把必须修的标为 FAIL：

```conf
# zap-rules.conf：规则ID  动作
# CSP 缺失，按安全基线必须补
10038	FAIL
# X-Content-Type-Options 缺失，禁止 MIME 嗅探
10021	FAIL
# 时间戳泄露，已确认无利用价值（2026-12-31 复核）
10096	IGNORE
```

```bash
docker run --rm --network host -v "$(pwd):/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://127.0.0.1:8080 -c zap-rules.conf -r baseline.html
```

每条 IGNORE 都要有复核日期和理由，否则一年后没人知道为什么忽略。

### 3.5 告警解读

| 告警 | 真实含义 | 修复位置 |
|---|---|---|
| CSP Header Not Set | 缺内容安全策略 | 网关或应用响应头 |
| X-Content-Type-Options Missing | 浏览器可能 MIME 嗅探 | 全局响应头 |
| Cookie No HttpOnly | 脚本可读会话 Cookie | Cookie 属性 |
| SQL Injection | 参数进入 SQL 且可注入 | 参数化查询 |
| Path Traversal | 文件路径可控 | 路径规范化 + 白名单 |
| CORS Misconfiguration | 任意源可读响应 | 允许源白名单 |

告警里的请求和响应是证据。修复前先复现一次，确认不是扫描器误报；修复后用同一规则回归。

## 四、越权与业务逻辑测试

越权是访问控制失效，工具很难自动发现。核心验证方法只有一个：用低权限身份访问不属于自己的资源，预期被拒绝。水平越权换对象 ID，垂直越权换角色。

### 4.1 水平越权

准备两个普通用户 A、B，各自有一个订单。用 A 的令牌访问 B 的订单：

```bash
BASE=http://127.0.0.1:8080
TOKEN_A=$(curl -s -X POST "$BASE/api/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"userA","password":"***"}' | jq -r '.data.token')

# A 访问自己的订单，预期 200
curl -s -o /dev/null -w 'own: %{http_code}\n' \
  -H "Authorization: Bearer $TOKEN_A" "$BASE/api/orders/1001"

# A 访问 B 的订单，预期 403 或 404；返回 200 即水平越权
curl -s -o /dev/null -w 'other: %{http_code}\n' \
  -H "Authorization: Bearer $TOKEN_A" "$BASE/api/orders/1002"
```

预期：

```text
own: 200
other: 403
```

实际返回 `other: 200` 时，响应体通常还带着 B 的收货地址和手机号，这就是可批量利用的漏洞。

批量验证脚本：

```bash
#!/usr/bin/env bash
# 枚举 1001-1100，统计有多少订单能被 A 读到
BASE=http://127.0.0.1:8080
TOKEN_A=$(curl -s -X POST "$BASE/api/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"userA","password":"***"}' | jq -r '.data.token')

hit=0
for id in $(seq 1001 1100); do
  code=$(curl -s -o /dev/null -w '%{http_code}' \
    -H "Authorization: Bearer $TOKEN_A" "$BASE/api/orders/$id")
  if [ "$code" = "200" ]; then
    hit=$((hit + 1))
    echo "LEAK id=$id"
  fi
done
echo "leaked=$hit/100"
```

> 边界：只在自己创建的测试数据上枚举，不要遍历真实用户 ID。测试结束清理数据并保留最小证据。

### 4.2 垂直越权

用普通用户令牌调用管理接口：

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $TOKEN_A" \
  -X POST "$BASE/api/admin/users/1001/disable"
# 预期 403；返回 200 即垂直越权
```

垂直越权还常见于：

- 前端隐藏了按钮，但后端接口没校验角色；
- 网关按路径前缀放行，绕过后直接访问服务端口；
- 批量接口只校验第一个对象，后续对象不校验；
- 导出、打印、分享链接使用无签名的固定 URL。

### 4.3 业务逻辑绕过

| 场景 | 测试方法 | 预期 |
|---|---|---|
| 优惠券叠加 | 同一券重复提交、并发提交 | 只生效一次 |
| 金额篡改 | 改请求体价格、数量为负 | 服务端重算 |
| 状态跳转 | 跳过支付直接发货 | 非法迁移拒绝 |
| 限量商品 | 并发超卖 | 库存不为负 |
| 试用期 | 改客户端时间/续期接口 | 服务端时间为准 |

这些用例无法靠扫描器生成，要写进接口测试和 E2E，作为回归的一部分。

### 4.4 修复原则

访问控制必须在服务端、在数据层做最终校验：

```java
@GetMapping("/api/orders/{id}")
public OrderDetail get(@PathVariable Long id, @AuthenticationPrincipal User user) {
    // 查询条件同时带 id 和当前用户，避免先查后判的竞态与遗漏
    return orderRepository.findByIdAndUserId(id, user.getId())
        .map(OrderDetail::from)
        // 不区分“存在但无权”和“不存在”，防止通过状态码枚举订单
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
}
```

三条规则：

1. 默认拒绝，白名单放行；
2. 权限判断和数据查询合并到同一条 SQL 或同一个聚合根；
3. 返回 404 而不是 403，减少对象枚举信息。

> 边界：只在 Controller 加 `if` 判断容易漏掉新增接口。用统一的授权注解或网关策略，并在测试里覆盖“新接口默认需要什么权限”。

## 五、依赖与镜像扫描

现代应用的代码大部分来自依赖。依赖扫描回答两个问题：用了什么组件、这些组件有没有已知漏洞和修复版本。镜像扫描在此之上加上操作系统包和基础层。

### 5.1 SCA 与 SBOM

软件物料清单（Software Bill of Materials，SBOM）是依赖清单的标准格式。生成 SBOM 既满足审计，也让漏洞响应更快：

```bash
# CycloneDX 格式，便于被 Dependency-Track 等平台消费
trivy image --format cyclonedx --output sbom.json ghcr.io/acme/order:1.0.0

# SPDX 格式，部分合规场景要求
trivy image --format spdx-json --output sbom.spdx.json ghcr.io/acme/order:1.0.0
```

SBOM 要随制品一起归档，保留时间与制品一致。没有 SBOM 时，出现新 CVE 只能重新构建才能知道受影响范围。

### 5.2 Trivy 的四种扫描对象

| 对象 | 命令 | 查什么 |
|---|---|---|
| 文件系统 | `trivy fs .` | 依赖锁文件、密钥、IaC |
| 镜像 | `trivy image app:1.0` | OS 包 + 语言依赖 |
| 仓库 | `trivy repo <url>` | 远程仓库全量 |
| 配置 | `trivy config .` | Dockerfile/K8s/Terraform |

常用参数：

```bash
trivy image \
  --severity HIGH,CRITICAL \   # 只关心可行动的级别，减少噪声
  --ignore-unfixed \           # 无修复版本的先不进构建门禁
  --exit-code 1 \              # 有命中即失败，供 CI 判定
  --format table \
  ghcr.io/acme/order:1.0.0
```

预期输出：

```text
ghcr.io/acme/order:1.0.0 (ubuntu 24.04)
=======================================
Total: 5 (CRITICAL: 2, HIGH: 3)

┌────────────────┬────────────────┬──────────┬───────────────────┐
│    Library     │ Vulnerability  │ Severity │  Fixed Version    │
├────────────────┼────────────────┼──────────┼───────────────────┤
│ snakeyaml      │ CVE-2022-1471  │ CRITICAL │ 2.0               │
│ spring-core    │ CVE-2024-22243 │ HIGH     │ 6.1.4             │
└────────────────┴────────────────┴──────────┴───────────────────┘
```

> 边界：`--ignore-unfixed` 会让“暂无修复”的漏洞静默通过。必须另建台账跟踪，不能当作已解决。

### 5.3 从扫描结果到修复

| 情况 | 处理 |
|---|---|
| 有修复版本 | 升级依赖/基础镜像，回归后合入 |
| 无修复版本、路径可达 | 加补偿控制，评估替换组件 |
| 无修复版本、路径不可达 | 记录，设复核日期 |
| 仅构建期依赖 | 评估是否进入运行时镜像 |
| OS 包漏洞 | 换更新的基础镜像或精简镜像 |

修复顺序按“可达性 × 严重级别”排。一个 CRITICAL 但如果对应类根本没被加载，优先级低于一个被所有请求调用的 HIGH。

验证依赖是否真的进入运行时：

```bash
# 看镜像里到底有哪些 jar 和版本
docker run --rm --entrypoint sh ghcr.io/acme/order:1.0.0 \
  -c 'ls /app/lib | grep -E "snakeyaml|spring-core"'

# 看依赖树里谁引入了它
mvn dependency:tree -Dincludes=org.yaml:snakeyaml
```

### 5.4 容器与 IaC 扫描

```bash
# Dockerfile 和 K8s 清单的安全配置
trivy config --severity HIGH,CRITICAL deploy/

# 输出示例
# Dockerfile (dockerfile)
# ========================
# Tests: 3 (HIGH: 2)
# HIGH: Specify a tag in the 'FROM' statement
# HIGH: Last USER should not be root
```

容器基线至少满足：非 root 运行、固定基础镜像摘要、只读根文件系统、最小权限、无特权模式。

## 六、密钥与配置扫描

凭据泄露是最容易被忽略、后果最直接的问题。密钥一旦进入 Git 历史，即使删除文件也仍然可被检出，必须按“已泄露”处理：先轮换，再清理。

### 6.1 常见泄露面

| 位置 | 示例 | 风险 |
|---|---|---|
| 源码常量 | `password = "Prod@123"` | 全历史可见 |
| 配置文件 | `.env`、`application-prod.yml` | 随制品分发 |
| 测试数据 | 真实手机号、身份证 | 合规问题 |
| 日志 | 打印 token、Cookie | 日志平台扩散 |
| 前端构建 | 把密钥打进 bundle | 任何人可读 |
| CI 变量 | 回显到构建日志 | 构建记录留存 |

### 6.2 gitleaks 扫描

```bash
# 扫描仓库全部历史
gitleaks git . --report-format json --report-path gitleaks.json

# 只扫暂存区，用于 pre-commit
gitleaks git --staged --redact

# 扫描指定提交区间
gitleaks git . --log-opts="origin/main..HEAD"
```

预期输出：

```text
Finding:     aws_access_key_id = "AKIA..."
Secret:      AKIA...
RuleID:      aws-access-token
File:        deploy/values-prod.yaml
Line:        18
Commit:      9f3c2a1
```

发现后处理顺序：

1. 立即轮换/吊销凭据，阻断利用；
2. 评估泄露时间窗和访问日志；
3. 用 `git filter-repo` 清理历史或直接判定仓库历史不可信；
4. 加 pre-commit 和 CI 扫描，防止再次进入；
5. 复盘为什么本地配置会被提交。

```bash
# 历史清理示例：删除 .env 的所有历史，操作前先备份并通知协作方
git filter-repo --path .env --invert-paths
```

> 边界：改写历史会影响所有协作者和已有克隆，必须在轮换凭据之后做，且不能把它当成唯一补救。凭据已经泄露，轮换才是止损。

### 6.3 配置基线

```yaml
# application-prod.yml 的关键项
server:
  error:
    include-stacktrace: never     # 不把堆栈返回给客户端
  servlet:
    session:
      cookie:
        http-only: true           # 禁止脚本读取会话
        secure: true              # 只走 HTTPS
        same-site: lax            # 降低 CSRF 面
management:
  endpoints:
    web:
      exposure:
        include: health,info      # 不暴露 env、heapdump 等敏感端点
```

配置扫描能发现“写错了”，但发现不了“权限设计错了”。两者要一起做。

## 七、CI 门禁与漏洞治理

门禁的作用是让新增风险无法合入，而不是追求零告警。策略要区分“新增”和“存量”，否则历史漏洞会让门禁永久红灯，团队只能整体绕过。

### 7.1 分阶段门禁

| 阶段 | 检查 | 失败条件 |
|---|---|---|
| 提交前 | gitleaks pre-commit | 发现新密钥 |
| 构建 | SCA + SBOM | 新增 CRITICAL |
| 镜像 | Trivy image | 新增 CRITICAL/HIGH |
| 部署后 | ZAP baseline | 新增 High 告警 |
| 夜间 | ZAP full/API | 趋势恶化 |

```yaml
# .github/workflows/security.yml（片段）
name: security
on: [pull_request]

jobs:
  secret-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # gitleaks 需要历史才能查泄露
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  image-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t app:${{ github.sha }} .
      - uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: app:${{ github.sha }}
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: '1'          # 命中即阻断，不给“稍后处理”留口子
```

> 边界：组织仓库使用 `gitleaks/gitleaks-action` 需要配置 `GITLEAKS_LICENSE`；没有 license 时改成直接运行 `gitleaks git` 步骤，不依赖该 Action。

### 7.2 豁免与到期

无法立即修复的漏洞要有豁免记录：

```yaml
# .security/exceptions.yaml
- id: CVE-2022-1471
  component: snakeyaml
  reason: 仅测试工具链使用，不进入运行时镜像
  owner: platform-team
  expires: 2026-12-31
  compensating: 镜像不含该类，已用依赖树确认
```

门禁读取豁免文件，过期自动恢复阻断。没有 owner 和到期日的豁免一律不合并。

### 7.3 修复 SLA

| 级别 | 修复窗口 | 临时措施 |
|---|---|---|
| CRITICAL 可利用 | 24 小时 | 下线/隔离/加规则 |
| HIGH | 7 天 | WAF/权限收紧 |
| MEDIUM | 30 天 | 排期 |
| LOW | 90 天 | 随版本 |

SLA 从“确认受影响”开始算，不从扫描时间算。先确认资产是否真的在跑、路径是否可达，再定级。

### 7.4 度量

只看“漏洞总数”会鼓励隐藏问题。更有用的指标：

- 新增漏洞的修复中位时间；
- 豁免过期未处理数；
- 扫描覆盖率（多少服务接入了 SCA/DAST）；
- 重复出现的漏洞类型；
- 从发现到轮换凭据的时间。

## 八、最佳实践案例

### 8.1 案例背景

某电商订单服务准备上线，技术栈是 Spring Boot 3.5 + MySQL 8.4 + Redis 7.4，部署在 Kubernetes。团队有 6 人，没有专职安全工程师。目标是在上线前完成一次动态扫描、越权验证和依赖清理，并把检查接进 GitHub Actions。约束：只有预发环境可用，不能压测生产，修复窗口 5 个工作日。

### 8.2 案例实操

第一步，跑 ZAP 基线，先拿到低风险的配置问题：

```bash
docker run --rm --network host -v "$(pwd)/zap:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://10.0.2.15:8080 \
  -c zap-rules.conf -r baseline.html -J baseline.json
```

结果（示例）：

```text
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 6
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 4
WARN-NEW: Cookie No HttpOnly Flag [10010] x 2
FAIL-NEW: 0
```

修复放在网关统一响应头，避免每个服务各写一遍：

```nginx
add_header Content-Security-Policy "default-src 'self'; object-src 'none'; frame-ancestors 'none'" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

第二步，跑 API 扫描。服务暴露 OpenAPI，扫描覆盖 38 个接口：

```bash
docker run --rm --network host -v "$(pwd)/zap:/zap/wrk:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py -t http://10.0.2.15:8080/v3/api-docs \
  -f openapi -r api.html -J api.json
```

结果（示例）：

```text
Total of 38 URLs
PASS: 29
WARN-NEW: 6
FAIL-NEW: 3
```

3 个 FAIL 中有 1 个是搜索接口的 SQL 注入告警。复现：

```bash
curl -s "http://10.0.2.15:8080/api/products/search?q=phone%27%20OR%201%3D1--" | jq '.total'
# 返回全部商品数量，确认注入可用
```

定位到拼接 SQL 的代码后改为参数化查询：

```java
// 错误写法：直接把 q 拼进 SQL
// String sql = "SELECT * FROM product WHERE name LIKE '%" + q + "%'";

// 正确写法：占位符由驱动转义，q 永远被当作数据
String sql = "SELECT * FROM product WHERE name LIKE ?";
return jdbc.query(sql, (rs, i) -> map(rs), "%" + q + "%");
```

第三步，验证越权。用两个普通账号，A 的订单号 1001，B 的订单号 1002：

```bash
TOKEN_A=$(curl -s -X POST http://10.0.2.15:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"qa_a","password":"***"}' | jq -r '.data.token')

for id in 1001 1002; do
  echo -n "$id: "
  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: Bearer $TOKEN_A" \
    "http://10.0.2.15:8080/api/orders/$id"
done
```

修复前：

```text
1001: 200
1002: 200
```

确认水平越权。修复为查询条件同时带用户：

```java
@GetMapping("/api/orders/{id}")
public OrderDetail get(@PathVariable Long id, @AuthenticationPrincipal User user) {
    return orderRepository.findByIdAndUserId(id, user.getId())
        .map(OrderDetail::from)
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
}
```

修复后：

```text
1001: 200
1002: 404
```

第四步，扫描依赖和镜像：

```bash
# SCA 会连 test scope 一起扫，正好用来确认它是否进入运行时
trivy fs --severity HIGH,CRITICAL --ignore-unfixed \
  --format table --output trivy-fs.txt .

docker build -t ghcr.io/acme/order:1.0.0 .
trivy image --severity HIGH,CRITICAL --ignore-unfixed \
  --format table --output trivy-image.txt ghcr.io/acme/order:1.0.0
```

依赖扫描结果（示例）：

```text
Total: 7 (CRITICAL: 2, HIGH: 5)
snakeyaml 1.33  CVE-2022-1471  CRITICAL  fixed 2.0
spring-core 6.1.3  CVE-2024-22243  HIGH  fixed 6.1.4
```

`snakeyaml` 是测试工具传递进来的。先用依赖树确认：

```bash
mvn dependency:tree -Dincludes=org.yaml:snakeyaml
# [INFO] +- org.testcontainers:testcontainers:jar:1.20.4
# [INFO] |  \- org.yaml:snakeyaml:jar:1.33:test
```

确认 scope 是 `test`，不会进入运行时镜像；升级到 2.0 并加豁免，同时把 `spring-core` 升到 6.1.4 或更高：

```xml
<dependency>
  <groupId>org.yaml</groupId>
  <artifactId>snakeyaml</artifactId>
  <version>2.0</version>
  <scope>test</scope>
</dependency>
```

第五步，密钥扫描：

```bash
gitleaks git . --report-format json --report-path gitleaks.json
```

命中 `deploy/values-prod.yaml` 里的数据库密码。处理顺序：轮换密码 → 从配置改为 Secret 引用 → 清理历史 → 加 pre-commit。

第六步，接入 CI。合并请求上跑密钥、依赖、镜像三条检查，部署后跑 ZAP 基线：

```yaml
name: security
on:
  pull_request:
  workflow_run:
    workflows: [deploy]
    types: [completed]

jobs:
  sca:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: fs
          severity: CRITICAL,HIGH
          exit-code: '1'

  secret:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  dast:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: ZAP baseline
        run: |
          docker run --rm --network host -v "$PWD:/zap/wrk:rw" \
            ghcr.io/zaproxy/zaproxy:stable \
            zap-baseline.py -t "${{ vars.STAGING_URL }}" \
            -c zap-rules.conf -r zap.html
```

### 8.3 案例结果

| 项目 | 修复前 | 修复后 | 门禁 |
|---|---|---|---|
| ZAP High 告警 | 3 | 0 | 阻断新增 |
| 越权接口 | 1 个可读他人订单 | 404 | 手工回归 |
| 依赖/镜像 CRITICAL | 2 | 0 | 阻断 |
| 依赖/镜像 HIGH | 5 | 1（已豁免） | 阻断 |
| 明文凭据 | 1 处 | 0 | 阻断 |
| 扫描耗时 | 无 | 4 分 20 秒 | 可接受 |

失败模式复盘：

- 第一次把 `--ignore-unfixed` 当成“忽略所有”，导致一个可修复的 HIGH 被静默放过；后来在门禁里同时要求“有修复版本必须修”；
- 只扫镜像不扫文件系统，漏掉了 `package-lock.json` 里的前端依赖；SCA 要覆盖所有构建产物；
- ZAP 用未认证模式扫业务接口，只看到登录页，误以为“没有问题”；认证上下文是 API 扫描的前提；
- 越权修复只改了 Controller 的一个方法，新增的导出接口又出现同类问题；最终用统一授权切面和接口测试兜底。

结论：安全门禁要覆盖“代码、依赖、镜像、运行时”四层，每层只拦新增风险，存量按 SLA 清理。工具负责已知模式，越权和业务逻辑必须靠双账号用例长期回归。
