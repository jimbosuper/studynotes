# Go请求处理与校验

> 这篇从请求数据的五种来源讲起，经过 Gin 的绑定选择、validator 校验规则与自定义校验、统一响应与错误码、文件上传的安全边界、日志与恢复中间件，最后落到一个商品发布接口的完整案例和请求层排障手册。
>
> 学完能独立写出“绑定 → 校验 → 业务 → 统一错误 → 结构化日志”的完整请求链路，能区分 400、415、422、413 的适用场景，并把上传接口做成内容嗅探与大小受限的安全实现。

> 版本基线（2026-11-13）：Go 1.24+（示例在 Go 1.27.x 验证），Gin 1.10+（示例在 v1.11.x 兼容），`github.com/go-playground/validator/v10` 随 Gin 引入。命令默认 Ubuntu 24.04。

## 一、请求数据的来源与绑定

HTTP 请求的数据分散在路径、查询串、请求头、表单和 JSON 体里。Gin 的绑定（binding）把这些来源统一映射到结构体，减少手写类型转换。

### 1.1 五种来源

| 来源 | 示例 | Gin 方法 | tag |
|---|---|---|---|
| 路径参数 | `/products/42` | `ShouldBindUri` | `uri:"id"` |
| 查询串 | `?page=2&size=20` | `ShouldBindQuery` | `form:"page"` |
| 请求头 | `X-Tenant: acme` | `ShouldBindHeader` | `header:"X-Tenant"` |
| 表单 | `name=book&price=10` | `ShouldBind` | `form:"name"` |
| JSON 体 | `{"name":"book"}` | `ShouldBindJSON` | `json:"name"` |

`ShouldBind` 自动按方法和 `Content-Type` 选择绑定器：GET 用查询串与表单，POST 用 JSON 或表单。它把选择权交给内容协商，适合一个接口接收多种格式；显式方法适合契约固定的 API。

```go
type ListQuery struct {
	Page   int    `form:"page" binding:"gte=1,lte=1000"`
	Size   int    `form:"size" binding:"gte=1,lte=100"`
	Status string `form:"status" binding:"omitempty,oneof=created paid shipped"`
}

var q ListQuery
if err := c.ShouldBindQuery(&q); err != nil {
	// 校验失败，转成统一错误响应
}
```

### 1.2 ShouldBind 与 Bind 的区别

`Bind` 系列在失败时自动写 400 并终止请求，`ShouldBind` 系列只返回错误，由代码决定响应格式。

```go
// 自动 400，响应体是纯文本，无法带错误码和 request_id
if err := c.BindJSON(&req); err != nil {
	return
}

// 手动处理，能返回统一的结构化错误
if err := c.ShouldBindJSON(&req); err != nil {
	writeBindError(c, err)
	return
}
```

API 一律用 `ShouldBind`。`Bind` 只适合原型或内部调试接口。

> 边界：`ShouldBind` 会把请求体读干净，同一个请求里第二次绑定不会报错，但读到的体是空的，校验规则里的 `required` 会全部失败。需要从多个来源取数时，分别用 `ShouldBindQuery`、`ShouldBindUri` 各绑一次，不要对 body 绑两次。

### 1.3 内容类型与 415

`ShouldBindJSON` 不看 `Content-Type`，直接按 JSON 解析。客户端发 `text/plain` 但内容是合法 JSON 时，接口仍会成功，契约被破坏。需要严格时先判断：

```go
if ct := c.ContentType(); ct != "application/json" {
	c.JSON(http.StatusUnsupportedMediaType, gin.H{"code": "UNSUPPORTED_MEDIA_TYPE"})
	return
}
```

| 状态码 | 含义 | 触发条件 |
|---|---|---|
| 400 | 请求体语法错 | JSON 截断、类型不符 |
| 415 | 媒体类型不支持 | `Content-Type` 不是 JSON |
| 422 | 语法对但语义不合法 | 字段校验失败 |

415 与 400 的分界线是“服务端是否支持这种格式”，不是“内容对不对”。

### 1.4 可选字段与指针

`binding:"required"` 对数值的零值也判为缺失：`stock=0` 会被拒。要区分“没传”和“传了 0”，用指针：

```go
type UpdateStock struct {
	Stock *int `json:"stock" binding:"omitempty,gte=0,lte=100000"`
}

// req.Stock == nil：没传，保持原值
// req.Stock != nil && *req.Stock == 0：显式清零
```

字符串同理，`omitempty` 让空串跳过后续规则；指针则能表达“显式传空串”。

> 边界：`omitempty` 在数字零值上也会跳过校验，`stock=0` 配 `omitempty,gte=1` 会通过。需要“必填且非零”时不要加 `omitempty`，需要“可选但非零”时用指针加 `gt=0`。

### 1.5 时间与枚举的绑定

JSON 里的时间默认按 RFC 3339 解析（`2026-11-13T10:00:00+08:00`）。前端传 `2026-11-13` 会失败，需要自定义类型：

```go
type Date struct{ time.Time }

func (d *Date) UnmarshalJSON(b []byte) error {
	s := strings.Trim(string(b), `"`)
	if s == "" || s == "null" {
		return nil
	}
	t, err := time.ParseInLocation("2006-01-02", s, time.Local)
	if err != nil {
		return fmt.Errorf("date must be YYYY-MM-DD: %w", err)
	}
	d.Time = t
	return nil
}
```

枚举用 `oneof` 约束，不用自定义类型；`oneof` 的比较是字符串精确匹配，大小写敏感。

## 二、校验规则

校验分两层：结构校验（字段级，用 tag）和业务校验（跨字段、查库，用代码）。tag 只做前者，后者放进 service，否则校验逻辑会和请求结构绑死。

### 2.1 常用 tag

| tag | 作用 | 示例 |
|---|---|---|
| `required` | 非零值 | `binding:"required"` |
| `min` / `max` | 字符串长度或数值范围 | `min=2,max=60` |
| `gte` / `lte` | 数值比较 | `gte=0,lte=100000` |
| `len` | 长度精确相等 | `len=6` |
| `oneof` | 枚举 | `oneof=book food` |
| `email` / `url` / `uuid` | 格式 | `email` |
| `dive` | 进入切片/映射元素 | `max=5,dive,min=1` |

注意 `min`/`max` 对字符串是字符数（rune 数），对数字是数值大小；`gte`/`lte` 只用于数字和时间。

```go
type CreateProductRequest struct {
	SKU      string   `json:"sku" binding:"required,sku"`
	Name     string   `json:"name" binding:"required,min=2,max=60"`
	Price    int64    `json:"price_cents" binding:"required,gt=0"`
	Stock    int      `json:"stock" binding:"gte=0,lte=100000"`
	Category string   `json:"category" binding:"required,oneof=book food digital"`
	Tags     []string `json:"tags" binding:"max=5,dive,min=1,max=16"`
}
```

### 2.2 嵌套结构体与切片

嵌套结构体默认会递归校验；切片和映射需要 `dive` 才能进入元素：

```go
type Address struct {
	City string `json:"city" binding:"required"`
	Zip  string `json:"zip" binding:"required,len=6"`
}

type Order struct {
	Address Address  `json:"address" binding:"required"` // required 校验结构体本身
	Items   []Item   `json:"items" binding:"required,min=1,max=20,dive"`
}
```

`dive` 之后的规则作用于每个元素；`dive` 可以出现多次，用于二维结构。

> 边界：结构体字段加 `required` 时，校验的是“结构体是否为零值”，嵌套结构体只要有任一字段非零就通过，不会逐字段判空。逐字段校验靠递归，不靠外层的 `required`。

### 2.3 跨字段校验

“结束时间晚于开始时间”“确认密码一致”属于跨字段规则，用 `eqfield` 或 `gtfield`：

```go
type Campaign struct {
	StartAt time.Time `json:"start_at" binding:"required"`
	EndAt   time.Time `json:"end_at" binding:"required,gtfield=StartAt"`
}
```

`gtfield` 取同结构体里的字段值比较，字段名用 Go 名。复杂条件（如“折扣价必须低于原价且不低于成本价”）写成自定义校验或在 service 里判断：

```go
func (r *CreateProductRequest) Validate() error {
	if r.PriceCents <= 0 {
		return errors.New("price must be positive")
	}
	return nil
}
```

> 边界：不要用 tag 表达依赖数据库的规则（SKU 是否重复、库存是否足够）。tag 在请求进入时执行一次，查库校验必须在事务内重做，否则并发下仍会超卖。

### 2.4 自定义校验器

内置规则覆盖不到的格式（企业内部 SKU、手机号段）注册自定义函数：

```go
func init() {
	v, ok := binding.Validator.Engine().(*validator.Validate)
	if !ok {
		return
	}
	// 用 json tag 作为错误里的字段名，前端能直接对到表单
	v.RegisterTagNameFunc(func(fld reflect.StructField) string {
		name := strings.SplitN(fld.Tag.Get("json"), ",", 2)[0]
		if name == "" || name == "-" {
			return fld.Name
		}
		return name
	})
	_ = v.RegisterValidation("sku", validateSKU)
}

func validateSKU(fl validator.FieldLevel) bool {
	s := fl.Field().String()
	if len(s) < 6 || len(s) > 20 {
		return false
	}
	for _, r := range s {
		// 只允许大写字母、数字和连字符，避免下游系统转义问题
		if (r < 'A' || r > 'Z') && (r < '0' || r > '9') && r != '-' {
			return false
		}
	}
	return true
}
```

`binding.Validator` 是全局单例，注册只做一次（`init` 或 `sync.Once`）。重复注册同名 tag 会 panic：`RegisterValidation` 在 tag 已存在时返回错误，忽略错误会让后注册的规则覆盖前面的。

### 2.5 校验错误的结构化

`validator.ValidationErrors` 是 `FieldError` 的切片，逐条转成前端能消费的结构：

```go
type FieldError struct {
	Field   string `json:"field"`
	Code    string `json:"code"`
	Message string `json:"message"`
}

func toFieldErrors(err error) []FieldError {
	var ve validator.ValidationErrors
	if !errors.As(err, &ve) {
		return nil // 不是校验错误，交给上层按 400 处理
	}
	out := make([]FieldError, 0, len(ve))
	for _, fe := range ve {
		out = append(out, FieldError{
			Field:   fe.Field(),
			Code:    fe.Tag(),
			Message: messageFor(fe),
		})
	}
	return out
}

func messageFor(fe validator.FieldError) string {
	switch fe.Tag() {
	case "required":
		return "不能为空"
	case "min":
		return "长度不能少于 " + fe.Param()
	case "max":
		return "长度不能超过 " + fe.Param()
	case "gt":
		return "必须大于 " + fe.Param()
	case "gte":
		return "不能小于 " + fe.Param()
	case "oneof":
		return "必须是以下之一: " + fe.Param()
	case "sku":
		return "格式为 6-20 位大写字母、数字或连字符"
	default:
		return "不合法"
	}
}
```

tag 到中文的映射表比引入完整 i18n 翻译器轻，维护成本低。多语言产品再上 `universal-translator` 加 `zh` 翻译包。

> 边界：`fe.Param()` 在 `required`、`email` 这类无参数规则里是空串；把参数直接拼进提示前要判断，否则会出现“长度不能少于 ”这种残句。

### 2.6 业务校验的位置

结构校验通过只代表“格式对”，不代表“能执行”。业务规则按顺序放在 service：

```text
格式校验（tag） → 权限校验（中间件） → 幂等校验（唯一键）
→ 状态校验（读当前状态） → 资源校验（库存/余额） → 落库
```

库存扣减这类校验必须在事务里用条件更新完成，不能在校验阶段“查到有库存”就放行。tag 是入口过滤，不是一致性保证。

## 三、统一响应与错误码

统一响应让前端只写一套解析逻辑，也让日志、监控、告警有稳定的字段。

### 3.1 响应结构

```go
type Response struct {
	Code      string `json:"code"`             // 业务码，稳定不变
	Message   string `json:"message"`          // 人类可读
	RequestID string `json:"request_id"`       // 与日志串联
	Data      any    `json:"data,omitempty"`   // 成功时的数据
	Details   any    `json:"details,omitempty"`// 校验失败的字段列表
}
```

```go
func OK(c *gin.Context, data any) {
	c.JSON(http.StatusOK, Response{
		Code: "OK", Message: "ok",
		RequestID: c.GetString("request_id"), Data: data,
	})
}

func Fail(c *gin.Context, status int, code, msg string, details any) {
	c.JSON(status, Response{
		Code: code, Message: msg,
		RequestID: c.GetString("request_id"), Details: details,
	})
}
```

业务码与 HTTP 状态码并存：状态码给网关和监控用，业务码给前端分支用。只有状态码时，前端无法区分“参数错”和“资源不存在”，都落在 400/404 上。

### 3.2 状态码映射

| 场景 | 状态码 | 业务码示例 |
|---|---|---|
| 创建成功 | 201 | `OK` |
| 参数校验失败 | 422 | `VALIDATION_FAILED` |
| JSON 语法错 | 400 | `MALFORMED_JSON` |
| 媒体类型不支持 | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 未认证 / 无权限 | 401 / 403 | `UNAUTHORIZED` / `FORBIDDEN` |
| 资源不存在 | 404 | `PRODUCT_NOT_FOUND` |
| 冲突（重复 SKU） | 409 | `SKU_CONFLICT` |
| 请求体过大 | 413 | `PAYLOAD_TOO_LARGE` |

> 边界：422 不是所有团队都接受。对外 API 用 400 加 `details` 也常见，关键是整个项目统一，不要让“参数错”一会儿 400、一会儿 422。

### 3.3 错误类型分层

用自定义错误类型携带状态码和业务码，handler 只做一次转换：

```go
type AppError struct {
	Status int
	Code   string
	Msg    string
	Err    error
}

func (e *AppError) Error() string { return e.Msg }
func (e *AppError) Unwrap() error { return e.Err }

var ErrNotFound = &AppError{Status: 404, Code: "PRODUCT_NOT_FOUND", Msg: "商品不存在"}

func writeError(c *gin.Context, err error) {
	var ae *AppError
	if errors.As(err, &ae) {
		Fail(c, ae.Status, ae.Code, ae.Msg, nil)
		return
	}
	// 未分类错误一律 500，且不把内部细节返回给客户端
	slog.Error("unhandled", "err", err, "request_id", c.GetString("request_id"))
	Fail(c, http.StatusInternalServerError, "INTERNAL", "服务器内部错误", nil)
}
```

`Unwrap` 让 `errors.Is/As` 能穿透包装；日志里保留原始错误，响应里只给安全文案。

### 3.4 分页参数

分页参数统一在入口处归一化，避免每层各自处理默认值：

```go
type Page struct {
	Page int `form:"page" binding:"omitempty,gte=1,lte=1000"`
	Size int `form:"size" binding:"omitempty,gte=1,lte=100"`
}

func (p *Page) Normalize() {
	if p.Page == 0 {
		p.Page = 1
	}
	if p.Size == 0 {
		p.Size = 20
	}
}
```

`offset = (page-1)*size`，上限 100 防止一次拉全表。深分页（offset 很大）在百万行表上会变慢，改用游标分页（`WHERE id < last_id ORDER BY id DESC LIMIT n`）。

## 四、文件上传

上传接口的风险集中在三处：体积、类型、文件名。三处都必须服务端校验，客户端的 `accept` 和大小提示只是体验优化。

### 4.1 multipart 的解析与内存

`multipart/form-data` 解析时，小文件放内存，大文件落临时文件。Gin 的阈值是 `MaxMultipartMemory`（默认 32 MiB）。

```go
r.MaxMultipartMemory = 8 << 20 // 8 MiB，超过的部分落磁盘临时文件
```

这个值只控制内存占用，不限制请求体大小；真正的上限靠 `MaxBytesReader`。

### 4.2 请求体硬上限

```go
const maxImage = 2 << 20 // 2 MiB

func upload(c *gin.Context) {
	// 多留 1 MiB 给 multipart 边界和表单字段，避免误伤
	c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxImage+(1<<20))

	file, err := c.FormFile("file")
	if err != nil {
		var maxErr *http.MaxBytesError
		if errors.As(err, &maxErr) {
			Fail(c, http.StatusRequestEntityTooLarge, "PAYLOAD_TOO_LARGE", "文件超过 2 MiB", nil)
			return
		}
		Fail(c, http.StatusBadRequest, "INVALID_MULTIPART", "缺少 file 字段", nil)
		return
	}
	if file.Size > maxImage {
		Fail(c, http.StatusRequestEntityTooLarge, "PAYLOAD_TOO_LARGE", "文件超过 2 MiB", nil)
		return
	}
	_ = file
}
```

`MaxBytesReader` 在超限时返回 `*http.MaxBytesError`，并关闭连接；不设它时，攻击者可以传几个 GB 把磁盘临时目录写满。

> 边界：只靠 `file.Size` 不够。`file.Size` 来自 multipart 头，可被伪造；`MaxBytesReader` 是实际读取上限，两者都要。

### 4.3 内容嗅探与白名单

`file.Header.Get("Content-Type")` 由客户端声明，可以随便写。真实类型用 `http.DetectContentType` 读前 512 字节判断：

```go
allowed := map[string]string{
	"image/jpeg": ".jpg",
	"image/png":  ".png",
	"image/webp": ".webp",
}

f, err := file.Open()
if err != nil {
	Fail(c, 400, "INVALID_FILE", "无法读取文件", nil)
	return
}
defer f.Close()

head := make([]byte, 512)
n, err := io.ReadFull(f, head)
if err != nil && !errors.Is(err, io.ErrUnexpectedEOF) {
	Fail(c, 400, "INVALID_FILE", "无法读取文件", nil)
	return
}
ct := http.DetectContentType(head[:n])
ext, ok := allowed[ct]
if !ok {
	Fail(c, http.StatusUnsupportedMediaType, "UNSUPPORTED_IMAGE_TYPE", "仅支持 JPEG/PNG/WebP", nil)
	return
}
```

`DetectContentType` 只认内容特征，改扩展名绕不过去。它不检测图片是否损坏、是否含恶意负载；需要更深校验时解码一次（`image.DecodeConfig`）确认尺寸。

### 4.4 文件名与存储

```go
// 原始文件名只用于取扩展名和展示，绝不拼进路径
original := filepath.Base(file.Filename)
_ = original
name := hex.EncodeToString(sum[:16]) + ext // 随机名，避免覆盖与路径注入
dst := filepath.Join(uploadDir, name)
if err := c.SaveUploadedFile(file, dst); err != nil {
	Fail(c, 500, "SAVE_FAILED", "保存失败", nil)
	return
}
```

`filepath.Base` 去掉 `../` 和路径分隔符；随机名防止“同名覆盖”和“通过文件名注入 HTML/JS”。存储目录不要放在静态资源根下，除非确认执行权限被关闭。

> 边界：`filepath.Join(uploadDir, name)` 里的 `name` 必须是服务端生成的。用原始文件名拼接时，Windows 的 `C:\` 和 Unix 的 `..` 都可能逃出目录。

### 4.5 下载与响应头

```go
c.FileAttachment(dst, "product-cover.png") // 设置 Content-Disposition: attachment
```

`FileAttachment` 会做 URL 转义，中文文件名可用。需要浏览器内联预览时用 `c.File`，但只对可信类型开放，HTML/SVG 内联会带来 XSS。

## 五、日志与恢复中间件

请求层的日志要回答四个问题：谁、请求了什么、结果如何、耗时多少；恢复中间件要保证 panic 不会把进程带走。

### 5.1 结构化日志

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
	Level: slog.LevelInfo,
}))
slog.SetDefault(logger)
```

JSON 格式便于采集到 Loki/ES，字段名稳定比可读性重要。

### 5.2 请求日志中间件

```go
func AccessLog(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()

		logger.LogAttrs(c.Request.Context(), slog.LevelInfo, "http_access",
			slog.String("request_id", c.GetString("request_id")),
			slog.String("method", c.Request.Method),
			slog.String("path", c.Request.URL.Path),
			slog.String("query", redactQuery(c.Request.URL.RawQuery)),
			slog.Int("status", c.Writer.Status()),
			slog.Int64("cost_ms", time.Since(start).Milliseconds()),
			slog.Int("bytes", c.Writer.Size()),
			slog.String("error_code", c.GetString("error_code")),
			slog.String("client_ip", c.ClientIP()),
		)
	}
}
```

`c.Writer.Size()` 在未写响应时返回 -1，日志里要允许这个值。状态码来自 `c.Writer.Status()`，默认 200。

### 5.3 恢复中间件

```go
func Recover(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		defer func() {
			if v := recover(); v != nil {
				// 记录完整堆栈，否则只有一个 panic 值无法定位
				logger.Error("panic",
					"request_id", c.GetString("request_id"),
					"path", c.Request.URL.Path,
					"panic", fmt.Sprint(v),
					"stack", string(debug.Stack()),
				)
				Fail(c, http.StatusInternalServerError, "INTERNAL", "服务器内部错误", nil)
				c.Abort() // 阻止后续中间件继续写响应
			}
		}()
		c.Next()
	}
}
```

顺序：Recover 要在 AccessLog 内层，这样 AccessLog 能记录到 500；Recover 之前不能有会 panic 的中间件。

### 5.4 脱敏

日志里不能出现密码、token、完整手机号：

```go
func redactQuery(raw string) string {
	u, err := url.ParseQuery(raw)
	if err != nil {
		return ""
	}
	for _, k := range []string{"password", "token", "secret", "id_card"} {
		if u.Has(k) {
			u.Set(k, "***")
		}
	}
	return u.Encode()
}
```

请求体默认不记日志。确需记录时按字段白名单序列化，不要 `io.ReadAll` 后整段打印——既会泄露，也会把日志系统撑爆。

> 边界：`c.Request.Body` 读一次就没了，日志中间件读了 body，绑定就会拿到空内容。需要同时记录和绑定，用 `c.Request.GetBody`（服务端请求不保证有）或 `io.TeeReader` 缓存后重置。

### 5.5 错误码与日志串联

在 `Fail` 里顺手写 `error_code`，日志就能按业务码聚合：

```go
func Fail(c *gin.Context, status int, code, msg string, details any) {
	c.Set("error_code", code) // AccessLog 在 c.Next() 之后读取
	c.JSON(status, Response{Code: code, Message: msg,
		RequestID: c.GetString("request_id"), Details: details})
}
```

## 六、排障现场手册

请求层的问题大多有固定形态，按“状态码 + 日志字段”两步就能定位。

| 现象 | 原因 | 第一条命令 |
|---|---|---|
| 400 `EOF` | 请求体为空 | `curl -d '{}'` 复现 |
| 422 但字段看着有值 | 类型不匹配或 tag 写错 | 看 `details[].code` |
| 上传 413 | 超过 `MaxBytesReader` | 查 `Content-Length` |
| 上传 415 | 嗅探类型不在白名单 | 用 `file` 命令看真实类型 |
| 中文乱码 | 未声明 charset | 响应头加 `charset=utf-8` |
| 第二次绑定全空 | body 已被读过 | 检查中间件是否读了 body |
| 启动 panic 校验 tag | 自定义 tag 未注册 | 看 panic 里的 tag 名 |

### 6.1 EOF 与 JSON 语法错误

```bash
curl -i -X POST localhost:8080/api/v1/products \
  -H 'Content-Type: application/json' -d ''
```

空体时 `json.Decoder` 返回 `io.EOF`，Gin 包装后是 `EOF`。区分三类解析错误：

```go
var syntaxErr *json.SyntaxError
var typeErr *json.UnmarshalTypeError
switch {
case errors.Is(err, io.EOF):
	// 请求体为空
case errors.As(err, &syntaxErr):
	// JSON 语法错误，syntaxErr.Offset 指出位置
case errors.As(err, &typeErr):
	// 字段类型不符，typeErr.Field 指出字段
}
```

### 6.2 校验失败却找不到字段

`fe.Field()` 默认返回 Go 结构体字段名（`PriceCents`），前端表单用的是 `price_cents`。注册 `RegisterTagNameFunc` 后返回 json 名，问题消失。没有注册时，`details` 里的字段名和前端对不上，是最常见的“校验提示不显示”原因。

### 6.3 上传大小与临时文件

```bash
du -sh /tmp/multipart-* 2>/dev/null | tail -5
df -h /tmp
```

请求体超限但没配 `MaxBytesReader` 时，multipart 会把超出内存阈值的部分写到 `/tmp`，磁盘先满。容器里 `/tmp` 常挂在内存盘上，表现是“上传大文件后 Pod 被 OOMKilled”。

### 6.4 中文与字符集

Gin 的 `c.JSON` 默认写 `application/json; charset=utf-8`，直接返回中文不会乱码。乱码通常来自两处：中间件手工写了 `Content-Type: text/plain` 后没加 charset；或者上游把 GBK 编码的字符串塞进了 JSON。后者要在入口转码，不能靠响应头补救。

### 6.5 validator 的 panic 形态

```text
panic: Undefined validation function 'sku' on field 'SKU'
```

说明 tag 用了但没注册。另一种：

```text
panic: struct field tag `json:"name" binding:"required,min=2,max=60"` not compatible
```

tag 的引号不配对，编译器不报错，validator 解析时 panic。启动即暴露，比线上好。

## 七、最佳实践案例

### 7.1 案例背景

一个内容电商后台要上线“商品发布”接口，需求包含 JSON 创建商品和封面上传两步。现状接口有三个问题：校验失败时返回一段纯文本，前端无法定位字段；上传接口只看扩展名，运营传了一个改名成 `.png` 的 HTML 文件，被直接存进静态目录；线上偶发 panic 导致整个进程退出。

目标是重写这两个接口：JSON 请求做严格绑定和字段级校验，上传做大小限制与内容嗅探，所有错误走统一结构，panic 被恢复并记录堆栈。约束是继续使用 Gin，不引入 ORM，商品数据先内存存储。

```go
package httpapi

import (
	"errors"
	"reflect"
	"strings"

	"github.com/gin-gonic/gin/binding"
	"github.com/go-playground/validator/v10"
)

type FieldError struct {
	Field   string `json:"field"`
	Code    string `json:"code"`
	Message string `json:"message"`
}

func init() {
	v, ok := binding.Validator.Engine().(*validator.Validate)
	if !ok {
		return
	}
	v.RegisterTagNameFunc(func(fld reflect.StructField) string {
		name := strings.SplitN(fld.Tag.Get("json"), ",", 2)[0]
		if name == "" || name == "-" {
			return fld.Name
		}
		return name
	})
	// 忽略返回值会让同名 tag 的第二次注册静默失败，这里只在 init 注册一次
	_ = v.RegisterValidation("sku", func(fl validator.FieldLevel) bool {
		s := fl.Field().String()
		if len(s) < 6 || len(s) > 20 {
			return false
		}
		for _, r := range s {
			if (r < 'A' || r > 'Z') && (r < '0' || r > '9') && r != '-' {
				return false
			}
		}
		return true
	})
}

func toFieldErrors(err error) []FieldError {
	var ve validator.ValidationErrors
	if !errors.As(err, &ve) {
		return nil
	}
	out := make([]FieldError, 0, len(ve))
	for _, fe := range ve {
		out = append(out, FieldError{
			Field: fe.Field(), Code: fe.Tag(), Message: messageFor(fe),
		})
	}
	return out
}

func messageFor(fe validator.FieldError) string {
	switch fe.Tag() {
	case "required":
		return "不能为空"
	case "min":
		return "长度不能少于 " + fe.Param()
	case "max":
		return "长度不能超过 " + fe.Param()
	case "gt":
		return "必须大于 " + fe.Param()
	case "gte":
		return "不能小于 " + fe.Param()
	case "oneof":
		return "必须是以下之一: " + fe.Param()
	case "sku":
		return "格式为 6-20 位大写字母、数字或连字符"
	default:
		return "不合法"
	}
}
```

```go
package httpapi

import (
	"crypto/rand"
	"encoding/hex"
	"encoding/json"
	"errors"
	"io"
	"log/slog"
	"net/http"
	"os"
	"path/filepath"
	"strings"
	"sync"

	"github.com/gin-gonic/gin"
)

type AppError struct {
	Status int
	Code   string
	Msg    string
	Err    error
}

func (e *AppError) Error() string { return e.Msg }
func (e *AppError) Unwrap() error { return e.Err }

type CreateProductRequest struct {
	SKU         string   `json:"sku" binding:"required,sku"`
	Name        string   `json:"name" binding:"required,min=2,max=60"`
	PriceCents  int64    `json:"price_cents" binding:"required,gt=0"`
	Stock       int      `json:"stock" binding:"gte=0,lte=100000"`
	Category    string   `json:"category" binding:"required,oneof=book food digital"`
	Tags        []string `json:"tags" binding:"max=5,dive,min=1,max=16"`
	Description string   `json:"description" binding:"max=500"`
}

type Product struct {
	ID          string   `json:"id"`
	SKU         string   `json:"sku"`
	Name        string   `json:"name"`
	PriceCents  int64    `json:"price_cents"`
	Stock       int      `json:"stock"`
	Category    string   `json:"category"`
	Tags        []string `json:"tags"`
	Description string   `json:"description"`
	ImageURL    string   `json:"image_url,omitempty"`
}

type ProductHandler struct {
	mu       sync.RWMutex
	bySKU    map[string]Product
	uploadTo string
}

func NewProductHandler(uploadTo string) *ProductHandler {
	return &ProductHandler{bySKU: map[string]Product{}, uploadTo: uploadTo}
}

func (h *ProductHandler) Create(c *gin.Context) {
	if ct := c.ContentType(); ct != "application/json" {
		Fail(c, http.StatusUnsupportedMediaType, "UNSUPPORTED_MEDIA_TYPE",
			"Content-Type 必须是 application/json", nil)
		return
	}

	var req CreateProductRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		var syntaxErr *json.SyntaxError
		fieldErrs := toFieldErrors(err) // 只解析一次，后续分支复用
		switch {
		case errors.Is(err, io.EOF):
			Fail(c, http.StatusBadRequest, "MALFORMED_JSON", "请求体为空", nil)
		case errors.As(err, &syntaxErr):
			Fail(c, http.StatusBadRequest, "MALFORMED_JSON", "JSON 语法错误", nil)
		case len(fieldErrs) > 0:
			Fail(c, http.StatusUnprocessableEntity, "VALIDATION_FAILED",
				"请求参数不合法", fieldErrs)
		default:
			Fail(c, http.StatusBadRequest, "INVALID_JSON", "JSON 字段类型不匹配", nil)
		}
		return
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	if _, ok := h.bySKU[req.SKU]; ok {
		Fail(c, http.StatusConflict, "SKU_CONFLICT", "SKU 已存在", nil)
		return
	}
	p := Product{
		ID: hex.EncodeToString(randomBytes(8)), SKU: req.SKU, Name: req.Name,
		PriceCents: req.PriceCents, Stock: req.Stock, Category: req.Category,
		Tags: req.Tags, Description: req.Description,
	}
	h.bySKU[req.SKU] = p
	OK(c, http.StatusCreated, p)
}

const maxImageBytes = 2 << 20

var allowedImages = map[string]string{
	"image/jpeg": ".jpg",
	"image/png":  ".png",
	"image/webp": ".webp",
}

func (h *ProductHandler) UploadCover(c *gin.Context) {
	if !strings.HasPrefix(c.ContentType(), "multipart/form-data") {
		Fail(c, http.StatusUnsupportedMediaType, "UNSUPPORTED_MEDIA_TYPE",
			"Content-Type 必须是 multipart/form-data", nil)
		return
	}
	// 硬上限：超出部分直接拒绝，避免临时文件写满磁盘
	c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxImageBytes+(1<<20))

	file, err := c.FormFile("file")
	if err != nil {
		var maxErr *http.MaxBytesError
		if errors.As(err, &maxErr) {
			Fail(c, http.StatusRequestEntityTooLarge, "PAYLOAD_TOO_LARGE", "文件超过 2 MiB", nil)
			return
		}
		Fail(c, http.StatusBadRequest, "INVALID_MULTIPART", "缺少 file 字段", nil)
		return
	}
	if file.Size > maxImageBytes {
		Fail(c, http.StatusRequestEntityTooLarge, "PAYLOAD_TOO_LARGE", "文件超过 2 MiB", nil)
		return
	}

	f, err := file.Open()
	if err != nil {
		Fail(c, http.StatusBadRequest, "INVALID_FILE", "无法读取文件", nil)
		return
	}
	defer f.Close()

	head := make([]byte, 512)
	n, err := io.ReadFull(f, head)
	if err != nil && !errors.Is(err, io.ErrUnexpectedEOF) {
		Fail(c, http.StatusBadRequest, "INVALID_FILE", "无法读取文件", nil)
		return
	}
	ct := http.DetectContentType(head[:n]) // 以真实内容判断，不信客户端声明的类型
	ext, ok := allowedImages[ct]
	if !ok {
		Fail(c, http.StatusUnsupportedMediaType, "UNSUPPORTED_IMAGE_TYPE",
			"仅支持 JPEG、PNG、WebP", nil)
		return
	}

	name := hex.EncodeToString(randomBytes(16)) + ext // 服务端生成文件名，避免路径注入
	if err := os.MkdirAll(h.uploadTo, 0o755); err != nil {
		Fail(c, 500, "SAVE_FAILED", "保存失败", nil)
		return
	}
	if err := c.SaveUploadedFile(file, filepath.Join(h.uploadTo, name)); err != nil {
		Fail(c, 500, "SAVE_FAILED", "保存失败", nil)
		return
	}
	slog.Info("cover uploaded", "name", name, "bytes", file.Size, "type", ct)
	OK(c, http.StatusCreated, gin.H{"image_url": "/uploads/" + name})
}

func randomBytes(n int) []byte {
	b := make([]byte, n)
	_, _ = rand.Read(b)
	return b
}
```

`internal/httpapi/middleware.go`（请求 ID、访问日志、panic 恢复，三件套都在请求层完成）：

```go
package httpapi

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"log/slog"
	"net/http"
	"net/url"
	"runtime/debug"
	"time"

	"github.com/gin-gonic/gin"
)

func RequestID() gin.HandlerFunc {
	return func(c *gin.Context) {
		id := c.GetHeader("X-Request-ID")
		if id == "" {
			b := make([]byte, 8)
			_, _ = rand.Read(b)
			id = hex.EncodeToString(b)
		}
		c.Set("request_id", id)
		c.Header("X-Request-ID", id) // 客户端报错时可直接提供这个 ID
		c.Next()
	}
}

func AccessLog(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		logger.LogAttrs(c.Request.Context(), slog.LevelInfo, "http_access",
			slog.String("request_id", c.GetString("request_id")),
			slog.String("method", c.Request.Method),
			slog.String("path", c.Request.URL.Path),
			slog.String("query", redactQuery(c.Request.URL.RawQuery)),
			slog.Int("status", c.Writer.Status()),
			slog.Int64("cost_ms", time.Since(start).Milliseconds()),
			slog.Int("bytes", c.Writer.Size()),
			slog.String("error_code", c.GetString("error_code")),
		)
	}
}

func Recover(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		defer func() {
			if v := recover(); v != nil {
				logger.Error("panic",
					"request_id", c.GetString("request_id"),
					"path", c.Request.URL.Path,
					"panic", fmt.Sprint(v),
					"stack", string(debug.Stack()), // 没有堆栈的 panic 日志基本无法定位
				)
				Fail(c, http.StatusInternalServerError, "INTERNAL", "服务器内部错误", nil)
				c.Abort()
			}
		}()
		c.Next()
	}
}

func redactQuery(raw string) string {
	u, err := url.ParseQuery(raw)
	if err != nil {
		return ""
	}
	for _, k := range []string{"password", "token", "secret", "id_card"} {
		if u.Has(k) {
			u.Set(k, "***")
		}
	}
	return u.Encode()
}
```

```go
}
```

### 7.3 案例结果

两个接口的错误响应从纯文本变为可解析结构，上传从“看扩展名”变为“看真实内容”，panic 不再影响进程。

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 校验失败响应 | 纯文本 | 422 + 字段级 details |
| 前端定位字段 | 猜 | 直接读 `details[].field` |
| 伪装图片 | 可上传 | 415 拒绝 |
| 超大文件 | 写满磁盘 | 413 拦截 |
| panic 影响 | 进程退出 | 单请求 500 + 堆栈 |
| 日志串联 | 无 | request_id 贯穿 |

失败模式与复盘：

- 最初用 `c.BindJSON`，校验失败自动返回纯文本 400，前端只能弹“请求错误”；换成 `ShouldBindJSON` 加统一 `Fail` 后才拿到字段级信息；
- `RegisterTagNameFunc` 漏写，`details[].field` 返回 `PriceCents`，前端表单字段叫 `price_cents`，提示不显示；补上 json tag 映射后修复；
- 上传只判断了 `file.Header.Get("Content-Type")`，改名的 HTML 直接通过；改用 `http.DetectContentType` 读前 512 字节，并同时校验扩展名白名单；
- 没有 `MaxBytesReader` 时，上传 500 MiB 文件会把 `/tmp` 写满，Pod 被 OOMKilled；加上限流后请求在入口就被拒；
- `Recover` 里只打了 `panic` 值没打堆栈，第一次线上 panic 排查花了两小时；补 `debug.Stack()` 后同类问题十分钟定位；
- 访问日志直接打印了原始 query，包含 `token` 参数；加 `redactQuery` 后不再泄露，日志字段名固定为 `error_code`，监控可以直接按业务码告警。
