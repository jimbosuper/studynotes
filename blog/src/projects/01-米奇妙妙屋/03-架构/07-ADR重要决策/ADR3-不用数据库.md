# 为什么不建数据库：内容即文件

## 一、Context 背景

「知识库站点」这句话很容易顺手带出一个后端：用户、文章表、标签表、搜索表。

但这个站的读者只有一个人（作者自己），要解决的是**「本地 Markdown 打不开、发不出去」**，不是「多人协作编辑」。如果建库，会立刻多出这些东西：

| 建库就要有 | 实际需要吗 |
|---|---|
| 表结构与迁移脚本 | 内容本来就是一层的目录 + 文件，没有关系要表达 |
| 备份与恢复流程 | 三个 Git 仓库本身就有完整历史 |
| 服务进程与端口 | 静态托管不需要进程，也就没有端口要占、没有进程要守 |
| 数据同步（文件 → 库） | 多一层搬运，反而多一处会不一致的地方 |

## 二、Decision 决定

1. 不建数据库。**内容的唯一形态是 Markdown 文件 + Git 历史**
2. 目录层级即数据关系：方向（`00-`…`09-`）→ 章节 → 篇
3. 结构化数据只有一处：frontmatter 的 `title` 与 `category`，由同步脚本按 H1 与目录名补
4. 运行时零查询：搜索索引在构建期生成，页面在构建期渲染成 HTML

## 三、Consequences 代价

- 好：**没有迁移**。改一个字段就是改一行 Markdown，不存在「表结构回滚」
- 好：**没有备份流程**。回滚内容靠 `git revert`，回滚站点靠 Cloudflare 的历史部署
- 好：本地能跑、线上能跑、克隆下来就能跑，不需要起任何服务
- 坏：**没有查询能力**。要「按标签筛选」「按时间排序」这类聚合，只能在构建脚本里扫盘现算
- 坏：**没有事务**。同步中途失败会留半成品，只能靠幂等重跑收敛
- 坏：**内容量到万级时，扫盘与构建都会变慢**；届时要么加索引层，要么分站

## 四、Alternatives 放弃过的选项

| 选项 | 做法 | 为什么不选 |
|---|---|---|
| A | SQLite 存文章与标签，构建时读库生成页面 | 多一份数据副本，正文改一次要写两处；回滚变成两件事 |
| B | **内容即文件 + Git，运行时零查询** | 选中 |
| C | 接一个托管数据库（如 Supabase），站点运行时查询 | 静态站变成有状态服务，多出可用性、限流、密钥三件要管的事 |
| D | 用 JSON 索引文件代替数据库 | 索引与正文仍可能不同步，且 JSON 无法表达层级，等于自制一个更差的库 |
