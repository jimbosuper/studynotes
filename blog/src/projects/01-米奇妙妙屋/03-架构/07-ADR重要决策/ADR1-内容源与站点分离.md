# 内容为什么不写在站点仓库里

## 一、Context 背景

站点的第一版是把笔记直接放在 `blog/src/notes/` 里写的：改一篇笔记就是改站点的提交。

量上来以后出现三个具体现象：

1. 笔记与站点配置在同一个提交里，`git log` 分不清「改内容」和「改样式」
2. 截图一多，仓库从几十 MB 涨到两百多 MB，克隆一次要几分钟，而其中九成是内容
3. 想在手机上改一篇笔记，要先装 Node、跑一遍构建才能看到效果

## 二、Decision 决定

1. 内容源独立成两个仓库：`fullstack-notes`（笔记）、`fullstack-workflow`（工作流文档）
2. 站点仓库只保留发布端：配置、脚本、模板，不存内容
3. 两者之间单向同步，入口是 `blog/scripts/sync-content.mjs`，命令 `npm run sync`
4. 站点侧的内容目录（`src/notes/`、`src/workflow/`）是同步产物，手改会被下一次同步覆盖

## 三、Consequences 代价

- 好：内容与呈现各自独立增长，内容库涨到 162 MB 不影响站点仓库的克隆速度
- 好：源库是纯 Markdown，Obsidian、VS Code、手机编辑器都能直接开
- 好：`git log` 两条线各自干净，内容改了什么、站点改了什么一目了然
- 坏：**改完内容必须手动跑一次同步**，忘了同步线上就是旧内容
- 坏：**线上构建不能带 sync**——Cloudflare 构建环境里没有 `../fullstack-notes`，所以每次发布都要先把同步产物提交进仓库
- 坏：跨仓库改一处链接要改两个仓库，容易半途而废

## 四、Alternatives 放弃过的选项

| 选项 | 做法 | 为什么不选 |
|---|---|---|
| A | 笔记直接写在 `blog/src/notes/`，一个仓库管到底 | 内容与配置混在一条历史里；仓库被截图撑大；手机改不了 |
| B | **内容源独立仓库 + 单向同步** | 选中 |
| C | 两个仓库用 Git submodule 挂进站点 | submodule 在 Cloudflare 构建里要额外拉取配置，且升级版本号要改两处；同步脚本已经足够 |
| D | 运行时从 GitHub API 拉内容（不落盘） | 要处理限流、缓存、失败降级，为了省一个同步脚本引入一整层运行时依赖 |
